## 1. 本書の目的と位置付け
### 1.1 本書の目的
本書は、Tank_Robot本体ソフトウェアのCommon Runtime詳細設計について、設計範囲、個別詳細設計書の構成と責任分界、共通設計方針および設計の進め方を定める。

Common Runtimeは、複数の機能モジュールが共通して利用する、Processの実行管理、進行監視、実行基盤で検出した異常の管理、およびデータの保持・受渡しの仕組みを提供する。

本書はCommon Runtime詳細設計書群の共通方針を示す文書とし、各構成要素の公開インターフェース、内部状態、データ構造、処理手順および実装方式は、それぞれの詳細設計書で定める。

### 1.2 上位設計との関係
Common Runtime詳細設計は、[Tank_Robot 本体詳細設計について](../00_Tank_Robot_本体詳細設計について.md)に定める共通方針に従い、[Tank_Robot 本体ソフトウェアアーキテクチャ詳細設計](../01_Tank_Robot_本体ソフトウェアアーキテクチャ/01_Tank_Robot_本体ソフトウェアアーキテクチャ詳細設計.md)で確定した構成、実行方式、責任分界およびモジュール間の共通契約を前提とする。

また、現行の基本設計を直接の設計基準とし、特に次の文書で定めた内容との整合を維持する。

- [Tank_Robot本体ソフトアーキテクチャ基本設計](../../../20_basic_design/07_本体ソフトウェアアーキテクチャ/Tank_Robot本体ソフトアーキテクチャ基本設計.md)
- [Tank_Robotシステムアーキテクチャ](../../../20_basic_design/02_システムアーキテクチャ/Tank_Robotシステムアーキテクチャ.md)
- [Tank_Robot性能・品質・検証基本設計](../../../20_basic_design/08_性能・品質・検証/Tank_Robot性能・品質・検証基本設計.md)
- [Tank_Robot詳細設計引継ぎ基本設計](../../../20_basic_design/09_詳細設計引継ぎ/Tank_Robot詳細設計引継ぎ基本設計.md)


Common Runtime詳細設計では、上位設計で確定した事項を独自に変更せず、実装に必要な内部仕様を具体化する。

上位設計との不整合や実現上の問題が判明した場合は、Common Runtime詳細設計だけで仕様を変更せず、該当する上位設計への影響を確認する。

## 2. Common Runtimeの設計範囲
### 2.1 Common Runtimeの役割
Common Runtimeは、Application、System / Safety Management、Serviceの各機能モジュールが共通して利用する、実行・監視・データ連携の基盤である。

Common Runtimeは、次の4つの構成要素で実現する。

|構成要素|主な役割|
|---|---|
|Scheduler|Processの実行可否、READY、優先度、周期、期限および実行順序を管理し、実行時間や遅延を計測する。|
|SystemMonitor|現在の監視条件に従って、必要なProcessが正常に進行しているかを評価し、IWDT更新判断に必要な監視結果を提供する。|
|RuntimeAnomaly|SchedulerやSystemMonitorなどの実行基盤で検出した異常について、継続・解消状態およびFaultへの通知を管理する。|
|共通Primitive|Queue、Slot、Snapshot、Event、Latchなど、データの保持・受渡しや同期に必要な共通の仕組みを提供する。|

また、非同期Request／Resultの共通利用規則や、処理完了後に対象ProcessへREADYを通知するための共通機構も設計対象とする。

ただし、個々のRequestの受付条件、処理状態、Resultおよび固定資源は、原則として要求を受け付けるProviderが管理する。

Common Runtimeは、各機能モジュールの実行と連携を支える仕組みを提供し、機能固有の判断とは分離する。

### 2.2 Common Runtimeが担当しない事項
Common Runtimeは、製品機能に固有の状態、判断および処理結果の意味を管理しない。

主な対象外事項は次のとおりとする。

- **システム状態・操作制御**：システム状態の遷移、操作可否、走行・砲塔・砲身の制御内容。
- **安全・異常処置**：停止成立、電気安全判定、異常の影響度、必要な処置および復旧可否。
- **電源・IWDT管理**：電源状態、低消費電力への移行・復帰可否、IWDT更新の判断および実行。
- **通信・セキュリティ**：通信内容の意味、認証・認可、鍵や認証情報の管理。
- **各機能のデータ・処理結果**：設定、永続データ、OTA更新、製品情報、時刻などの状態および処理結果の確定。
- **ハードウェア制御**：MCU周辺機能、FSP、デバイス固有の操作および物理的な非同期処理の管理。

これらの事項は、本体ソフトウェアアーキテクチャ詳細設計で定めた担当モジュールが管理する。

Common Runtimeは、担当モジュールが公開する情報や実行条件を利用する場合でも、その情報の意味を独自に判断したり、管理主体を変更したりしない。

また、Common Runtimeを共通化するためだけに、各機能固有の状態管理や一連の処理を汎用的な管理機構へ統合しない。

## 3. 詳細設計書の構成と責任分界

### 3.1 詳細設計書の構成
Common Runtimeの詳細設計は、本書と5つの個別詳細設計書で構成する。

各文書は次のとおりとする。

|文書|位置付け|
|---|---|
|`00_Common_Runtime詳細設計について.md`|Common Runtime全体の設計方針と文書間の責任分界|
|`01_Scheduler詳細設計.md`|Processの実行管理|
|`02_SystemMonitor詳細設計.md`|Processの進行監視|
|`03_RuntimeAnomaly詳細設計.md`|ランタイム実行異常の管理|
|`04_Common_Runtime共通Primitive詳細設計.md`|共通のデータ保持・受渡し機構|
|`05_Common_Runtime非同期連携・完了通知詳細設計.md`|非同期Request／Resultの共通契約と論理的な完了通知機構|

共通Primitiveと非同期連携・完了通知は、設計する内容と責任範囲が異なるため、個別の文書として扱う。

この文書分割は、Common Runtimeに新たな実行モジュールやProcessを追加することを意味しない。具体的な実装構成は、上位アーキテクチャの制約に従って各詳細設計で定める。

### 3.2 各詳細設計書の設計範囲
各詳細設計書では、上位アーキテクチャで定めた責任を実現するため、公開インターフェース、内部状態、データ構造、処理手順、異常時の動作および使用資源を必要な粒度まで具体化する。

個別文書の主な設計範囲を次に示す。

| 文書             | 主な設計範囲                                                                      |
| -------------- | --------------------------------------------------------------------------- |
| Scheduler      | Processの登録情報、READY管理、優先度、実行順序、周期・期限管理、ISRからの実行契機の受渡し、実行統計、低消費電力時の実行制限       |
| SystemMonitor  | 監視フェーズ、監視対象、Checkpointの受付、監視世代、正常進行の評価、監視結果の公開、低消費電力時の監視                    |
| RuntimeAnomaly | 実行異常の識別、継続・解消状態、異常情報の保持、Faultへの通知と結果確認、通知失敗時の処理                             |
| 共通Primitive    | Queue、Slot、Snapshot、Event、Latchなどのデータ保持・受渡し、同期、共通時間演算、共通基盤の健全性情報を保持・公開する仕組み |
| 非同期連携・完了通知     | 非同期Request／Resultの共通利用規則、処理結果の取得・放棄に関する共通契約、完了通知先の対応付け、READY通知との連携          |

具体的なAPI、識別子、内部構造および数値は、上位設計で確定済みの事項を除き、担当する個別詳細設計書で定める。

### 3.3 文書間の責任分界
複数の詳細設計書が関係する事項は、それぞれが管理する情報と処理を区別し、同じ仕様を独立して定義しない。

主な責任分界は次のとおりとする。

|関係する構成要素|責任分界|
|---|---|
|Scheduler／SystemMonitor|SchedulerはProcessの実行と時間上の違反を管理する。SystemMonitorはCheckpointなどから正常な進行を評価する。|
|Scheduler・SystemMonitor／RuntimeAnomaly|SchedulerとSystemMonitorは担当する実行・監視上の異常を検出する。RuntimeAnomalyは通知された異常の継続・解消とFaultへの通知を管理する。|
|RuntimeAnomaly／Fault|RuntimeAnomalyはランタイム異常の管理と通知を担当する。Faultは製品への影響、必要な処置および復旧可否を判断する。|
|SystemMonitor／Power|SystemMonitorはIWDT更新判断に使用する監視結果を提供する。Powerは管理責任の移管後、更新条件の判断と更新命令の実行を担当する。|
|共通Primitive／非同期連携・完了通知|共通Primitiveはデータ保持・受渡しの仕組みを定める。非同期連携・完了通知は、その仕組みを利用するRequest／Resultの共通契約と論理的な完了通知を定める。|
|非同期連携・完了通知／各Provider|共通の連携規則は非同期連携・完了通知詳細設計で定める。個々のRequestの受付条件、処理状態、Result、固定資源および解放条件は、原則として各Providerの詳細設計で定める。|
|非同期連携・完了通知／Platform|機能モジュール間の論理的な完了通知はCommon Runtimeで扱う。Platformにおける物理的な非同期操作と、その完了通知契約はPlatform詳細設計で扱う。|

また、Processの実行世代、監視世代、各機能の処理世代などは、それぞれを管理する構成要素が発行・更新する。
共通機構を利用するために、世代の管理主体を変更しない。

各詳細設計書では、自身が担当する仕様を定義し、他の詳細設計書が担当する仕様については、必要な利用条件と参照先を示す。

安全上必要な処理は、RuntimeAnomalyからFaultへの通知完了や、通常の非同期処理の完了を待たずに実行できる構成を維持する。

## 4. Common Runtime詳細設計の共通方針
### 4.1 上位設計と実行方式の遵守
各詳細設計書は、現行の基本設計および本体ソフトウェアアーキテクチャ詳細設計で定めた実行方式、責任分界および共通契約に従う。

特に、RTOSを使用しない協調実行方式を前提とし、各Processは短時間で処理を終了してSchedulerへ戻る構成とする。外部応答や他Processの完了を同期待ちせず、必要に応じて非同期処理や分割処理によって進行させる。

Processの実行契機、優先度、周期、期限、実行時間上限および監視条件は、上位設計の制約を維持したうえで具体化する。

また、ISRから機能Processを直接呼び出さず、ハードウェア固有の処理はPlatformが提供するインターフェースを介して扱う。

### 4.2 データ管理と非同期連携の責任分界
状態、Request、Result、Snapshotなどのデータは、その意味と確定条件を定めるモジュールが管理する。共通Primitiveがデータの保持・受渡しを提供する場合も、データの意味や管理主体は変更しない。

READYはProcessの実行契機として扱い、処理対象のデータ本体とは分離する。データを更新してProcessへ実行契機を通知する場合は、必要な情報を公開した後にREADYを通知する。

非同期Request／Resultでは、Requestの受付成功と処理の完了を区別する。個々のRequestの受付条件、処理状態、Resultおよび固定資源は、原則としてProviderが管理する。

共通の非同期連携・完了通知詳細設計では、Request／Resultの利用規則と論理的な完了通知の仕組みを定める。ただし、個々のProviderに固有の処理手順や状態遷移は定義しない。

また、Resultの取得、受領放棄および処理取消しを区別し、処理中の資源を安全に再利用できる条件を明確にする。

### 4.3 安全性、固定資源および異常時の設計方針
Common Runtimeの各構成要素は、安全上必要な処理を通常の通信、ログ保存、Fault通知およびその他の非安全処理の完了待ちにしない。

使用するQueue、Slot、Bufferなどの資源は、固定上限を設けて管理する。通常本体処理では、`malloc/calloc/realloc/free`による動的メモリ確保・解放を使用しない。外部ライブラリ内部で動的確保を避けられない場合の扱いは、本体ソフトアーキテクチャ基本設計15.1に従う。

各詳細設計では、資源の管理主体、容量、占有・解放条件および容量不足時の動作を明確にする。安全処理に必要な資源は、通常処理によって使用不能にならないようにする。

実行基盤の内部不整合、期限違反、進行停止および資源不足などについては、検出する構成要素と異常情報の管理・通知先を明確にする。

異常や不明な状態を正常として扱わず、古い監視結果や失効した情報を現在の正常動作の根拠として再利用しない。

具体的な異常検出方法、内部状態、通知方法および資源管理方式は、それぞれを担当する個別詳細設計書で定める。

## 5. 詳細設計の進め方と完了確認
### 5.1 詳細設計書の作成順序
Common Runtimeの詳細設計は、本書で設計範囲と責任分界を整理した後、各構成要素の依存関係を考慮して進める。

推奨する作成順序は次のとおりとする。

| 順序 | 詳細設計書 | 主な作業内容 |
|---|---|---|
| 1 | `00_Common_Runtime詳細設計について.md` | 設計範囲、文書構成および共通方針の整理 |
| 2 | `04_Common_Runtime共通Primitive詳細設計.md` | データ保持・受渡し、同期、共通処理部品の具体化 |
| 3 | `01_Scheduler詳細設計.md` | Process実行、READY、優先度、周期・期限管理の具体化 |
| 4 | `05_Common_Runtime非同期連携・完了通知詳細設計.md` | Request／Resultの共通契約、論理的な完了通知機構の具体化 |
| 5 | `02_SystemMonitor詳細設計.md` | Checkpoint、進行監視、監視結果の管理と公開の具体化 |
| 6 | `03_RuntimeAnomaly詳細設計.md` | ランタイム実行異常の管理、Fault通知の具体化 |

この順序は設計上の依存関係を考慮したものであり、先に作成した詳細設計書を変更せずに固定することを意味しない。

後続の設計で共通インターフェースや処理方式の調整が必要になった場合は、関係する詳細設計書との整合を確認する。

### 5.2 関連設計との整合および変更時の扱い
各詳細設計書は、現行の基本設計、本体ソフトウェアアーキテクチャ詳細設計および本書を基準として作成する。

各詳細設計書の作成時には、特に次の整合を確認する。

- 上位設計で定めた責任分界、実行方式、時間条件および安全条件との整合
- Scheduler、SystemMonitor、RuntimeAnomaly間の実行情報、監視結果および異常情報の受渡し
- 共通Primitive、非同期連携・完了通知および利用側モジュール間の公開インターフェースとデータ管理責任
- Platform、Power、Faultなど、Common Runtime外の関連モジュールとの責任分界
- 固定資源の管理主体、容量、占有・解放条件および資源の重複管理の有無

共通の仕様は、その事項を担当する詳細設計書で定義し、利用側の文書では必要な利用条件と参照先を示す。

上位設計との不整合や、設計済みの共通契約を変更する必要が生じた場合は、影響する文書と変更内容を確認したうえで、該当する設計へ反映する。

また、実機評価などによる確認が必要な事項は、設計上の決定事項と評価未完了事項を区別し、担当する詳細設計書から追跡できるようにする。

### 5.3 Common Runtime詳細設計の完了条件
Common Runtime詳細設計は、各構成要素を実装するために必要な仕様が明確になり、文書間の整合を確認できた段階で完成とする。

完了時には、少なくとも次の事項を確認する。

1. 各構成要素の責務と責務外が明確であり、同じ状態や判断を複数の構成要素が独立して管理していない。
2. Processの実行、進行監視、ランタイム異常管理および共通データ連携の処理方式を、各詳細設計書から確認できる。
3. 公開インターフェースの利用条件、引数・戻り値、データの管理主体および有効期間が明確である。
4. 正常処理、異常処理、期限超過、資源不足、リセットおよび低消費電力時の動作が、必要な範囲で具体化されている。
5. 固定資源の容量、占有・解放条件および容量不足時の動作が明確であり、上位設計の資源制約との整合を確認できる。
6. Scheduler、SystemMonitor、RuntimeAnomaly、共通Primitiveおよび非同期連携・完了通知の間で、公開契約や処理順序に矛盾がない。
7. 単体試験・結合試験で確認すべき主要な条件が明確であり、実機評価を必要とする事項が識別されている。
8. 実装時に主要な設計判断を新たに行う必要がなく、C言語による実装へ移行できる。

すべての個別詳細設計書が揃った段階で、Common Runtime全体の横断レビューを行い、責任分界、共通インターフェース、依存関係および設計内容の重複を最終確認する。

また、本書についても個別詳細設計の結果を踏まえて見直し、実際の文書構成および責任分界と一致していることを確認する。

なお、詳細設計の完成は、実装、単体試験、結合試験または実機評価の完了を意味しない。

実機評価による成立性確認が必要な事項は、該当する上位設計および評価計画で定めた条件を満たしたうえで、正式に確定する。

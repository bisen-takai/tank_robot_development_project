## 1. 本書の目的

### 1.1 目的

本書の目的は、システムアーキテクチャで独立機能として定義した「時刻管理」について、RTC時刻、絶対時刻、時刻信頼状態、時刻同期、時刻補正および関連機能への提供条件を、詳細設計へ展開可能な粒度まで具体化することである。

公開用システム要求仕様には「時刻管理」という独立章は存在しない。本機能は、VPS接続・デバイス認証、ログ・診断、セキュリティ管理、永続データ管理、性能・品質・耐久性その他に分散している時刻要求を、システムアーキテクチャの責任分界に従って集約する。

### 1.2 対象範囲

本書は、Tank_Robot本体における絶対時刻、RTC、時刻信頼状態、VPSからのUTC時刻同期、時刻補正、起動・低消費電力・主電源OFFをまたぐRTC保持、ログ・診断へ提供する時刻品質、VPS証明書検証へ提供する信頼時刻および時刻喪失時の復旧について具体化する。

時刻管理は、走行・停止・緊急停止・電源保護・通信タイムアウト等の安全・制御期限をRTCで判定しない。これらは各機能が持つ単調時刻・専用timerを判断基準とする。本書は、主にUTC絶対時刻とその信頼可否を管理し、ログ・診断、VPS接続・デバイス認証、セキュリティ、状態表示等へ提供する。

#### 基本設計と詳細設計の区分

本書で定めるtrust state、quality、RTC continuity判定、Time Update transaction、VPS sample採否、補正閾値、同期周期、時刻喪失時のVPS利用可否、時間・容量上限その他、外部から見た製品挙動または信頼可否を変える方式・値は、評価確定待ちを含む基本設計で定める事項とする。実機評価で変更が必要となった場合は詳細設計だけで変更せず、本書または値・方式を定める関連基本設計へ反映する。RTC register、FSP API、byte offset、C構造体、task、mutex、物理address等、基本設計の外部挙動を変更しない実装方法は詳細設計で具体化してよい。

## 2. 設計方針と適用範囲

### 2.1 基本方針

時刻管理は次の原則で設計する。

1. 絶対時刻の取得元をRA8M2内蔵RTCとする。
2. システム内の絶対時刻表現はUTCとし、JST等のlocal timezoneへ変換してRTCへ保存しない。
3. RTC値と「その時刻を信頼してよいか」を別に管理する。
4. RTCがcalendar上もっともらしいだけではTRUSTEDとしない。
5. 通常運用のVPS時刻同期は、既に信頼できる時刻を用いて正当性確認済みのVPS通信が成立した場合に限る。
6. RTC trust lossから通常VPSへ接続して時刻をbootstrapする経路は初期製品へ設けない。
7. RTC trust loss時は、セキュリティ管理に従って物理的なwired開発・保守時刻設定で復旧する。
8. 一般操作者・所有者・BLEアプリ・未認証NTPから絶対時刻を設定しない。
9. UTC補正によって、走行制御、停止、緊急停止、通信timeout、OTA deadline等の単調時間判定を変化させない。
10. 既存ログのUTCを後から書き換えず、発生順序はbootInstanceId/eventSequence/monotonicTimeUsで維持する。
11. 時刻同期のためだけに低消費電力状態からWi-Fi/VPSを起こさない。
12. RTC保持不能・信頼不能だけを理由として、安全なローカルBLE操作を全面禁止しない。影響するVPS管理・UTCログ等だけを縮退させる。
13. RTC calendar変更、Trusted Time Record更新、Time Update Record更新を一つの物理atomic writeと仮定せず、Timeが機能上の整合を保つ一連の処理を所有して永続データ管理のdataset別原子更新を組み合わせる。
14. 最新のTrusted Timeの内容の版が正常であることを確認できない場合、物理的に正常な古い版を自動採用してTIME_TRUSTEDへ戻さない。ただし、未完了のPREPAREDをABORTする場合に限り、更新前の確定済みの版が、その更新処理の開始時点で使用していた値であることを一意に確認できれば、継続して使用できる。
15. TIME_TRUSTED喪失時は新規VPS開始を禁止するだけでなく、VPS接続・デバイス認証へ既存VPS sessionの即時終了を要求する。

### 2.2 対象外

初期製品では次を対象外とする。

- NTP/SNTPによる公開時刻server同期
- smartphone時刻を信頼時刻として採用する方式
- GPS/GNSS時刻
- secure time bootstrap用の限定TLS接続
- PTP等の高精度分散時刻同期
- leap smear serverとの特殊連携
- timezone/DSTを本体RTCへ保持する機能
- 通常利用者向け手動時刻設定UI
- 時刻補正を安全・制御timerの代替として使用すること

## 3. 責任分界と時刻の種類

### 3.1 関連機能との責任分界

| 機能 | 主な責任 |
| --- | --- |
| 時刻管理 | RTC、UTC、trust、quality、同期、補正、Trusted Time/Update transactionの意味、trust喪失通知 |
| VPS接続・デバイス認証 | 認証済みHTTPS、`/time` request/response、通信結果、RTT用monotonic timestamp、TIME_TRUSTED喪失時のactive session終了 |
| セキュリティ | VPS証明書検証、trusted time要求、critical state MAC、time trustを暗号検証成功だけで上書きしないこと |
| ログ・診断 | uint64 bootInstanceId、event ordering、monotonicTimeUs、utcEpochMs、timeQuality/timeSyncGeneration保存 |
| 永続データ管理 | Trusted Time Record/Time Update Recordそれぞれのphysical原子保存、A/B/commit marker、readback、復旧材料提供 |
| 電源・省電力管理 | PWR_AON、VBATT供給条件、低消費電力、主電源OFF |
| 起動・終了・再起動管理 | 起動sequence、Time初期化結果の受領、終了 |
| 固定ブート・復旧 | reset要因capture、application起動前の最小boot。RTC trustは起動許可根拠にしない |
| 異常管理 | Time異常の影響度、復旧可否、通常操作可否 |
| 状態表示・利用者通知 | trust loss、VPS利用不能等の具体表示 |

### 3.2 絶対時刻と単調時刻を分離する

UTC/RTCは、ログ、診断、証明書有効期間、管理・保守表示等に使用する。

単調時刻は、少なくとも次に使用する。

- BLE受信順序・timeout
- 停止・緊急停止timeout
- sensor監視時間窓
- OTA deadline
- log event順序
- retry/backoff

RTC時刻補正によって単調timerをreset、加速、減速または巻き戻さない。

### 3.3 ログ・診断のmonotonicTimeUsとbootInstanceId

ログ・診断が定義済みの`monotonicTimeUs`は同一起動中のevent順序の判断基準とする。本書はこれをUTCへ置換しない。

起動相関に使用する`bootInstanceId`はログ・診断が管理するuint64値を使用し、本書が別幅のboot IDを生成しない。Time初期化より前などログ・診断のbootInstanceIdをまだ取得できない管理処理では0を「相関なし」として使用できるが、別の32 bit boot IDを作らない。

時刻同期処理ではVPS接続・デバイス認証/ログ・診断等が取得する同一起動内の単調増加するタイムスタンプを受け取り、request/response間のRTTおよび補正eventの相関に使用できる。

## 4. RA8M2 RTCとハードウェア構成

### 4.1 RTC

初期製品はRA8M2内蔵RTCを使用する。

外付けRTC ICを初期必須構成へ追加しない。

### 4.2 RTC clock source

RTCの基本clock sourceは32.768 kHz sub-clock oscillator（SOSC）とする。

具体crystal、load capacitance、基板配線、起動安定時間および温度範囲はハードウェア設計で確定する。

### 4.3 VBATT

RTC/VBATTの保持電源は、`VBAT_PROTECTED`から分岐する`PWR_AON`由来の低待機電流電源と、RTCバックアップ電池の2系統とする。通常は`PWR_AON`由来の電源を優先し、これが失われた場合はRTCバックアップ電池で保持を継続する。

初期製品は、交換可能な3 Vコイン形一次電池（CR2032クラス）をRTCバックアップ電池の基本方式とする。保持電源の構成と切替えは、「RTC継続性・時刻復旧契約基本設計」の2章に従う。

VBATTの給電回路は次を満たす。

- `PWR_CTRL`停止後も主バッテリー接続中は`PWR_AON`由来の電源でRTCを保持する。
- RA8M2 VBATTの許容電圧範囲を満たす。
- VCC/VBATT間の逆流または意図しない給電を防ぐ。
- 性能・品質・検証基本設計／電源・ハードウェア基本設計に定める主電源OFF時の待機電流の配分を満たす。
- 低バッテリーによるハードウェア遮断等で`PWR_AON`由来の保持電源が失われた場合は、RTCバックアップ電池がVBATTを保持する。切替えによってRTC時刻や保持領域を初期化しない。
- RTCバックアップ電池へ充電電流を流さず、同電池から`PWR_AON`や本体の通常動作用電源へ逆給電しない。

### 4.4 主バッテリーの取外し

主バッテリーの取外しだけを理由に、RTCの保持継続が失われたとは判定しない。RTCバックアップ電池による保持と、保持継続を確認する情報の判定は、「RTC継続性・時刻復旧契約基本設計」の5章に従う。

VBATT回路の故障などにより保持継続を失った可能性があり、継続を確認できない場合は、次回起動でRTCを無条件に`TIME_TRUSTED`として使用せず、`TIME_UNTRUSTED`とする。復旧は第12章および「RTC継続性・時刻復旧契約基本設計」の有線復旧手順に従う。

### 4.5 FSP r_rtc

RTC accessはRenesas FSP `r_rtc`を使用することを基本とする。

warm resetまたはVBATT保持後の起動でRTC sourceを不要に再初期化し、保持中時刻を破壊しない。

初回設定またはRTC source異常時だけclock source設定を行う。

FSPの`Set Source Clock in Open`設定および`R_RTC_ClockSourceSet()`使用条件は詳細設計で固定する。

## 5. 時刻管理の内部状態

### 5.1 trust state

時刻信頼状態を次で管理する。

| state | 意味 |
| --- | --- |
| `TIME_UNSET` | RTCへ使用可能なcalendar時刻が設定されていない |
| `TIME_UNTRUSTED` | RTC値は読めるが、信頼済みsourceまたはcontinuityを確認できない |
| `TIME_TRUSTED` | 証明書有効期間判定等へ使用可能な信頼時刻が成立している |

### 5.2 sync state

時刻同期処理状態はtrust stateとは別に管理する。

- `SYNC_IDLE`
- `SYNC_REQUEST_PENDING`
- `SYNC_IN_PROGRESS`
- `SYNC_ACCEPTED`
- `SYNC_REJECTED`
- `SYNC_FAILED`

同期開始中であっても、直前のTRUSTED RTCが有効ならtrust stateを直ちに失わない。

### 5.3 quality

時刻情報を利用する機能へ、次の時刻品質を提供する。

| quality | 意味 |
| --- | --- |
| `TIME_QUALITY_NONE` | 絶対時刻なし |
| `TIME_QUALITY_UNTRUSTED` | 絶対時刻値はあるが信頼不可 |
| `TIME_QUALITY_TRUSTED_HOLDOVER` | TIME_TRUSTEDだが、現在起動でまだaccepted syncがない、または最後のaccepted syncから24時間以上経過している |
| `TIME_QUALITY_TRUSTED_SYNCED` | 現在起動でwired/VPSの正常Time UpdateをCOMMITTED済みで、最後のaccepted syncから24時間未満 |

24時間は第13章の通常同期周期と同じ基本設計値とする。再起動後はRTC continuityを確認できても、現在起動でまだaccepted syncを完了していない間は`TIME_QUALITY_TRUSTED_HOLDOVER`から開始する。24時間経過によってtrust自体を失効させず、qualityだけをHOLDOVERへ変更する。

### 5.4 update transaction state

時刻更新取引を次で管理する。

- `TIME_UPDATE_NONE`
- `TIME_UPDATE_PREPARED`
- `TIME_UPDATE_COMMITTED`
- `TIME_UPDATE_ABORTED`

PREPAREDは、新しい信頼できる時刻の提供元の正当性確認と、更新候補を含む処理情報の保存は完了しているが、RTC設定、Trusted Time Recordの保存確定、または最終的なCOMMITTEDへの確定のいずれかが未完了である状態を意味する。

### 5.5 internal stateとsystem state

時刻管理内部状態をシステム状態として追加しない。

TIME_UNTRUSTEDでも、他の起動条件が成立すればローカルBLE操作を許可できる。

ただし、セキュリティ管理/VPS接続・デバイス認証により通常VPS管理通信は利用不可となる。

## 6. RTC時刻表現とUTC変換

### 6.1 RTC内部表現

RA8M2 RTCはcalendarとして設定し、保存するcalendarはUTCとして解釈する。

本体内でJST等へ変換してRTCへ書き込まない。

### 6.2 API時刻表現

本体機能間の絶対時刻は`int64 utcEpochMs`を基本表現とする。

UTC不明またはuntrusted時に0を「現在時刻」として利用しない。値とvalid/trust flagを必ず組み合わせる。

### 6.3 許容calendar範囲

初期製品の正常なcalendar判定範囲を、

- 2025-01-01T00:00:00Z以上
- 2100-01-01T00:00:00Z未満

とする。

範囲外を自動補正してTRUSTEDにしない。

将来製品寿命またはRTC仕様により範囲を変更する場合はTime format versionを更新する。

### 6.4 sub-second表現

RTC calendarの秒分解能だけでログの細かな順序を判定しない。

`utcEpochMs`のsub-second補間が必要な場合、同一起動中に取得したRTC anchorと同一起動内の単調時刻を組み合わせる。

低消費電力復帰後はmonotonic timer停止条件を考慮し、RTCを再読出ししてanchorを再確立する。

### 6.5 leap second

初期製品はleap secondを独自に挿入・削除しない。

VPSが提供するUTC epochの連続表現を使用し、OS/RTC calendarへ特別な60秒表現を導入しない。

## 7. 時刻信頼状態と時刻品質

### 7.1 TRUSTEDとなる条件

TIME_TRUSTEDへ遷移できるのは次のいずれかとする。

1. 製造・開発・保守の管理されたwired手順によって時刻設定し、Time Update transactionをCOMMITTEDまで完了した場合。
2. 既にTIME_TRUSTEDである状態で、正当性確認済みVPSから取得したUTC sampleを本書の検証により受入れ、Time Update transactionをCOMMITTEDまで完了した場合。
3. 再起動・主電源OFF後にRTC continuity、現在のlogical Trusted Time Recordおよび未完了Time Update Recordの状態を確認し、以前のTRUSTED状態をholdoverとして継続できる場合。

### 7.2 calendar plausibleだけでは信頼しない

RTCが2026年等の妥当そうな値を返すだけでは、初回起動またはcontinuity不明時にTIME_TRUSTEDとしない。

### 7.3 holdover

前回TRUSTED確定後、RTC continuityが維持され、現在のlogical Trusted Time Recordとの整合が成立する間は`TIME_QUALITY_TRUSTED_HOLDOVER`として使用できる。

VPS再同期時刻から長時間経過したことだけを理由として、機械的にUNTRUSTEDへ落とさない。

ただしlast sync ageおよび推定RTC driftは診断情報へ提供し、証明書有効期間境界付近の精度は実機評価で確認する。

### 7.4 trust失効条件と通知

少なくとも次でTIME_UNTRUSTEDまたはTIME_UNSETとする。

- RTC read失敗
- calendar範囲外
- 現在のlogical Trusted Time Record不正
- HMAC/CRC不一致
- RTC値が保存済みlastTrustedUtcより許容差を超えて過去
- VBATT continuity喪失が検出された
- RTC source再初期化が必要となりcontinuityを証明できない
- RTC時刻が不合理に飛躍し原因を確認できない
- PREPARED transactionの復旧判定を一意に完了できない
- 現在のrevisionを確定できず、古いlogical revisionしか正常に読めない

TIME_TRUSTEDから失効した時点でVPS接続・デバイス認証/セキュリティ管理/異常管理へ通知し、VPS接続・デバイス認証は第19～20章の契約に従って既存VPS sessionを終了する。

## 8. Trusted Time Record

### 8.1 目的

RTCの日時情報だけでは、どの時刻源を用いて信頼を確立したかを再起動後に判断できない。
このため、次の二つの記録を`PERSIST_CRITICAL`に、別々のデータ集合として保持する。

| 記録 | 役割 |
| --- | --- |
| Trusted Time Record | 最後に正常確定した時刻、その取得元、版・世代などを保存する |
| Time Update Record | RTC変更とTrusted Time Record更新を、同じ時刻更新処理として対応付け、その途中状態と確定結果を管理する |

RTCの書換えと記録の確定の間で電源断やリセットが発生しても、時刻の信頼状態を誤って確定しないために、両方の記録を用いる。
具体的な更新手順は第12.4節・第15.3節、中断後の復旧判定は第9.4節に従う。

### 8.2 Trusted Time Record基本項目

少なくとも次を保持する。

| 項目 | 型 | 意味 |
| --- | --- | --- |
| `formatVersion` | uint16 | 初期1 |
| `timeTrustRevision` | uint32 | 0無効、機能上の条件を満たして更新を確定したときに増加 |
| `lastTrustedUtcMs` | int64 | 最後に正常確定したUTC |
| `rtcUtcAtCommitMs` | int64 | commit時RTC readback値 |
| `source` | enum | WIRED_PROVISIONING / WIRED_MAINTENANCE / VPS_AUTHENTICATED |
| `sourceRequestId` | uint64 | VPS request等の相関。非VPSは0可 |
| `acceptedRttMs` | uint32 | VPS sample時RTT。非VPSは0 |
| `timeSyncGeneration` | uint32 | 時刻情報を利用する機能へ提供する同期の世代 |
| `lastSyncBootInstanceId` | uint64 | ログ・診断のbootInstanceId。相関なしは0 |
| `flags` | bitset | large correction等 |
| `CRC32C` | uint32 | 偶発破損検出 |
| `HMAC-SHA-256` | 32 byte | セキュリティ管理のK_SEC_STATE_MACによる認証 |

### 8.3 Time Update Record

少なくとも次を保持する。

- updateState
- updateTransactionId uint32
- candidate timeTrustRevision
- candidate timeSyncGeneration
- candidateUtcMs
- previousTimeTrustRevision
- previousTrustedUtcMs
- source
- sourceRequestId uint64
- acceptedRttMs uint32
- preparedBootInstanceId uint64（ログ・診断のbootInstanceId。取得不能時0）
- candidate Trusted Time Record識別に必要なrevision／transaction相関
- CRC32C
- K_SEC_STATE_MAC HMAC

### 8.4 revision

`timeTrustRevision`、`timeSyncGeneration`および`updateTransactionId`はuint32とし、0をinvalidへ予約する。

機能上の条件を満たした更新の確定または新Time Update transactionごとに増加する。最大値へ到達した場合はwrapせず保守異常とする。

ログ・診断の`bootInstanceId`は別のuint64単調値であり、本書のuint32 revisionへ切り詰めない。

### 8.5 更新頻度

1秒ごと等の定期書込みを行わない。

Trusted Time Record/Time Update Recordは次でのみ更新する。

- wired trusted time設定
- accepted VPS sync
- 未完了update transactionの復旧・中止
- trust状態を永続的に失効させる必要がある保守処理

### 8.6 状態保護用MACと巻戻し防止の範囲

#### 記録ごとの認証対象の分離

Trusted Time RecordとTime Update Recordは、セキュリティ管理機能の`K_SEC_STATE_MAC`を共用する場合も、認証対象をデータ集合ごとに区別する。

状態保護用MAC（state MAC）の入力には、少なくとも次を含める。

| 入力情報 | 内容 |
| --- | --- |
| データ集合固有の区別用情報（domain separator） | どのデータ集合の認証かを区別する情報 |
| 製品情報管理機能が提供するDevice ID | 対象の本体識別情報 |
| データ集合・種類の識別情報 | 対象のデータ集合とデータの種類 |
| `formatVersion` | データ形式の版 |
| 対象の版・世代（revision）／`updateTransactionId` | 対象の記録や時刻更新処理を対応付ける情報 |
| 形式を一意に定めたデータ本体（canonical payload） | 認証対象となるデータ本体 |

Trusted Time Recordの正常な認証タグを、Time Update Recordへ流用できるような曖昧な連結形式は使用しない。
各項目の具体的なバイト配置は、詳細設計で固定してよい。

#### HMACで確認できる範囲

HMACは、レコードの改ざん検出に使用する。
ただし、攻撃者が重要データ用のMRAM領域全体を、整合した過去の保存状態へ物理的に戻す高度な巻戻しについて、HMACだけで新旧の順序まで確認し、検出できるとはみなさない。

#### 同じ版の複製と過去の版を区別する

最新のTrusted Time Recordが破損、MAC不一致、または版・世代不明となった場合、古い版・世代のHMACが正常であることだけを根拠に、`TIME_TRUSTED`へ自動復帰しない。

物理的なA/Bの複製のうち、**同じ版・世代**を保持する正常な複製を使用することと、過去の版・世代へ戻ることは区別する。

## 9. 起動時RTC初期化と信頼判定

### 9.1 起動処理

本体アプリケーション起動後、時刻管理は次の順で初期化する。

1. RTC driverをopenする。
2. RTCを再設定する前にcalendar値とRTC状態を取得する。
3. 永続データ管理から現在のlogical Trusted Time Record、Time Update Recordおよび各保存処理の確定状態を読出す。
4. セキュリティ管理へdataset-domain分離HMAC検証を要求する。
5. calendar format/rangeを確認する。
6. COMMITTED record、revisionおよびRTC continuityの整合を確認する。
7. PREPARED transactionがある場合は第9.4節の復旧判定を行う。
8. trust state/qualityを確定する。
9. 起動・終了・再起動管理/VPS接続・デバイス認証/ログ・診断/セキュリティ管理へavailabilityを提供する。

### 9.2 continuity確認

少なくとも次を満たす場合、前回TRUSTED状態をholdover継続できる。

- 現在のlogical Trusted Time Recordまたは同revisionの冗長保存用の複製が正常
- Time Update RecordがNONE/COMMITTEDまたは正常復旧済み
- RTC calendar正常
- RTC sourceを保持中に再初期化していない
- VBATT lossが既知でない
- RTC現在値が`lastTrustedUtcMs - 2000 ms`以上

2秒の後退許容はRTC calendar設定・読出し境界の評価確定待ち基本設計値である。評価で変更する場合は本書へ反映する。

前回より古いlogical Trusted Time revisionしか正常確認できない場合は、このcontinuity条件を満たしたとは扱わない。

### 9.3 明らかな後退

RTC現在値が`lastTrustedUtcMs - 2000 ms`より小さい場合、RTC backup喪失または時刻改変の可能性としてTIME_UNTRUSTEDとする。

古いTrusted Time Recordの時刻をRTCへ自動設定してTIME_TRUSTEDへ復帰しない。

### 9.4 PREPAREDの更新処理の復旧

PREPAREDが残っている場合は、旧Trusted Time Record、候補レコードまたはRTC値のいずれかを、推測で採用しない。

時刻管理は、同一の`updateTransactionId`について、永続データ管理から保存処理の確定状態、候補・更新前の版、およびTrusted Time Recordの現在の版を取得する。RTCの読戻し値も取得し、次の規則で復旧する。

- 新しいTrusted Time Recordが候補の版として正常に保存確定済みで、RTCがその候補に基づく時刻と矛盾せず、Time Update RecordだけがPREPAREDで残ったと一意に確認できる場合：同じ更新処理を、冪等に`TIME_UPDATE_COMMITTED`へ確定する。
- 新しいTrusted Time Recordが保存確定されておらず、RTC変更も成立していないことを一意に確認でき、更新前の版が処理開始時に使用していた確定済みの版である場合：候補を`TIME_UPDATE_ABORTED`として、更新前の信頼状態を継続できる。
- RTC変更後・Trusted Time Recordの保存確定前等で、候補の適用済みと更新前の状態の継続のどちらも一意に証明できない場合：TIME_UNTRUSTEDとし、古いレコードまたは候補を推測で採用しない。
- 候補と更新前の状態の両方が成立し得る、版の関係が不明、HMAC/CRCが不正、または現在の内容の版を確定できない場合：TIME_UNTRUSTEDとする。

RTCの読取り分解能等に応じた比較許容差は、「一意に判断できない場合はUNTRUSTEDとする」という上記の基本挙動を変えない範囲で、評価により確定する。詳細設計だけで、曖昧なPREPAREDをTRUSTEDへ昇格させるしきい値を追加しない。

### 9.5 startup blocking

時刻管理初期化はローカル操作の起動を無期限に待たせない。

正常RTC保持時の初期化を100 ms以内とする。

sub-clock再起動等で100 ms以内に利用可能にならない場合、TIME_UNTRUSTEDとして起動処理を進め、時刻管理の復旧を別処理として扱う。

### 9.6 初回起動

製造provisioning前またはTrusted Time Record未作成時は、calendar値が存在してもTIME_TRUSTEDとしない。

## 10. 通常主電源OFF・低消費電力・再起動

### 10.1 通常主電源OFF

main battery接続中の通常主電源OFFでは、PWR_CTRLが停止してもPWR_AON由来VBATTによってRTC継続を基本とする。

通常終了時にRTCを停止しない。

### 10.2 低消費電力

RA8M2がSoftware Standby等へ移行してもRTCは継続する構成とする。

時刻同期期日到来だけを理由にWi-Fi/VPSをwakeしない。

次回通常復帰後にsync pendingを処理する。

### 10.3 再起動

software reset/IWDT reset/OTA resetでRTCが保持される場合、RTC値を初期値へ戻さない。

### 10.4 wake後re-anchor

低消費電力中に同一起動内で使用する高分解能タイマが停止した可能性があるため、復帰後はRTCを再読出しし、UTC補間anchorを再確立する。

### 10.5 主バッテリーの取外し

主バッテリーを取り外しても、RTCバックアップ電池が正常にVBATTを保持していれば、取外しだけを理由に`TIME_UNTRUSTED`としない。次回起動時に、`RTC_CONTINUITY_MARKER`、RTCのクロック源、時刻およびTrusted Time Recordの整合を確認できれば、`TIME_TRUSTED_HOLDOVER`を継続できる。

保持継続の喪失または不明を確認した場合は`TIME_UNTRUSTED`とし、第12章および「RTC継続性・時刻復旧契約基本設計」に従って有線復旧を行う。

## 11. 時刻源と信頼確立条件

### 11.1 信頼済み時刻の確立・更新に使用する時刻源

初期製品でTRUSTEDを新規確立できる時刻源は次とする。

- 管理された製造時の初期設定
- 管理された有線保守

既存のTRUSTED状態を更新できる時刻源として、認証済みVPS UTCを加える。

### 11.2 VPS通信だけでは時刻の信頼を新たに確立しない

TIME_UNSET/TIME_UNTRUSTEDから、通常VPS通信を使用してTIME_TRUSTEDへ直接復帰しない。

セキュリティ管理および公開用システム要求仕様「20. セキュリティ管理」により、信頼済み時刻がなければサーバ証明書有効期間を正常検証できず、通常VPS管理通信を開始しないためである。

### 11.3 信頼済み時刻の確立に使用しない時刻源

次をTRUSTEDの時刻源として使用しない。

- スマートフォンのOS時刻
- BLEメッセージで受信した時刻
- Wi-FiモジュールのRTC
- DHCPオプション
- 公開NTP/SNTP
- HTTP Dateのみ
- 認証されていない保守用UART入力
- ビルド時刻

### 11.4 時刻源の記録

TRUSTED確定時にsourceをTrusted Time Recordとevent logへ記録する。

## 12. 製造・有線保守による時刻設定

### 12.1 使用条件

wired trusted time設定は通常利用者UIではなく、次の管理環境でだけ使用する。

- 製造provisioning
- DEVELOPMENT/EVALUATION用tool
- 定義された保守手順

### 12.2 ログ・診断の保守UARTとの分離

ログ・診断の通常保守UARTはread-only診断を基本としているため、一般read-only commandへ時刻変更commandを追加しない。

時刻設定は、physical accessを伴うprovisioning/maintenance tool、service buildまたは同等の管理経路として分離する。

### 12.3 設定入力

設定値はUTCで受け付け、少なくとも次を確認する。

- calendar範囲
- tool/procedureが許可されたenvironmentであること
- 現在のsecurity lifecycleがmaintenance/provisioningを許可すること
- 永続データ管理がTime Update Record PREPAREDを安全にcommit可能であること

### 12.4 時刻更新の手順

有線経路から信頼できる時刻を設定する場合は、次の順を基本とする。

1. 入力UTCを検証する。
2. 候補のTrusted Time RecordとTime Update Recordを生成する。新しい`timeTrustRevision`、新しい`timeSyncGeneration`、更新前の版、および同一の`updateTransactionId`へ対応付ける。
3. セキュリティ管理のデータ集合ごとのドメイン分離規則に従い、両レコードへHMACを付与する。
4. 永続データ管理が、Time Update Recordの`TIME_UPDATE_PREPARED`を原子的に保存・確定する。
5. RTCへ設定する。
6. RTCを読み戻し、候補と整合することを確認する。
7. 候補のTrusted Time Recordを、次の確認を経て保存・確定する。
   - 永続データ管理が候補のバイト列をそのまま書き込み、読戻し、エンベロープ、長さ、CRCおよび`persistRevision`を確認する。
   - セキュリティ管理が、読み戻したバイト列のHMACを検証する。時刻管理が、`timeTrustRevision`、内容、および対象処理との対応関係を確認する。
   - これらの確認後に、永続データ管理が保存の確定を完了する。
8. 同じ`updateTransactionId`のTime Update Recordを、原子的に`TIME_UPDATE_COMMITTED`へ確定する。
9. 両方の論理データ集合とRTCの関係が正常であることを確認した後だけ、TIME_TRUSTEDと新しい`timeSyncGeneration`を公開する。

Trusted Time RecordとTime Update Recordを、一回の物理的な原子書込みで保存できるとは仮定しない。PREPAREDより前にRTCを変更しない。

### 12.5 中断

PREPARED前に失敗した場合、RTCを変更しない。

PREPARED後に中断した場合は、第9.4節の起動時復旧判定に従う。候補のTrusted Time Recordだけが保存確定済みで、更新処理全体の確定前に中断した場合も、推測で旧版へ巻き戻さない。

### 12.6 first provisioning

製造時はdevice credential/provisioningと同じ製造記録へ、時刻設定結果、source、tool revisionおよびDevice IDを対応付けることができる。

## 13. VPS時刻同期要求

### 13.1 開始条件

VPS時刻同期を開始できるのは少なくとも次の場合とする。

- 現在のtrust stateがTIME_TRUSTED
- VPS接続・デバイス認証が認証済みVPS通信を使用可能
- shutdown/low power transition/OTA critical phase等の上位処理がない
- time sync requestが未実行
- 永続データ管理がTime Update Record PREPAREDを安全にcommit可能

### 13.2 周期

VPS接続・デバイス認証で確定済みの周期を使用する。

- 起動後の最初の正常VPS通信時に1回
- その後24時間ごとを基本

24時間のdue判定は、TIME_TRUSTED中のRTCと最後にCOMMITTEDしたaccepted syncの時刻を使用する。再起動後もTrusted Time Recordからlast syncを復元できる。TIME_UNTRUSTED中はこの値を信頼した定期同期を実行しない。

24時間経過だけを理由としてWi-Fiを起こさず、次に正常VPS通信を実行可能となった時点で行う。

### 13.3 API

VPS接続・デバイス認証の次APIを使用する。

`GET /api/v1/device/{deviceId}/time`

TimeはHTTPS/TLS socketを直接所有しない。

### 13.4 request相関

同期要求ごとに次を管理する。

- `timeSyncRequestId` uint32
- VPS接続・デバイス認証の`requestId`
- request送信直前monotonic timestamp
- response受信完了monotonic timestamp
- 現在の`timeSyncGeneration`
- 現在のログ・診断の`bootInstanceId` uint64（取得可能な場合）

### 13.5 concurrent request

同時に実行するtime sync transactionは1件とする。

新しい定期syncが到来しても実行中syncへ重ねない。

---

## 14. VPS時刻サンプルの受入れ検証

### 14.1 VPS接続・デバイス認証から受け取る情報

Timeは少なくとも次を受け取る。

- VPS接続・デバイス認証のrequestId
- authenticated VPS session結果
- `serverUtcEpochMs`
- response取得結果
- request送信monotonic time
- response受信完了monotonic time
- Device ID一致結果

### 14.2 server timestamp契約

VPSは`serverUtcEpochMs`をresponse body送出直前に取得し、当該responseに固定する。

事前生成cacheの古い時刻やrequest受付時点から長時間経過した値を返さない。

### 14.3 基本検証

次をすべて満たすsampleだけを候補とする。

- 現在のrequestとrequestId一致
- 認証済みTLS sessionから取得
- target Device ID/現在のAPI context正常
- HTTP/API response正常
- serverUtcEpochMsが第6.3節範囲内
- response途中・cache残骸・前回request結果でない
- monotonic receive >= send
- RTTが許容上限内

### 14.4 RTT

`rttMs = receiveMonotonic - sendMonotonic`

とする。

初期基本値として、時刻サンプル受入れのRTT上限を4,000 msとする。

4秒を超えたsampleは通信失敗ではなく`TIME_SAMPLE_RTT_TOO_LARGE`として時刻補正には使用せず、現在TRUSTED RTCを維持して後の同期を待つ。

### 14.5 receive時刻推定

server timestampをresponse送出直前値とする第14.2節の契約を前提に、初期製品はnetwork pathを概ね対称とみなし、

`estimatedUtcAtReceive = serverUtcEpochMs + rttMs / 2`

を採用する。

server processing timeおよびpath非対称性により誤差が生じるため、高精度時刻源とはみなさない。実機・実networkで誤差を評価する。

### 14.6 sample rejection

sample拒否だけを理由として、直前まで正常だったTRUSTED RTCを直ちにUNTRUSTEDへ落とさない。

RTC自身のcontinuity異常が別途成立した場合はtrustを失効する。

## 15. RTC補正方式

### 15.1 基本方式

初期製品はaccepted trusted sampleを用いてRTC calendarを直接補正するstep correctionを基本とする。

複雑なNTP-style slew algorithmを初期必須としない。

### 15.2 補正前capture

補正前に次をcaptureする。

- oldRtcUtcMs
- estimatedUtcAtReceive
- offsetMs
- timeSyncRequestId
- 現在のtimeSyncGeneration
- 現在のmonotonic timestamp
- 現在のbootInstanceId（取得可能な場合）

### 15.3 VPS同期による時刻更新の手順

受入れ済みのサンプルは、次の順で反映する。

1. サンプルの検証を完了する。
2. 候補のTrusted Time RecordとTime Update Recordを生成する。新しい版・世代、更新前の版、および同一のupdateTransactionIdへ対応付ける。
3. セキュリティ管理のデータ集合ごとのドメイン分離規則に従い、両レコードへHMACを付与する。
4. 永続データ管理が、`TIME_UPDATE_PREPARED`を原子的に保存・確定する。
5. RTCをestimatedUtcAtReceiveへ補正する。
6. RTCを読み戻し、候補と整合することを確認する。
7. 候補のTrusted Time Recordを、次の確認を経て保存・確定する。
   - 永続データ管理が候補のバイト列をそのまま書き込み、読戻し、エンベロープ、長さ、CRCおよび`persistRevision`を確認する。
   - セキュリティ管理が、読み戻したバイト列のHMACを検証する。時刻管理が、`timeTrustRevision`、内容、および対象処理との対応関係を確認する。
   - これらの確認後に、永続データ管理が保存の確定を完了する。
8. 同じupdateTransactionIdのTime Update Recordを、原子的に`TIME_UPDATE_COMMITTED`へ確定する。
9. 最終確認後に、新しい`timeSyncGeneration`と`TIME_QUALITY_TRUSTED_SYNCED`を利用側へ公開する。

PREPAREDより前にRTCを変更しない。Trusted Time RecordとTime Update Recordを、一つの保存処理で確定できるとは仮定しない。

### 15.4 小さい差

絶対値10分以下のoffsetは、第14章のsample検証に成功した場合、1回のaccepted sampleで補正できる。

### 15.5 保存確定の失敗

RTC補正後に、Trusted Time Recordの保存確定またはTime Updateの最終的なCOMMITTEDへの確定が失敗した場合は、その起動中に新時刻を「正常確定済み同期結果」として公開しない。

PREPAREDまたは最終確定が未完了の状態を保持し、第9.4節の復旧判定対象とする。候補のTrusted Time Recordが既に保存確定済みの場合は、失敗を理由に推測で旧版へ巻き戻さない。

### 15.6 既存ログ

RTC stepによって既存ログの`utcEpochMs`を再計算・上書きしない。

### 15.7 error adjustment

FSP/RA8M2 RTCはsub-clock error adjustmentを利用できるが、初期製品では毎日同期を前提とし、automatic drift compensationを必須としない。

実機で24時間driftが大きい場合は、固定補正またはmanufacturing calibrationの採否を評価する。採用によりholdover精度や信頼判定条件を変更する場合は本基本設計へ反映する。

---

## 16. 大きな時刻差の扱い

### 16.1 大きな時刻差の補正

現在`TIME_TRUSTED`であっても、VPSからの取得時刻サンプルに対する時刻差（offset）の絶対値が10分を超える場合は、1回のサンプルだけで即時補正しない。

`TIME_LARGE_OFFSET_VERIFYING`として、二回目の取得時刻サンプルを要求する。

### 16.2 二回目確認

次の順に、VPSから取得した時刻の一貫性を確認する。

1. 最初の取得時刻サンプルから2秒以上後、60秒以内に、二回目のサンプルを取得することを基本とする。
2. 二つのサンプルについて、それぞれの単調時刻による経過時間を考慮して比較する。差が2秒以内で整合していれば、VPS時刻が一貫していると判断し、大きな時刻差の補正を許可する。

### 16.3 不一致

二回目と整合しない場合、RTCを変更せず、`TIME_VPS_SAMPLE_INCONSISTENT`を記録する。

現在のRTC continuityが正常ならTIME_TRUSTEDを維持する。

### 16.4 RTC自身の異常

RTCが自発的に大幅jumpしたことを検出した場合はVPS sample rejectionとは別にTIME_UNTRUSTEDへ遷移し、通常VPS通信を停止する。

## 17. 時刻補正とイベント順序

### 17.1 monotonic order

時刻補正前後でも`monotonicTimeUs`およびeventSequenceを巻き戻さない。

### 17.2 backward step

accepted correctionによりUTCが過去方向へ変化する場合も、既存eventの順序はmonotonic情報で維持する。

後続eventのutcEpochMsが直前eventより小さくなる可能性を許容する。

### 17.3 timeSyncGeneration

正常COMMITTED補正ごとに`timeSyncGeneration`を増加する。

ログ・診断は現在generationを各recordへ保持し、補正前後を識別できるようにする。uint32最大値へ到達した場合はwrapさせず保守異常とする。

### 17.4 補正event

補正時には少なくとも次をログ・診断へeventとして提供する。

- old UTC
- new UTC
- offset
- source
- timeSyncGeneration
- requestId
- RTT
- correction direction
- large correction verification有無
- updateTransactionId

## 19. VPS接続・デバイス認証との連携

### 19.1 VPS開始・継続可否

VPS接続・デバイス認証へ`TIME_TRUSTED`可否を提供する。

VPS接続・デバイス認証は公開用システム要求仕様「20. セキュリティ管理」/セキュリティ管理に従い、サーバ証明書有効期間を検証できないTIME_UNTRUSTED状態で通常VPS管理・保守通信を開始しない。

TIME_TRUSTED→TIME_UNTRUSTEDとなった場合は、VPS接続・デバイス認証の切断契約に従い新規HTTP要求を停止し、実行中要求を未完了として中断し、TLS/TCPを終了して`VPS_AUTHENTICATED`、`vpsSessionId`および一時session情報を無効化する。同じtime trust条件のまま自動再接続しない。

### 19.2 bootstrap loopを作らない

VPS接続・デバイス認証の`/time` APIをTIME_UNTRUSTEDからのbootstrapへ使用しない。

### 19.3 VPS接続・デバイス認証への要求

VPS接続・デバイス認証へ次を要求する。

- `/time` responseの`serverUtcEpochMs`はresponse body送出直前に取得する。
- responseをcache reuseしない。
- request/response相関を維持する。
- send/receive monotonic timestampをTimeへ提供する。
- authenticated TLS結果をTimeへ提供する。
- TIME_TRUSTED喪失を切断・認証状態喪失条件として扱う。

### 19.4 time sync failureとtrust lossを分離する

個々のVPS時刻サンプルがRTT超過、large-offset二回目不一致等で拒否された場合、RTC continuityが正常でTIME_TRUSTEDを維持する限りVPS session全体を切断しない。

一方、RTC continuity異常、record異常等によってTIME_TRUSTED自体を失った場合は、第19.1節に従って既存sessionを終了する。protocol不正、認証状態異常等はVPS接続・デバイス認証/セキュリティ管理の通信異常方針へ従う。

## 20. セキュリティとの連携

### 20.1 時刻の信頼情報を利用する機能

セキュリティ管理はTimeのtrust結果をサーバ証明書有効期間検証可否へ使用する。

### 20.2 HMAC

Trusted Time RecordおよびTime Update Recordはセキュリティ管理の`K_SEC_STATE_MAC`でHMAC-SHA-256認証する。

両datasetは第8.6節のdomain分離を使用し、Timeはraw keyを取得しない。

### 20.3 起動依存関係

Security coreは、Time trustを必要とするVPS certificate有効期間検証より前に、K_SEC_STATE_MAC検証serviceを利用可能にする。

これにより「Time recordを検証するためSecurityが必要だが、Security初期化にtrusted timeが必要」という循環依存を作らない。

### 20.4 trust loss

TIME_TRUSTED→TIME_UNTRUSTEDとなった場合、セキュリティ管理/VPS接続・デバイス認証/異常管理へ即時通知する。

セキュリティ管理は時刻未信頼を暗号検証成功だけで上書きしない。VPS接続・デバイス認証は新しい通常VPS session開始を禁止するとともに、既存sessionを終了し認証状態を無効化する。既存session継続可否をセキュリティ管理が都度判断する方式にはしない。

### 20.5 所有者権限との分離

OWNER roleを持つBLE端末でもtrusted timeを直接設定できない。

### 20.6 security event

時刻source異常、Trusted Time Record HMAC失敗、不自然なRTC後退、logical revision rollback拒否、大幅VPS時刻不一致をsecurity/diagnostic eventとして識別可能にする。

---

## 21. 永続データ管理との連携

### 21.1 保存するデータ集合

Trusted Time RecordとTime Update Recordを、それぞれ別の小容量の重要な論理データ集合として、永続データ管理の`PERSIST_CRITICAL`へ保存する。

### 21.2 データ集合ごとの原子的更新

各レコードは、次の順序で、それぞれ物理的に原子更新する。

1. 永続データ管理が旧データの保存用複製を保持する。
2. 永続データ管理が新しいデータのバイト列を書き込み、読み戻す。
3. 永続データ管理が保存形式、長さ、CRC、および`persistRevision`を確認する。
4. セキュリティ管理がHMACを検証する。
5. 時刻管理がデータ内容の版、内容、および更新処理との対応関係を確認する。
6. 永続データ管理が確定マーカーを確定する。

書込み途中のレコードをTRUSTEDの根拠に使用しない。Trusted Time RecordとTime Update Recordを、一つの物理的な更新処理で同時に確定できるとは仮定しない。

### 21.3 PREPARED/Trusted/COMMITTEDの整合

時刻管理が、Time Update RecordのPREPARED、RTC設定、候補のTrusted Time Recordの保存確定、およびTime Update RecordのCOMMITTEDを管理する。これらを、同じ`updateTransactionId`、候補の`timeTrustRevision`、および旧版の値で対応付ける。

永続データ管理は、各論理データ集合の物理的な原子性を保証し、復旧の判断材料を提供する。PERSIST自身がRTCの意味や、旧版と候補のどちらを信頼するかを選ばない。

PREPAREDを経ずに、新しいTrusted Time Recordを通常更新しない。新しいTrusted Time Recordが保存確定済みで、最終的なCOMMITTEDへの確定だけが未完了の場合は、第9.4節に従い、同じ更新処理を完了できるかを時刻管理が判断する。

### 21.4 処理の優先度

時刻レコードの更新は、安全停止・電源保護より優先しない。

低電圧等でPREPAREDを安全に保存確定できない場合、RTC補正を開始しない。

PREPARED後に電源条件が成立しなくなった場合は、新しい書込みを無理に完了させず、次回起動時の第9.4節の処理へ引き継ぐ。

### 21.5 代替データの使用と巻戻し

物理的なA/B複製のうち、同じ論理版の正常な複製へ切り替えることは許可できる。

一方、最新の論理版のTrusted Time Recordが正常であると確認できないことだけを理由に、それ以前の`timeTrustRevision`をTIME_TRUSTEDの判断基準として自動採用しない。代替データの使用と巻戻しの方針は時刻管理が定める。時刻管理は、セキュリティ管理のMAC検証結果と永続データ管理の物理保存の状態を判断材料として、TIME_UNTRUSTEDへ移る。

例外は、未完了のPREPARED処理について、次の両方を一意に確認し、ABORTする場合である。

- 新しいTrusted Time Recordがまだ保存確定されていない。
- 旧版が、この処理の開始時点で現在有効な確定済みの版だった。

この処理は、確定済みの時刻情報の巻戻しではなく、未確定の更新処理の取消しである。

古いレコードの値をRTCへ書き戻してTIME_TRUSTEDへ復帰しない。

## 22. 電源・省電力管理との連携

### 22.1 PWR_AON/VBATT

電源・省電力管理へ、VBATTを主バッテリー接続中の通常主電源OFF時にも維持するための低待機電流給電を要求する。主バッテリー側の保持電源喪失時には、第4.3節のRTCバックアップ電池で保持を継続する。

### 22.2 待機電流

主電源OFF時に主バッテリーから流れるシステム全体の待機電流は、性能・品質・検証基本設計に従い100 µA以下とする。`PWR_AON`全体には、電源・ハードウェア基本設計が定める50 µA以下の電流枠を割り当てる。`PWR_AON`由来のRTC保持電源はその内数とし、5 µA以下を評価目標とする。主バッテリー取外し中にRTCバックアップ電池から流れる電流は、この主バッテリー側の待機電流の算定対象に含めない。時刻管理はこれらの値を変更せず、RTC/VBATTを利用する立場でハードウェアの評価結果を参照する。

### 22.3 low power

Time sync dueだけを理由としてlow powerを解除しない。

### 22.4 power loss

`PWR_AON`由来の保持電源喪失と、VBATT自体の保持喪失を区別する。`PWR_AON`側の電源喪失だけでは時刻の信頼を失効させず、RTCバックアップ電池による保持継続を含めて、次回起動時に判定する。

判定に用いる保持情報と取得手順は、「RTC継続性・時刻復旧契約基本設計」の4章・5章に従う。情報が取得できない、矛盾する、または一意に判定できない場合は、RTCとTrusted Time Recordの整合だけから保持継続を推測せず、`TIME_UNTRUSTED`とする。

### 22.5 battery protection

低バッテリーによるハードウェア遮断で`PWR_AON`由来の保持電源が失われても、RTCバックアップ電池でVBATTを保持する。保持継続の喪失または不明を確認した場合は、安全側に`TIME_UNTRUSTED`とする。

---

## 23. 起動・終了・固定ブートとの連携

### 23.1 fixed boot

固定ブート・復旧の固定ブートはRTC trustをapplication起動可否のroot conditionにしない。

不正applicationを起動しない責任と時刻trustは分離する。

### 23.2 Boot Handoff

必要に応じて固定ブート・復旧のBoot Handoffからreset reasonを受け取り、time trust loss eventとの相関へ使用する。

### 23.3 起動・終了・再起動管理の起動結果

Time初期化結果を次で起動・終了・再起動管理/異常管理へ提供する。

- NORMAL: trusted RTC available
- DEGRADED: time untrusted/unsetだがlocal安全機能は初期化可能
- FAILED: RTC driver/resource異常でTime service自体利用不能

DEGRADEDだけを理由としてローカルBLE操作の起動失敗とはしない。

### 23.4 終了

通常終了時にRTCを停止しない。

Trusted Time Recordへ毎回終了時時刻を書き込むことを必須としない。

## 24. OTA・設定・製品情報との連携

### 24.1 OTA

OTA update、trial boot、PREVIOUS recoveryによってRTC/Trusted Time Recordを初期化しない。

OTA deadlineはRTCではなくOTA更新の単調時刻で管理する。

### 24.2 firmware変更

firmware update後もTime record formatVersionが対応していれば継続利用する。

非対応formatを黙って初期値としてTRUSTED扱いしない。

### 24.3 設定管理

初期製品の管理設定packageから次を変更できない。

- trust policy
- trusted source種別
- 24時間sync基本周期
- RTT受入れ上限
- large correction閾値

これらはsecurity/time基本方式であり、remote operational settingとしない。

### 24.4 製品情報

wired/provisioning eventへ製品情報管理のDevice ID、hardwareProfileId、firmware identityを対応付けられるようにする。

製品情報管理の`calibratedAtUtcMs`等へtrusted absolute timeを提供する場合も、Time qualityを同時に提供し、untrusted RTC値を正常な校正時刻として扱わせない。

- time trusted/untrusted
- VPS disabled because time unavailable
- wired maintenance required
- time sync in progress/failed

### 25.2 表示priority

### 25.3 一般利用者表示

- `TIME_VBATT_CONTINUITY_LOST`
- `TIME_VPS_SYNC_FAILED`
- `TIME_SAMPLE_RTT_TOO_LARGE`
- `TIME_VPS_SAMPLE_INCONSISTENT`
- `TIME_LARGE_OFFSET_DETECTED`
- `TIME_WIRED_SET_REQUIRED`

### 26.2 local operation

Time異常単独では、走行/停止/緊急停止等が時刻に依存していないため、当該安全機能を停止させない。

### 26.3 VPS機能

TIME_UNTRUSTEDでは通常VPS管理・保守通信を利用不可とする。

その結果、設定取得、ログupload、OTA確認、VPS時刻同期等も利用不可となる。TIME_TRUSTED喪失時は既存VPS sessionもVPS接続・デバイス認証により終了する。

### 26.4 logs

時刻異常中もmonotonic ordering付きevent logを継続する。

### 26.5 recovery

trust lossの復旧は第12章のwired maintenanceを基本とする。

VPSへのretryを繰り返してtrust復旧しようとしない。

PREPARED中断は第9.4節の一意性を要求する復旧を先に試し、candidate/previousいずれのtrustも一意に確認不能な場合はTIME_UNTRUSTEDを維持してwired maintenanceへ移る。

## 27. 工場初期化・所有者変更・保守

### 27.1 所有者再登録

所有者再登録によってRTCまたはTrusted Time Record/Time Update Recordを変更しない。

### 27.2 factory reset

factory resetによってRTC、Trusted Time Record、Time Update Recordまたは正常なtime trust metadataを利用者データとして削除・巻戻ししない。

時刻は製品管理・セキュリティ通信成立に必要なsystem metadataとして保持する。

### 27.3 explicit service reset

時刻信頼情報を意図的に失効する必要がある場合、通常factory resetではなく管理されたservice procedureとして行う。

### 27.4 電池交換

主バッテリーの交換中はRTCバックアップ電池でVBATTを保持する。主バッテリー交換だけを理由に時刻の信頼を失効させず、交換後の判定は「RTC継続性・時刻復旧契約基本設計」の5.3節に従う。

RTCバックアップ電池の交換条件は、同書5.4節に従う。保持継続を確認できない場合に`TIME_UNTRUSTED`となり、有線復旧が必要となる条件を、保守・取扱手順に明記する。

RTC access、HMAC、VPS sync、record commitによって緊急停止、安全停止、電源保護、IWDT等を阻害しない。

## 29. 検証方針

### 29.1 RTC保持

- main power OFF/ONでRTC継続
- software reset/IWDT resetでRTC継続
- low power移行/復帰でRTC継続
- PWR_CTRL OFF中のVBATT供給
- RTC VBATT branch 5 µA、`PWR_AON` 50 µA sub-budgetおよび主電源OFF時のシステム総量100 µAの包含関係
- RTCバックアップ電池が正常な状態での主バッテリー取外し・再接続と、次回起動時の保持継続の確認
- 主バッテリー側とバックアップ電池側の両方からの保持電源を失った場合、または保持継続を確認できない場合の`TIME_UNTRUSTED`判定

### 29.2 trust

- Trusted Time Recordなし
- 有効な現在のlogical record＋valid RTC
- CRC破損
- HMAC破損
- 現在のrevision破損＋old logical revision正常でもfallback拒否
- same logical revisionのA/B片側破損時に正常copy採用
- RTC 2秒境界の後退
- calendar範囲外
- source clock再初期化
- VBATT loss
- TRUSTED_SYNCED→HOLDOVER quality遷移

### 29.3 Time Update transaction fault injection

- PREPARED commit直前reset
- PREPARED commit直後、RTC set前reset
- RTC set直後reset
- RTC readback直後reset
- candidate Trusted Time Record commit直前/直後reset
- Time Update COMMITTED finalize直前/直後reset
- candidate record commit済み＋PREPARED残存で冪等finalize
- new record未commit＋previous currentを一意確認してABORT
- candidate/previous双方が成立し得る場合はUNTRUSTED
- dataset-domain違いの正常HMAC tag流用を拒否

### 29.4 VPS sync

- 24h periodic request
- normal boot first VPS sync
- low power中defer
- RTT境界3,999/4,000/4,001 ms
- offset境界10分
- large correction二回一致/不一致
- TLS/session不正時拒否
- stale response/requestId mismatch拒否
- server timestamp生成位置の検証

### 29.5 correction

- forward step
- backward step
- old log不変
- monotonic order不変
- timeSyncGeneration増加
- correction event内容
- ログ・診断のuint64 bootInstanceId相関

### 29.6 security/lifecycle

- TIME_UNTRUSTEDで新規VPS開始禁止
- TIME_TRUSTED→UNTRUSTED時に既存VPS session終了・request中断・認証状態無効化
- sample拒否だけでTIME_TRUSTED維持時はsessionを不要に切断しない
- 所有者再登録・工場初期化時の、時刻レコードと更新処理情報の保持
- OTA後Time保持
- wired maintenance設定
- BLEまたは所有者操作から時刻を設定できないこと

### 29.7 RTC精度

- 温度範囲ごとの24時間drift
- main power OFF holdover
- low battery条件
- crystal個体差
- FSP error adjustment使用有無比較

## 32. 他文書へのフィードバック

### F-01 VPS接続・デバイス認証

`/time` responseへresponse body送出直前の`serverUtcEpochMs`を含め、requestId、authenticated session結果、send/receive monotonic timestampをTimeへ提供する。

時刻同期周期は起動後最初の正常VPS通信＋24時間ごとを維持する。

VPS接続・デバイス認証側は既にTIME_TRUSTED喪失を切断条件としているため、本書も同じ契約を正とする。trust喪失時は新規要求受付停止、実行中request中断、TLS/TCP close、`VPS_AUTHENTICATED`/`vpsSessionId`/一時session情報無効化を行い、同じ時刻信頼条件のまま自動再接続しない。

### F-02 電源・省電力／ハードウェア

`PWR_AON`由来の低待機電流VBATT給電とRTCバックアップ電池による二つの保持電源、逆流防止、電源切替えおよびRTC/SOSC保持を具体化する。主バッテリー側の電流について、RTC VBATT branch 5 µA、`PWR_AON` 50 µAの内訳、および主電源OFF時のシステム総量100 µAの成立性を電源・ハードウェア基本設計／性能・品質・検証基本設計へフィードバックする。

RTCバックアップ電池には、交換可能な3 Vコイン形一次電池（CR2032クラス）を採用する。具体部品、切替え回路、保持寿命等の評価は、「RTC継続性・時刻復旧契約基本設計」に従う。

### F-03 永続データ管理

PERSIST_CRITICALへTrusted Time Record＋Time Update Record合計1 KiB以下のcritical領域を確保する。

両者は別logical datasetとして各々A/Bまたは同等の原子更新を行い、PREPARED→RTC set→Trusted Time Record commit→COMMITTED finalizeを同一`updateTransactionId`で相関する。PERSISTがold/new trustを意味判断せず、復旧材料を時刻管理へ返す。

### F-04 セキュリティ管理

Time trust stateをcertificate validity検証条件へ使用し、TIME_UNTRUSTEDから通常VPSによるbootstrapを許可しない既存方針を維持する。

K_SEC_STATE_MAC serviceはTime trustが未確立でも起動初期に使用可能とし、Trusted Time RecordとTime Update Recordをdataset-domain分離して認証する。old logical revisionの正常tagだけでTIME_TRUSTEDへ戻さない。

### F-05 ログ・診断

Timeからutc valid/trust/`TIME_QUALITY_*`/timeSyncGenerationを受け、ログ・診断のuint64 bootInstanceIdとmonotonicTimeUsによる順序を維持する。

時刻補正eventとTime Update recovery eventを記録し、既存recordのUTCを変更しない。

### F-06 起動・終了・再起動管理

Time DEGRADEDをlocal operation起動失敗と同義にせず、VPS利用制限付き起動として異常管理/システム状態管理と整合する。

### F-07 状態表示・利用者通知

状態表示・利用者通知へTIME_UNTRUSTED、VPS disabled due time、wired maintenance required、RTC fault、Time Update recovery failedを提供する。安全関連表示が最優先である既存契約を変更しない。

### F-08 保守・取扱・量産

製造時trusted time provisioningと、battery removal等でRTC continuityを失った場合のwired recovery手順を具体化する。

## 33. 初版の自己確認結果と引継ぎ条件

### 33.1 初版自己確認

以下は初版作成時の自己確認と、その後の整合確認の記録である。RTCバックアップ電池と主バッテリー取外し時の扱いは、後に「RTC継続性・時刻復旧契約基本設計」で確定した方針へ変更済みであり、現在の設計は本書4章・10.5節に示す。

- 時刻管理に独立公開要求章がないことを明示し、公開用システム要求仕様「12. VPS接続・デバイス認証」/公開用システム要求仕様「14. ログ・診断」/公開用システム要求仕様「20. セキュリティ管理」等へtraceを設定した。
- VPS接続・デバイス認証の`/time` APIと24時間同期周期を維持し、TIME_TRUSTED喪失時の既存VPS session終了契約へ整合した。
- secure time bootstrap、NTP、smartphone時刻を初期製品へ追加していない。
- ログ・診断のuint64 bootInstanceId、monotonicTimeUs、utcEpochMs、TIME_QUALITY、timeSyncGenerationへ整合し、時刻管理独自の32 bit boot IDを作らないよう修正した。
- UTC補正がcontrol/safety timeoutへ影響しない構成を維持した。
- 初版では、RA8M2内蔵RTC＋SOSCとPWR_AON由来VBATTを基本とし、専用CR2032を必須構成に含めていなかった。現在はRTCバックアップ電池を採用している。
- 初版では、主バッテリー取外し後のRTC信頼喪失を前提として有線復旧を定めた。現在は取外しだけで信頼を失効させず、保持継続の喪失または不明を確認した場合に有線復旧を行う。
- trust state、sync state、qualityを分離し、TRUSTED_SYNCEDとHOLDOVERの24時間境界を基本設計で明確化した。
- Trusted Time RecordとTime Update Recordを別logical datasetとしてPERSIST_CRITICALへ保持し、セキュリティ管理のdataset-domain分離K_SEC_STATE_MACで認証するよう整合した。
- RTC calendarがもっともらしいだけでTRUSTEDにしない。
- latest logical Trusted Time revisionを正常確認できない場合、old logical revisionへ自動fallbackしてTIME_TRUSTEDへ戻さない規則を追加した。
- Time UpdateをPREPARED→RTC set→Trusted Time Record commit→COMMITTED finalizeのデータ管理機能が管理する transactionとし、二recordが一つの物理atomic writeであるという前提を除いた。
- PREPARED中断について、new record commit済みなら冪等finalize、new未commitかつprevious currentを一意確認できる場合だけABORT、曖昧ならUNTRUSTEDとするよう具体化した。
- PREPAREDを安全にcommitできない電源条件ではRTC補正自体を開始しない。
- VPS sampleをrequest/session/RTT/rangeで検証し、server timestamp生成時点とRTT/2補正前提を維持した。
- large correctionを単一sampleで即時反映しない方式を維持した。
- correction後も過去logを書換えない。
- 所有者再登録・工場初期化・OTAによって、RTCの信頼状態、Trusted Time Record、Time Update Recordを削除・巻戻ししない。
- TIME_UNTRUSTED単独でlocal安全機能を停止しない。
- 容量、時間、RTT、offset、sync周期、quality境界、transaction/fallback条件を評価確定待ちを含む基本設計で管理する値として明確化した。
- malloc/freeに依存しない固定資源方式とした。

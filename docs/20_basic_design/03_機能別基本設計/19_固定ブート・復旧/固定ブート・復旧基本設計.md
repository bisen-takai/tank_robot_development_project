## 1. 本書の目的

### 1.1 目的

本書の目的は、公開用システム要求仕様に分散して定義されている起動対象ファームウェアの検証、セキュアブート、OTA更新後試行起動、直前正常ファームウェアへの復旧および有線復旧を、システムアーキテクチャで独立機能として定義した「固定ブート・復旧」の責任へ集約し、詳細設計へ展開可能な粒度まで具体化することである。

公開用システム要求仕様には「固定ブート・復旧」という独立章は存在しない。本書は主に起動・終了・再起動、OTA更新、セキュリティ管理、永続データ管理、性能・品質・耐久性、保守・サポート・製品ライフサイクルおよび関連基本設計から要求と責任を受ける。

### 1.2 対象範囲

本書は、Tank_Robot本体のRA8M2がリセット解除された後、本体アプリケーションファームウェアへ制御を移す前に実行する固定ブート・復旧機能について、起動対象の選択、署名・完全性・SecurityGen・製品互換性確認、OTA更新候補のOverwrite反映、一回限りの試行起動、直前正常ファームウェアへの自動復旧、電源断・リセット中断時の再判定、リセット要因・起動結果の引継ぎ、IWDT更新実行権の管理および有線復旧への移行を具体化する。

固定ブート・復旧は、本体アプリケーションファームウェアより先に動作し、本体アプリケーションから独立した信頼境界として扱う。通常のOTA更新対象には含めない。BLE、Wi-Fi、VPS通信、通常操作、設定適用、ログ送信その他の本体アプリケーション機能を固定ブート内へ持ち込まず、起動・復旧に必要な最小機能だけで構成する。

#### 基本設計と詳細設計の区分

本書で定める起動可否・起動先の判断、試行起動の実施回数を計上する時点、PREVIOUSによる復旧の条件、Boot Interface、メモリ容量・時間の上限、IWDT更新責任・進行確認の条件、有線復旧の条件等は、基本設計で管理する。起動・復旧の可否や外部から見た製品挙動に影響する方式・値については、評価による確定待ちのものもこの対象とする。

実機評価で変更が必要となった場合は、詳細設計だけで変更せず、本書またはその値・方式を定める関連基本設計へ反映する。物理アドレス、バイトオフセット、ドライバAPI、リンカーセクション、具体的なタスク・構造体等、基本設計の外部挙動を変えない実装方法は、詳細設計で具体化してよい。

### 1.4 外部技術資料

採用方式の成立性確認に、Renesas RA8M2/FSPの次の公開資料を使用する。

- RA Flexible Software Package Documentation: MCUboot Port (`rm_mcuboot_port`)
- RA Flexible Software Package Documentation: RA8M2
- Renesas Boot Firmware for RA8M2 MCU Group
- Renesas Flash Programmer V3 documentation
- RA8M2 Group Datasheet / Hardware User's Manual
- MCUboot documentation

参照時点のRenesas FSPではRA8M2に対してMCUboot OverwriteおよびOSPI_B secondary storageがサポートされる。OSPI_B external storageを使用するSwap modeは使用しない。RA8M2標準Boot FirmwareはCortex-M85を使用する。

外部資料は上位製品要求ではない。採用FSP/MCUboot版で制約が変化した場合、要求上の目的である「不正imageを起動しない」「固定ブートを通常OTAで変更しない」「未実施trialは一回だけ開始し、試行済み未VALIDATEDならPREVIOUSへ復旧する」を維持し、具体実装を再評価する。

## 2. 設計方針と適用範囲

### 2.1 基本方針

固定ブート・復旧は次の原則で設計する。

1. 正当性、完全性、対象製品、対象hardwareおよびSecurityGenを確認できないapplicationへ制御を移さない。
2. 通常起動でもPRIMARY imageを毎回検証する。
3. 通常PRIMARY検証を外付けSerial NORへ依存させず、OTA/recoveryが不要ならbulk media failureだけで基本起動を失わない。
4. 通常OTAはapplicationだけを更新し、fixed boot/trust sectionを変更しない。
5. FSPでサポートされるMCUboot Overwrite＋OSPI_B secondaryをinstall/recoveryに採用し、OSPI_B Swap rollbackへ依存しない。
6. PREVIOUS復旧authorizationの意味と管理はOTA更新、reset時起動可否・起動先の判断とboot-critical markerの意味と管理は固定ブート・復旧が担当し、永続データ管理はその永続OTA状態を物理保存する。fixed bootはOTA更新の定義外のOTA policyを追加しない。
7. OTA applicationは`INSTALL_REQUESTED`をcontrolled reboot前に確定し、`PRIMARY_OVERWRITE_STARTED`はfixed bootがfirst erase/program直前に確定する。
8. `PRIMARY_OVERWRITE_STARTED`だけをtrial試行済みの根拠にしない。candidate書込み後検証と`TRIAL_ARMED`が未確定ならPREVIOUS復旧へ倒し、`TRIAL_ARMED=true`かつ`trialAttempted=false`なら公開用システム要求仕様「15. OTA更新」の`SYS-OTA-104`に従って未実施trialを一回開始する。
9. candidateへbranchする直前に`trialAttempted=true`を永続確定し、当該candidateの試行起動の実施回数を計上する時点とする。`trialAttempted=true`かつ未VALIDATEDなら再trialしない。
10. ordinary PRIMARY破損だけを理由としてPREVIOUSへ暗黙fallbackしない。
11. fixed bootはBLE、Wi-Fi、VPS、設定適用、通常operationを実行しない。
12. actuator出力を有効化せず、CPU1も検証済みapplicationが必要とするまで起動しない。
13. IWDTはreset直後から有効とし、固定ブート中は正常進行確認後だけ更新する。
14. reset/power loss後も、永続状態から安全側に一意な再判定を行う。
15. 自動復旧不能時は不正imageを起動するよりwired recovery必要状態へ移る。
16. fixed boot自身の信頼は自己署名検証ではなく、通常applicationから書込み不能とする固定領域・製品のセキュリティライフサイクル・DLM/Access Window等をroot of trustの一部として成立させる。
17. 起動・終了・再起動管理が所有する起動・再起動end-to-end時間契約について、Application前区間の経過時間・残り時間・timeout事実を管理し、Application開始時に時間上限を再付与しない。

### 2.2 本書で扱わない事項

次は担当基本設計に従う。

- OTA配信可否、VPSからのimage取得、CANDIDATE/PREVIOUS意味：OTA更新
- 署名方式、SecurityGen policy、鍵ライフサイクル：セキュリティ管理
- OTA状態・SecurityGen等の物理A/B保存：永続データ管理
- 起動・再起動end-to-end時間契約、Application到達後の監視および最終timeout結果：起動・終了・再起動管理
- application起動後の機能初期化・起動完了判定：起動・終了・再起動管理
- BLE接続待機状態その他の起動後状態の確定：システム状態管理
- OTA final confirm：OTA更新
- PREVIOUS imageを正常FWとして最終確定する意味：OTA更新
- 利用者表示具体pattern：状態表示基本設計

### 2.3 初期製品のsingle-image方針

初期製品の通常OTA対象はCPU0で実行する本体アプリケーション一つとする。

CPU1 Cortex-M33を独立した更新imageとして扱うmulti-image MCUboot構成は採用しない。将来CPU1に独立firmwareを配置し、CPU0/CPU1を別々に更新する必要が生じた場合は、OTA更新と本書を改訂し、二つのimageの同時互換性・rollbackを設計する。

## 3. 責任分界と共通条件

### 3.1 機能責任

#### 各機能が担当する処理

| 機能 | 主な責任 |
| --- | --- |
| 固定ブート・復旧 | リセット要因を早期に取得し、起動対象の判断とPRIMARYの起動前検証を行う。下表の情報を確定し、MCUboot Overwriteによる書換えとPREVIOUSからの復旧を実行する。本体アプリケーション開始前の起動・再起動全体の時間監視、起動時引継ぎ情報（Boot Handoff）の作成、起動失敗の事実の引継ぎも担当する |
| OTA更新管理 | 更新候補と復旧の方針、OTA取引、CANDIDATE/PREVIOUSの意味を定める。`recoveryEligible`、`INSTALL_REQUESTED`の発行条件、`TRIAL_BOOT_VALIDATED`、本体のOTA最終結果、`CONFIRMED`およびVPSへの結果報告状態を管理する |
| セキュリティ管理 | `PK_FW_VERIFY`、`SecurityGen`、`K_SEC_STATE_MAC`の意味と鍵の管理方針、および署名方式を定める |
| 永続データ管理 | OTA・セキュリティ・起動状態の物理保存、A/B方式、保存の確定、電源断時の整合性維持、および固定ブートから利用する最小アクセス経路を担当する |
| 製品情報管理 | Product Descriptorの生成元、製品・機種・`hardwareProfileId`、および実行中ファームウェアの識別情報の意味を定める |
| 起動・終了・再起動管理 | 起動・再起動全体の時間条件を定め、本体アプリケーション開始後の監視と起動処理を行う。起動結果、リセット理由の解釈、起動失敗および最終的なタイムアウト結果を担当する |
| 電源・省電力管理 | 本体アプリケーション側の機能が確立した後のIWDT更新実行権と、電源状態を管理する |
| 異常管理 | 固定ブートから引き継いだ失敗がシステム全体へ与える影響を判断し、本体アプリケーション側の復旧を担当する |
| ログ・診断 | 引き継いだ起動・復旧イベントを記録・送信する |

#### 固定ブートが確定する起動情報

固定ブート・復旧機能は、本体アプリケーションが動作していない間に、起動対象を判断し、次の情報を確定する。

| 情報 | 意味と確定する時点 |
| --- | --- |
| `PRIMARY_OVERWRITE_STARTED` | PRIMARYの書換え開始を示す。PRIMARYに対する最初の消去・書込みの直前に確定する |
| `TRIAL_ARMED` | 更新候補のPRIMARYの書込み後検証が完了し、一回の試行起動を開始できることを示す |
| `trialAttempted` | 一回の試行起動を消費したことを示す。更新候補へ制御を移す直前に`true`を確定する |
| `RECOVERY_BOOT_PENDING` | 復元したPRIMARYの検証が完了し、本体アプリケーションの正常起動確認を待つことを示す |

各情報の確定順序は、第14～20章に従う。

#### OTA状態の判断と永続保存の分担

OTA更新管理機能は、OTA状態と本体のOTA最終結果の意味を定める。
固定ブート・復旧機能は、本体アプリケーションが動作していない間の起動判断と、前記の起動情報の確定を担当する。
永続データ管理機能は、各機能が指定した情報の永続保存を実行する。

本体アプリケーションを起動できないまま復旧が最終的に失敗した場合、固定ブート・復旧機能は`FAILED_RECOVERY`を代理で確定できる。
この場合も、OTA更新管理機能が定めた条件とデータ形式に従い、新たなOTA結果の意味を独自に決めない。

### 3.2 fixed bootが決定するもの

fixed bootは次を最終決定する。

- 今回PRIMARYへ制御を移してよいか
- `INSTALL_REQUESTED`と再検証結果に従ってCANDIDATE installを開始してよいか
- OTA stateに従って未実施trial、PREVIOUS recoveryまたはsettlement bootのどれを開始すべきか
- 起動対象imageがcryptographic/compatibility条件を満たすか
- wired recovery以外に自動boot/recovery経路が残っているか

### 3.3 fixed bootが決定しないもの

fixed bootは次を独自決定しない。

- VPS上のcandidateが最新か
- OTAを開始するか
- trial applicationがBLE接続待機まで正常起動したか
- candidateを最終的にcurrent FWとしてCONFIRMEDにするか
- アプリケーションで使用する設定・校正情報の意味
- 安全監視の正常性

---

## 4. RA8M2起動コアと固定ブート構成

### 4.1 primary boot CPU

初期製品はRA8M2 CPU0 Cortex-M85をprimary boot CPUとして使用する。

CPU1 Cortex-M33をprimary boot CPUへ変更しない。

理由は次のとおりである。

- RA8M2の標準構成でCPU0がprimaryである。
- Renesas Boot FirmwareはCortex-M85を使用する。
- 現行FSP/MCUbootのRA8M2標準support pathと一致する。
- CPU1 primary化のために追加のtool依存・製品security設定を初期製品へ導入しない。

### 4.2 CPU1の扱い

fixed boot中はCPU1を起動しない。

CPU1がreset/wait状態にあることを前提とし、fixed bootから未検証codeをCPU1へ転送・実行しない。

本体アプリケーションが将来CPU1を利用する場合も、CPU0 applicationが検証済みであり、本体アプリケーション側の初期化責任が成立した後にCPU1をactivateする。

### 4.3 論理構成

固定ブート・復旧は次の要素から構成する。

1. BSP/startup minimum
2. reset cause capture
3. IWDT更新責任・処理の進行監視
4. Boot Coordinator
5. PERSISTの重要データに必要な最小限の読出し・書込み処理
6. minimal RSIP/security bootstrap
7. Product Descriptor fixed copy
8. Primary-only verifier
9. OSPI_B minimum driver
10. MCUboot Overwrite path
11. image compatibility validator
12. PREVIOUS recovery stager
13. Boot Handoffの書込み処理
14. Boot Watchdog Service
15. application jump routine
16. boot failure/service-required routine

### 4.4 不要機能を持ち込まない

fixed bootへ次をlinkしないことを基本とする。

- BLE stack
- Wi-Fi AT stack
- TCP/TLS/HTTP client
- smartphone protocol
- setting JSON parser
- log ring/VPS sender
- actuator control
- servo/drive PWM
- low-power state machine

これにより固定ブート領域を小さく保ち、attack surfaceと通常更新できないcode量を抑える。

## 5. メモリ・パーティション・書込み境界

### 5.1 内蔵MRAM

OTA更新/永続データ管理の現行設計と整合し、1 MiB MRAMの論理budgetを次とする。

| 領域 | 上限 |
| --- | ---: |
| fixed boot/recovery executable + trust section | 224 KiB |
| `PERSIST_CRITICAL` | 32 KiB |
| PRIMARY application slot | 768 KiB |

物理address、erase/program block境界、vector、linker sectionは詳細設計で固定する。

224 KiB＋32 KiB＋768 KiBの境界はOTA更新のD-04、永続データ管理および電源・ハードウェア基本設計と整合済みであり、本書でも同じ値を基本設計で管理する値として使用する。

### 5.2 外付けSerial NOR

OTA更新/永続データ管理に従い、最低8 MiB external Serial NOR内に少なくとも次を独立partitionとして持つ。

- CANDIDATE / MCUboot secondary：1 MiB
- PREVIOUS：1 MiB
- OTA管理・その他bulk領域

PREVIOUSとCANDIDATEを同一erase単位へ混在させない。

### 5.3 PRIMARY書込み範囲

fixed bootのapplication overwrite routineはPRIMARYのlinker-defined range外を拒否する。

次を通常OTA write targetにしない。

- fixed boot executable
- fixed boot vector/trust section
- PK_FW_VERIFY
- fixed boot Product Descriptor
- `PERSIST_CRITICAL`

range overflow、length overflow、alignment errorはwrite前に拒否する。

### 5.4 外付けFlash非依存の通常起動

通常PRIMARY bootではexternal Serial NORを初期化しないことを基本とする。

OTA/recovery stateがactiveでなく、PRIMARYとcritical stateが正常なら、external media failureだけを理由としてapplication bootを禁止しない。

CANDIDATE installまたはPREVIOUS recovery時だけOSPI_B/secondaryを必須とする。

## 6. 固定ブート信頼情報とProduct Descriptor

### 6.1 trust section

fixed boot trust sectionへ少なくとも次を保持する。

- `PK_FW_VERIFY`
- fixed boot Product Descriptor
- fixed boot version/build identity
- supported image format version
- supported boot interface version
- crypto algorithm identifiers

trust sectionは通常OTA/設定/factory resetから変更しない。

### 6.2 firmware verification key

`PK_FW_VERIFY`はセキュリティ管理で定めたECDSA P-256 firmware署名検証公開鍵とする。

application imageはSHA-256 digestとECDSA P-256署名で検証する。

公開鍵交換を通常OTAから実行しない。

### 6.3 Product Descriptor

製品情報管理と同じgenerated descriptor sourceからfixed boot用descriptorを生成する。

少なくとも次を使用する。

- productFamilyId
- modelId
- hardwareProfileId
- mechanism/component compatibility classのうちboot互換性に必要な値

application image内のsigned Product Descriptor/metadataとfixed boot側descriptorが一致しない場合は起動しない。

### 6.4 root of trustの境界

fixed bootは、自分自身の領域に格納した公開鍵を用いて自分自身を「自己検証したから信頼できる」とは扱わない。

初期製品のboot root of trustは、少なくとも次の組合せで成立させる。

- 通常のアプリケーション・OTAの書込み処理から、固定ブート・信頼情報のセクションを書き換えられないメモリ境界
- NORMAL_OPERATIONのDLM/Access Level/Access Window等の製品security設定
- 製造・保守時に正規fixed boot/trust imageだけを書き込む管理手順
- RA8M2内蔵Boot Firmwareによる最終有線programming/recovery path
- application imageに対する`PK_FW_VERIFY`署名検証

hardware secure boot等の追加root-of-trust機構を採用する場合は将来hardeningとして評価するが、初版で実装済みとみなさない。

### 6.5 trust section保護

量産NORMAL_OPERATIONでは、通常applicationからfixed boot/trust sectionを書き換えられないhardware/software protectionを使用する。

Access Window、DLM/Access Levelその他の最終設定は、セキュリティ管理で残したwired recoveryとの両立評価後に決定する。

不可逆設定を評価前に固定しない。

## 7. ファームウェアイメージと起動互換性情報

### 7.1 基本形式

application imageはMCUboot互換のsigned imageとし、Tank_Robot固有metadataを署名保護範囲へ含める。

### 7.2 起動前に必要なmetadata

少なくとも次を起動前に取得・検証可能とする。

- image format/version
- image length
- firmwareId
- SemVer
- BuildID
- SecurityGen
- productFamilyId
- modelId
- hardwareProfileId
- boot interface compatibility range
- config schema compatibility summary
- persistent format compatibility summary
- SHA-256 hash / signature info

設定・永続data互換性のapplication-level最終判断は設定管理/OTA更新および各データ管理機能に残し、永続データ管理はphysical stateとreadback結果を提供する。signed metadata上の宣言値が破損・欠損しているimageはfixed bootで拒否する。

### 7.3 boot interface version

fixed bootとapplication間のBoot Handoff/Boot Service ABI互換性を`bootInterfaceVersion`で管理する。

初期形式はuint16とし、上位8 bitをmajor、下位8 bitをminorとする。

application signed metadataは`bootInterfaceMin`と`bootInterfaceMax`を持ち、fixed bootのversionが範囲内であることを確認する。

major非互換を暗黙に許可しない。

初期数値そのものはrelease構成管理で一意に割り当てる内部互換性識別子であり、変更時も上記range判定とmajor互換性規則を変更しない。具体初期値は詳細設計・release定義で固定してよい。

### 7.4 image size

PRIMARY signed image slot上限はOTA更新で確定した768 KiBを維持する。

MCUboot header/trailer/alignmentを含む実slot layoutが768 KiB boundary内で成立することを詳細設計・link時に検査する。

## 8. 固定ブート内部状態と起動判定

### 8.1 boot mode

fixed boot内部では少なくとも次のmodeを区別する。

| mode | 意味 |
| --- | --- |
| `FB_NORMAL_VERIFY` | 通常PRIMARY検証 |
| `FB_INSTALL_CANDIDATE` | `INSTALL_REQUESTED`に基づきcandidateをPRIMARYへOverwrite |
| `FB_TRIAL_BOOT` | candidate一回試行起動 |
| `FB_SETTLEMENT_BOOT` | trial validated後、CONFIRMED前のcandidate再起動 |
| `FB_RECOVER_PREVIOUS` | PREVIOUSをPRIMARYへ復元 |
| `FB_RECOVERY_BOOT` | 復元したPREVIOUSの起動 |
| `FB_WIRED_RECOVERY_REQUIRED` | 自動boot/recovery不能 |
| `FB_FATAL` | fixed boot自身が正常進行不能 |

### 8.2 mode決定入力

mode決定には少なくとも次を使用する。

- reset cause
- OTA state record
- INSTALL_REQUESTED
- PRIMARY_OVERWRITE_STARTED
- TRIAL_ARMED
- trialAttempted
- TRIAL_BOOT_VALIDATED
- otaSettlementPending
- RECOVERY_REQUIRED
- `RECOVERY_BOOT_PENDING`、固定ブート・復旧のrecovery execution status、OTA更新のlocal final result参照
- currentAllowedSecurityGen
- PRIMARY/CANDIDATE/PREVIOUS validity summary

### 8.3 起動可否・起動先の判断の優先順位

最初に、同時成立してはならないstate combination、revision不整合、state MAC不正、未知stateを検出した場合は通常bootへ推測せずWIRED/FATAL側へ移る。

正常に解釈できるstateでは基本優先順位を次とする。

1. fixed boot/trust/critical stateが解釈不能 → WIRED/FATAL
2. `RECOVERY_BOOT_PENDING`が正常で、PRIMARY identityが復元PREVIOUSと一致 → restored PRIMARY recovery boot
3. `TRIAL_BOOT_VALIDATED=true`またはvalidated candidateの`otaSettlementPending=true` → 現在のPRIMARY candidateを再検証してsettlement boot
4. `TRIAL_ARMED=true`かつ`trialAttempted=false` → candidateを再検証し、未実施trialを一回開始
5. `TRIAL_ARMED=true`かつ`trialAttempted=true`かつ`TRIAL_BOOT_VALIDATED=false` → PREVIOUS recovery
6. `RECOVERY_REQUIRED` → PREVIOUS recovery
7. `PRIMARY_OVERWRITE_STARTED=true`かつ正常な`TRIAL_ARMED`が未確定 → install/destructive phase中断としてPREVIOUS recovery
8. `INSTALL_REQUESTED=true`かつ`PRIMARY_OVERWRITE_STARTED=false` → candidate/PREVIOUS再検証後install
9. normal state → PRIMARY normal verify/boot

`PRIMARY_OVERWRITE_STARTED`の存在だけで、正常にcommit済みの未実施trial（`TRIAL_ARMED=true`、`trialAttempted=false`）をPREVIOUS recoveryへ上書きしない。

### 8.4 non-destructive install request

`INSTALL_REQUESTED`はPRIMARYがまだ旧正常imageである段階の状態とする。

この状態でresetしてもPRIMARYを破損済みとみなさない。fixed bootはcandidate/PREVIOUS/critical stateを改めて検証し、条件が正常ならinstallを開始できる。検証不能ならinstallを開始せず、旧PRIMARYを維持したままOTA失敗情報をapplicationへ引き継げる場合は通常PRIMARYへ戻す。

## 9. リセット要因取得とBoot Handoff Block

### 9.1 reset cause早期取得

reset status register等、BSP/application初期化でclearまたは意味が変化し得るreset causeをfixed bootの最初期にsnapshotする。

少なくとも次を区別可能とする。

- power-on
- software reset
- IWDT reset
- watchdog reset
- voltage/power related reset
- OTA controlled reboot
- other hardware reset
- unknown/multiple cause

### 9.2 rawとnormalizedを保持

Boot Handoffには、可能な範囲で次を保持する。

- raw reset status bits
- normalized reset reason
- reset reason validity
- capture completed flag

raw registerをapplicationが再読出しして別の意味に再解釈した結果を、正式なリセット理由として使用しない。

### 9.3 Boot Handoff Block

fixed boot→application引継ぎ用に予約SRAMの`.boot_handoff`を設ける。

初期上限を512 byteとする。

application startupのBSS/heap/stack初期化で上書きしないNOINIT/専用sectionとする。

### 9.4 Handoff最低項目

少なくとも次を含める。

- magic
- handoffVersion
- totalLength
- CRC32C
- bootAttemptId
- reset raw/normalized reason
- fixed boot version/BuildID summary
- boot mode/decision
- boot result (`IMAGE_VERIFIED_AND_STARTED`等)
- image role NORMAL/CANDIDATE/PREVIOUS
- running firmware identity summary
- `runningImageSecurityGen`
- `currentAllowedSecurityGen`
- product/model/hardwareProfileId
- OTA state summary
- install/trial/validated/settlement flags
- recovery result/reason
- fixed boot failure reason
- `startupTimingContext`（計時区分、適用上限、規定起点からHandoffまでの経過上限、残り時間、計時有効性、Application前timeout事実）
- IWDT ownership transfer state/id

`runningImageSecurityGen`は起動対象signed image metadataの値、`currentAllowedSecurityGen`はセキュリティ管理のcritical stateの現在許可値とし、両者を一つのSecurityGenとして混同しない。

秘密鍵、credential、full key materialを含めない。

### 9.5 Handoff検証

applicationはmagic/version/length/CRCを確認した後だけHandoffを使用する。

不正の場合、reset reasonやrecovery結果を推測せず`BOOT_HANDOFF_INVALID`として起動・終了・再起動管理/異常管理へ提供する。

### 9.6 起動・再起動時間コンテキスト

起動・終了・再起動管理が所有するend-to-end時間契約について、fixed bootはApplication前区間の監視実行主体となる。通常の主電源投入では主電源投入を、事前処理のない異常resetではreset発生を規定起点とする。fixed bootが時刻を直接取得できる前のhardware立上り区間は、電源・reset設計のworst-case上限を加算し、規定起点からの経過時間を過小評価しない。

計画的再起動では、起動・終了・再起動管理がreset前に確定したreset-retained `rebootTimingContext`から、再起動要求識別子、15秒上限およびreset前経過上限を取得する。reset reason、完全性または識別子が一致しないcontextを使用せず、reset時点から新しい15秒を開始しない。

Boot Handoffの`startupTimingContext`は既存の`bootAttemptId`へ結び付け、少なくとも次を含む。

- 計時区分（通常主電源投入、計画的再起動、事前処理なしreset）
- 適用するend-to-end上限
- 規定起点からBoot Handoffまでの過小評価しない経過上限
- Applicationへ引き継ぐ残り時間
- 計時情報の有効性
- Application前timeout事実および検出stage

resetを越えて連続するcounterを使用するか、reset前経過上限と各区間の保守的なworst-case budgetを合成するかは詳細設計で定めてよい。ただし、経過時間を過小評価せず、計時context不正時に全時間を再付与しない。

通常起動または通常再起動の上限へApplication branch前に到達した場合は`FB_E2E_TIMEOUT_PRE_APPLICATION`を確定し、actuator-safe状態を維持して通常Applicationへ進まない。OTA PREVIOUS復旧の120秒上限等、OTA更新/公開用システム要求仕様「22. 性能・品質・耐久性」が別に定める復旧transactionは対応する別時間契約として識別し、通常主電源投入10秒または通常再起動15秒のcontextへ混在させない。

## 10. 起動直後の安全状態と最小初期化

### 10.1 actuator禁止

fixed bootは左右DC motor出力、servo PWMおよびactuator power enableを有効化しない。

起動中のGPIO初期化で瞬間的なactive pulseを生成しない。

### 10.2 最小初期化順

基本順序を次とする。

1. reset cause capture
2. CPU/stack/vector minimum
3. actuator-safe pin状態の確認
4. IWDT状態の確認と、固定ブートによる更新責任の確立
5. clock minimum
6. Product Descriptor利用可能化
7. PERSIST_CRITICAL minimum read
8. RSIP/security bootstrap
9. Security state検証
10. OTA state判定
11. normal pathならPRIMARY-only検証
12. install/recovery pathだけOSPI_B初期化
13. image verify/install/recovery
14. Boot Handoff作成
15. application handoff

### 10.3 通信初期化禁止

fixed bootは通常Wi-Fi/BLE/VPS通信を開始しない。

ネットワーク未接続、RTC未信頼をfixed boot通常起動のblock条件にしない。

### 10.4 CPU1禁止

CPU1を固定ブートの補助処理に使用しない。

fixed boot failure時にもCPU1へ復旧処理を移さない。

## 11. IWDT監視と更新実行権

### 11.1 固定ブートが初期の更新責任を持つ

電源・省電力管理/起動・終了・再起動管理に従い、IWDTはOFSによるauto-startを基本としreset直後から継続動作する。

本体アプリケーションへ更新実行権を正常に移管するまでは、論理的な更新責任を`FIXED_BOOT`が持つ。

### 11.2 無条件feed禁止

固定bootは周期timerだけを根拠にIWDTを更新しない。

次のような正常進行が確認できた場合だけ更新する。

- critical state読出し・検証完了
- PRIMARY-only verify chunk進捗
- image verify chunk進捗
- OSPI read/write chunk正常完了
- PRIMARY erase/program chunk正常完了
- recovery stage進捗
- readback verify進捗
- application handoff前最終整合確認

### 11.3 3秒deadlineとの整合

電源・省電力管理/バッテリー・電気安全監視で要求されるIWDTの3秒以内reset上限を維持する。

60秒級のOverwrite/recovery処理は、3秒を超える単一blocking操作へしない。erase/program/hash等はbounded chunkとして処理し、各chunk正常完了後にだけ次回IWDT updateを許可する。

実Flash APIが3秒を超えてCPUを占有する場合は、IWDT期限を暗黙に延長せず、本基本設計または書込み方式を見直す。

### 11.4 IWDT update transaction

固定boot内のIWDT更新ごとに少なくとも次をRAM管理する。

- updateTransactionId
- IWDT更新責任：`owner=FIXED_BOOT`
- bootStageId
- progressCounter
- previous successful progressCounter
- requestedTime
- execution result

同じprogressCounterのままfeedを繰り返さない。

### 11.5 正常進行停止

signature verify、OSPI、MRAM write等が停止し進捗を確認できない場合、IWDTを更新し続けない。

IWDT resetにより再起動し、第21章の永続状態から再判定する。

## 12. Critical Security Stateの読出し・検証

### 12.1 使用するcritical情報

fixed bootは少なくとも次をPERSIST_CRITICALから使用する。

- 現在の許可済みSecurityGen
- K_SEC_STATE_MAC Wrapped Key参照/metadata
- OTA state record
- install/trial/recovery state
- fixed boot failure/service metadata
- factory reset等、起動判断に影響する最低state reference

### 12.2 early security bootstrap

full application Security機能はまだ起動していないため、fixed bootはセキュリティ管理と同じkey format/RSIP policyを使用するminimum security bootstrapを持つ。

minimum bootstrapは次に限定する。

- RSIP minimum init
- K_SEC_STATE_MAC HMAC verify
- ECDSA/SHA-256 image verify support
- SecurityGen読出し/検証

TLS、BLE HMAC、Wi-Fi AES-GCM等は初期化しない。

`K_SEC_STATE_MAC`検証ではセキュリティ管理のdataset-domain分離契約を使用する。SecurityGen、OTA boot state、BOOT_FAILURE_STATUSその他のcritical recordは、それぞれのdomain separator、Device ID、dataset/type識別、format/revisionおよびcanonical payloadへ結び付けて検証し、別datasetの正常tagを流用しない。

### 12.3 Security state MAC failure

SecurityGenまたは起動判断用critical metadataのHMACを正常確認できない場合、CRCが正常でも安全な値を推測しない。

old smaller SecurityGenへfallbackしない。

normal PRIMARY/candidate/PREVIOUS bootを禁止し、wired recovery必要またはsecurity service requiredへ移る。

### 12.4 SecurityGen比較

起動対象imageの`runningImageSecurityGen`が`currentAllowedSecurityGen`未満の場合は起動しない。

PREVIOUS recoveryでも同じ条件を適用する。

trial正常確認前に`currentAllowedSecurityGen`をfixed boot側で増加させない。

## 13. 通常起動時のPRIMARY検証

### 13.1 毎起動検証

通常OTAを実行していないbootでもPRIMARYを起動前に毎回検証する。

### 13.2 PRIMARY-only validation path

normal bootではexternal secondaryを必要とする`boot_go()` pathへ入らず、PRIMARY一つだけを検証可能なfixed boot verifierを使用する。

実装は次のいずれかを採用FSP/MCUboot versionで確認して決定する。

- MCUboot bootutilのprimary image validation primitiveをsecondary非依存で利用
- Renesas/FSPが提供するprimary validation APIを利用
- 同じMCUboot signed image/TLV形式とRSIP cryptoを使用するTank_Robot固定Primary-only verifier

どの実装でも、署名方式や管理情報の意味を別仕様にしない。

FSPのexternal-secondary設定で`boot_go()`前にOSPI_B初期化が必須であっても、normal PRIMARY bootまで外付けFlashへ依存させない。

### 13.3 検証項目

少なくとも次を確認する。

1. image header/magic/format
2. image length / slot boundary
3. SHA-256
4. ECDSA P-256 signature
5. protected metadata format
6. productFamilyId
7. modelId
8. hardwareProfileId
9. bootInterfaceVersion compatibility
10. `runningImageSecurityGen >= currentAllowedSecurityGen`
11. firmware identity format

### 13.4 検証結果

すべて正常なら`PRIMARY_VERIFIED`とする。

signatureだけ正常でもproduct/hardware mismatchなら起動しない。

SemVerが古いという理由だけで通常起動を拒否せず、SecurityGen policyおよびOTA確定状態を判断基準とする。

### 13.5 MCUbootとの責任

install/recovery時のMCUbootとnormal Primary-only verifierで、image format、protected TLV、SHA-256、ECDSA P-256、Product Descriptor、Boot Interface、SecurityGenの意味を共通化する。

同じimageを一方では許可し他方では拒否する不整合を結合試験で検出する。

---

## 14. OTA更新反映要求の受付

### 14.1 OTA機能の本体アプリケーション側の準備

fixed bootへinstallを委譲する前にOTA更新が次を完了していることを前提とする。

- CANDIDATE全量取得・検証
- PREVIOUS退避・検証
- OTA開始/継続条件確認
- candidate/previous identity保存
- `INSTALL_REQUESTED`の原子的commit
- controlled reboot要求

この時点では`PRIMARY_OVERWRITE_STARTED`を成立させない。

### 14.2 INSTALL_REQUESTED

`INSTALL_REQUESTED`は「fixed bootでcandidate installを開始してよい」というauthorizationであり、PRIMARYがまだ旧正常imageとして保持されているnon-destructive stateである。

少なくとも次と対応付ける。

- otaTransactionId/otaOfferId
- candidate firmware identity/hash
- previous firmware identity/hash
- 現在のPRIMARY identity
- expected candidate SecurityGen
- install request revision/CRC/HMAC

### 14.3 fixed boot再検証

controlled reboot後、fixed bootは`INSTALL_REQUESTED`を確認し、candidate/PREVIOUS/critical stateを再検証する。

再検証が失敗した場合、PRIMARYを書き換えない。

`PRIMARY_OVERWRITE_STARTED=false`でPRIMARY自体が正常なら、Boot HandoffへOTA install失敗を記録して旧PRIMARYを起動可能とする。OTA取引の最終失敗確定はOTA更新が行う。

### 14.4 PRIMARY_OVERWRITE_STARTEDの所有

`PRIMARY_OVERWRITE_STARTED`はfixed bootが所有するdestructive markerとし、PRIMARYの最初のerase/programを実行する直前にPERSIST_CRITICALへ原子的にcommitする。

このcommitが成功しない場合、PRIMARY erase/programを開始しない。

これにより、controlled rebootそのものをdestructive phaseの失敗と誤認しない。

### 14.5 MCUboot upgrade markerの順序

`PRIMARY_OVERWRITE_STARTED`正常commit後に、fixed bootがMCUboot upgrade/pending markerまたはそれに相当するinstall triggerを設定し、Overwrite pathへ進む。

secondaryにcandidate body/trailer断片が存在するだけではinstallを開始しない。

---

## 15. CANDIDATEのMCUboot Overwrite反映

### 15.1 OSPI_B初期化

CANDIDATE/PREVIOUSを使用するbootだけでOSPI_Bをinitializeする。

採用FSP/MCUbootが要求するinitializationをOverwrite用`boot_go()`等の呼出し前に完了する。

### 15.2 erase sizeとslot

MCUboot secondary slot、PRIMARY slotおよびUpdate Area Block Erase Sizeは採用external Flashのerase geometryと整合させる。

unsupported erase sizeを設定しない。

### 15.3 candidate再検証

install前に次を確認する。

- candidate signed image完全性
- expected otaOfferId/firmware identityとの一致
- product/model/hardware
- `runningImageSecurityGen >= currentAllowedSecurityGen`
- boot interface
- image length <= 768 KiB slot条件
- OTA更新が確定したPREVIOUS `recoveryEligible`
- INSTALL_REQUESTEDのcandidate identity一致

### 15.4 destructive markerとOverwrite開始

第14.4節の`PRIMARY_OVERWRITE_STARTED`を正常commitした後にだけ、MCUboot install triggerを設定しOverwrite処理を実行する。

Swap scratch/Swap rollbackを使用しない。

### 15.5 overwrite中の安全

- actuator outputは無効のまま
- CPU1はinactive
- Wi-Fi/BLEは未初期化
- IWDTはprogress確認後だけ更新
- PRIMARY以外のMRAM range writeを拒否

### 15.6 書込み後検証

Overwrite完了後、PRIMARYを起動する前に第13章と同等の検証を再実施する。

書込み成功returnだけで起動しない。

検証失敗は`RECOVERY_REQUIRED`とし、candidateをtrial-readyとして扱わない。

---

## 16. 更新候補の一回限りの試行起動

### 16.1 trial arm

candidate PRIMARYが書込み後検証に成功した後、固定ブート・復旧はOTA更新が定義するOTA transactionへ相関した次のboot-critical markerを、永続データ管理の記憶媒体への保存を用いて一つのtrial-ready状態として原子的に確定する。

- `TRIAL_ARMED=true`
- `trialAttempted=false`
- `otaSettlementPending=true`

このcommit済み組合せは「candidateがtrial-readyであり、許可された一回のtrialをまだ消費していない」ことを意味する。`PRIMARY_OVERWRITE_STARTED`が残っていても、このstateをdestructive phase未完了と誤認しない。

### 16.2 一回消費点

candidate applicationへbranchする直前に`trialAttempted=true`をPERSIST_CRITICALへ原子的に確定する。

このcommitが成功しない場合、candidateへbranchしない。状態を一意に再評価し、同じattemptを推測消費または未消費として扱わない。

### 16.3 reset直後の判定

次回reset時は永続stateに基づき次を区別する。

- `TRIAL_ARMED=true`、`trialAttempted=false`、`TRIAL_BOOT_VALIDATED=false`：candidateを再検証し、未実施trialを一回開始する。
- `TRIAL_ARMED=true`、`trialAttempted=true`、`TRIAL_BOOT_VALIDATED=false`：同一candidateを再trialせず`RECOVERY_REQUIRED`へ移る。
- `TRIAL_BOOT_VALIDATED=true`：PREVIOUSへrollbackせずsettlementを継続する。

trialAttempted commit直後にbranch前resetとなった場合も、保守的に一回のtrialを消費済みとしてPREVIOUS recoveryへ進む。これによりbranch直後resetとの識別不能で二回目trialを許さない。

### 16.4 trial applicationの操作禁止

fixed bootはBoot Handoffで`trialPending=true`、`otaSettlementPending=true`を引き継ぐ。

システム状態管理/起動・終了・再起動管理/OTA更新が正常確認するまで通常操作を許可しない。

fixed boot自身はBLE待機到達を判定しない。

---

## 17. 試行起動正常確認とOTA settlement連携

### 17.1 normal validationの責任

candidate applicationが正常起動しBLE接続待機状態まで到達したことの判定は起動・終了・再起動管理/システム状態管理/OTA更新が担当する。

fixed bootの`PRIMARY_VERIFIED`はapplication正常起動確定ではない。

### 17.2 TRIAL_BOOT_VALIDATED

OTA更新が`TRIAL_BOOT_VALIDATED`をPERSIST_CRITICALへcommitした後は、同candidateを「trial未確認」としてPREVIOUSへrollbackしない。

### 17.3 settlement途中reset

`TRIAL_BOOT_VALIDATED=true`かつ`CONFIRMED`未完了、またはvalidated candidateの`otaSettlementPending=true`でresetした場合、fixed bootはPRIMARY candidateを再検証して起動する。

PREVIOUSへ自動rollbackしない。

本体アプリケーション側は通常操作を禁止したまま残りのSecurityGen/現在のFW/OTA result commitを再開する。

### 17.4 SecurityGen順序

fixed bootはtrial validation前に`currentAllowedSecurityGen`を増加させない。

OTA更新/セキュリティ管理がvalidation後にcandidate `runningImageSecurityGen`を基準として必要なSecurityGen commitを行う。

その後のbootでは更新後の`currentAllowedSecurityGen`を比較基準に使用する。

## 18. PREVIOUS自動復旧の開始条件

### 18.1 自動復旧を許可する条件

PREVIOUS自動復旧は、少なくとも次のいずれかを、OTA更新が意味を定め、永続データ管理が物理保存した正当な永続state、および固定ブート・復旧が所有するboot-critical markerから確認した場合に限る。

- `RECOVERY_REQUIRED`
- `PRIMARY_OVERWRITE_STARTED=true`で、candidate書込み後検証または正常な`TRIAL_ARMED`確定まで完了していないdestructive phase中断
- candidate overwrite/readback/verify failure
- `TRIAL_ARMED=true`かつ`trialAttempted=true`かつ`TRIAL_BOOT_VALIDATED=false`
- trial stateが矛盾し、未実施trialを安全に識別できない状態

### 18.2 未実施trialは復旧条件ではない

`TRIAL_ARMED=true`かつ`trialAttempted=false`は公開用システム要求仕様「15. OTA更新」の`SYS-OTA-104`で定める未実施trialであり、それ自体をPREVIOUS recovery条件としない。

candidate PRIMARYを再検証し、OTA state/identityが一致する場合に一回のtrialを開始する。再検証できない場合は`RECOVERY_REQUIRED`またはwired recoveryへ移る。

### 18.3 INSTALL_REQUESTEDだけでは復旧しない

`INSTALL_REQUESTED=true`でも`PRIMARY_OVERWRITE_STARTED=false`なら、PRIMARYはまだdestructive phaseへ入っていない。

この状態だけを理由としてPREVIOUS recoveryへ移らない。

### 18.4 ordinary corruptionとの差

OTA destructive phaseに属さない通常bootでPRIMARY signature/formatが突然破損していても、本書だけの判断で古いPREVIOUSへ戻さない。

理由は次のとおりである。

- PREVIOUSはOTA transactionの復旧用imageであり、通常の任意fallback世代ではない。
- SecurityGenや設定/永続formatとの整合を古いimageが必ず満たすとは限らない。
- corruption/attackを古いimage起動で隠さない。

通常PRIMARY異常は第22章へ進む。

### 18.5 PREVIOUS存在だけでは不十分

external FlashにPREVIOUSらしいimageが存在しても、OTA stateがrecoveryをauthorizeしていない場合は自動復旧しない。

## 19. PREVIOUS復旧イメージの検証・staging・Overwrite

### 19.1 PREVIOUS検証

復旧開始前にPREVIOUSについて少なくとも次を確認する。

- image structure/length
- SHA-256
- ECDSA P-256 signature
- product/model/hardwareProfile
- boot interface
- expected previous firmware identity
- `runningImageSecurityGen >= currentAllowedSecurityGen`
- OTA更新が確定した`recoveryEligible`

### 19.2 PREVIOUS破損

PREVIOUSを正常検証できない場合、PRIMARYへ書き込まない。

`WIRED_RECOVERY_REQUIRED`とする。

### 19.3 recovery staging

OSPI_B Swap rollbackを使用しないため、PREVIOUSをMCUboot secondaryとして使用可能なCANDIDATE/secondary staging areaへcopyする。

candidate失敗identity/結果はOTA metadataへ残した後、secondary image bodyをPREVIOUSへ置き換えてよい。

### 19.4 staging検証

staging後にreadback/hash/signature/identityを再確認する。

PREVIOUS原本をstaging成功確認前に消去しない。

### 19.5 recovery overwrite

staged PREVIOUSに対してfixed bootがMCUboot install triggerを設定し、同じOverwrite pathでPRIMARYへ復元する。

`RECOVERY_REQUIRED`はrecovery PRIMARYの正常検証とrecovery boot state確定まで維持する。

### 19.6 recovery後PRIMARY検証

overwrite return後、第13章と同等のPRIMARY検証を行う。

正常なら、復元PRIMARY identityとrecovery transactionを結び付けた`RECOVERY_BOOT_PENDING`を原子的に永続確定し、generic `RECOVERY_REQUIRED`を同じ機能上の状態遷移で完了扱いにする。次回bootで両方が競合して再overwriteを誘発しない状態とする。

`RECOVERY_BOOT_PENDING`は固定ブート・復旧のboot-critical markerであり、OTA更新の`RECOVERY_BOOT` semantic phaseとは別物とする。前者は復元PRIMARY検証完了とApplication確認待ちを表し、後者はOTA更新が復元Applicationの正常起動確認中であることを表す。

その後PREVIOUS applicationを起動する。検証失敗ならwired recoveryへ移る。

## 20. 復旧後起動と復旧完了判定

### 20.1 fixed bootの完了点

fixed bootは、復元PRIMARYのsignature/metadata/SecurityGen検証が正常でapplicationへbranch可能となった時点を`RECOVERY_IMAGE_VERIFIED_AND_STARTED`としてHandoffする。

これだけでOTA recovery成功を最終確定しない。

### 20.2 本体アプリケーションの正常起動とOTA結果の確定

復元したPREVIOUSの正常起動とOTA復旧結果は、次の順序と担当で確認・確定する。

| 順序 | 担当機能 | 確認・確定する内容 |
| --- | --- | --- |
| 1 | 起動・終了・再起動管理 | 復元した本体アプリケーションの起動正常完了を確定する |
| 2 | システム状態管理 | BLE接続待機状態への遷移を確定する |
| 3 | OTA更新管理 | 前記の起動結果とシステム状態に加え、実行中ファームウェアの識別情報も確認する |

これらの確認が成立した場合、OTA更新管理機能は次を行う。

1. `RECOVERY_BOOT`から`RECOVERY_SUCCEEDED`へ遷移する。
2. `FAILED_RECOVERED`等の本体のOTA最終結果と、VPSへの報告状態`otaResultReportState=PENDING`を確定する。

本体のOTA最終結果を確定することと、その結果をVPSへ報告することは区別する。

固定ブート・復旧機能、起動・終了・再起動管理機能およびシステム状態管理機能は、本体のOTA最終結果を独自に確定しない。
本体アプリケーションを起動できない場合の`FAILED_RECOVERY`の代理確定は、第3.1節の条件に従う。

### 20.3 復旧後の起動中にリセットした場合

PREVIOUSによる上書きに成功した後、復元したファームウェアの正常起動を確定する前にリセットした場合、PRIMARYの内容は既にPREVIOUSである。このため、次回の固定ブート・復旧はPRIMARYを再検証する。

同じPREVIOUSのコピーを毎回実行せず、`RECOVERY_BOOT_PENDING`の状態とPRIMARYの識別情報の一致を確認して、復旧後の起動を継続できる。

### 20.4 無限の再起動を禁止する

同じPREVIOUSが本体アプリケーションの起動完了前に異常リセットを繰り返す場合、起動・終了・再起動管理および異常管理の異常リセット管理と連携する。通常動作への移行を無期限に再試行しない。

固定ブート・復旧側では、同じ復旧対象の識別情報に対して、本体アプリケーション起動前の検証失敗を1回でも検出した場合、有線復旧へ移る。

本体アプリケーションへ制御を移した後の再起動回数の上限は、起動・終了・再起動管理および異常管理で確定する。

## 21. 電源断・リセット・処理中断時の再判定

### 21.1 基本原則

reset後は前回RAM stateを信用せず、PERSIST_CRITICALのcommitted stateと各imageの再検証結果から判断する。

`PRIMARY_OVERWRITE_STARTED`はPRIMARY破壊開始の証拠、`TRIAL_ARMED`はcandidate trial-readyの証拠、`trialAttempted`は試行起動の実施回数の計上の証拠として役割を分離する。

### 21.2 状態別判定

| reset時点 | 次回基本動作 |
| --- | --- |
| candidate download/verify中、PRIMARY未変更 | PRIMARY通常boot可。incomplete candidateは使用しない |
| PREVIOUS backup中、PRIMARY未変更 | PRIMARY通常boot可。OTA取引失敗/再取得はOTA更新 |
| `INSTALL_REQUESTED`後、`PRIMARY_OVERWRITE_STARTED`前 | candidate/PREVIOUSを再検証しinstallを再判定。PRIMARYは旧正常のまま |
| `PRIMARY_OVERWRITE_STARTED` commit後、candidate overwrite/書込み後検証/`TRIAL_ARMED`確定前 | PRIMARYを旧正常と仮定せずPREVIOUS recovery |
| candidate overwrite途中 | PREVIOUS recovery |
| candidate overwrite完了・`TRIAL_ARMED=true`・`trialAttempted=false` | candidateを再検証し、未実施trialを一回開始 |
| trial branch前に`trialAttempted=true` commit済み | PREVIOUS recovery |
| trial中reset/power loss | PREVIOUS recovery |
| `TRIAL_BOOT_VALIDATED`後 | candidateを再検証しsettlement継続、rollbackしない |
| SecurityGen commit後/CONFIRMED前 | candidate boot、finalization継続 |
| PREVIOUS staging途中 | independent PREVIOUS原本からstagingを再実行 |
| recovery overwrite途中 | RECOVERY_REQUIREDを維持しPREVIOUSから再復旧 |
| recovery PRIMARY検証後・`RECOVERY_BOOT_PENDING`確定 | PRIMARY previousを再検証してrecovery bootを継続し、再copyしない |

### 21.3 電源断時も試行起動の実施回数の計上状態を判断基準にする

`PRIMARY_OVERWRITE_STARTED`以後のpower lossを一律PREVIOUS recoveryにはしない。

- `TRIAL_ARMED`未確定：candidateをtrial-readyと証明できないためPREVIOUS recovery。
- `TRIAL_ARMED=true`かつ`trialAttempted=false`：未実施trialとしてcandidateを一回trial。
- `trialAttempted=true`かつ未VALIDATED：同candidateを再trialせずPREVIOUS recovery。
- `TRIAL_BOOT_VALIDATED=true`：candidate settlement継続。

これにより`SYS-OTA-103/104`の「試行実施有無」を永続stateから判定し、同candidateの二回目trialを許さない。

### 21.4 write途中metadata

永続データ管理のA/B/commit方式で未完了stateを正常stateとして採用しない。

commit状態不明で起動判断を一意にできない場合は、PRIMARYが旧正常またはtrial未実施と推測して進まず、recovery/service-required状態を選択する。

## 22. 通常起動時PRIMARY異常と自動fallback禁止

### 22.1 対象

OTA transactionがactiveでなく、normal boot時に次を検出した場合を扱う。

- PRIMARY signature failure
- hash mismatch
- image format invalid
- product/model/hardware mismatch
- SecurityGen rollback
- boot interface incompatible

### 22.2 自動PREVIOUS禁止

PREVIOUSが存在しても自動起動しない。

`BOOT_PRIMARY_INVALID`として起動失敗を確定し、wired recoveryまたは明示された保守手順を要求する。

### 22.3 理由

古いPREVIOUSを自動採用すると、

- 古いpersistent/config formatを起動する
- SecurityGen policyを壊す
- primary corruptionを隠す
- 保存していた偶然の旧imageへrollbackする

可能性があるためである。

### 22.4 安全状態

applicationへbranchしない。

actuator出力を無効のまま維持する。

fixed bootで通常操作を開始しない。

---

## 23. 本体アプリケーションへの制御移譲

### 23.1 handoff前条件

少なくとも次が成立した場合だけapplicationへbranchする。

- PRIMARY verification成功
- `runningImageSecurityGen >= currentAllowedSecurityGen`
- Product Descriptor compatibility正常
- Boot Interface compatibility正常
- Boot Handoff構築/CRC正常
- 固定ブートがIWDT更新責任を持つ状態が正常
- boot modeとOTA state整合
- actuator-safe状態維持

### 23.2 fixed boot固有peripheralの整理

branch前に、applicationへ暗黙依存を残さないようfixed boot専用IRQ/DMA/OSPI operationを停止・完了させる。

ただしIWDTは停止しない。

applicationが使用するclock/cache/MPU等について、startup contractに定めた既知状態へ整える。

### 23.3 vector/jump

Primary-only verifierまたはMCUboot pathで検証済みとなったPRIMARY entryを使用し、vector table、stack pointer、interrupt state等を詳細設計で定めた手順に従ってapplication reset handlerへ移る。

未検証addressへ直接function pointer jumpしない。

### 23.4 branch後の自動再開禁止

applicationへ制御を移した事実だけで、走行、砲塔、servo PWM、過去BLE session等を再開しない。

起動・終了・再起動管理/システム状態管理/BLE接続・認証/砲塔・砲身制御の初期化・認証・状態条件を経る。

---

## 24. IWDT更新実行権の本体アプリケーションへの移管

### 24.1 branch直後

アプリケーションのリセットハンドラへ移った直後も、電源・省電力管理／起動・終了・再起動管理が扱う論理的なIWDT更新責任は、まだ`FIXED_BOOT`にある。

本体アプリケーション側Power Managementが確立するまで、通常taskが自由にIWDTをfeedしない。

### 24.2 immutable Boot Watchdog Service

branch後から正式移管までの短いbootstrap区間を扱うため、fixed boot領域にversionedな最小Boot Watchdog Serviceを残す。

application起動bootstrapは、Boot Handoffのcurrent boot attemptと定義済みstartup stageを伴ってこのserviceへIWDT更新要求を出せる。

### 24.3 Boot Watchdog Serviceの受入れ条件

serviceは次をすべて満たす場合だけ1回のIWDT更新を許可する。

- IWDT更新責任は`FIXED_BOOT`
- `bootAttemptId`がBoot Handoffと一致
- `iwdtTransferId`またはtransfer generationがcurrent Handoffと一致
- request sourceがapplication bootstrapの固定entry/ABIからの呼出し
- startup stageが定義済み順序で前進している
- 同じstage/progress tokenを再利用していない
- previous update transactionが正常完了
- request interval/windowがIWDT設定条件内
- `startupTimingContext`が現在の`bootAttemptId`と一致し、計時有効かつApplication前timeout未確定
- fixed boot branchからのbootstrap総時間が起動・終了・再起動管理/公開用システム要求仕様「22. 性能・品質・耐久性」の起動全体上限内

単に増加する任意counterをapplicationが与えるだけでは更新しない。

### 24.4 bootstrap stage上限

Boot Watchdog Serviceが受け付けるstageを初期製品では有限表として固定する。

各基本段階の意味は次とする。

1. application reset/startup
2. memory/runtime minimum init
3. Power Management init start
4. Power Management self-check complete
5. ownership transfer prepare

前進だけを許可し、後戻り・未定義stage・同stageの無制限反復を拒否する。

branchからPower Management ownership transferまでのbootstrapは、Boot Handoffで引き継いだend-to-end残り時間の内側で完了し、各IWDT progress間隔は3秒未満かつ実IWDT window内とする。通常主電源投入では全体10秒、再起動では全体15秒の規定起点を維持する。具体stage別時間配分は、このend-to-end上限と3秒契約を変更しない範囲で詳細設計に定めてよい。

### 24.5 Power Managementへの移管

起動・終了・再起動管理/電源・省電力管理で定めた起動順序でPower Management確立後、次の一回だけownership transferを行う。

1. 現在のIWDT更新責任がFIXED_BOOTにあることを確認する
2. 未完了IWDT update transactionなし確認
3. 単調増加`iwdtTransferId`発行
4. Handoff/control blockへtransfer pending保存
5. Power Managementが同じidで受領・条件確認
6. IWDT更新責任のPOWER_MANAGERへの移管を確定する
7. transfer resultを双方が確認

### 24.6 commit前後の排他

- commit前：Boot Watchdog Serviceだけが更新可能
- commit後：Power Managementだけが更新可能

commit後にBoot Watchdog Serviceへupdate要求が来ても必ず拒否する。

### 24.7 移管失敗

ID不一致、状態破損、受領不明、Power Management未確立等では起動正常完了へ進まない。

固定ブートが更新責任を持つ間の正常進行条件を満たさない場合、IWDT更新を継続せず、IWDTによるリセットへ移る。

## 25. 有線復旧

### 25.1 目的

次の場合、通常application/MCUboot自動復旧に依存しない有線復旧を使用する。

- fixed boot/trust section破損
- PRIMARYとPREVIOUSの双方が使用不能
- PERSIST_CRITICAL security stateを安全に解釈不能
- PK_FW_VERIFY/trust情報異常
- recovery overwrite失敗
- fixed boot/app互換性を通常手段で回復不能

### 25.2 基本方式

RA8M2内蔵Boot Firmwareのserial programming機能とRenesas Flash Programmer V3を基本とする。

初期製品では2-wire SCIを優先保守経路とし、必要なservice pad/connectorとして少なくとも次を考慮する。

- RX/TX
- MD/boot mode制御
- RESET
- GND
- 必要な3.3V基準/level

### 25.3 fixed bootがsoftwareでBoot Firmwareを代替しない

fixed boot自身が壊れた場合にも復旧できるよう、内蔵Boot Firmwareを最終経路とする。

独自の第三bootloaderを追加しない。

### 25.4 保守手順

wired recoveryでは、少なくとも次を一つの保守手順として扱う。

1. actuator安全・主電源/電源条件確認
2. physical boot mode設定
3. official programmer接続
4. fixed boot/trust/application/critical dataの対象範囲を明示
5. 正規release imageを書込み
6. 必要なtrust/product/security provisioningを復旧
7. verify
8. normal boot復帰
9. device identity/security state/firmware/product info確認
10. service log記録

### 25.5 通常利用者からの制限

wired recoveryは通常利用者向け操作としない。

セキュリティ管理/公開用システム要求仕様「24. 法令・規格・量産移行」と整合し、NORMAL_OPERATIONで不要なdebug/program機能を開放したままにしない。

## 26. 固定ブート・信頼情報の保守更新

### 26.1 通常OTA禁止

fixed boot、PK_FW_VERIFY、fixed boot Product Descriptor、boot trust metadataを通常OTA更新対象にしない。

### 26.2 保守更新

fixed boot自体の更新が必要な場合、wired development/maintenance procedureでのみ実施する。

application OTAと同じ自動無人更新pathへ載せない。

### 26.3 更新前条件

fixed boot保守更新では少なくとも次を確認する。

- release/signing approval
- 対象product/hardware一致
- PK_FW_VERIFY/trust移行計画
- application image compatibility
- PERSIST_CRITICAL format compatibility
- wired recovery継続可能性
- programming protection/DLM設定

### 26.4 検証鍵交換

PK_FW_VERIFY交換を通常の単一firmware updateとして行わない。

必要な鍵移行方式はセキュリティ管理の将来/保守設計責任とし、初期製品でmultiple key online rotationを追加しない。

## 27. 所有者再登録・工場初期化・通常OTAとの境界

### 27.1 所有者再登録

所有者再登録で次を変更しない。

- fixed boot
- PK_FW_VERIFY
- Product Descriptor
- SecurityGen
- boot interface version
- wired recovery capability

### 27.2 factory reset

factory resetでも同じ項目を保持する。

工場出荷状態への初期化が中断した状態がPERSIST_CRITICALに残っていても、固定ブートは所有者データを処理しない。アプリケーションへ安全に分岐できるかという、起動の完全性だけを判断する。

製品情報管理のUnit Product Data、`highestCommittedProductDataRevision`、時刻管理のTrusted Time Record等、factory reset保持対象の他critical datasetをfixed bootが初期化・巻戻ししない。

### 27.3 通常OTA

通常OTAはCANDIDATE/PREVIOUS/application stateを変更できるがfixed boot trust boundaryを変更しない。

OTA packageへfixed boot binaryを同梱しても通常OTAでは無視すればよい、という設計にはせず、package format自体でapplication-onlyを明確にする。

## 28. 固定ブート異常・診断・利用者通知

### 28.1 failure分類

少なくとも次を識別する。

- `FB_RESET_CAUSE_CAPTURE_FAILED`
- `FB_CRITICAL_STATE_INVALID`
- `FB_SECURITY_STATE_MAC_FAILED`
- `FB_SECURITY_GEN_INVALID`
- `FB_PRODUCT_DESCRIPTOR_INVALID`
- `FB_PRIMARY_IMAGE_INVALID`
- `FB_PRIMARY_SIGNATURE_FAILED`
- `FB_PRIMARY_PRODUCT_MISMATCH`
- `FB_PRIMARY_HW_MISMATCH`
- `FB_BOOT_INTERFACE_INCOMPATIBLE`
- `FB_INSTALL_REQUEST_INVALID`
- `FB_INSTALL_MARKER_COMMIT_FAILED`
- `FB_OSPI_INIT_FAILED`
- `FB_CANDIDATE_INVALID`
- `FB_CANDIDATE_OVERWRITE_FAILED`
- `FB_TRIAL_STATE_INVALID`
- `FB_PREVIOUS_INVALID`
- `FB_RECOVERY_STAGE_FAILED`
- `FB_RECOVERY_OVERWRITE_FAILED`
- `FB_RECOVERY_PRIMARY_INVALID`
- `FB_HANDOFF_FAILED`
- `FB_IWDT_SERVICE_REJECTED`
- `FB_IWDT_TRANSFER_FAILED`
- `FB_E2E_TIMEOUT_PRE_APPLICATION`
- `FB_WIRED_RECOVERY_REQUIRED`

### 28.2 applicationへ到達できる場合

Boot Handoffから起動・終了・再起動管理/異常管理/ログ・診断へfailure/recovery情報を引き継ぎ、必要なeventとして記録する。

### 28.3 applicationへ到達できない場合

PERSIST_CRITICALへ小容量`BOOT_FAILURE_STATUS`を原子的に保存できる場合、次を保持する。

- failure code
- stage
- image identity summary
- reset reason
- recovery required/result
- `bootAttemptId`、計時区分、経過上限およびApplication前timeout事実
- bootloader version

毎回正常bootで書き換えず、failure/recovery transition時だけ更新する。

### 28.4 BOOT_FAILURE_STATUSの権限

`BOOT_FAILURE_STATUS`は診断・表示用情報であり、boot authorizationの判断基準にしない。

このstatusに「PREVIOUS使用可」等が残っていても、それだけでold imageを起動しない。起動可否・起動先の判断はdataset-domain分離したK_SEC_STATE_MAC、保存処理の確定状態、OTA/Security stateおよび実image検証結果から決定する。

`BOOT_FAILURE_STATUS`自体も専用domainで永続データ管理/セキュリティ管理のcritical record方式により完全性を確認する。

### 28.5 表示

application起動不能でもwired recovery必要を利用者/保守者が識別できるよう、状態表示基本設計へminimal boot-error indicationを要求する。

fixed bootから使用可能な専用LED/7seg pathを設けるか、reset patternで示すかは状態表示/ハードウェア設計で決定する。

actuator関連pinを表示用途へ転用しない。

### 28.6 service-required状態でのIWDT

normal progressが停止したservice-required状態でIWDTを無期限にfeedしない。

bounded indication/record処理後はIWDT resetを許容し、physical boot modeによるwired recoveryを可能にする。

## 29. 実行時間・RAM・固定資源・性能方針

### 29.1 時間基本値

| 処理 | 基本設計値 |
| --- | ---: |
| reset cause capture | 10 ms以内 |
| critical state + security bootstrap | 100 ms以内目標、500 ms上限 |
| normal PRIMARY full verify | 500 ms以内目標、2秒上限 |
| fixed boot normal path全体 | 1秒以内目標、2秒上限 |
| OSPI_B init | 200 ms以内上限 |
| candidate PRIMARY overwrite + verify | OTA更新の60秒以内 |
| PREVIOUS recovery開始→復元PRIMARY verify | 90秒以内を内部budgetとし、OTA更新/公開用システム要求仕様「22. 性能・品質・耐久性」の正常起動含む120秒以内を満たす |
| Boot Handoff構築 | 10 ms以内 |
| Application前end-to-end監視 | 通常主電源投入は規定起点から10秒上限、通常再起動は規定起点から15秒上限。起動・終了・再起動管理へ残り時間を引継ぐ |
| アプリケーションへの分岐→IWDT更新責任の移管 | Boot Handoffで引き継いだ起動処理全体の残時間以内。Boot Watchdogへ進行を通知する各間隔は3秒未満 |
| IWDT progress間隔 | 3秒未満、実設定window内 |

normal path2秒は起動・終了・再起動管理/公開用システム要求仕様「22. 性能・品質・耐久性」の主電源投入から状態遷移まで10秒上限の一部として扱う。計画的再起動ではreset前経過上限を含む15秒の残り時間だけをApplicationへ引き継ぎ、resetまたはbranchで時間budgetを再開始しない。

上表の容量・時間・trial/recovery条件は評価確定待ちを含む基本設計で管理する値である。実機評価で変更する場合は詳細設計だけで変更せず本書または管理元の文書へ反映する。

### 29.2 固定RAM

fixed bootのRAM使用は静的確保し、標準`malloc/free`を使用しない。

少なくとも次を上限管理する。

| 資源 | 基本値 |
| --- | ---: |
| Boot Handoff Block | 512 byte |
| image header/TLV work | 4 KiB以下 |
| hash/crypto work | FSP/RSIP要求量を静的確保 |
| OSPI copy buffer | 16 KiB以下 |
| recovery staging buffer | OSPI bufferと共用可 |
| error/status work | 2 KiB以下 |

固定boot全体RAM peakは詳細設計で測定し、application runtime用RAMを不用意に常時予約しない。

### 29.3 code size

fixed boot executable/trust sectionを224 KiB以内に収める。

超過した場合、PRIMARY 768 KiBまたはPERSIST_CRITICAL 32 KiBを暗黙に侵食せず、本設計を見直す。

### 29.4 CPU負荷

normal boot以外のOverwrite/recoveryは操作応答時間の対象外だが、安全hardware/IWDT監視を止めない。

## 31. 検証方針と異常注入

### 31.1 normal boot

- valid PRIMARY起動
- 100回以上resetして同一image検証結果
- power-on/software/IWDT reset reason引継ぎ
- external Flash未接続でもnormal PRIMARY boot
- external Flash故障時にnormal verifierがOSPI初期化へ入らない
- CPU1がfixed boot中に起動しない
- actuator outputがboot中に有効化されない

### 31.2 signature/metadata

- hash corruption
- signature corruption
- wrong productFamily/model
- wrong hardwareProfileId
- runningImageSecurityGen低下
- unsupported image format
- boot interface incompatible
- image length overflow
- normal Primary-only verifierとinstall後verifierの結果一致

全ケースでapplicationへbranchしない。

### 31.3 install marker境界

- candidate/PREVIOUS準備後`INSTALL_REQUESTED` commit
- INSTALL_REQUESTED直後reset
- fixed boot再検証失敗
- PRIMARY_OVERWRITE_STARTED commit失敗
- PRIMARY_OVERWRITE_STARTED直後power cut
- first erase直前/直後reset
- candidate overwrite完了後・TRIAL_ARMED commit前reset

`INSTALL_REQUESTED`だけでは旧PRIMARYを破損扱いにしない。`PRIMARY_OVERWRITE_STARTED`後でも`TRIAL_ARMED`未確定ならPREVIOUS recoveryへ移り、`TRIAL_ARMED`が正常確定した後は第31.5節の試行起動の実施回数の計上状態を判断基準とすることを確認する。

### 31.4 candidate install

- valid candidate/PREVIOUS
- install authorizationなしでsecondary data存在
- secondary trailer異常
- OSPI init failure
- candidate hash/signature mismatch
- candidate identity mismatch
- PRIMARY erase/program failure
- overwrite後PRIMARY readback mismatch

### 31.5 trial

- TRIAL_ARMED保存前reset → PREVIOUS recovery
- `TRIAL_ARMED=true / trialAttempted=false`保存直後reset → candidateを一回trial
- trialAttempted保存前resetで上記未実施stateが維持 → candidateを一回trial
- trialAttempted保存直後reset → PREVIOUS recovery
- candidate branch直後reset → PREVIOUS recovery
- trial中IWDT reset → PREVIOUS recovery
- trial中power loss → PREVIOUS recovery
- BLE_WAIT到達前reset → PREVIOUS recovery
- TRIAL_BOOT_VALIDATED直前reset → PREVIOUS recovery
- TRIAL_BOOT_VALIDATED直後reset → candidate settlement継続

未実施trialを誤って捨てず、試行済みcandidateの二回目trialを許さないことを確認する。

### 31.6 recovery

- PREVIOUS正常復旧
- PREVIOUS signature failure
- SecurityGen不適合
- staging中power cut
- recovery overwrite中power cut
- recovery PRIMARY verify failure
- RECOVERY_BOOT_PENDING確定直後resetで再copyせずrecovery boot継続
- recovery boot中reset
- wired recovery required

### 31.7 critical state

- SecurityGen CRC破損
- K_SEC_STATE_MAC/HMAC failure
- SecurityGen用tagをOTA stateへ流用する等のdataset-domain tag mismatch
- OTA state one copy torn
- both critical copies invalid
- unknown/矛盾OTA state

安全値を推測してbootしないことを確認する。

### 31.8 IWDT

- normal stage progressで更新
- hash処理hang
- OSPI read hang
- MRAM program hang
- 同一progressCounter feed要求連発
- application bootstrap未定義stage
- stage後戻り
- bootAttemptId mismatch
- ownership transfer前後の二重feed要求
- transfer ID mismatch
- ownership commit後のBoot Watchdog Service呼出し

3秒の上限、有限の初期化段階、および更新責任の排他が成立することを確認する。

### 31.9 wired recovery/root of trust

- MD/SCI service path
- fixed boot破損からの復元
- PRIMARY/PREVIOUS双方破損
- RFP書込み・verify
- wired recovery後のsecurity/product/firmware整合
- NORMAL_OPERATION debug/program制限との両立
- fixed boot/trust領域がnormal application write APIから変更できないこと

## 33. 設計判断・後続事項

### 33.1 設計判断

### 33.2 評価事項

## 34. 他文書へのフィードバック

### F-01 起動・終了・再起動管理

Boot Handoffからreset reason、fixed boot result、image role、trial/recovery state、fixed boot failure、runningImageSecurityGen/currentAllowedSecurityGenおよび`startupTimingContext`を受け取り、application起動理由・起動失敗とend-to-end残り時間へ反映する。

計画的再起動ではreset前に`rebootTimingContext`を確定し、Boot Watchdog Serviceを介したearly application stageの有限progress通知、end-to-end時間の継続およびPower Management確立後のownership transferを起動・終了・再起動管理のsequenceへ具体化する。

### F-02 電源・省電力管理

電源・省電力管理で定義済みのIWDT更新責任の移管を、本書のBoot Watchdog Service、Boot Handoffのtransfer id、有限の起動段階と整合させる。起動全体10秒以内、各進行通知の間隔3秒未満という時間条件も維持する。

### F-03 OTA更新

OTA更新の現行設計は次と整合済みであり、本書も同じ契約を正とする。

1. CANDIDATE/PREVIOUS準備後、controlled reboot前にnon-destructive `INSTALL_REQUESTED`をcommitする。
2. `PRIMARY_OVERWRITE_STARTED`は本体アプリケーション側ではなくfixed bootがfirst PRIMARY erase/program直前にcommitする。
3. MCUboot install triggerはdestructive marker commit後にfixed bootが設定する。
4. fixed boot/recovery executable+trust最大224 KiB＋PERSIST_CRITICAL 32 KiB＋PRIMARY 768 KiBとする。
5. normal PRIMARY検証はexternal secondary非依存とし、OSPI_Bをinstall/recovery時のみ必須とする。
6. `TRIAL_ARMED=true`かつ`trialAttempted=false`は未実施trialとしてcandidateを一回起動し、`trialAttempted=true`かつ未VALIDATEDではPREVIOUS復旧する。

### F-04 永続データ管理

永続データ管理はPERSIST_CRITICALへ`INSTALL_REQUESTED`、`PRIMARY_OVERWRITE_STARTED`、`TRIAL_ARMED`、`trialAttempted`、`TRIAL_BOOT_VALIDATED`、`otaSettlementPending`、`RECOVERY_REQUIRED`、`RECOVERY_BOOT_PENDING`、`BOOT_FAILURE_STATUS`等を一意に復旧可能な形で保持する。

fixed bootから利用するcritical recordのAPIはapplication full PERSIST初期化へ依存しないminimum read/commit pathを提供し、固定ブート・復旧は当該契約を使用する。

### F-05 セキュリティ管理

セキュリティ管理のminimum security bootstrap、PK_FW_VERIFY、SecurityGen、dataset-domain分離K_SEC_STATE_MACを使用し、full Security taskへ循環依存しない。

fixed bootが自分自身を自己署名検証してtrustを確立するという扱いにせず、fixed region protection/DLM/Access Window/wired provisioningをboot root of trustとして維持する。

### F-06 製品情報管理

fixed boot Product Descriptorは製品情報管理と同じgenerator sourceを使用し、application ProductInfo APIは起動前に使用しない。

製品情報管理のrunningImageSecurityGen/currentAllowedSecurityGen区別をBoot Handoffと検証結果へ反映する。

### F-07 状態表示・利用者通知

application起動不能時にも、`WIRED_RECOVERY_REQUIRED`等の最低限のboot failureを保守者が識別できる表示手段を検討する。

fixed bootからの表示はactuator safe状態を乱さず、専用status outputに限定する。

### F-08 ハードウェア・保守設計

RA8M2 Boot Firmware SCI recovery用RX/TX/MD/RESET/GND service pad/connectorと、通常利用者が誤使用しにくいアクセス方法を具体化する。

## 35. 初版の自己確認結果と引継ぎ条件

### 35.1 初版自己確認

初稿作成後の自己確認および後続基本設計との整合レビューを含め、次を確認・修正した。

- 固定ブート・復旧に独立公開要求章がないことを明示し、公開用システム要求仕様「01. 起動・終了・再起動」/公開用システム要求仕様「15. OTA更新」/公開用システム要求仕様「18. 永続データ管理」/公開用システム要求仕様「20. セキュリティ管理」/公開用システム要求仕様「22. 性能・品質・耐久性」等へtraceを設定した。
- OTA更新のMCUboot Overwrite＋OSPI_B secondary方針を変更していない。
- OSPI_B Swap rollbackを前提にしていない。
- OTA更新/永続データ管理の224 KiB fixed boot、32 KiB critical、768 KiB PRIMARYへ整合した。
- セキュリティ管理のPK_FW_VERIFY、dataset-domain K_SEC_STATE_MAC、SecurityGen、minimum security bootstrap責任を維持した。
- 製品情報管理のgenerated Product DescriptorとrunningImageSecurityGen/currentAllowedSecurityGen区別をfixed bootでも使用する構成とした。
- CPU0 Cortex-M85をprimary fixed bootとし、CPU1 M33をboot中起動しない初期製品方針とした。
- fixed bootがBLE/Wi-Fi/VPS/actuator機能を持たない最小構成とした。
- reset causeをapplication初期化前にcaptureしてBoot Handoffへ渡す構成とした。
- critical security stateのHMAC失敗時にSecurityGenを推測fallbackしない。
- non-destructive `INSTALL_REQUESTED`とfixed boot所有`PRIMARY_OVERWRITE_STARTED`を別のstateとして維持した。
- candidate bodyやsecondary trailer断片の存在だけでinstallせず、install authorizationとdestructive markerのcommit順を固定した。
- normal bootの毎回署名検証を外付けFlash非依存のPrimary-only verifierへ分離した。
- fixed bootのroot of trustを自己署名検証と誤認せず、固定領域保護、DLM/Access Window、製造・保守provisioning、内蔵Boot Firmwareの境界を維持した。
- 公開用システム要求仕様「15. OTA更新」の`SYS-OTA-104`に整合し、`TRIAL_ARMED=true / trialAttempted=false`の未実施trialはreset/power loss後も一回開始し、`trialAttempted=true`未VALIDATEDならPREVIOUS復旧するよう起動可否・起動先の判断、復旧条件、電源断表、設計判断、試験期待値を一貫して修正した。
- `PRIMARY_OVERWRITE_STARTED`だけで試行起動の実施回数が計上済みであるとみなさない。
- TRIAL_BOOT_VALIDATED後settlement中resetでは誤rollbackしない。
- PREVIOUS recoveryをindependent PREVIOUS→secondary staging→Overwriteとし、RECOVERY_BOOT_PENDING後は同じPREVIOUSを無条件再copyしない。
- ordinary PRIMARY corruptionをPREVIOUSへ自動fallbackしない。
- external Flash異常だけでvalid PRIMARY normal bootを失わない構成とした。
- IWDTをnormal progressなしでfeedし続けない構成とした。
- 起動・終了・再起動管理/電源・省電力管理のFIXED_BOOT→POWER_MANAGER IWDT ownership transferをBoot Watchdog Serviceで実装可能な形へ具体化した。
- Boot Watchdog Serviceは有限startup stage、bootAttemptId/transferId一致、一progress一feed、起動・終了・再起動管理/公開用システム要求仕様「22. 性能・品質・耐久性」の起動全体10秒内、各progress 3秒未満、移管後全面拒否を基本契約とした。
- BOOT_FAILURE_STATUSを診断専用とし、古いimage起動のauthorizationへ使用しないことを明示した。
- wired recoveryをRA8M2内蔵Boot Firmware/RFPへ分離した。
- 固定ブート・信頼情報を、通常OTA、工場出荷状態への初期化、所有者再登録によって変更しない。
- malloc/freeに依存しない固定資源方式とした。
- 容量・時間・trial/recovery条件を評価確定待ちを含む基本設計で管理する値として明確化した。

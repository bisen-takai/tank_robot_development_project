## 1. 本書の目的

### 1.1 目的

本書の目的は、公開用システム要求仕様「14. ログ・診断」を実現するため、イベントログ、診断情報および評価用トレースの生成・識別・保持・保存・参照・送信を、詳細設計へ展開可能な粒度まで具体化することである。

### 1.2 対象範囲

本書は、Tank_Robot本体におけるイベントログ、診断情報および評価用トレースについて、共通識別、記録形式、時刻・順序、優先度、抑制、固定資源、永続保存要求、VPS送信、保守参照、完全性確認、異常処理および関連機能との責任分界を具体化する。

ログ・診断機能は、安全状態、操作可否、異常重大度または復旧可否を決定する管理元機能ではない。各機能が確定した事象・状態を記録し、解析可能な形で保持・提供する。安全処理、停止処理、異常判断および電源保護は、ログ保存または外部送信の成否を待たずに実行する。

#### 基本設計と詳細設計の区分

本書で定めるイベント分類、識別子体系、ログレコードの内容、容量、queue、抑制条件、送信・再送条件、診断時間上限、trace周期・容量その他、利用者・関連機能から見たログ・診断結果または解析可能性を変える値・方式は、本書または参照する担当基本設計で定める事項とする。実機評価で変更が必要となった場合は詳細設計だけで変更せず、本書または値・方式を定める関連基本設計へ評価結果をフィードバックして正式値を更新する。物理sector、固定バッファ配置、task、event通知実装、parser内部構造その他、外部振る舞いを変更しない実装方法は詳細設計で具体化してよい。

### 1.3 上位文書・関連文書

本書の主対象要求は公開用システム要求仕様「14. ログ・診断」とし、関連する公開用要求および完成済み基本設計について、ログ・診断との責任分界に必要な範囲を参照する。

`20_要求仕様`および`30_コア要求仕様`は本書の上位要求として使用しない。公開用要求で未確定の方式について本書で具体化する場合は、本書の設計判断として明示する。

関連基本設計との整合確認結果を本書へ反映する。後続基本設計で具体化された永続ログレコード不変性・metadata journal、製品／firmware情報の正式な管理元、時刻品質・`timeSyncGeneration`、VPS application retry責任および状態表示契約が本書の外部振る舞いを具体化している場合は、その確定内容を本書でも使用する。

### 1.4 用語

| 用語 | 本書での意味 |
| --- | --- |
| イベントログ | 状態遷移、主要処理、警告、停止、異常、復旧等をイベント単位で保存する情報 |
| 診断情報 | 保守・解析時点の現在状態を各機能から取得して構成する参照専用スナップショット |
| 評価用トレース | 高周期の指令・制御出力・監視値等を固定RAMへ一時保持する時系列データ |
| 重要ログ | 安全・故障・重大異常等、通常ログより保存・送信を優先するイベントログ |
| 通常ログ | 通常状態遷移、通信ライフサイクル、主要処理成功等のイベントログ |
| `eventId` | イベントの意味を一意に識別する32 bit識別子 |
| `bootInstanceId` | 起動単位を識別する単調増加64 bit値 |
| `eventSequence` | 同一起動中のイベント発生順序を識別するuint32値 |
| `logId` | `bootInstanceId`と`eventSequence`の組合せで表すイベントログ識別子 |
| `correlationId` | 一連の要求・処理に属する複数イベントを関連付ける64 bit識別子 |
| `timeQuality` | 時刻管理が正式に管理する時刻品質。`TIME_QUALITY_NONE`、`TIME_QUALITY_UNTRUSTED`、`TIME_QUALITY_TRUSTED_HOLDOVER`、`TIME_QUALITY_TRUSTED_SYNCED`を区別する |
| `timeSyncGeneration` | 時刻管理が正常な時刻更新commitごとに増加するuint32世代。時刻補正前後の解析相関に使用する |
| `firmwareBuildFingerprint` | 製品情報管理が、実行中ファームウェアのビルド識別情報から提供する64 bitの識別値。同じビルド識別情報からは常に同じ値を生成する |
| 未送信 | VPSから当該ログの正常受領確認を取得していない状態 |

## 2. 設計方針と適用範囲

### 2.1 基本方針

ログ・診断機能は次の原則で設計する。

1. イベントログ、診断情報および評価用トレースを異なる情報種別として管理する。
2. 通常運用のログを高周期サンプリングではなくイベント単位とする。
3. イベントログは動作・異常・セキュリティの種別と、重要・通常の保存優先度を別属性として保持する。
4. 安全処理・停止処理・異常処置をログ生成・保存・送信より優先し、ログ機能の遅延や故障によって安全処理を待たせない。
5. イベント受付は固定容量・非ブロッキングを基本とし、重要ログ用の受付資源を通常ログから分離する。
6. 各イベントログへ起動単位と起動内順序を必ず付与し、RTC時刻を使用できない場合でも発生順序を失わない。
7. 不揮発ログは固定長レコードとCRC32Cを基本とし、偶発的破損を検出可能とする。本機能がcommit後のイベントデータ本体のレコードを、内容が変更されないものと定め、SENT/UNSENTやlifecycle等の可変状態を別metadataとして永続データ管理へ保存要求する。
8. ローカル保存は容量ベースの循環管理とし、初期製品へ固定7日・30日等の長期保持保証を追加しない。
9. 未送信ログと重要ログを送信済み通常ログより優先して保存する。
10. VPS送信完了は、VPS接続・デバイス認証から対象ログの受領確認を得た場合だけ確定する。
11. 診断情報は各機能が管理する現在状態を取得して構成し、過去ログから現在状態を推定しない。
12. 評価用トレースは固定RAM内でのみ高周期保持し、通常イベントログ領域を消費しない。
13. 保守用インターフェースは初期製品では参照専用とし、アクチュエータ・電源・通信状態を変更する能動診断コマンドを持たない。
14. 秘密鍵、Wi-Fi認証情報、操作端末長期認証鍵、認証トークンその他の秘密情報をログ・診断・トレースへ平文で含めない。
15. 標準`malloc/free`を使用せず、すべての受付キュー、レコード、batch、診断情報のスナップショットおよびtraceを固定上限で管理する。
16. 工場初期化等で削除対象と確定した未送信ログを、その後の新所有者のデータとしてVPSへ送信しない。
17. 時刻管理が提供する時刻trust/quality/`timeSyncGeneration`をそのまま使用し、ログ側で時刻信頼状態を独自再判定しない。

### 2.2 対象範囲

本書は次を対象とする。

- イベント分類・重要度
- イベントID割当て方式
- `logId`、`bootInstanceId`、`eventSequence`、`correlationId`
- 共通固定長イベントレコード
- イベント受付・優先処理・欠落管理
- 同一事象の抑制・集約
- UTC時刻・単調時刻・発生順序・`timeSyncGeneration`
- ローカル循環保存の論理容量・再利用順序
- CRC32Cによるイベントレコード破損検出
- 未送信管理・VPS batch送信・再送
- 診断スナップショット
- 保守用UART参照インターフェース
- 評価用トレースRAM
- ログ・診断機能自身の異常
- 各機能とのログ・診断契約
- 工場初期化等のデータライフサイクルとの連携

### 2.3 対象外

次は本書の対象外とし、各担当設計に従う。

- システム状態の決定
- 異常重大度・処置・復旧可否の決定
- 停止・緊急停止の成立判断
- 電気安全しきい値および保護判断
- VPSのTLS・HTTPS通信実装
- 不揮発メモリの物理アドレス、sector割当、wear leveling実装
- VPS側ログ・診断の60日保存・期限満了削除実装
- ログの収集目的、個人情報削除ポリシー
- 秘密鍵管理、認証・認可方式
- 管理Webアプリ上のログ画面
- 保守用UARTの基板端子番号・コネクタ部品

### 2.4 初期製品で対象外とする拡張

公開用システム要求仕様「14. ログ・診断」の将来検討事項に従い、初期製品では次を必須実装しない。

- 4段階以上のログ重要度
- ログ種別ごとの複雑な送信期限・再送policy
- 通常ログ7日以上・重要ログ30日以上等の固定長期保持保証
- 所有者向けアプリでの詳細ログ履歴表示
- ログ容量不足だけを理由とする通常操作禁止
- 保守UARTからの能動診断・強制出力
- 一般操作者・所有者による詳細ログ抽出
- ログ圧縮

## 3. 責任分界と共通条件

### 3.1 関連機能との責任分界

| 機能 | 主な責任 |
| --- | --- |
| ログ・診断 | 共通イベント形式、ID、受付、`IMPORTANT`／`NORMAL`の共通の意味と最低優先度、格下げ禁止・昇格の規則、保存要求、未送信管理、キュー・保存・領域再利用・VPS送信の方針、診断情報のスナップショット、トレース、保守参照 |
| 各機能 | 自機能で記録すべき事象の意味、成立判定、イベントの内容に応じた最低優先度、イベント固有データ、現在診断値の正式な管理 |
| システム状態管理 | 現在のシステム状態および状態遷移の決定・管理 |
| 異常管理 | 現在異常、異常識別子、処置、復旧可否の決定・管理 |
| 永続データ管理 | 永続データ管理のlog partition、event record不変保存、LOG_META_JOURNAL、checkpoint、電源断復旧、媒体完全性、書換え寿命 |
| VPS接続・デバイス認証 | 認証済みHTTPS、`/logs` API、HTTP結果、VPS受領結果、接続retry |
| 時刻管理 | 時刻管理のRTC/UTC、trust state、quality、`timeSyncGeneration`、時刻補正 |
| 製品情報管理 | 製品情報管理のDevice ID、製品・HW・running firmware identity、`firmwareBuildFingerprint` |
| セキュリティ | 秘密情報の非出力規則、保守アクセス制約、セキュリティイベントの意味・成立判定・記録すべき最低優先度 |
| データ・プライバシー | 収集目的、VPS保存期間、削除条件、個人情報の取扱い |
| 状態表示・利用者通知 | ログ・診断異常の具体表示 |

### 3.2 現在の状態は各担当機能が管理する

ログを失った、破損した、VPSへ送信できない、または診断情報のスナップショットの一部を取得できない場合でも、システム状態、停止状態、異常状態、電気安全状態、OTA状態その他の安全上必要な現在値は各担当機能で維持する。

ログを読み直して安全状態を復元する設計としない。

### 3.3 ログ要求の優先順位

ログ・診断処理内の優先順位は次とする。

1. 重要イベント受付
2. 重要ログの不揮発保存要求
3. 通常イベント受付
4. 通常ログ保存要求
5. 診断情報のスナップショット作成
6. VPS送信用batch構築
7. 評価用トレース参照・出力

ただし、安全停止、緊急停止、電気安全処理、異常処置、終了・電源遮断は常に上記より優先する。

### 3.4 非ブロッキング原則

安全関連機能からイベント通知を受けるAPIは、ログ保存完了を待って戻らない。

イベント受付時には固定RAMキューへコピーするか、受付不能を即時返す。送信元はログ保存成功を安全処理の成立条件にしない。

## 4. ログ・診断情報モデル

### 4.1 情報種別

| 種別 | 用途 | 主な保持先 | 通常VPS送信 |
| --- | --- | --- | --- |
| イベントログ | 意味を持つ事象の記録 | RAM受付＋不揮発循環領域 | 対象 |
| 診断情報 | 現在状態の参照 | 要求時RAM snapshot | 対象になり得る |
| 評価用トレース | 高周期時系列解析 | 固定64 KiB RAM | 初期製品の通常送信対象外 |

### 4.2 イベント種別

`eventCategory`は次の3種とする。

- `OPERATION`
- `FAULT`
- `SECURITY`

一つのeventIdに対してcategoryは基本的に固定する。

### 4.3 保存優先度

`logPriority`は次の2種とする。

- `IMPORTANT`
- `NORMAL`

`eventCategory`と`logPriority`は独立した属性である。例えば、通常のセキュリティ状態変更は`NORMAL`、通常操作を禁止するセキュリティ異常は`IMPORTANT`とすることができる。

#### 比較する二つの最低優先度

最低優先度は、そのイベントに必要な保存優先度の下限を示す。次の二つを区別する。

| 呼び方 | 決定する機能と判断基準 |
| --- | --- |
| 発生元が要求する最低優先度 | 各発生元機能が、自機能で管理するイベントの意味と成立状態に基づいて決定する。少なくとも`NORMAL`が必要か、`IMPORTANT`が必要かを選び、イベント通知時の`priority`として提供する |
| ログ共通ルールの最低優先度 | ログ・診断機能が、本節および第7.1節の共通ルールに従って定める |

セキュリティ管理機能が定めるセキュリティイベントの優先度も、「発生元が要求する最低優先度」として扱う。

#### 実際の保存優先度の決定

ログ・診断機能は、二つの最低優先度を比較し、高い方をレコードに格納する`logPriority`として確定する。
`IMPORTANT`を`NORMAL`より高い優先度として扱う。

| 発生元が要求する最低優先度 | ログ共通ルールの最低優先度 | 実際の保存優先度（`logPriority`） |
| --- | --- | --- |
| `NORMAL` | `NORMAL` | `NORMAL` |
| `NORMAL` | `IMPORTANT` | `IMPORTANT` |
| `IMPORTANT` | `NORMAL` | `IMPORTANT` |
| `IMPORTANT` | `IMPORTANT` | `IMPORTANT` |

発生元が`IMPORTANT`を指定したイベントを、ログ・診断機能が`NORMAL`へ格下げしない。
発生元が`NORMAL`を指定しても、共通ルールが`IMPORTANT`を要求する場合は、`IMPORTANT`へ引き上げる。

#### 確定した優先度の使用範囲

確定した`logPriority`は、受付キュー、循環保存領域、容量不足時に削除・再利用するログの選択、抑制管理表が不足したときの優先処理、VPSへまとめて送るログの選択など、ログ・診断機能の処理に一貫して使用する。

発生元機能は、ログ・診断機能のキュー状態、保存容量または送信都合を理由として、イベントの意味に基づく最低優先度を変更しない。

### 4.4 有効性属性

イベント固有データおよび診断値は必要に応じて次を区別する。

- `VALID`
- `UNAVAILABLE`
- `STALE`
- `ERROR`
- `NOT_APPLICABLE`

取得できない値を0、最大値、前回値等へ置換して正常値に見せない。

## 5. イベント識別子・ログ識別子・相関情報

### 5.1 `sourceFunctionId`

各イベント発生元へuint16の`sourceFunctionId`を割り当てる。

現在の機能別基本設計番号と一致するIDをログformat version 1の基本割当てとし、次を固定する。

| sourceFunctionId | 機能 |
| ---: | --- |
| `0x0001` | システム状態管理 |
| `0x0002` | 起動・終了・再起動管理 |
| `0x0003` | 停止・緊急停止管理 |
| `0x0004` | 異常管理 |
| `0x0005` | 電源・省電力管理 |
| `0x0006` | バッテリー・電気安全監視 |
| `0x0007` | 走行制御 |
| `0x0008` | 砲塔・砲身制御 |
| `0x0009` | BLE接続・認証 |
| `0x000A` | 所有者・操作端末管理 |
| `0x000B` | Wi-Fi接続 |
| `0x000C` | VPS接続・デバイス認証 |
| `0x000D` | 設定管理 |
| `0x000E` | ログ・診断 |
| `0x000F` | OTA更新 |
| `0x0010` | 永続データ管理 |
| `0x0011` | セキュリティ管理 |
| `0x0012` | 製品情報管理 |
| `0x0013` | 固定ブート・復旧 |
| `0x0014` | 時刻管理 |
| `0x0015` | 状態表示・利用者通知 |

将来機能を追加する場合は未使用IDを割り当てる。既存IDの意味を変更したり別機能へ再利用したりしない。割当て変更が必要な場合はログformat versionを更新する互換性変更として扱う。

### 5.2 `eventId`

`eventId`はuint32とし、次で構成する。

`eventId = (sourceFunctionId << 16) | localEventCode`

`localEventCode`は各機能が自機能内で重複しないuint16値を割り当てる。

詳細なlocalEventCode一覧は詳細設計で固定するが、イベントの意味を変更して既存番号を再利用しない。

### 5.3 `bootInstanceId`

起動単位を識別する`bootInstanceId`はuint64の単調増加値とする。

ログ・診断初期化時に永続データ管理から直前値を取得し、1増加した値を原子的に確定して現在起動の値とする。

一起動につき1回だけ永続更新する。

`bootInstanceId`は、所有者再登録または工場出荷状態への初期化だけを理由として0へ戻さない。Device IDが同じ製品で過去にVPS送信済みのlogIdと将来logIdが重複することを防ぐため、利用者データとは分離した製品診断用単調メタデータとして維持する。

`bootInstanceId`の読出し・更新を正常に確認できない場合、ログ識別子の永続的一意性を保証できないためログ・診断機能異常として扱う。安全処理は継続する。

### 5.4 `eventSequence`

同一起動中のイベントへuint32の`eventSequence`を1から単調増加で割り当てる。

0は未割当てを表す。wraparoundを通常運用で許可しない。

### 5.5 `logId`

`logId`は`bootInstanceId` 64 bitと`eventSequence` 32 bitの組合せで論理的な96 bit識別子とする。

VPS・保守出力では次の固定文字列表現を使用する。

`BBBBBBBBBBBBBBBB-SSSSSSSS`

`B`は16桁hexの`bootInstanceId`、`S`は8桁hexの`eventSequence`とする。

### 5.6 `correlationId`

一連の処理に複数イベントが属する場合、送信元機能が既に持つ要求識別子・取引識別子を64 bitで一意に表現できる場合は、その値または機能間で共有した64 bit相関値を`correlationId`として提供する。

128 bit等の大きい識別子を単純に下位64 bitへ切り詰めて相関IDとしない。必要な場合は、処理開始時に64 bitの相関値を別途発行して関係機能へ引き渡し、完全な元識別子は必要に応じてevent payloadまたは診断情報へ保持する。

適切な識別子がない場合、ログ・診断機能が新しい64 bit値を発行できる。

異なる処理のイベントを同じcorrelationIdへ暗黙にまとめない。

## 6. イベントログ共通レコード形式

### 6.1 ローカル保存形式

不揮発保存するイベントログは、初期製品では**128 byte固定長binary record**とする。

固定長とする理由は次である。

- 破損recordの境界を再同期しやすい。
- 循環領域のslot計算を固定できる。
- mallocを使用せずに扱える。
- 書込み途中recordをCRCで識別しやすい。
- 記録処理時間と最大RAM使用量を見積りやすい。

### 6.2 共通record構造

初版formatVersion 1の論理構造を次とする。

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `magic` | u32 | record識別子 `TRLG`相当 |
| `formatVersion` | u16 | 初版1 |
| `recordLength` | u16 | 128 |
| `bootInstanceId` | u64 | 起動単位 |
| `eventSequence` | u32 | 起動内順序 |
| `eventId` | u32 | イベント識別子 |
| `sourceFunctionId` | u16 | 発生元 |
| `eventCategory` | u8 | OPERATION/FAULT/SECURITY |
| `logPriority` | u8 | IMPORTANT/NORMAL |
| `systemState` | u16 | 発生時システム状態 |
| `timeQuality` | u8 | 時刻管理の`TIME_QUALITY_*` |
| `flags` | u8 | repeat、欠損、代替情報等 |
| `monotonicTimeUs` | u64 | 起動中単調時刻 |
| `utcEpochMs` | i64 | 時刻管理がtrustedとして提供できる場合のUTC。無効時は0 |
| `configGeneration` | u32 | 設定管理の有効設定generation。適用外は0 |
| `timeSyncGeneration` | u32 | 時刻管理の時刻同期世代。未確立は0 |
| `correlationId` | u64 | 処理相関。なしは0 |
| `firmwareBuildFingerprint` | u64 | 製品情報管理が提供する記録時running firmware build識別 |
| `payloadLength` | u16 | event固有payload長 |
| `reserved` | u16 | 0固定 |
| `payload` | 48 byte | event固有binary payload |
| `crc32c` | u32 | record先頭124 byteに対するCRC32C |

上記で128 byteを維持する。`configGeneration`のデータ型は設定管理のuint32へ一致させ、従来の不要な64 bit拡張を行わない。その4 byteを時刻管理の`timeSyncGeneration`へ使用する。

具体offset、alignmentおよびendiannessは詳細設計で固定する。RA8M2内部表現はlittle-endianを基本とする。

### 6.3 event固有payload

payloadはeventIdごとに固定schemaを定義し、48 byteを超えない。

48 byteを超えるデータを一つのイベントログへ直接埋め込まない。必要な場合は、同一correlationIdを持つ複数イベントへ分割するか、診断情報のスナップショット・評価trace等の別情報種別を使用する。

### 6.4 firmware識別

`firmwareBuildFingerprint`は製品情報管理がrunning signed image metadataおよびbuild生成物から提供する64 bit値を使用する。

製品情報管理とビルドシステムは、同じビルド識別情報から常に同じfingerprintを生成する。また、fingerprintから完全なSemVer・BuildIDを照合できるビルド一覧を保持する。

ログ・診断機能がOTA状態や過去ログからrunning firmware identityを推測してfingerprintを生成しない。

起動時のBOOT_CONTEXTイベントおよび診断情報では製品情報管理から完全なSemVer・BuildIDを取得して提供する。個々のrecordはfingerprintを持つため、BOOT_CONTEXTがローカルringから先に再利用された場合でも記録時firmwareをrelease情報と照合できる。

fingerprintの具体生成アルゴリズム、byte order、collision検査は製品情報管理/build詳細設計と共通化する。

### 6.5 VPS表現

VPSへ送信するときはローカルbinary recordの意味をJSON objectへ展開する。

VPS上の`logId`、eventId、category、priority、時刻品質、`timeSyncGeneration`、設定generation、correlationId、firmwareBuildFingerprint等がローカルrecordと対応可能であることを維持する。

VPS送信用JSONの構造はVPS接続・デバイス認証/VPS詳細設計で固定するが、ローカルrecordの意味を変更しない。

## 7. イベント分類・重要度・記録対象

### 7.1 IMPORTANTとする最低イベント群

少なくとも次をIMPORTANTとする。

- 緊急停止成立および解除結果
- 停止処理失敗
- 安全停止結果を確認できない状態
- 異常停止への移行
- 起動失敗
- 危険低電圧、重大過電流、短絡、重大異常発熱等の重大電源事象
- 必須安全監視の利用不能
- OTA更新失敗および復旧失敗
- 設定切戻し失敗、正常設定を確保できない状態
- 本体を通常操作禁止へする重大セキュリティ異常
- 重要ログ欠落が発生したことを示すログ・診断異常

本節の一覧は、ログ・診断がすべてのイベント提供元へ適用する最低優先度を定める。各担当機能の基本設計が、イベントの意味に基づいてこれより強い保存要求を定める場合は、IMPORTANTへ分類する。逆に、本節でIMPORTANTとしたイベントを、提供元の`NORMAL`指定だけで格下げしない。

### 7.2 NORMALとする主なイベント群

次をNORMALの代表例とする。

- 起動開始・正常完了
- 通常終了開始・正常完了
- システム状態の正常遷移
- BLE接続・切断・認証成功
- Wi-Fi接続・切断
- VPS接続・正常切断
- 設定取得・適用正常完了
- OTA更新情報確認・正常進行・正常完了
- 通常の警告成立・解除
- 所有者・端末管理の正常な管理処理結果

### 7.3 eventCategoryの例

| 事象 | category | priority |
| --- | --- | --- |
| 正常状態遷移 | OPERATION | NORMAL |
| 低バッテリー警告 | FAULT | NORMAL |
| 危険低電圧 | FAULT | IMPORTANT |
| BLE認証成功 | SECURITY | NORMAL |
| 連続認証失敗による制限 | SECURITY | IMPORTANT（セキュリティ管理のイベントの内容に応じた最低優先度） |
| OTA更新失敗 | FAULT | IMPORTANT |

### 7.4 高周期値をイベント化しない

操作指令、PWM値、電流、温度等の周期更新値を毎周期イベントログとして保存しない。

意味を持つしきい値成立、状態変化、開始・完了・失敗だけをevent化し、高周期波形は16章のtraceを使用する。

## 8. イベント受付・優先処理・欠落管理

### 8.1 固定受付キュー

イベント受付用に次の固定RAM queueを設ける。

| queue | slot数 | 1 slot | RAM |
| --- | ---: | ---: | ---: |
| IMPORTANT受付 | 16 | 128 byte | 2 KiB |
| NORMAL受付 | 48 | 128 byte | 6 KiB |

合計8 KiBを基本値とする。

### 8.2 受付順序

ログ保存workerはIMPORTANT queueを優先してdrainする。

NORMALの大量発生によってIMPORTANT slotを消費しない。

### 8.3 queue full時

NORMAL queueがfullの場合、新しいNORMAL eventは受付失敗とし、`droppedNormalCount`を増加させる。

IMPORTANT queueがfullの場合も安全処理をblockせず、`droppedImportantCount`を増加させ、ログ・診断機能異常として異常管理へ通知する。

ログを保存できないために「ログ欠落イベントそのもの」を無限生成しない。drop counterと`lossPending`をRAM管理し、次回正常保存可能時に1件の集約イベントとして記録する。

### 8.4 送信元への結果

イベントpublish APIは少なくとも次を返す。

- ACCEPTED
- DROPPED_NORMAL_QUEUE_FULL
- DROPPED_IMPORTANT_QUEUE_FULL
- LOGGER_UNAVAILABLE
- INVALID_EVENT

送信元はACCEPTEDを安全処理完了条件にしない。

### 8.5 レコード生成の分担

#### 発生元が提供する情報

イベントの発生元機能は、次の情報を提供する。

| 情報 | 内容 |
| --- | --- |
| `eventId` | イベント識別子 |
| `category` | イベントの種別 |
| `priority` | イベントの意味に基づいて発生元が要求する最低優先度 |
| イベント固有データ（`payload`） | 当該イベントで記録するデータ |
| `correlationId` | 必要な場合に提供する、関連するイベントの対応付けに使用する識別子 |

#### ログ・診断機能が付与する情報

ログ・診断機能は、第4.3節および第7.1節に従い、発生元が要求する最低優先度とログ共通ルールの最低優先度を比較する。
高い方を実際の保存優先度（`logPriority`）として確定し、発生元が`IMPORTANT`を指定したイベントを`NORMAL`へ格下げしない。

確定した`logPriority`とともに、次の情報をレコードへ付与する。

| 情報 | 内容または提供元 |
| --- | --- |
| `bootInstanceId` | 起動単位の識別情報 |
| `eventSequence` | 同一起動中のイベント順序 |
| 時刻情報 | 時刻管理機能が提供する情報 |
| `systemState` | システム状態 |
| `configGeneration` | 設定管理機能が提供する有効な設定世代 |
| `firmwareBuildFingerprint` | 製品情報管理機能が提供するファームウェア識別情報 |
| `formatVersion` | レコード形式の版 |
| CRC | レコードの破損検出に使用する情報 |

#### ログ初期化前に発生したイベント

ログ初期化前に発生したイベント（pre-log event）にも、発生元が保持した最低優先度を用いて同じ規則を適用する。
第17.2節で定める発生時の情報を使用し、LOG_READY後の引渡し時刻をイベントの発生時刻として付け直さない。

## 9. 同一事象の抑制・集約

### 9.1 基本方式

同一状態または同一異常が継続する間、周期ごとに同じログを生成しない。

同一episodeの判定keyを次の組合せとする。

- sourceFunctionId
- eventId
- 担当機能が指定するepisodeKeyまたはcorrelationId

### 9.2 onsetとclear

状態・異常の成立時にonset eventを1件記録する。

同じepisode中の同一event通知は新しい不揮発event recordを生成せず、RAM上のepisode stateにある`repeatCount`と`lastOccurrenceMonotonicTime`だけを更新する。永続データ管理が定めるcommit済みevent payload recordを後から書き換えない。

状態解除時にclearまたはsummary eventを新しいevent recordとして記録し、必要に応じて継続時間、repeatCountおよび最終発生時刻を含める。

### 9.3 長時間継続

同一episodeが60秒を超えて継続し、担当機能が解析上の継続確認を必要とする場合は、最大60秒に1回のsummary eventを許可する。

60秒値はログ量制御のログ・診断基本設計値であり、安全監視周期を意味しない。実機でログ量・解析性の両面から変更が必要な場合は本書へ評価結果を反映する。

### 9.4 抑制しないイベント

異なるcorrelationIdを持つ独立処理の開始・結果、緊急停止の新規成立、起動単位の変化等は、eventIdが同じでも別episodeとして記録する。

### 9.5 抑制情報の上限

抑制状態tableは32 episodeを基本上限とする。

上限を超えた場合はIMPORTANT episodeを優先し、NORMALの抑制状態をLRUで解放できる。抑制table不足そのものを通常操作禁止条件にしない。

## 10. 時刻・発生順序・起動単位管理

### 10.1 単調時刻

全イベントへRA8M2の単調増加timerを基準とする`monotonicTimeUs`を付与する。

同一起動中はUTC補正の影響を受けない。時刻管理もlog event orderingの基準として本値を使用する。

### 10.2 時刻管理の時刻情報

絶対時刻、trustおよびqualityの正式な管理元は時刻管理とする。

ログ・診断機能は時刻管理から少なくとも次を取得する。

- `utcEpochMs`
- UTC valid flag
- trust state
- quality
- `timeSyncGeneration`

recordの`timeQuality`へ次の時刻管理の品質を格納する。

- `TIME_QUALITY_NONE`
- `TIME_QUALITY_UNTRUSTED`
- `TIME_QUALITY_TRUSTED_HOLDOVER`
- `TIME_QUALITY_TRUSTED_SYNCED`

`TIME_QUALITY_TRUSTED_HOLDOVER`または`TIME_QUALITY_TRUSTED_SYNCED`でUTC validの場合だけ`utcEpochMs`を有効値として記録する。それ以外では`utcEpochMs=0`とし、0を正常UTCと解釈しない。

### 10.3 RTC時刻が信頼できない場合

RTC未設定または時刻信頼不能でも、`bootInstanceId`、`eventSequence`および`monotonicTimeUs`により同一起動中の順序を維持する。

信頼できない絶対時刻を推定して正常UTCとしてログへ書き込まない。

### 10.4 時刻補正

時刻管理がRTCを補正しても、既に保存済みイベントの`utcEpochMs`を書き換えない。

補正前後の順序は`monotonicTimeUs`で確認し、正常commitされた時刻補正世代はrecordの`timeSyncGeneration`で識別できるようにする。

時刻同期・補正自体は時刻管理からeventとして受け取り、少なくとも旧UTC、新UTC、offset、source、`timeSyncGeneration`、requestId、RTT、補正方向およびlarge correction確認有無のうちevent payloadで必要な情報を記録する。

### 10.5 起動間順序

`bootInstanceId`が単調増加するため、絶対時刻が利用不能でも起動単位の新旧を識別できる。

bootInstanceIdの更新失敗時はこの保証を失うため、ログ・診断機能異常として扱う。

## 11. ローカル保存・容量管理・再利用

### 11.1 論理保存領域

初期製品のevent log用論理容量を合計1 MiBとする。

| 領域 | 基本容量 | 128 byte record数 |
| --- | ---: | ---: |
| IMPORTANT_LOG_RING | 256 KiB | 2048 |
| NORMAL_LOG_RING | 768 KiB | 6144 |

永続データ管理はこの論理容量を外付け永続領域へ割り当てる。物理sector配置、erase blockおよび実際のmetadata領域は永続データ管理が管理する。

1 MiBは固定日数保持保証ではなく、初期の基本設計容量である。記録頻度評価により容量不足が判明した場合は、詳細設計だけで変更せず、本書と永続データ管理を同時に見直す。

### 11.2 重要領域の分離

NORMALログが増加してもIMPORTANT_LOG_RINGを直接消費しない。

これにより通常ログのburstだけで重要ログ保存枠を使い切らない。

### 11.3 NORMAL_LOG_RINGの再利用

容量不足時の再利用順序は次とする。

1. 最も古い送信済みNORMALログ
2. データ・プライバシー上削除可能と確定したNORMALログ
3. それでも空きがない場合、新しいNORMALログをdropしてloss counterへ反映

未送信NORMALログを、送信済みNORMALログより先に消去しない。

### 11.4 IMPORTANT_LOG_RINGの再利用

再利用順序は次とする。

1. 最も古い送信済みIMPORTANTログ
2. データ・プライバシー上削除可能と確定したIMPORTANTログ
3. 全recordが未送信で新しいIMPORTANTログを保存できない場合、最古の未送信IMPORTANTを失うことを最後の手段として許可し、`importantLogLossCount`を永続管理情報へ反映する

IMPORTANT喪失を正常状態として隠さない。

### 11.5 管理メタデータ

少なくとも次を管理する。

- ring write cursor
- oldest valid cursor
- sent/unsent state
- data lifecycle state
- valid record count
- droppedNormalCount
- droppedImportantCount
- importantLogLossCount
- corruptionCount
- bootInstanceId counter
- last successful VPS batch情報

永続データ管理に従い、event payload recordとは別の`LOG_META_JOURNAL`または固定metadataへ保持する。

### 11.6 固定長期保持を保証しない

初期製品ではローカルに「通常ログ7日」「重要ログ30日」等の固定日数を製品保証値としない。

保持期間はevent発生頻度、送信状況、媒体容量およびデータ・プライバシー条件によって変わる。

公開用システム要求仕様「19. データ・プライバシー管理」が定めるVPS上の通常イベントログ・診断情報の60日保存はVPS側のデータライフサイクル責任であり、本体ローカルringの固定日数保証へ読み替えない。

## 12. 完全性確認・破損検出・電源断との連携

### 12.1 record CRC

各128 byte recordの末尾4 byteへCRC32Cを保存する。

CRC対象は先頭124 byteとする。

magic、version、lengthおよびCRCが正常なrecordだけを有効recordとして扱う。

### 12.2 書込み途中record

電源断等で一部だけ書き込まれたrecordはCRC不一致または管理commit不成立として無効とする。

直前まで正常だったrecordを巻き込んで破損扱いにしない。

### 12.3 破損record

読出し時にrecord破損を検出した場合、次を行う。

1. 当該slotをCORRUPTとして識別する。
2. 内容を正常ログとしてVPSまたは保守インターフェースへ提供しない。
3. corruptionCountを更新する。
4. 次の正常保存可能位置へログ破損イベントを記録する。
5. 異常管理へ必要な異常情報を提供する。

破損内容から安全状態を推定しない。

### 12.4 record不変性・管理情報の完全性

本機能は、正常commit後のイベントデータ本体のレコードを、内容が変更されないものとし、永続データ管理へそのexact bytesの不変保存を要求する。

本機能が所有するSENT/UNSENT、data lifecycle、cursor、drop/corruption counter等の可変状態は既存event recordへ上書きせず、永続データ管理が物理管理する`LOG_META_JOURNAL`の固定長state journalまたはbitmapへ分離する。

ring cursor等のcheckpointは永続データ管理の初期方式の最大32 record間隔を使用し、power loss後は最新checkpoint以降だけをbounded scanして正常committed recordを回収する。通常起動で1 MiB ring全件scanを必須としない。

管理情報についてもCRC、commit markerその他永続データ管理の偶発破損検出方式を使用し、破損したmetadataからSENT/UNSENTやlifecycleを推測して正常確定しない。

### 12.5 セキュリティ完全性との分離

本章のCRC32Cは偶発的データ破損の検出を目的とする。

攻撃者による改ざん防止、暗号学的MAC、署名その他の高度な耐改ざんログは初期製品の通常event logへ独自追加しない。公開用システム要求仕様「20. セキュリティ管理」で将来検討とされる高度な監査基盤を、本書だけで必須化しない。

## 13. 未送信管理・VPS送信・再送

### 13.1 VPS送信対象

初期製品では、保存済みイベントログのうちdata lifecycle上VPS送信を許可されているrecordをVPS送信対象とする。

診断情報のスナップショットは管理・保守要求で必要な場合に送信対象とできる。

評価用トレースは通常の自動VPS送信対象としない。

削除対象または`RESET_DELETE_PENDING`等の送信禁止状態にあるrecordをbatch選択しない。

### 13.2 batch選択順序

VPS送信batchは次の順序で選択する。

1. 未送信IMPORTANTログの古い順
2. 未送信NORMALログの古い順
3. 必要な診断情報のスナップショット

一つのbatchへ最大64 event recordを含める。

JSON変換後のHTTP bodyが16 KiBを超える場合は、record数が64未満でもそこでbatchを分割する。

### 13.3 `logBatchId`

各送信batchへuint64の`logBatchId`を付与する。

同一batchを再送する場合は同じlogBatchIdと同じlogId集合を使用する。

batch内容を変更した場合は新しいlogBatchIdを発行する。

`logBatchId`は一送信batchのtransport相関用であり、イベントの永続的一意性は`logId`を基準に判定する。VPSは同一`logId`の再送をidempotentに扱う。

### 13.4 送信完了

VPS接続・デバイス認証から、対象logBatchIdについてVPSが正常受領したことを示す結果を取得した場合だけ、当該batch内の受領対象logIdをSENTへ変更する。

HTTP write成功、TCP送信完了、TLS record送信完了だけではSENTとしない。

VPSが部分受領を返す設計を採用する場合は、明示的に受領確認できたlogIdだけをSENTとする。

### 13.5 送信結果不明

timeout、切断、応答欠損等で結果を確認できない場合、対象logをUNSENTのまま保持する。

次回送信時に同じlogIdを使用する。

VPSは同一logIdを同一eventとしてidempotentに扱えることをVPS接続・デバイス認証/VPS側へ要求する。

### 13.6 送信タイミング

NORMALログは、他の管理・保守通信で認証済みVPS sessionが存在する場合に相乗りして送信することを基本とし、通常ログだけを理由として低消費電力状態からWi-Fiを復帰させない。

IMPORTANT未送信ログが存在し、次のすべてを満たす場合はログ・診断機能からVPS送信要求を発行できる。

- システム状態管理/電源・省電力管理が管理・保守通信を許可する状態である。
- 低消費電力移行中・終了中・緊急処理中でない。
- Wi-Fi接続/VPS接続・デバイス認証を利用可能である。

同時発生ログをまとめるため、最初のIMPORTANT保存後5秒を基本debounceとする。ただし終了・省電力要求を遅延させない。

5秒はログ・診断が所有する初期基本設計値であり、重要ログの安全成立や保存自体を5秒遅延させる意味ではない。評価で変更する場合は本書へ反映する。

### 13.7 一送信機会内のapplication再送

VPS接続・デバイス認証が現在のTLS sessionを`VPS_AUTHENTICATED`として継続利用可能と判断し、HTTP結果を要求元再試行可能として返した場合に限り、同一batchを初回送信に加えて最大2回再送できる。

待機は1秒、2秒を基本とする。同一セッションで3回以上連続送信しない。

HTTP 429等でVPSから明示的な再試行待ち時間が提供され、1秒／2秒より長い待機が必要な場合は、短時間固定再送を優先せず当該送信機会を終了して次回送信機会へ持ち越してよい。

response確定前の切断等によりVPS接続・デバイス認証がTLS sessionを無効化した場合は、本節の同一セッション再送を行わない。対象logをUNSENTのまま保持し、VPS接続・デバイス認証の接続復旧後の次回送信機会へ持ち越す。

### 13.8 次回送信機会への持越し

一送信機会で完了しなくても、グローバルな「3回失敗したのでログを破棄する」上限は設けない。

UNSENT状態で容量の許す範囲保持し、次回の管理・保守通信機会に同じlogIdで再送する。

容量不足時の最終的なログ喪失は11章の優先規則に従う。

### 13.9 VPS接続・デバイス認証の再接続との分離

Wi-Fi/TLS/VPS接続自体の再接続回数・backoffはWi-Fi接続/VPS接続・デバイス認証が管理する。

本書の1秒・2秒は、認証済みsessionが継続利用可能な場合のapplication batch再送policyであり、VPS接続・デバイス認証の接続確立retryをbatch再送回数へ読み替えない。

接続喪失後にVPS接続・デバイス認証が新しいTLS sessionを確立した場合、それは新しい送信機会として扱う。旧セッションのHTTP requestIdや途中送受信状態を再利用しない。

## 14. 診断スナップショット

### 14.1 基本方式

診断情報は保存済みevent logの寄せ集めではなく、要求時に各担当機能から現在状態を取得してsnapshotとして構成する。

### 14.2 最低診断項目

公開用システム要求仕様「14. ログ・診断」に従い、少なくとも次を含める。

- 製品情報管理のDevice ID、製品・ハードウェア構成識別
- 製品情報管理のrunning firmware SemVer/BuildID/`firmwareBuildFingerprint`
- 現在有効な設定のgenerationと取得元
- 起動理由・前回終了状態
- 現在システム状態
- BLE状態
- Wi-Fi状態
- VPS通信状態・認証状態
- 走行状態
- 砲塔・砲身状態
- 停止・緊急停止状態
- バッテリー電圧
- 走行系・サーボ系監視電流
- バッテリー温度・モータドライバ温度
- 現在発生中異常
- 時刻管理の時刻trust/quality/`timeSyncGeneration`/last sync age
- event log領域使用量
- 未送信IMPORTANT/NORMAL件数
- dropped/corruption/importantLogLoss count
- OTA状態・直近更新結果

### 14.3 項目共通属性

各診断項目に必要に応じて次を付ける。

- value
- validity
- sourceFunctionId
- acquisitionMonotonicTime
- ageMs

STALE値をVALIDに見せない。

### 14.4 部分成功

一部の情報提供機能から取得できなくても、診断情報のスナップショット全体を破棄せず、取得できた項目を返す。

取得不能の項目はUNAVAILABLE、期限超過はSTALE、提供元でのエラーはERRORと明示する。

### 14.5 参照専用

診断情報のスナップショット取得要求は、アクチュエータ、設定、通信状態、停止状態、電源状態または異常状態を変更しない。

診断のためだけに通常操作を開始・停止しない。

### 14.6 診断情報のスナップショットの資源上限

内部診断情報のスナップショットを生成するバイナリ作業バッファは、最大8 KiBとする。

各情報提供機能の応答待ち上限は基本値20 msとし、診断情報全体の取得処理は基本値200 ms以内に終える。個々の応答待ち時間を順に加算して、全体の200 msを延長しない。

期限内に応答しない情報提供機能の項目はUNAVAILABLE/STALEとし、スナップショットの生成を無期限に待たない。

スナップショットの生成は、安全関連の制御処理とは別の低優先度処理として実行する。

8 KiB、20 ms、200 msはログ・診断が管理する初期基本設計値であり、評価で変更する場合は本書へ反映する。

### 14.7 現在異常と過去異常

「現在発生中異常」は異常管理の現在状態を使用する。

保存済みFAULT eventは過去履歴として別に扱い、過去ログが存在することだけで現在異常を成立させない。

## 15. 保守用インターフェース

### 15.1 基本方式

初期製品の保守用診断インターフェースは、**3.3 V TTL UART**を基本とする。

基本通信条件を次とする。

- 115200 bit/s
- 8 data bit
- no parity
- 1 stop bit
- hardware flow controlなし
- GND/TX/RXの3線を基本

RA8M2の使用SCIチャネル、端子、connector/test padはハードウェア詳細設計で決定する。

### 15.2 外部接続

PCとの接続には外付けUSB-UART adapter等を使用できる。

Tank_Robot製品側に汎用USB serial機能を必須追加しない。

電圧レベルを誤接続しないよう3.3 V TTLであることを保守資料へ明示する。

### 15.3 初期コマンド

参照専用commandを次に限定する。

- `HELP`
- `INFO`
- `STATUS`
- `LOG META`
- `LOG READ <cursor> <count>`
- `TRACE STATUS`
- `TRACE READ`

具体的なASCII grammar、cursor型、エラーコードは詳細設計で固定する。

### 15.4 禁止command

通常保守診断では次を設けない。

- ログ消去
- 設定変更
- Wi-Fi/VPS接続先変更
- actuator強制動作
- PWM/モータ出力変更
- 電源系統強制ON/OFF
- 異常状態強制解除
- 鍵・credential・秘密情報dump
- firmware書換え
- 時刻設定

時刻管理のtrusted time設定、有線firmware復旧、製造provisioning等の書込み系保守経路は本UARTの通常read-only commandへ混在させず、physical accessを伴う別の管理された保守経路として扱う。

### 15.5 出力形式

人とtoolの双方が扱いやすいよう、初期製品のUART出力を1行1objectのUTF-8 JSON Lines形式とする。

一行最大1024 byteとし、長い結果は複数行に分割する。

不正・過大commandは64 byteで打ち切り、状態変更せずエラーを返す。

### 15.6 セキュリティ

保守用UARTから秘密鍵、Wi-Fi credential、BLE長期認証鍵、VPS private key、認証token、復旧秘密情報その他の秘密情報を取得できないようにする。

Device ID、firmware version、event log等は公開用システム要求仕様「19. データ・プライバシー管理」/公開用システム要求仕様「20. セキュリティ管理」の参照範囲および通常運用で不要なdebug／製造機能を有効にしない原則へ従う。初期製品では汎用の認証付き保守sessionを通常運用機能として追加しない。

### 15.7 低消費電力中

低消費電力状態中にUART参照要求だけを理由として本体を通常復帰させることを初期製品の必須機能としない。

PWR_CTRLが通常電力で保守参照可能な状態で使用することを基本とする。

## 16. 評価用トレース

### 16.1 目的

通常eventでは確認できない短時間の指令・出力・監視値関係を解析するため、固定RAMの評価用トレースを設ける。

### 16.2 RAM構成

trace bufferを64 KiB固定とする。

1 frameを64 byte、1024 frameの循環bufferとする。

### 16.3 取得周期

基本取得周期を10 msとする。

約10.24秒分を保持できる。

温度等の更新周期が10 msより遅い信号は、最新値とそのvalidity/ageをframeへ格納する。

### 16.4 基本trace対象

少なくとも評価時に次を選択可能とする。

- 走行指令
- 左右走行出力要求
- 砲塔・砲身指令
- サーボPWM要求
- バッテリー電圧
- 走行系合計電流
- サーボ系合計電流
- バッテリー温度
- モータドライバ温度
- システム状態
- 停止・緊急停止状態
- 異常・保護flag

実際のframe layoutとscaleは詳細設計で固定する。

### 16.5 triggerと前後時間

trigger時点を中心に、約5秒前＋約5秒後を保持する。

1024 frameのうち512 frameをpre-trigger相当、残りをpost-trigger相当として扱う。

代表triggerは次とする。

- 緊急停止成立
- 安全停止開始
- 異常停止成立
- 危険電気事象
- 走行/砲塔異常
- OTA更新失敗
- 開発・評価用明示trigger

### 16.6 複数trigger

一つのcapture中に追加triggerが発生した場合、trigger markerだけを追加し、capture時間を無期限に延長しない。

最初のtriggerを基準にpost-trigger区間完了後bufferをfreezeする。

### 16.7 通常イベントログとの分離

trace sampleをevent logへ変換して不揮発ringへ連続保存しない。

trace保存失敗・未取得だけを理由として安全処理を変更しない。

### 16.8 低消費電力

低消費電力状態への移行準備で高周期trace取得を停止する。

低消費電力状態の周期監視をtraceのためだけに増やさない。

## 17. 起動・状態・停止・異常・省電力との連携

### 17.1 起動時

ログ・診断初期化では次を行う。

1. 固定RAM queue初期化
2. 永続管理情報読出し
3. bootInstanceId更新・確定
4. log ring管理情報検証と永続データ管理のbounded recovery
5. 破損slot・未完了writeの識別
6. 未送信数・drop count等の再構築
7. pre-log event取込み
8. LOG_READYまたはDEGRADED結果を起動・終了・再起動管理/異常管理へ提供

ログ・診断の一部異常だけを理由として安全な基本操作を必ず禁止するとは限らず、影響度判断は異常管理に委ねる。

### 17.2 起動前半のpre-log event

ログ初期化以前の重要な起動・失敗eventは起動・終了・再起動管理等の起動側が固定pre-log queueへ最大16件保持し、LOG_READY前の取込み段階で本機能へ引き渡す契約とする。

pre-log entryは少なくとも次を発生時に保持する。

- eventId/category/priority
- event固有payload
- correlationId（存在する場合）
- 発生時`monotonicTimeUs`
- 発生時systemStateまたは起動段階識別子

loggerはpre-log queueの発生順序を維持して、通常producerの後発eventより先に`eventSequence`を割り当てる。引渡し時刻を発生時刻として再スタンプしない。

pre-log queueがoverflowした場合も起動・安全処理をblockせず、欠落件数または`preLogLossPending`を保持し、LOG_READY後に一件の集約欠落eventとして記録する。

pre-log取込み完了後に通常event受付をLOG_READYとして全面開放するか、同時受付する場合は発生時monotonic時刻とqueue順序を用いてeventSequenceが前後逆転しないようにする。

### 17.3 システム状態

システム状態管理から確定した状態遷移eventを受け取り記録する。

ログ・診断がシステム状態を独自に再判定しない。

### 17.4 停止・緊急停止

停止・緊急停止管理から停止要求、停止種別、開始、完了、失敗、緊急停止解除等の確定eventを受け取る。

緊急停止処理はログ受付・flash書込み・VPS送信を待たない。

### 17.5 異常管理

異常管理から異常識別子、現在異常状態、処置開始・完了、原因解消、復旧結果等を受け取る。

現在異常の診断表示は異常管理が管理する現在値を参照し、過去FAULT logを現在異常として扱わない。

### 17.6 電気安全

バッテリー・電気安全監視の警告・危険事象では、可能な範囲で監視値、validity、しきい値種別、成立時刻、関連異常識別子をevent payloadへ含める。

重大電気事象時にログ取得待ちで遮断を遅らせない。

### 17.7 低消費電力

低消費電力移行時は次を行う。

- 受付済みIMPORTANT recordを可能な範囲で不揮発保存へflushする。
- NORMAL flushは時間余裕の範囲とし、移行を無期限に待たせない。
- VPS送信を中断する。
- trace取得を停止する。
- 低消費電力移行eventを可能な範囲で保存する。

低消費電力状態中にNORMAL未送信ログだけを理由としてWi-Fiを復帰させない。

### 17.8 終了処理

通常終了時は、残存IMPORTANT queueのflushを優先する。

終了上位deadlineを超えてログ保存を待たない。未保存eventが残る場合はdrop/loss管理情報を可能な範囲で確定し、電源安全を優先する。

## 18. セキュリティ・データ保護

### 18.1 秘密情報禁止

ログ、診断、traceおよび保守出力へ次を平文で含めない。

- Wi-Fi passphrase/credential
- VPS private key
- TLS一時秘密情報
- BLE long-term authentication key
- 所有者復旧用の秘密情報
- registration ticket
- password
- authentication token
- HMAC key
- firmware signing private key

### 18.2 セキュリティeventの記録

セキュリティ機能は、秘密値そのものではなく、次のような情報を提供する。

- event種別
- 発生元interface
- 認証成功/失敗
- 権限拒否
- replay/sequence異常
- 証明書検証失敗種別
- 対象terminalRegistrationId等の非秘密識別子
- 処置結果

### 18.3 ネットワーク情報

SSID、MACアドレス、IPアドレス、証明書subject等は公開用システム要求仕様「19. データ・プライバシー管理」に従い、一般的な動作ログ・診断情報の通常記録項目としない。

障害解析で必要な場合も、解析目的達成に必要な最小範囲だけを保守向け情報として扱い、一般利用者向け状態表示または通常event payloadへ無条件に含めない。

### 18.4 個人情報

操作端末の個人名、メールアドレス、位置情報その他の個人情報を、ログ・診断上の識別に不要であれば収集しない。

端末識別が必要な場合はterminalRegistrationId等の本体内識別子を使用する。

### 18.5 保存期間・削除

本体ローカルringの固定日数保持は本書で保証しない。

公開用システム要求仕様「19. データ・プライバシー管理」によりVPS上の通常イベントログおよび診断情報はVPS受信後60日間を保存期間とし、期限満了後は通常検索・参照対象から除外して削除する。これはVPS／データライフサイクル側の実装責任であり、本体のログ・診断は送信dataに必要な識別情報を提供する。

データ・プライバシー管理がローカル削除を要求する場合、ログ・診断機能は対象recordを識別し、永続データ管理と連携して送信禁止・削除・再利用できるようにする。

### 18.6 工場初期化・所有者変更との連携

工場初期化またはその他のデータライフサイクル処理で公開用システム要求仕様「19. データ・プライバシー管理」が削除対象としたevent log・未送信logは、削除開始が確定した時点からVPS送信選択対象から除外する。

工場初期化の`RESET_PENDING`等、不可逆削除へ移行する状態を受けた場合、対象recordのdata lifecycle stateを`RESET_DELETE_PENDING`へ変更し、削除完了前であっても新しいVPS batchへ含めない。

永続データ管理に従い、送信禁止状態はevent payload record自体を書き換えず`LOG_META_JOURNAL`等のlifecycle metadataへ保持する。

削除完了後、当該未送信ログを新しい所有者のデータとして再送しない。これは公開用システム要求仕様「19. データ・プライバシー管理」の`SYS-DATA-094`と整合させる。

一方、`bootInstanceId`の単調counterはVPS上の過去logIdとの重複防止に必要な製品診断メタデータであり、利用者ログ本体と分離して工場初期化では巻き戻さない。

所有者再登録だけを理由としてどのログを削除・保持するかは公開用システム要求仕様「19. データ・プライバシー管理」に従い、本書で一律削除しない。

ログ機能だけで製品固有Device IDや製造情報等を削除対象へ追加しない。

## 19. ログ・診断機能自身の異常と復旧

### 19.1 異常分類

少なくとも次を識別する。

- LOG_GENERATION_FAILURE
- IMPORTANT_QUEUE_OVERFLOW
- NORMAL_QUEUE_OVERFLOW
- PRE_LOG_OVERFLOW
- LOG_PERSIST_FAILURE
- LOG_STORAGE_FULL
- LOG_RECORD_CORRUPTION
- LOG_METADATA_CORRUPTION
- BOOT_INSTANCE_ID_FAILURE
- TIME_INFORMATION_INVALID
- DIAG_PROVIDER_FAILURE
- DIAG_SNAPSHOT_TIMEOUT
- VPS_LOG_SEND_FAILURE
- UNSENT_STATE_INCONSISTENT
- TRACE_BUFFER_FAILURE
- MAINT_UART_PROTOCOL_ERROR

### 19.2 異常管理へ提供する情報

異常通知には可能な範囲で次を含める。

- 異常種別
- 発生箇所
- firstOccurrenceMonotonicTime
- count
- 重要ログ保存可否
- 通常ログ保存可否
- 未送信管理可否
- 診断情報のスナップショット可否
- trace可否
- 推奨する機能制限

### 19.3 logger異常時の安全

ログ保存不能でも、安全停止、緊急停止、電気保護、異常停止を阻害しない。

ログを安全状態の唯一の永続記録として使用しない。

### 19.4 一次復旧

異常管理が自動復旧を許可する軽微異常について、次を許可する。

- RAM queue再初期化
- ring metadata再読出し
- 破損recordのskip
- VPS送信sessionの再要求
- maintenance parser再初期化

不揮発媒体全体を消去する復旧を自動実行しない。

### 19.5 容量不足

LOG_STORAGE_FULLだけを理由として初期製品の通常操作を直ちに禁止しない。

重要ログ保存不能等、安全解析上の影響を異常管理へ通知し、異常管理がシステム全体の処置を判断する。

## 20. 実行時間・CPU・RAM・固定資源方針

### 20.1 基本性能・資源値

| 項目 | 基本設計値 |
| --- | ---: |
| event publish処理 | 200 µs以内目標、1 ms hard upper bound |
| IMPORTANT/NORMAL RAM queue | 合計8 KiB |
| 1 event record | 128 byte |
| event local logical NVM | 1 MiB |
| suppression summary間隔 | 最大60 sに1回 |
| IMPORTANT送信debounce | 5 s |
| trace RAM | 64 KiB |
| trace frame | 64 byte |
| trace周期 | 10 ms |
| 診断情報のスナップショット work | 8 KiB |
| 情報提供機能の応答待ち | 基本値20 ms以内 |
| 診断情報のスナップショット全体 | 200 ms以内 |
| VPS batch event数 | 最大64 |
| VPS batch JSON body | 最大16 KiB |
| application batch追加再送 | 最大2回、1 s→2 s |
| maintenance command | 最大64 byte |
| maintenance 1出力行 | 最大1024 byte |

これらは評価確定待ちを含むログ・診断が所有する初期基本設計値である。実機・結合評価で成立しない場合は詳細設計だけで変更せず、本書と容量・通信・永続値を管理する関連基本設計へ結果を反映する。

### 20.2 CPU負荷

通常イベント記録は高周期control task内でCRC計算・flash書込みを直接完了させない。

control側はeventをfixed queueへpublishし、logger workerがrecord生成・CRC・永続保存要求を行う。

### 20.3 flash書込み

永続flash erase/writeの具体時間を安全関連taskのdeadlineへ持ち込まない。

永続データ管理が非同期保存または時間分割を行い、loggerは結果を相関して管理する。

### 20.4 malloc禁止

次を静的確保する。

- IMPORTANT/NORMAL queue
- event build buffer
- suppression table
- VPS batch buffer
- diagnostics snapshot buffer
- trace buffer
- maintenance command/response buffer

### 20.5 overflow方針

上限超過時に配列拡張、heap確保、unbounded queue作成を行わない。

明示的にdrop、split、partial snapshotまたはerrorとする。

## 21. 検証方針と確認ケース

### 21.1 基本検証

| ID | 確認内容 |
| --- | --- |
| T-01 | sourceFunctionIdが機能別基本設計01～21の固定割当てと一致し、Security=セキュリティ管理 `0x0011`、Time=時刻管理 `0x0014`等が衝突しない |

| T-08 | 製品情報管理のfirmwareBuildFingerprintから記録時firmwareをrelease情報と照合できる |

| T-20 | 同じlogBatchId/logId集合再送をVPSが重複eventとして登録しない |
| T-21 | VPS接続・デバイス認証のsessionが継続有効なretryable結果だけ1 s/2 sの同一セッション再送を行い、session喪失時はUNSENTで次回へ持ち越す |
| T-22 | IMPORTANTをNORMALより先にbatch選択する |
| T-23 | low power中にNORMAL logだけでWi-Fiをwakeしない |
| T-24 | 診断情報のスナップショットの取得時、一部の情報提供機能が失敗しても、取得できた他の項目を返せる |
| T-25 | STALE/UNAVAILABLE/ERRORをVALIDと区別できる |
| T-26 | 診断参照がactuator状態を変更しない |
| T-27 | maintenance UARTから設定・出力・時刻を変更できない |
| T-28 | maintenance UARTから秘密情報を取得できない |
| T-29 | trace 10 ms/64 KiBで約5秒pre＋5秒postを保持できる |
| T-30 | trace取得が通常event ringを消費しない |
| T-31 | 重大電源異常時にlogger遅延が遮断処理を遅らせない |
| T-32 | logger persistence failureを異常管理へ通知して安全機能は継続する |
| T-33 | 工場初期化で削除対象となった未送信logを初期化後VPSへ再送しない |
| T-34 | log/diag固定バッファ上限を超えてRAMが増加しない |
| T-35 | 永続データ管理のcheckpoint後最大32 record範囲のbounded recoveryでring状態を再構築できる |
| T-36 | pre-log eventが発生時monotonic時刻と順序を維持して通常eventより先に取り込まれる |
| T-37 | pre-log overflow時も起動・安全処理をblockせず欠落を集約記録する |
| T-38 | 提供元とログ・診断が定める最低優先度について、次に示す二つの条件が成立する |

T-38では、次の両方を確認する。

1. イベントの提供元が最低優先度を`IMPORTANT`とした場合、ログ・診断は`NORMAL`へ下げない。
2. ログ・診断の共通規則が`IMPORTANT`を要求する場合、提供元の指定が`NORMAL`でも、実際の`logPriority=IMPORTANT`となる。

### 21.2 fault injection

次を意図的に発生させる。

- record CRC破損
- ring metadata片側破損
- flash write途中電源断
- IMPORTANT/NORMAL queue burst
- pre-log queue overflow
- VPS ACK消失
- TLS session喪失中のlog送信結果UNKNOWN
- 情報提供機能の応答期限超過
- RTC未設定・時刻補正
- UART過大command
- trace trigger集中
- 工場初期化中断と未送信logの残存

### 21.3 性能評価

最大イベントburst時に、停止・緊急停止、安全監視、制御周期のdeadlineを満たすことを測定する。

VPS送信・trace出力中のCPU使用率、RAM使用量、UART/TLS帯域を測定する。

第20.1節の基本性能・資源値が成立しない場合は、外部振る舞い・解析性を変える値を詳細設計だけで変更せず、本書へ評価結果を反映する。

## 24. 他文書へのフィードバック

### 24.1 F-01 永続データ管理

永続データ管理で次が具体化済みであり、本書へ反映した。

- IMPORTANT_LOG_RING 256 KiB、NORMAL_LOG_RING 768 KiB
- 128 byte record＋CRC32C
- commit後event record不変
- SENT/UNSENT・data lifecycleをLOG_META_JOURNALへ分離
- checkpoint最大32 record間隔＋bounded recovery
- bootInstanceIdを工場初期化で巻き戻さない
- `RESET_DELETE_PENDING`等の送信禁止metadata

詳細設計では永続データ管理の物理保存方式へ従い、本書のイベントの意味・優先順序を変更しない。

### 24.2 F-02 起動・終了・再起動管理

ログ初期化前の起動・失敗eventを失わないため、最大16件の固定pre-log event queueを用意し、発生時monotonic時刻、起動段階／systemState、イベントの内容を保持してLOG_READY前に本機能へ引き渡す。

loggerはpre-logを後発通常eventより先に順序付けるため、起動・終了・再起動管理側でもqueue順序を変更しない。

ログflush失敗だけで安全な終了を無期限に待たせない。

### 24.3 F-03 各機能基本設計

各機能は、eventId、category、イベントの内容に応じた最低優先度、イベントのデータ本体、およびcorrelationIdを定義し、ログ・診断へ提供する。ログ・診断は、提供された最低優先度を格下げしない。ログ・診断の共通規則で定める最低優先度の方が高い場合だけ、実際の`logPriority`を`IMPORTANT`へ昇格する。

周期値をeventとして大量送信せず、意味eventとtraceを分離する。

128 bit等の取引識別子をcorrelationIdへ単純切詰めせず、必要な場合は関係機能間で共有する64 bit相関値を使用する。

### 24.4 F-04 VPS接続・デバイス認証

VPS接続・デバイス認証で次が具体化済みであり、本書へ反映した。

- `/api/v1/device/{deviceId}/logs`
- log batch最大64 event・16 KiB body
- 一意に識別可能な`logBatchId`
- VPS ACK取得時だけ送信完了
- unknown結果の再送判断はログ・診断が行う
- application batch再送は一送信機会で追加最大2回、1秒→2秒
- VPS接続・デバイス認証の接続確立retryをbatch再送回数へ読み替えない

本書ではVPS接続・デバイス認証のsessionが継続利用可能な場合だけ同一セッション再送を行い、session喪失時はUNSENTのまま次回送信機会へ持ち越す。

### 24.5 F-05 セキュリティ管理

セキュリティ管理/公開用システム要求仕様「20. セキュリティ管理」の秘密情報非出力規則およびセキュリティevent契約を使用する。Security eventの記録すべき最低優先度はセキュリティ管理が決定し、ログ・診断はその指定を格下げせず共通priority policyへ反映する。

保守UARTおよびVPS送信log/diagnosticへ、秘密鍵、credential、token、登録秘密情報等を平文出力しない。

初期製品の通常保守UARTはread-onlyのままとし、公開用システム要求仕様「20. セキュリティ管理」で将来検討とされた汎用認証付き保守sessionや能動診断を本書へ追加しない。

### 24.6 F-06 データ・プライバシー管理

公開用システム要求仕様「19. データ・プライバシー管理」ではVPS上の通常イベントログ・診断情報をVPS受信後60日間保存し、期限満了後は通常検索・参照対象から除外して削除することが要求されている。これはVPS／管理側のデータライフサイクルへ引き継ぐ。

工場初期化で削除対象となった未送信logは、RESET_PENDING後ただちに送信禁止状態へ移し、初期化後の新所有者データとして送信しない契約を維持する。

本体local ringについては固定7日/30日保持を製品保証しない。

### 24.7 F-07 状態表示・利用者通知

状態表示・利用者通知へ次の情報を提供する契約を維持する。

- ログ保存縮退
- 重要ログ欠落
- 診断一部利用不能
- VPSログ送信失敗

具体表示・利用者向けエラーコードは状態表示・利用者通知基本設計に従う。

### 24.8 F-08 製品情報管理

製品情報管理でDevice ID、製品/HW識別、running firmware identityおよび64 bit `firmwareBuildFingerprint`が具体化済みであり、本書へ反映した。

ログ・診断は製品情報を独自生成せず製品情報管理から参照する。

### 24.9 F-09 時刻管理

時刻管理からUTC valid/trust/quality/`timeSyncGeneration`を受け、`monotonicTimeUs`による順序を維持する契約を本書へ反映した。

過去eventのUTCを書き換えず、時刻補正eventと`timeSyncGeneration`で補正前後を解析可能とする。

## 25. 初版の自己確認結果と引継ぎ条件

### 25.1 自己確認結果

初版作成後のレビューおよび後続基本設計との整合確認を含め、次を確認・修正した。

- 公開用システム要求仕様「14. ログ・診断」の`SYS-DIAG-001～004`、`010～014`、`020～024`、`030～034`、`040～041`、`050～052`、`060～065`、`070～074`、`080～082`、`090～091`、`100～101`の全42要求へ主対応箇所を設定した。
- 公開用システム要求仕様「14. ログ・診断」第14.13節の具体化対象11項目へ基本方式を設定した。
- event log、diagnostics、traceを混在させていない。
- 通常ログを高周期sampleとして保存せず、意味eventへ限定した。
- sourceFunctionIdを機能別基本設計01～21の現行機能番号へ固定し、旧記述のSecurity=`0x0014`をセキュリティ管理=`0x0011`へ修正して時刻管理のTime=`0x0014`との衝突を解消した。
- eventId、logId、bootInstanceId、correlationIdの生成責任を明確化し、128 bit識別子の単純切詰めを禁止した。
- 情報の提供元機能がイベントの内容に応じた最低優先度を決定し、ログ・診断が`IMPORTANT`／`NORMAL`の共通の意味、共通の最低優先度、格下げ禁止・昇格の規則、およびキュー・保存・領域再利用・送信の方針を定める担当関係へ統一した。提供元の`IMPORTANT`を`NORMAL`へ格下げせず、共通規則がより高い優先度を要求する場合だけ`IMPORTANT`へ昇格する。
- bootInstanceIdを工場初期化でも巻き戻さず、同じDevice IDのVPS上過去logIdと将来logIdが衝突しない方式を維持した。
- 時刻管理の時刻品質NONE/UNTRUSTED/TRUSTED_HOLDOVER/TRUSTED_SYNCEDと`timeSyncGeneration`をrecordへ反映し、RTC非信頼でもbootInstanceId/eventSequence/monotonicTimeで順序を保持する方式とした。
- 製品情報管理の64 bit `firmwareBuildFingerprint`をrunning firmwareの正式な識別値として参照し、ログ側でOTA状態から推測しない方式とした。
- 128 byte固定record＋CRC32Cを維持し、設定管理のuint32 configGeneration＋時刻管理のuint32 timeSyncGenerationを格納した。
- ログ・診断がcommit済みevent recordの不変性とSENT/UNSENT・lifecycleの意味を定め、永続データ管理のLOG_META_JOURNALへ物理分離するよう整理した。
- 同一episodeのrepeatCount等はRAM episode stateで更新し、既存recordを書換えずsummary/clearを新recordとして保存する方式へ明確化した。
- IMPORTANT/NORMAL受付queueと保存ringを分離し、通常event burstで重要資源を直接消費しない方式を維持した。
- queue overflow時も安全処理をblockせず、drop counterで欠落を明示する方式を維持した。
- 永続データ管理の最大32 record checkpoint＋bounded recoveryを取り込み、通常起動で全1 MiB scanを要求しない方式とした。
- 固定7日/30日のローカル保持は追加せず、公開用システム要求仕様「19. データ・プライバシー管理」のVPS側60日保存と責任を分離した。
- VPS送信完了をVPS ACK取得後だけとし、結果不明ではUNSENTを維持する方式を維持した。
- 最新のVPS接続・デバイス認証基本設計の責任分界へ合わせ、TLS session継続時のapplication batch retryと接続retryを分離し、session喪失時は次回送信機会へ持ち越す方式とした。
- 公開用システム要求仕様「19. データ・プライバシー管理」で工場初期化時に削除対象となった未送信logをLOG_META_JOURNAL上の送信禁止状態へ移し、初期化後の新所有者データとして再送しない方式を維持した。
- NORMAL logだけでlow powerからWi-Fiをwakeしない方式を維持した。
- 各機能が提供する現在状態から診断情報のスナップショットを作る方式とした。製品情報管理の製品・ファームウェア情報と、時刻管理の時刻品質を含め、過去のログから現在状態を推定しない。
- maintenance interfaceを3.3 V UART/115200/8N1/read-onlyとし、時刻管理の時刻設定やfirmware復旧等の書込み経路を混在させていない。
- logger初期化前のpre-log eventに発生時monotonic情報を保持し、引渡し時刻で再スタンプしない契約を追加した。
- traceを固定64 KiB RAM、10 ms、約5秒pre＋5秒postとしてevent保存領域から分離した。
- 秘密鍵、credential、token等をlog/diagnostic/trace/UARTへ平文出力しない方式を維持した。
- ログ・診断異常を安全状態の唯一の判断源にせず、異常管理へ影響情報を渡す責任分界を維持した。
- malloc/freeを使用しない固定資源方針を維持した。
- event publish 1 ms hard upper bound、log容量、queue、60秒summary、5秒debounce、diagnostic 200 ms、trace周期・容量等を評価確定待ちを含む基本設計で管理する値として明確化した。

## 1. 本書の目的

### 1.1 目的

本書の目的は、公開用システム要求仕様「18. 永続データ管理」を実現するため、各機能が再起動または電源再投入後も必要とするデータを、安全かつ復旧可能に不揮発保存する基本方式を、詳細設計へ展開可能な粒度まで具体化することである。

### 1.2 対象範囲

本書は、Tank_Robot本体が再起動、電源OFF、予期しないリセットおよび電源断をまたいで保持するデータについて、内蔵MRAMと外付けSerial NORの役割分担、障害分離、データ識別、完全性確認、原子的更新、起動時復旧、容量管理、書換え寿命、工場出荷状態への初期化および関連機能との責任分界を具体化する。

永続データ管理は、保存するデータの機能上の意味、正常値、適用条件、失効条件、復旧条件または削除対象を独自に決定しない。各機能が定めるデータの意味を変えずに、安全に保存・読出し・更新・消去する基盤責務を担う。

#### 基本設計と詳細設計の区分

本書と各データ管理機能の基本設計、および詳細設計で定める事項を、次のように区分する。

| 区分 | 定める事項 |
| --- | --- |
| 本書 | 記憶容量、記憶領域の分割、重要データ領域の総量、記憶媒体上での原子的な更新方式、再試行回数・間隔、終了時最小保存の時間、チェックポイント間隔、共通の`fallbackPolicy`区分。その他、関連機能へ提供する保存・復旧の基本処理を変える値・方式 |
| 各データ管理機能の基本設計 | 個々のデータ集合の内容と使用条件、データ内容の版、代替データへの切替可否、巻戻し判定の下限値、状態の更新対象、および複数のデータ集合にまたがる機能上必要な処理順序 |
| 詳細設計 | 物理アドレス、保存枠内の具体的なオフセット、ドライバAPI、タスク、バッファ配置など、外部から見た動作を変更しない実装方法 |

実機評価で変更が必要となった場合は、詳細設計だけで変更しない。本書または値・方式を定める関連基本設計へ評価結果を反映して、正式値を更新する。

### 1.3 上位文書・関連文書

本書の主対象要求は公開用システム要求仕様「18. 永続データ管理」とする。

関連する公開用要求および完成済み基本設計について、データを管理する機能、保存要否、更新単位、工場初期化、秘密情報、設定、ログおよびOTAとの責任分界に必要な範囲を参照する。

`20_要求仕様`および`30_コア要求仕様`は本書の上位要求として使用しない。公開用要求で未確定の方式を具体化する場合は、本書の設計判断として明示する。

### 1.4 外部技術資料の位置付け

RA8M2 Group DatasheetおよびRenesas FSPのMRAM/OSPI関連資料を、採用方式の成立性確認に使用する。

参照時点のEK-RA8M2搭載MCU `R7KA8M2JFLCAC` は1 MiB MRAMを搭載し、独立Data Flash容量は0 KiBである。このため本書では、内蔵MRAMのPRIMARY以外の領域から重要永続データ領域を明示的に予約する。

外部技術資料は製品上位要求ではない。最終採用MCU、FSPまたは外付けSerial NORが変わる場合は、本書の障害分離・原子性・復旧可能性を維持した上で詳細構成を再評価する。

### 1.5 用語

本書でいうデータ管理機能（owner）は、データの意味や使用条件を管理する機能を指す。製品の利用者である「所有者」とは区別する。

| 用語 | 本書での意味 |
| --- | --- |
| データ管理機能（owner） | データの意味、正常値、保存要否、更新・失効・削除条件を決定する機能 |
| PERSIST | 永続データ管理機能。各データ管理機能から要求された保存・読出し・更新・消去を実行する |
| `PERSIST_CRITICAL` | RA8M2内蔵MRAMに確保する小容量の重要永続データ領域 |
| BULK NVM | 外付けSerial NORによる大容量の永続データ領域 |
| データ集合（logical dataset） | 保存・更新の単位として区別する、データのまとまり |
| データ本体（payload） | 共通の管理情報とは別に、各データ管理機能が内容や形式を定める保存対象データ |
| 共通管理情報（envelope） | レコードの識別、形式、長さ、保存世代、完全性、確定状態などを管理する情報。項目は第8.1節で定める |
| 確定済みレコード（committed record） | 全体の書込み、読戻し、完全性確認、および保存の確定を示す印（commit marker）の確定を完了したレコード |
| 保存用の複製（physical copy） | 同じ保存対象データを冗長に保持する複製。電源断への耐性を確保するために使用する |
| データ内容の版・世代（semantic revision） | データ管理機能が、自機能のデータの新旧を区別するために管理する値。`ownerDataRevision`、`configGeneration`、`productDataRevision`、`timeTrustRevision`などが該当する |
| `persistRevision` | `(datasetId, logicalSlot)`ごとの保存処理の世代。PERSISTがA/Bの複製の選択と競合検出に使用し、データ内容の版・世代とは独立して管理する |
| 巻戻し判定の下限値（rollback floor） | SecurityGen、highestCommittedGenerationなど、正常確定後に小さくしてはならない、各データ管理機能が管理する基準値 |
| 書込み途中の不完全レコード（torn write） | 電源断、リセット、書込み失敗などにより、一部だけが更新されたレコード |
| 論理保存枠（logical slot） | ACTIVE/PREVIOUSなど、機能上の意味を持つ保存枠 |
| 終了時最小保存（minimum save） | 低電圧終了時に200 ms以内で保存を完了させる、最小限のデータ集合 |

## 2. 設計方針と適用範囲

### 2.1 基本方針

永続データ管理は次の原則で設計する。

1. データの意味は各機能が所有し、PERSISTは保存媒体、完全性、原子性、読出し、更新中断および容量を管理する。
2. 小容量かつ起動・安全・認証・復旧に必要な重要情報と、大容量・管理保守用データを物理的・論理的に分離する。
3. すべてのdatasetへ一律の汎用A/B、世代管理、履歴探索または汎用Copy-on-Writeを適用しない。
4. 電源断時に旧正常値を失ってはならない小容量重要datasetには、個別に二重copyまたは同等の旧正常値保持方式を使用する。
5. 新recordをcommittedとして確定する前に旧committed recordを無効化しない。
6. 「旧データの保存用複製のCRCが正常であること」と「古い内容の版へ戻してよいこと」は区別する。巻戻しによって意味が変わるデータ集合については、管理元の機能が定める版・下限値の契約に従って、代替データを使用できるか判断する。
7. torn writeを正常値として使用しない。
8. 起動時に安全・操作可否へ必要な小容量datasetを優先確認し、大容量領域の全走査を起動完了条件にしない。
9. BULK NVM異常だけで、安全機能およびBULK NVMへ依存しないBLE基本操作まで停止させない。
10. 正常操作可否への影響は異常管理/システム状態管理が各データ管理機能の結果を用いて判断し、PERSISTが独自にシステム状態を決めない。
11. 秘密情報はPERSISTが平文化・意味解釈せず、Security機能が生成した暗号化済みまたはwrapped blobとして保存する。
12. 書込み処理を安全関連task内で同期完了させず、原則として非同期・固定資源で処理する。
13. 安全処理、緊急停止、電源保護、強制電源遮断を永続書込み完了待ちで阻害しない。
14. 工場初期化は所有者・操作端末管理/公開用システム要求仕様「19. データ・プライバシー管理」および各データ管理機能が決める削除・保持・key rotation順序を実行し、PERSISTが独自にデータ範囲を拡大しない。
15. 標準`malloc/free`を使用しない。

### 2.2 対象範囲

本書は次を対象とする。

- 内蔵MRAM重要永続領域
- 外付けSerial NOR論理partition
- dataset識別・format version
- 保存用の複製／`persistRevision`とデータ管理機能が付与する版の分離
- 偶発破損検出
- 原子的更新・データ管理機能が管理する複数dataset transaction支援
- 読戻し・commit確認
- 起動時復旧
- 容量・残容量
- 書換え寿命
- 保存要求の排他・優先順位
- 工場初期化時の物理処理
- 記憶媒体異常と有限retry
- 各完成済み基本設計との保存契約

### 2.3 対象外

次は本書で意味を決定しない。

- 設定値の安全範囲
- 所有者・端末の役割と権限
- Wi-Fi credentialの内容
- ログevent分類・保存優先度
- OTA candidate適用可否
- 異常の重大度・復旧権限
- SecurityGen・productDataRevision・timeTrustRevision等の意味
- 秘密情報の暗号方式・鍵管理方式
- 工場初期化で削除対象とする利用者データの意味

また、次の高度な汎用機能は初期製品へ追加しない。

- 全dataset共通の多世代DB
- 任意世代rollback
- media全体scanによる自動再構築
- dynamic partition resize
- 汎用GC
- bad block remapping layer
- 永続データ圧縮
- 汎用backup/restore

## 3. 責任分界と論理インターフェース

### 3.1 PERSISTの責任

永続データ管理機能（PERSIST）は、主に次を担当する。

- 記憶媒体を初期化し、利用可否を確認する。
- データ集合と保存領域の対応を管理する。
- データを読み出し、書き込み、消去する。
- レコードの共通管理情報を検証する。
- CRCなどを用いて偶発的な破損を検出する。
- 原子的更新を記憶媒体上で実行する。
- 保存用の複製について、確定済みか、書込み途中で不完全かを識別する。
- データ集合の容量と残容量を管理する。
- 同時アクセスが競合しないように排他制御を行う。
- 書込みと読戻しの結果を返す。
- 記憶媒体の異常や容量不足を通知する。
- データ管理機能が定めた、処理の未完了状態や最終確定を表すレコードを物理的に保存する。
- 工場初期化時に、指定されたデータ集合を消去・無効化する。

### 3.2 データ管理機能の責任

データ管理機能は、次を担当する。

- データ本体の構造・形式を定める。
- データ本体の内容が、機能上の条件を満たすか検証する。
- 保存が必要かどうかを判断する。
- 論理保存枠の意味を定める。
- 期待するデータ内容の版・世代を定める。
- 保存されたデータを使用してよいか判断する。
- 代替データへ切り替えてよいか判断する。
- 巻戻し判定の下限値を管理する。
- 複数のデータ集合を一つの機能上の更新処理として扱う場合に、保存を確定する順序を定める。
- データの削除・保持条件を定める。
- 工場初期化時の取扱いを定める。

PERSISTは、保存済み内容が機能上正しい値かを独自に判定しない。保存処理の成否と、そのデータを使用してよいかの判断は分けて扱う。

#### OTA管理データへの適用

OTAの`CRIT_OTA_BOOT`についても、同じ分担を適用する。

| 機能 | 担当する内容 |
| --- | --- |
| OTA更新管理 | OTA取引、`internalPhase`、`recoveryEligible`、`TRIAL_BOOT_VALIDATED`、本体の最終結果およびVPSへの報告状態の意味を管理する |
| 固定ブート・復旧 | 本体アプリケーションの停止中に、`PRIMARY_OVERWRITE_STARTED`、`TRIAL_ARMED`、`trialAttempted`、`RECOVERY_BOOT_PENDING`などを、規定された順序で確定する |
| 永続データ管理（PERSIST） | どちらの機能が管理する情報についても意味を再判定せず、要求されたレコードをA/B、完全性確認および保存確定の規則に従って保存する |

### 3.3 Securityとの責任分界

Securityは次を担当する。

- 暗号鍵・credentialの生成
- AEAD/HMAC/署名等の暗号学的保護
- key wrap/unwrapping
- SecurityGen等のsecurity rollback判定
- credential失効
- secure invalidation/crypto eraseの意味

PERSISTは、暗号化済みのデータ、Wrapped Key、状態保護用MAC付きのレコードを、内容を解釈せずに保存する。平文の秘密情報を共通ヘッダ、ログまたは診断へ出力しない。

CRCとcommit markerが正常でも、データ管理機能／SecurityによるHMAC・AEAD・巻戻し防止の下限値の確認が正常に完了するまでは、セキュリティ上重要なデータ集合を、現在使用できるデータとして公開しない。

### 3.4 システム状態管理/起動・終了・再起動管理/異常管理/バッテリー・電気安全監視との責任分界

- システム状態管理：システム状態・通常操作可否の最終判断
- 起動・終了・再起動管理：起動・終了・再起動sequenceとminimum save対象集約
- 異常管理：PERSIST異常の影響度・処置・復旧可否
- バッテリー・電気安全監視：重要書込み・minimum saveを開始・継続可能な電源条件

PERSISTはバッテリー・電気安全監視の電圧・温度値を再判定せず、バッテリー・電気安全監視が提供する開始・継続可能結果を使用する。

### 3.5 共通保存要求

保存要求は論理的に少なくとも次を持つ。

- `persistRequestId`：uint64
- `datasetId`
- operation：READ / WRITE / INVALIDATE / ERASE / QUERY
- logicalSlot
- payload reference
- payloadLength
- datasetFormatVersion
- `expectedPersistRevision`またはNONE
- transactionCorrelationId
- priorityClass
- completion deadline class
- dataOwnerFunctionId

具体API、queue、構造体は詳細設計で固定する。

### 3.6 共通結果

少なくとも次を区別する。

- ACCEPTED
- COMPLETED
- BUSY
- INVALID_REQUEST
- FORMAT_UNSUPPORTED
- REVISION_MISMATCH
- READ_FAILED
- WRITE_FAILED
- ERASE_FAILED
- READBACK_MISMATCH
- CORRUPT
- NO_SPACE
- MEDIA_UNAVAILABLE
- ABORTED_POWER_CONDITION
- TIMEOUT
- ROLLBACK_REJECTED
- OWNER_VALIDATION_REQUIRED

`ROLLBACK_REJECTED`は、データ管理機能が固定のデータ一覧に指定した方針（policy）または下限値の参照（floor参照）に対して、機械的な不一致を検出した場合だけ返す。永続データ管理は、保存対象データの内容を解釈して、巻戻し判定の下限値や代替データへの切替可否を独自に決めない。

## 4. 不揮発メモリ全体構成と障害分離

### 4.1 内蔵MRAMと外付けSerial NOR

初期製品は次の二層構成とする。

| 媒体 | 主用途 | 障害時の基本影響 |
| --- | --- | --- |
| RA8M2内蔵MRAM | 小容量重要管理データ、起動・安全・認証・復旧・巻戻し防止・製品校正・時刻trust情報 | 使用不可時は安全な起動・通常操作を保証できない可能性が高く、異常管理/システム状態管理が安全側へ判断 |
| 外付けSerial NOR 8 MiB以上 | OTA image、log、設定package、Wi-Fi設定、管理保守用大容量データ | 対象機能を縮退。内蔵重要情報と安全機能が正常ならBLE基本操作を一律禁止しない |

### 4.2 内蔵MRAM論理境界

1 MiB内蔵MRAMの論理budgetを次とする。

| 領域 | 基本budget |
| --- | ---: |
| 固定ブート・復旧 executable＋trust | 最大224 KiB |
| `PERSIST_CRITICAL` | 32 KiB |
| PRIMARY本体アプリケーション slot | 最大768 KiB |

`PERSIST_CRITICAL`は通常OTAのPRIMARY書込み対象外とする。

32 KiB総量は現時点の基本設計値である。後続製品情報管理/時刻管理により、Unit Product Data最大4 KiB logical snapshotの旧正常copy保持、`highestCommittedProductDataRevision`、Trusted Time Record／Time Update Record合計1 KiB以下、Wi-Fi key/revision metadata、OTA result report state等が追加されたため、旧版の「4/4/8/8/8 KiBを固定分割する」方式は採用しない。

詳細設計freeze前に第6章の全critical logical datasetについて、header、CRC/HMAC、二面copy、journal、commit marker、alignmentを含む**32 KiB physical capacity proof**を実施する。32 KiBへ収まらない場合、critical dataを外付けへ安易に移動せず、fixed boot 224 KiB／PRIMARY 768 KiB／critical 32 KiBのメモリ容量の配分を本基本設計へ戻して見直す。

### 4.3 障害分離

次を満たす。

- log ring満杯でcritical metadata領域を消費しない。
- OTAの候補領域が破損しても、所有者・認証情報を破損させない。
- Wi-Fi設定破損でSecurityGenやfactoryResetStateを破損させない。
- 外付けSerial NOR全体使用不可でも、内蔵critical datasetを読出せる。
- 内蔵critical dataset破損を外付けlogから推測して正常扱いしない。
- product/calibrationまたはtime trust異常を古い正常copyへ暗黙fallbackして隠さない。

### 4.4 partition map

外付けSerial NORのpartition mapはhardware profileおよびpersistent layout versionに対応付けた固定layoutとし、通常運用中に動的変更しない。

firmwareは自機hardware profileに対応するlayoutだけを使用する。

## 5. 永続化対象データの分類と配置

### 5.1 データclass

永続datasetを次のclassへ分類する。

| class | 例 | 主媒体 |
| --- | --- | --- |
| CRITICAL_BOOT | 起動・終了識別、factoryResetState、boot/recovery handoff参照 | MRAM |
| CRITICAL_AUTH | 所有者登録情報、authorizationRevision、利用者認証情報のデータ本体・参照 | MRAM |
| CRITICAL_ANTIROLLBACK | SecurityGen、highestCommittedGeneration、highestCommittedProductDataRevision、bootInstanceId等 | MRAM |
| CRITICAL_FAULT | 再起動後も必要な異常・復旧情報 | MRAM |
| PRODUCT_CRITICAL | Unit Product Data、校正、製造情報、保持対象device key/trust metadata | MRAM |
| TIME_CRITICAL | Trusted Time Record、Time Update Record | MRAM |
| BULK_CONFIG | ACTIVE/PREVIOUS/STAGED設定package、AES-GCM保護済みWi-Fi設定 | Serial NOR |
| BULK_LOG | IMPORTANT/NORMAL event log、未送信・lifecycle metadata | Serial NOR |
| BULK_OTA | CANDIDATE、PREVIOUS firmware image | Serial NOR |
| PRODUCT_AUX | certificate chain等の比較的大きい製品・security補助情報 | Serial NORまたは製品構成で定める |

Device IDは製品情報管理に従いRA8M2 128 bit Unique IDから、同じUnique IDには常に同じ値が得られる規則で生成し、文字列を基準となる永続データとして重複保存しない。

### 5.2 配置判断原則

次のいずれかに該当する小容量情報はMRAMを優先する。

- 外付けNVM障害時にも安全起動判断へ必要
- 正常操作可否または認証可否へ直接影響
- OTA recovery判定へ必要
- 過去値復元による巻戻しを避ける必要がある
- 製品校正・時刻trust等、破損時に古い値へ暗黙fallbackしてはならない
- 低電圧終了で短時間に確定保存する必要がある

大容量・頻繁書込み・循環保存・image dataは外付けSerial NORへ配置する。

### 5.3 保存対象データの管理表（dataset catalog）

#### 管理する項目

詳細設計では、データ集合ごとに少なくとも次の項目を固定表として管理する。

| 項目 | 管理する内容 |
| --- | --- |
| `datasetId` | データ集合の識別子 |
| `semanticOwnerFunctionId` | データの意味や更新条件を管理する機能 |
| `commitRequesterFunctionId` | 保存の確定を要求する機能 |
| `physicalWriter` | 物理的な書込みを実行する主体。本体アプリケーション側のPERSIST、または固定ブートの最小保存経路 |
| `storageClass` | 保存先の区分 |
| `logicalSlot` | 機能上の意味を持つ保存枠 |
| `maxPayloadLength` | データ本体の最大長 |
| `formatVersion` | データ形式の版 |
| `updateUnit` | 更新単位 |
| `atomicityMethod` | 原子的更新の方式 |
| `persistRevision`規則 | 保存処理の世代を管理する規則 |
| `ownerSemanticRevisionField`または`NONE` | データ内容の版・世代を保持する項目との対応。該当項目がない場合は`NONE` |
| `confidentialityClass` | 機密性の区分 |
| `integrityMethod` | 完全性を確認する方式 |
| `integrityProvider` | 完全性の確認を担当する機能 |
| `rollbackSensitive` | 古い版・世代への巻戻しに制約があるか |
| `rollbackPolicyOwnerFunctionId` | 巻戻し・代替データへの切替えの方針を判断する機能 |
| `rollbackFloorDataset`または`NONE` | 巻戻し判定の下限値を保持するデータ集合。該当しない場合は`NONE` |
| `fallbackPolicy` | 使用する複製や代替データを選ぶ際の方針 |
| `factoryResetAction` | 工場初期化時の処置 |
| `bootCriticality` | 起動上の重要度 |
| アクセス主体 | データへのアクセスを行う主体 |

#### 複製の復旧と代替データへの切替え

`fallbackPolicy`は、少なくとも次の3種類を区別する。

| 値 | 意味 |
| --- | --- |
| `SAME_PERSIST_REVISION_ONLY` | 同じ`persistRevision`を持つ、物理的に冗長化した複製の使用だけを許可する |
| `OWNER_DECIDES` | PREVIOUS/FACTORYなどの代替データを使用してよいかを、データ管理機能が判断する |
| `NO_OLDER_SEMANTIC_REVISION` | 古いデータ内容の版・世代へ戻さない |

永続データ管理機能は、上記の共通の定義と、記憶媒体上での処理を担当する。
次の判断は、`rollbackPolicyOwnerFunctionId`で示すデータ管理機能が行う。

- 各データ集合へ、どの方針を適用するか。
- どの値を巻戻し判定の下限値とするか。
- 代替値を、機能が現在使用するデータとして採用してよいか。

#### 検証方式と担当機能

検証方式を表す`integrityMethod`と、検証担当を表す`integrityProvider`を分けて管理する。

| 検証内容 | 担当機能 |
| --- | --- |
| CRCによる確認 | 永続データ管理 |
| HMAC／AEAD／署名などの暗号学的検証 | セキュリティ管理 |
| データ本体の構造、プロファイル、データ内容の版・世代の検証 | 各データ管理機能 |

初期製品では、この管理表を設計・ビルド時に固定する。実行中に変更できる汎用の属性表としては扱わない。

## 6. 内蔵MRAM重要永続領域

### 6.1 `PERSIST_CRITICAL`対象

`PERSIST_CRITICAL`総量は32 KiBとする。旧版の物理group別4/4/8/8/8 KiB固定割当ては、後続製品情報管理/時刻管理のcritical data追加後は使用しない。

32 KiB内へ少なくとも次のlogical datasetを収容する。

- `CRIT_MIN_SAVE`：minimum save。logical payload最大1 KiB、二面copyを含む物理budget 4 KiBを維持
- system lifecycle／factoryResetState／管理transaction metadata
- 所有者・端末登録情報、authorizationRevision、ownerDataRevision、保護された認証情報への参照・データ本体
- SecurityGen、`highestCommittedGeneration`、`highestCommittedProductDataRevision`、bootInstanceId等のrollback-sensitive metadata
- セキュリティ管理がcritical保存を要求するWrapped Key参照、state MAC対象metadata、VPS device trust関連の小容量record
- 製品情報管理のUnit Product Data：logical payload最大4 KiB、旧正常copy保持、CRC32C＋K_SEC_STATE_MAC
- 時刻管理のTrusted Time Record＋Time Update Record：logical合計1 KiB以下、CRC32C＋K_SEC_STATE_MAC
- OTA更新/固定ブート・復旧のOTA boot/recovery state：`internalPhase`、`recoveryEligible`、`INSTALL_REQUESTED`、`PRIMARY_OVERWRITE_STARTED`、`TRIAL_ARMED`、`trialAttempted`、`TRIAL_BOOT_VALIDATED`、`otaSettlementPending`、`RECOVERY_REQUIRED`、固定ブート・復旧のrecovery execution status、`RECOVERY_BOOT_PENDING`、local OTA final result、`otaResultReportState`等
- 異常管理/起動・終了・再起動管理が再起動後にも必要とするfault/recovery/reset-loop state

各logical datasetの最終physical slot sizeは第4.2節のcapacity proofで固定する。32 KiBを超える結果になった場合は詳細設計だけで削減・外付け移動せず本書を見直す。

### 6.2 logical datasetの独立性

同一physical area内のSecurityGen、highestCommittedGeneration、productDataRevision、time record、bootInstanceId、fault state等は独立logical datasetとして管理し、一つの値更新だけを理由として無関係なデータ集合の内容を更新しない。

工場出荷状態への初期化や所有者削除等でも、物理領域単位で全消去しない。データ一覧で削除対象とされた論理レコードだけを無効化する。

### 6.3 二重copy・journal

旧正常値保持が必要なsmall datasetは各logical datasetについて二重copyまたは同等方式を持つ。

新しい保存用複製への書込みを確定するまで、確定済みの旧複製を維持する。ただし、データを管理する機能が新しい版への更新をいったん確定した後は、その複製が破損したという理由だけで古い版を現在有効なデータへ戻してはならないデータ集合がある。第10.4節の代替データの選択規則に従う。

### 6.4 単調counter

SecurityGen、highestCommittedGeneration、highestCommittedProductDataRevision、bootInstanceIdその他の単調値は、各管理元の設計が定める型・予約値・周回禁止の規則に従う。

高頻度に更新するbootInstanceIdは、同一wordを毎起動で単純上書きする方式ではなく、固定長append journalまたは同等のwrite distribution方式を使用する。journal満了時のcompactionは、旧正常counterを失わない二面方式で行う。

値上限へ到達した場合、0または小さい値へwrapして継続せずその情報を管理する機能へ更新不能を返す。

### 6.5 MRAM領域保護

通常applicationの汎用write APIから、固定ブート領域および`PERSIST_CRITICAL`外へ書き込めないrange guardを設ける。

通常OTAのPRIMARY書込みから`PERSIST_CRITICAL`を除外する。

TrustZone/MPU、Access Window、DLM等の最終使用方法はセキュリティ管理/固定ブート・復旧/hardware設計と整合して固定する。

### 6.6 固定ブートからのminimum access path

固定ブート・復旧がapplication起動前に起動可否・起動先の判断、install、trial、recoveryへ必要なcritical recordを読出し・原子的commitできるよう、`CRIT_OTA_BOOT`相当のlogical dataset、SecurityGen／K_SEC_STATE_MAC関連metadataおよび必要なboot stateにはminimum read/commit pathを設ける。

このminimum pathは本体アプリケーション側PERSIST worker、外付けBULK NVM全体初期化または通常task schedulerの確立を前提としない。record envelope、二重copy、完全性確認およびcommit規則は本体アプリケーション側と共通化し、fixed bootだけが異なる保存形式を持たない。

## 7. 外付けSerial NOR論理領域

### 7.1 容量

OTA更新で確定した製品外付けSerial NOR **8 MiB以上**を前提とする。

EK-RA8M2搭載64 MiB品を製品必須とはしない。

### 7.2 8 MiB時の論理budget

最小8 MiB構成では次を基本budgetとする。

| partition | 基本容量 | 主用途 |
| --- | ---: | --- |
| `OTA_CANDIDATE` | 1 MiB | 更新候補image |
| `OTA_PREVIOUS` | 1 MiB | 直前正常image |
| `IMPORTANT_LOG_RING` | 256 KiB | important event log |
| `NORMAL_LOG_RING` | 768 KiB | normal event log |
| `CONFIG_STORE` | 256 KiB | ACTIVE/PREVIOUS/STAGED＋metadata。各logical slotの二重copy余裕を含む |
| `WIFI_STORE` | 64 KiB | AES-256-GCM保護済みWi-Fi設定blob |
| `LOG_META_JOURNAL` | 64 KiB | ring cursor、lifecycle、sent state等 |
| `PRODUCT_SEC_AUX` | 256 KiB | certificate chain等の比較的大きい製品・security補助data |
| `BULK_RESERVE` | 残容量 | erase alignment、将来評価余裕、partition予備 |

8 MiB構成では上記固定用途が3.625 MiBであり、`BULK_RESERVE`は4.375 MiBとなる。

ログ・診断の評価用トレースは64 KiB RAMのみであり、通常運用でtrace用不揮発partitionを設けない。

### 7.3 alignment

各partitionは採用Serial NORのerase boundaryに合わせる。

上表の容量を64 KiB単位で構成できるようにし、4 KiB sector対応品または64 KiB block単位品のどちらでも詳細layoutを作成可能とする。

### 7.4 partition header

各partitionには少なくとも次を識別できるheaderまたは固定design情報を持つ。

- partitionId
- persistentLayoutVersion
- hardwareProfileId
- logicalCapacity
- dataset type

partition header破損だけを理由として別partitionへ書き込まない。

### 7.5 動的再配分禁止

runtimeにlog領域をOTA領域へ拡張する等のdynamic repartitionを行わない。

容量不足時は20章の用途別policyで処理する。

## 8. 共通レコード・形式バージョン・完全性

### 8.1 共通管理情報（envelope）

#### 共通管理情報の項目

PERSISTが管理する小容量レコードには、論理的に次の共通管理情報を持たせる。

- magic
- datasetId
- envelopeVersion
- datasetFormatVersion
- headerLength
- payloadLength
- physicalCopyId
- `persistRevision`
- transactionCorrelationId
- flags
- payloadCRC32Cまたはセキュリティ保護結果への参照
- headerCRC32C
- 保存確定を示す印（commit marker）

#### 保存処理の世代とデータ内容の版・世代

次の二つは管理する目的が異なるため、別々に扱う。

| 区分 | 管理する機能 | 更新する契機 | 使用目的 |
| --- | --- | --- | --- |
| 保存処理の世代（`persistRevision`） | 永続データ管理（PERSIST） | `(datasetId, logicalSlot)`ごとに、新しい物理保存が確定したとき | A/Bの複製の選択と、保存要求の競合検出 |
| データ内容の版・世代（semantic revision） | 各データ管理機能 | 各機能が定めるデータ更新・確定の規則に従う | データの機能上の新旧や、使用してよい内容かの判断 |

PERSISTは、データ内容の版・世代を生成・増加・解釈しない。両方の値が一致することも前提にしない。

#### `persistRevision`の型と上限

`persistRevision`は64ビット符号なし整数（uint64）とし、0は無効値とする。
PERSISTが、新しい物理保存の確定ごとに単調増加させる。

最大値に達した場合は、値を0や小さい値へ戻して使い続けず、更新不能を返す。

#### データ内容の版・世代の保持先

データ内容の版・世代は、データ本体、またはデータ管理機能が管理する処理の管理情報へ保持する。
第5.3節の管理表にある`ownerSemanticRevisionField`で、対応する項目を明示する。

各項目の具体的な配置位置、配置境界の揃え方、バイトの並び順は、詳細設計で固定する。

### 8.2 format version

`envelopeVersion`と`datasetFormatVersion`を分離する。

PERSISTは保存用のエンベロープを解釈し、データ本体の内容を表す形式はデータ管理機能が判断する。

unsupported datasetFormatVersionを旧versionと推測して使用しない。

### 8.3 偶発破損検出

暗号学的保護を要求しないsmall metadataはCRC32Cを基本とする。

ログ・診断のevent recordはログ・診断で定めた128 byte record＋CRC32Cをそのまま保持し、PERSISTで別payload形式へ変換しない。

### 8.4 security-sensitive data

機密性・認証完全性が必要なpayloadはセキュリティ管理がAEAD、HMAC、Wrapped Keyまたは同等方式で保護する。

PERSISTのCRCはmedia/torn-write検出補助であり、暗号学的改ざん検出の代替としない。

PERSISTは認証タグを独自に再計算せず、セキュリティ管理／データ管理機能が検証できるバイト列を、そのまま保持する。

### 8.5 commit marker

新しいレコードのcommit markerは、次の確認がすべて正常に完了した後、最後に確定する。

- 永続データ管理によるエンベロープ・長さ・CRC・読戻しの確認
- 必要な場合の、セキュリティ管理による暗号学的検証
- データ管理機能による内容の検証と、保存確定の許可

commit marker未確定recordはtorn writeとして使用しない。

commit markerは**保存レコードの完成**を示す。複数のデータ集合にまたがる一連の更新について、管理元機能によるGLOBAL_COMMITまで成立したことを示すものではない。

---

## 9. 永続データ要求・排他・優先制御

### 9.1 媒体ごとの書込み主体を一つに定める

MRAMと外付けSerial NORの各mediaについて、同時に複数のprogram/eraseを実行しない。

PERSISTがmedia accessを一元調停する。fixed boot minimum pathとapplication PERSIST workerは同時実行されない起動phaseで使用し、同一record formatと排他規則を共有する。

### 9.2 priority class

| priority | 主な処理 |
| --- | --- |
| P0 CRITICAL | minimum save、factoryResetState、OTA trial/recovery metadata、SecurityGen、time update commit等 |
| P1 MANAGEMENT | 所有者・認証情報の更新確定、設定の更新確定、Wi-Fi設定の更新確定、Product Data更新、重要な状態の保存 |
| P2 IMPORTANT | IMPORTANT log、重要diagnostic metadata |
| P3 BULK | NORMAL log、OTA image chunk、background check |

緊急停止等の安全task自体はPERSIST queueよりさらに上位であり、PERSIST完了を待たない。

### 9.3 固定queue

初期基本値を次とする。

| queue | slot数 |
| --- | ---: |
| MRAM request | 8 |
| Serial NOR request | 16 |

queue full時に呼出元を無期限blockしない。

P0要求をP3大量要求だけで枯渇させないため、P0/P1用予約slotを持つ。

### 9.4 bulk処理のchunk化

OTA copy、log erase等の長時間処理はerase/program単位で分割し、各単位間に高priority request受付点を設ける。

ただし進行中erase/programを電気的に安全でない方法で強制中断しない。

### 9.5 expected persist revision

データ管理機能が`expectedPersistRevision`を指定した場合、現在確定済みの`persistRevision`と一致しなければ、新たな書込みを開始せず`REVISION_MISMATCH`を返す。READ／QUERYの結果には、後続の比較付き書込みに使用できる現在の`persistRevision`を含める。

PERSISTは新しい物理書込みの確定時に、次の`persistRevision`を付与する。ただし、データ管理機能が管理する内容の版を生成・増加・解釈しない。CRCが正常であることだけを根拠として、その機能が管理する現在有効なデータ内容・状態を変更しない。

## 10. 原子的更新方式

### 10.1 小容量の重要データ集合

基本手順を次のとおりとする。

1. データ管理機能が、直前のREAD／QUERYで取得した`expectedPersistRevision`と、新しいデータ本体に含まれる内容の版・対象処理との対応情報を指定する。
2. PERSISTが現在の`persistRevision`を照合し、使用していない保存用複製を選ぶ。
3. PERSISTが、次の`persistRevision`を持つ新しいヘッダを未確定状態で書き込む。
4. PERSISTが、データ管理機能から受け取ったデータ本体のバイト列を、そのまま書き込む。
5. PERSISTが、CRCと、データ管理機能／セキュリティ管理から受け取った認証タグへの参照を含む、完全性確認用の情報を書き込む。
6. PERSISTがレコード全体を読み戻す。
7. PERSISTがエンベロープ、長さ、CRCおよび`persistRevision`を検証する。
8. セキュリティ上重要なデータでは、セキュリティ管理が読み戻したバイト列のAEAD／HMAC／状態保護用MACを検証する。
9. データ管理機能が、データ本体の構造、プロファイル、内容の版、巻戻し防止の下限値、および対象処理との対応関係を検証し、そのレコードの保存確定を許可する。
10. PERSISTが最後にcommit markerを確定する。
11. PERSISTがcommit markerを読み戻す。
12. データ管理機能へ、新しい物理レコードの保存確定が成功したことと、新しい`persistRevision`を返す。
13. データ管理機能が一連の更新処理を確定するまで、旧データの保存用複製を再利用しない。

### 10.2 外付けsmall dataset

CONFIG_STORE、WIFI_STORE等も、各機能が必要とするlogical slot単位で二面または固定slotを使って原子的更新する。

全外付けdatasetへ共通A/B DBを設けず、設定管理/Wi-Fi接続の論理要件に合わせた専用slotを使用する。

### 10.3 複数のデータ集合にまたがる更新処理

PERSISTは、全機能に共通する分散トランザクション管理機構を設けない。

複数の論理データ集合または媒体を、機能上の一つの更新単位として扱う場合は、データ管理機能が処理順序と復旧規則を定める。PERSISTは、その機能が管理する確定待ち状態・完了状態の管理情報を原子的に保存する。

代表例は次のとおりである。

- 設定管理：`CONFIG_COMMIT_PENDING` → CONFIG_STOREのACTIVE/PREVIOUS確定 → MRAMの`highestCommittedGeneration`を単調に進めて保存確定 → 確定待ち状態の完了処理
- 製品情報管理：Unit Product Dataの候補 → Product Data更新の確定待ち状態 → `highestCommittedProductDataRevision`を単調に進めて保存確定 → 最新のProduct Dataを確定
- 時刻管理：Time Update RecordのPREPARED → RTC設定・読戻し → Trusted Time RecordとTime UpdateのCOMMITTED/ABORTED
- 所有者・操作端末管理／セキュリティ管理：`RESET_PENDING` → 所有者情報・Wi-Fi・セキュリティ等のデータ集合の無効化・鍵等の更新 → `FACTORY_DEFAULT_COMPLETE`

これらを一つの物理書込みであると仮定しない。

### 10.4 起動時の複製選択と巻戻し禁止

保存用複製の選択と、データ内容を旧版へ戻せるかどうかの判断を分離する。

1. PERSISTは、commit marker、エンベロープ、長さ、CRCおよび`persistRevision`から、物理的に使用候補となるレコードを識別する。同じ`persistRevision`を持つ冗長複製が複数ある場合は、物理検証が正常な複製を使用できる。
2. 新しい物理書込みがcommit markerの確定前に中断した場合は、そのレコードを書込み途中として除外する。この場合、直前の確定済み`persistRevision`を持つレコードを、物理的な使用候補としてデータ管理機能へ返せる。
3. 異なる`persistRevision`のうち、どれを現在有効なデータとして扱うか、または古い内容の版を代替として使用できるかは、データ管理機能が判断する。PERSISTは、データ一覧で指定された管理元の方針を機械的に適用し、判断材料と結果を返す。
4. **データを管理する機能が新しい版への更新をいったん確定した後は、その複製が破損したことだけを理由に古い版へ自動的に戻してはならないデータ集合がある。** 管理元が定める巻戻し防止の下限値と`fallbackPolicy`に従う。
5. SecurityGen、highestCommittedGeneration、highestCommittedProductDataRevision、所有者・認証情報の失効状態、Wi-Fi認証情報の版等は、小さい値の旧版へ戻すことで、失効済みの状態や古い校正・設定を復活させない。
6. Wi-Fi接続の設定では、最新の`wifiCredentialRevision`について認証・復号・版の確認に失敗しても、過去の認証情報へ自動的に戻さない。
7. 製品情報管理のProduct Dataでは、最新の確定済みの版が正常であることを確認できない場合、古い校正スナップショットを自動採用しない。
8. 設定管理の設定では、代替としてPREVIOUS/FACTORYの使用を許可する場合でも、`highestCommittedGeneration`を小さくしない。
9. 所有者情報・セキュリティ情報は、所有者・操作端末管理／セキュリティ管理が定める失効・ownerDataRevisionの契約に従う。古いスナップショットを使って失効済み端末をACTIVEへ戻さない。
10. 時刻管理の時刻更新は、PREPAREDからの復旧規則に従う。古いTrusted Time Recordを無条件に採用してTIME_TRUSTEDへ戻さない。

どの複製を現在有効なデータとして扱えるかをデータ管理機能が判断できない場合、PERSISTは古い複製を独自に選ばず、`CORRUPT`／`OWNER_VALIDATION_REQUIRED`等を返す。

## 11. 起動時初期化・読出し・中断復旧

### 11.1 起動時優先順

application起動後の基本順序を次とする。ただし固定ブート・復旧のfixed bootが必要とするcritical stateはapplication前に第6.6節minimum pathで確認済みとする。

1. MRAM access／PERSIST critical interface初期化
2. system/factory reset state、Security rollback state、OTA/boot handoff state確認
3. 所有者・認証に関する重要状態の確認
4. Unit Product Data／`highestCommittedProductDataRevision`確認
5. Trusted Time Record／Time Update Record確認
6. minimum save・前回正常終了識別確認
7. factory reset、CONFIG_COMMIT_PENDING、Product Data pending、Time Update PREPARED、OTA settlement/recovery等の未完了transaction識別
8. 外付けSerial NOR interface初期化
9. persistent layout/partition header確認
10. CONFIG_STORE/WIFI_STORE等のsmall bulk領域確認
11. LOG_META_JOURNAL確認
12. OTA bulk領域は必要時のみ確認

PERSISTは未完了の処理があることを各管理元へ通知する。再開・中止・代替データの使用について、機能上の条件に基づく判断は、その情報を管理する機能へ委ねる。

### 11.2 起動完了を待たない領域

通常起動完了に次の全件scanを要求しない。

- NORMAL_LOG_RING全件
- IMPORTANT_LOG_RING全件
- OTA_CANDIDATE全image hash
- OTA_PREVIOUS全image hash
- 未使用BULK_RESERVE

OTA recoveryが必要な場合だけOTA更新/固定ブート・復旧の手順に従って必要imageを検証する。

### 11.3 log bounded recovery

ログ・診断のring metadataの最新正常checkpointを読出した後、checkpoint以降の最大32 record相当をbounded scanして、metadata更新前にcommittedしたeventを回収する方式を基本とする。

全1 MiB ring scanを通常起動必須処理としない。

checkpoint間隔32 recordは評価確定待ちのログ・診断/永続データ管理基本設計で管理する値であり、write enduranceと起動時間を実機評価する。

### 11.4 起動結果

PERSISTは少なくとも次を、起動・終了・再起動管理／異常管理および各データ管理機能へ提供する。

- CRITICAL_READY
- BULK_READY
- DEGRADED_BULK
- CRITICAL_CORRUPT
- BULK_MEDIA_UNAVAILABLE
- RESET_CONTINUATION_REQUIRED
- CONFIG_TRANSACTION_RECOVERY_REQUIRED
- PRODUCT_DATA_RECOVERY_REQUIRED
- TIME_UPDATE_RECOVERY_REQUIRED
- OTA_RECOVERY_STATE_PRESENT
- UNSUPPORTED_FORMAT

起動・通常操作可否はシステム状態管理/異常管理および各データ管理機能が最終判断する。

## 12. 通常終了・低電圧終了・電源断との連携

### 12.1 通常終了

通常終了で保存すべきpayloadは各データ管理機能が決定する。

起動・終了・再起動管理は保存要否と保存状態を集約し、PERSISTへ必須保存要求を発行する。

PERSISTは必須保存結果を起動・終了・再起動管理へ返す。

正常終了識別情報は、正常終了に必要な必須保存が完了した後にだけcommitする。

### 12.2 minimum save

バッテリー・電気安全監視/起動・終了・再起動管理で確定済みの低電圧終了契約に従い、終了時最小保存は`CRIT_MIN_SAVE`へ保存する。

minimum save 保存対象データ本体の容量上限を**1 KiB**とし、二面copyを含む物理4 KiB budget内で管理する。

保存対象は起動・終了・再起動管理が各機能から集約した固定長情報だけとし、log ring、設定package全体、OTA image、Product Data全体等のbulk／大payloadを含めない。

### 12.3 200 ms上限

起動・終了・再起動管理/バッテリー・電気安全監視が同一の低電圧終了識別子、電源条件定義世代、監視更新世代について開始可能と確認した場合だけminimum saveを開始する。

開始後、**200 ms以内**に書込み、読戻し、完全性確認を行い、保存の確定結果を得る。この時間上限は基本設計で管理する。

バッテリー・電気安全監視から同じ終了識別子で継続不可通知を受けた場合、まだcommit前なら新recordを正常確定せず中止する。

追加retryを行う場合も200 ms全体上限を延長しない。

### 12.4 予期しない電源断

突然の電源断では、新しい任意dataを保存できることを前提としない。

次回起動では、確定済みの物理レコードと、データ管理機能が管理する一連の処理の状態から、使用できるデータを再判定する。

安全処理または強制電源遮断を「ログを書けていない」「metadataを完了できない」ことを理由に遅延させない。

## 13. システム状態・異常・起動・時刻管理データ

### 13.1 system lifecycle

`PERSIST_CRITICAL`へ、データ管理機能が必要とする次のsmall情報を保持可能とする。

- 前回正常終了識別
- 終了理由・再起動理由の引継ぎ
- factoryResetState
- management/reset correlation情報
- boot/recovery handoff参照

製品情報管理のProduct DescriptorやDevice IDについて、PERSISTが別の管理元にならない。

### 13.2 fault/recovery

異常管理が再起動後にも必要と判断したfault/recovery stateは独立logical datasetとして保持する。

過去ログが存在するだけでcurrent faultを復元しない。

### 13.3 reset loop・bootInstanceId

異常管理/起動・終了・再起動管理が必要とする再起動回数、起動失敗継続情報等は固定上限counter/recordとして保持できる。

ログ・診断の`bootInstanceId`はuint64の単調counterとしてfactory resetでも巻き戻さず、append journal等でwriteを分散する。wrapして0へ戻さない。

自動復旧回数の意味・reset条件は異常管理/起動・終了・再起動管理が所有する。

### 13.4 時刻管理の時刻trust record

時刻管理のTrusted Time RecordおよびTime Update Recordを`PERSIST_CRITICAL`へ保持する。

- 両recordのlogical data合計上限は時刻管理の1 KiB以下を使用する。
- CRC32Cに加えてセキュリティ管理の`K_SEC_STATE_MAC`によるHMACを保持する。
- Time Update RecordのPREPARED/COMMITTED/ABORTEDとTrusted Time candidateを同一`updateTransactionId`で対応付ける。
- PERSISTはRTC値との整合を判断せず、時刻管理が起動時にresume/abort/TIME_UNTRUSTEDを決定する。
- 所有者再登録、工場出荷状態への初期化、OTAだけを理由に、Trusted Time Recordを削除しない。

## 14. 所有者・操作端末・認証関連データ

### 14.1 所有者情報のデータ集合

所有者・操作端末管理の所有者登録情報を、`PERSIST_CRITICAL`へ保存する。

少なくとも次を、一つの所有者情報のスナップショットとして原子的に扱えるようにする。

- 所有者の状態
- OWNER/GENERAL_1/GENERAL_2 slot情報
- terminalRegistrationId
- role
- registrationState
- authorizationRevision
- credentialRefまたはprotected credential blob
- ownerDataRevision
- recovery verifier metadata
- revocation情報

### 14.2 所有者登録情報の保存確定

所有者・操作端末管理が候補の所有者データを確定する場合、次の役割を分ける。

- 所有者・操作端末管理は、所有者データの内容の版である`ownerDataRevision`が期待値と一致することを確認する。
- 永続データ管理（PERSIST）は、保存処理の版が`expectedPersistRevision`と一致することを確認し、新しい所有者データのスナップショットを原子的に更新する。

PERSISTによる保存確定の成功だけを、端末の認証情報のACTIVE化やBLE利用開始と同一視しない。保存確定後の有効化と整合処理は、所有者・操作端末管理およびセキュリティ管理が定める順序に従う。

### 14.3 失効と巻戻し

一般端末の失効は、所有者・操作端末管理が定める順序に従う。REVOKEDのスナップショットを保存・確定した後に、BLE接続・認証／セキュリティ管理へ失効を公開する。

新しいownerDataRevisionで失効・削除を一度正常確定した後は、最新のスナップショットが破損したことを理由に、古いスナップショットから端末をACTIVEへ戻さない。

### 14.4 工場出荷状態への初期化の未完了状態

所有者・操作端末管理が、`factoryResetState=RESET_PENDING`、managementTransactionIdおよび次のownerDataRevisionを保存・確定する処理は、P0 CRITICALとする。

この保存確定後は、次回起動でも旧所有者情報のデータ集合を通常操作へ使用しない。この条件を所有者・操作端末管理へ通知できる状態を保持する。

## 15. Wi-Fi・VPS・製品固有・秘密情報関連データ

### 15.1 Wi-Fi設定

Wi-Fi接続が管理するWi-Fi設定はRA8M2側に置き、物理blobは`WIFI_STORE`へ保存する。

SSID、security mode、passphraseその他Wi-Fi接続が定めるWi-Fi設定全体をセキュリティ管理がAES-256-GCMで保護したrecordとして保存する。PERSISTはSSIDだけを平文fieldとして別管理しない。

新blobのcommit成功前に旧committed blobを失わない。ただし新しい`wifiCredentialRevision`が現在有効なデータとして確定した後、latest blobが認証/decrypt/revision不正となっても過去Wi-Fi設定へ自動fallbackしない。

### 15.2 Wi-Fi security metadata

セキュリティ管理が生成する次のcritical metadataを`PERSIST_CRITICAL`へ保存可能とする。

- `K_WIFI_STORE` AES Wrapped Keyまたはその参照
- `wifiNoncePrefix`
- uint64 `wifiCredentialRevision`
- key/revision format version
- state MAC／commit metadata

`nonce = wifiNoncePrefix[32] || wifiCredentialRevision[64]`の一意性を壊すようなrevision巻戻しをPERSIST側で行わない。

### 15.3 VPS device information

Device ID文字列は製品情報管理がMCU Unique IDから生成するためPERSISTへ基準となる値として保存しない。

工場出荷状態への初期化後も保持する小容量のデバイス鍵参照、ラップされたVPSデバイス秘密鍵、信頼の基点の版・状態等は、所有者・端末情報の削除対象へ混在させない。セキュリティ管理／VPS接続・デバイス認証が指定する、保持対象の重要な論理データ集合へ配置する。

certificate chain等の比較的大きい非秘密／保護補助dataは`PRODUCT_SEC_AUX`へ配置可能とする。

### 15.4 製品情報管理のUnit Product Data

製品情報管理のUnit Product Dataはlogical payload最大4 KiBの一つのsnapshotとして`PERSIST_CRITICAL`へ保存する。

- CRC32Cおよびセキュリティ管理の`K_SEC_STATE_MAC` HMACを保持する。
- `productDataRevision`と別critical metadata `highestCommittedProductDataRevision`を保持する。
- latest revision破損時に古い校正へ暗黙fallbackしない。
- 所有者再登録、工場出荷状態への初期化、OTAだけを理由に、削除・巻戻ししない。

製品情報管理が一組の製品情報を分割せずに更新できるようにするため、PERSISTはProduct Data candidate、old/new revision参照およびpending/finalize metadataを保存可能とする。snapshotとhighest revisionを一つの物理writeと仮定しない。

### 15.5 running firmware identityとの分離

製品情報管理のrunning firmware identityの取得元は実行中signed image metadataであり、PERSISTが別の「現在のfirmware identity」を生成しない。

OTA更新が必要とする「正常確認済み現在／candidate/previous」のOTA role/settlement metadataだけを`CRIT_OTA_BOOT`側へ保持する。

## 16. 設定管理データ

### 16.1 FACTORY

設定管理のFACTORY設定は署名済みfirmware/product profile側の値を基準とし、通常書換え可能なSerial NORをFACTORY設定の唯一の取得元にしない。

### 16.2 CONFIG_STORE

CONFIG_STOREは**256 KiB**とし、次のphysical budgetを基本とする。

| area | physical budget | 保存対象データ本体の容量上限 | 主用途 |
| --- | ---: | ---: | --- |
| ACTIVE_AREA | 64 KiB | 16 KiB | ACTIVEの二重copy、header、erase alignment |
| PREVIOUS_AREA | 64 KiB | 16 KiB | PREVIOUSの二重copy、header、erase alignment |
| STAGED_AREA | 64 KiB | 16 KiB | STAGEDの二重copy、header、erase alignment |
| CONFIG_META_AREA | 64 KiB | small | slot関係、revision、`CONFIG_COMMIT_PENDING`等 |

### 16.3 STAGEDとapply前保存

設定管理に従い、単なる適用条件待ちcandidateはRAMに保持し、再起動をまたぐqueueとしない。

全PREPARE成功後、APPLY直前の取引用candidateだけをSTAGED_AREAへ永続保存する。起動時に残存STAGEDを自動ACTIVE化しない。

### 16.4 ACTIVE/PREVIOUSとhighestCommittedGeneration

設定管理が定める更新の確定順序を次のように支援する。

1. 設定管理の要求で旧ACTIVE/PREVIOUS参照、新STAGED、new generation、configApplyIdを含む`CONFIG_COMMIT_PENDING`をatomic保存する。
2. CONFIG_STORE内でACTIVE/PREVIOUS slot関係をatomic metadata updateする。
3. 設定管理が新ACTIVE candidateをHMAC/generation込みで再確認する。
4. MRAM側`highestCommittedGeneration`をセキュリティ管理のstate MAC付きで単調commitする。
5. CONFIG_STORE側pendingをfinalizeする。
6. その後設定管理が各機能へGLOBAL_COMMITする。

CONFIG_STOREとMRAM counterを一つの物理原子writeであると仮定しない。

### 16.5 起動時CONFIG_COMMIT_PENDING復旧

起動時に`CONFIG_COMMIT_PENDING`が残っている場合、PERSISTはpending metadata、旧/new slot参照、各record commit状態、現在の`highestCommittedGeneration`を設定管理へ提供する。

設定管理が機能上の条件に基づく再開・切戻し・代替データ利用を判断する。PERSISTが旧ACTIVEを自動currentへ戻したり、highestCommittedGenerationを小さくしたりしない。

### 16.6 CONFIG_STORE全体障害

CONFIG_STOREを使用できない場合、設定管理がPREVIOUS/FACTORY等の安全な代替設定を使用可能か判断する。

PREVIOUS/FACTORY fallbackを行っても`highestCommittedGeneration`を小さくしない。PERSISTは古い破損packageを推測復元しない。

## 17. ログ・未送信ログ・診断管理データ

### 17.1 log partition

ログ・診断の設計を使用する。

- IMPORTANT_LOG_RING：256 KiB
- NORMAL_LOG_RING：768 KiB
- 1 event record：128 byte
- 各record：CRC32C

### 17.2 record不変性

ログ・診断が内容を変更しないと定めたイベントデータ本体のレコードは、保存確定後も、そのバイト列を原則として変更しない。

SENT/UNSENT、data lifecycle等の可変状態をrecord payloadへ上書きしてCRCを崩さず、`LOG_META_JOURNAL`の固定長state journalまたはbitmapへ分離する。

### 17.3 ring metadata

最低限次を保持する。

- write cursor
- oldest valid cursor
- valid count
- sent/unsent state
- lifecycle state
- droppedNormalCount
- droppedImportantCount
- importantLogLossCount
- corruptionCount
- last successful batch情報

### 17.4 metadata checkpoint

write cursor等のcheckpointを最大32 record間隔でcommitする初期方式とする。

power loss後は最新checkpoint以降をbounded scanし、正常committed recordを回収する。

### 17.5 SENT更新

VPS接続・デバイス認証はVPS ACKのtransport evidenceをログ・診断へ返す。ログ・診断が`logBatchId`と受領対象`logId`を照合してSENT遷移を判断し、対象`logId`を明示したmetadata更新をPERSISTへ要求する。PERSISTはACKの意味やSENT対象を再判定せず、ログ・診断が指定したSENT metadataだけを物理的にcommitする。

ログ・診断の要求に従ってbatch単位でlifecycle journalをまとめて更新し、recordごとの不要なmetadata rewriteを抑制する。

OTA更新のOTA result APIの`otaResultReportState`はログ・診断のevent logのSENT/UNSENTとは別datasetとして扱う。

### 17.6 工場初期化

公開用システム要求仕様「19. データ・プライバシー管理」/ログ・診断で削除対象となった未送信logは、RESET_PENDING後に`RESET_DELETE_PENDING`または同等の送信禁止stateへ先に移し、新しいVPS batchへ含めない。

物理消去完了前でも送信禁止を維持する。

`bootInstanceId`は利用者log本体と分離した単調counterとしてfactory resetで巻き戻さない。

### 17.7 trace

ログ・診断の初期製品では評価traceは64 KiB RAMのみであり、通常運用で不揮発保存しない。

このため初版ではtrace用Serial NOR partitionを設けない。

## 18. OTA更新候補・直前正常FW・OTA管理情報

### 18.1 image領域

OTA更新に従い次を独立partitionとする。

- OTA_CANDIDATE：1 MiB
- OTA_PREVIOUS：1 MiB

一方のerase/programが他方を消去しない境界とする。

### 18.2 OTA management

boot/recoveryに必須なsmall stateを`PERSIST_CRITICAL`へ保存する。

- otaOfferId
- otaTransactionId
- expected candidate/previous identity
- OTA更新の`internalPhase`
- OTA更新の`recoveryEligible`
- OTA更新の`INSTALL_REQUESTED`
- 固定ブート・復旧の`PRIMARY_OVERWRITE_STARTED`
- 固定ブート・復旧の`TRIAL_ARMED`
- 固定ブート・復旧の`trialAttempted`
- OTA更新の`TRIAL_BOOT_VALIDATED`
- OTA更新の`otaSettlementPending`
- `RECOVERY_REQUIRED`、固定ブート・復旧のrecovery execution status、固定ブート・復旧の`RECOVERY_BOOT_PENDING`
- local OTA final result
- `otaResultReportState`（NOT_READY/PENDING/SENT）
- 固定ブート・復旧の`BOOT_FAILURE_STATUS`、現在のboot attempt／IWDT handoff参照

固定ブート・復旧が所有する起動失敗の意味をPERSISTが再定義しない。

### 18.3 trial/recovery原子性

OTA更新/固定ブート・復旧が定める順序を維持する。

1. OTA applicationがCANDIDATE/PREVIOUS準備完了後、controlled reboot前にnon-destructive `INSTALL_REQUESTED`をcommitする。
2. controlled reboot後、fixed bootがcandidate/PREVIOUS/critical stateを再検証する。
3. fixed bootがfirst PRIMARY erase/program直前に`PRIMARY_OVERWRITE_STARTED`をcommitする。
4. commit成功後にMCUboot install triggerを設定する。
5. candidate書込み後検証成功時にTRIAL_ARMED、trialAttempted=false、otaSettlementPending=trueをcommitする。
6. candidate branch直前にtrialAttempted=trueをcommitする。
7. 起動・終了・再起動管理がApplication起動正常完了を提供し、システム状態管理がBLE接続待機状態を確定した後、OTA更新が`TRIAL_BOOT_VALIDATED`をcommitする。
8. OTA更新/セキュリティ管理によるSecurityGen更新は`TRIAL_BOOT_VALIDATED`後に行う。
9. OTA更新がlocal final resultを確定するときに`otaResultReportState=PENDING`をcommitし、VPS受領確認後だけOTA更新が`SENT`とする。
10. PREVIOUS復旧では、固定ブート・復旧がstaging、Overwriteおよび復元PRIMARY検証後に`RECOVERY_BOOT_PENDING`をcommitする。
11. 起動・終了・再起動管理の復元Application起動正常完了とシステム状態管理のBLE接続待機状態確定後、OTA更新が`RECOVERY_SUCCEEDED`および`FAILED_RECOVERED`をcommitする。
12. pre-Application terminal failureでは、固定ブート・復旧はOTA更新の定義済みschemaに従う`FAILED_RECOVERY`の代理commitだけを実行できる。

`TRIAL_ARMED=true`かつ`trialAttempted=false`は公開用システム要求仕様「15. OTA更新」の`SYS-OTA-104`上の**未実施trial**であり、reset後もcandidateの一回trialを開始できるstateとして保持する。

`trialAttempted=true`かつ未VALIDATEDでは同candidateを再trialせずPREVIOUS recoveryへ移る。

`PRIMARY_OVERWRITE_STARTED=true`でもTRIAL_ARMEDまで正常commitされていない場合はcandidateをtrial-readyと推測せずPREVIOUS recovery側へ倒す。

TRIAL_BOOT_VALIDATED後はPREVIOUSへrollbackせずcandidate settlementを継続する。

`internalPhase`はOTA更新が管理する処理段階であり、固定ブート・復旧が起動可否・起動先を決める基準にしない。`RECOVERY_BOOT_PENDING`は固定ブート・復旧が起動可否・起動先の判断に使用するマーカー、`RECOVERY_BOOT`はOTA更新が管理する処理段階として区別する。

固定ブート・復旧の復旧処理の実行状況は、実行・診断情報であり、その情報だけで自動復旧を許可しない。永続データ管理は、名称が定義された各マーカーを判断に使用する際の優先順位を決めない。OTA更新／固定ブート・復旧が指定した原子的な状態遷移を、物理的な保存処理で成立させる。

### 18.4 image取得中断

CANDIDATE途中dataはcomplete imageとしない。

initial productではdownload resumeを行わないため、途中offsetを永続resume stateとして細かく管理しない。

### 18.5 PREVIOUS保持

OTA更新が更新成功を確定するまでPREVIOUSを消去・上書きしない。

PERSISTの容量reclaim機能がPREVIOUSをlog用に再利用しない。

### 18.6 OTA result report

local OTA final resultとVPS result report状態を分離して永続保持する。

- local result確定前：NOT_READY
- local result確定後／VPS受領未確認：PENDING
- VPSが同一logical resultを正常受領：SENT

HTTP送信完了、TLS送信完了、response UNKNOWNだけでSENTとしない。

PENDING recordを詳細設計が別transaction resultで無断上書きしない。新しいOTA開始可否はOTA更新が判断する。

## 19. 工場出荷状態への初期化

### 19.1 責任分界

削除・保持・key rotation対象の意味は所有者・操作端末管理/公開用システム要求仕様「19. データ・プライバシー管理」/Wi-Fi接続/設定管理/セキュリティ管理/製品情報管理/時刻管理および各データ管理機能が決定する。

PERSISTは対象datasetのatomic state更新、invalidate/eraseを実行し結果を返す。

### 19.2 RESET_PENDING後の基本順序

工場初期化は次を基本とする。

1. 各機能PREPARE。保持／削除／rotate対象と、処理可能性を確認する。
2. 所有者・操作端末管理の要求で`factoryResetState=RESET_PENDING`、managementTransactionId、次ownerDataRevisionをMRAMへatomic commitする。
3. RESET_PENDINGを起動時に最優先で認識できるようにし、旧所有者情報のデータ集合を通常操作向けに再公開しない。
4. 公開用システム要求仕様「19. データ・プライバシー管理」/ログ・診断の対象logを送信禁止stateへ先に移す。
5. セキュリティ管理/Wi-Fi接続の契約に従い、旧Wi-Fi security stateを再利用できないよう新`K_WIFI_STORE`／wifiNoncePrefix／revision stateを安全に確立し、旧key/blobを失効・削除対象へ移す。RESET_PENDING前に不可逆key rotationを開始しない。
6. 所有者・端末認証情報、保護されたWi-Fi設定、ACTIVE/PREVIOUS/STAGED等、各データ管理機能が削除対象としたデータ集合を無効化・消去する。
7. 製品固有の保持対象データ集合と、巻戻し防止の下限値を再確認する。
8. 所有者・操作端末管理が、工場出荷状態の所有者情報のスナップショットを保存・確定する。
9. 各機能の完了結果を確認後、`FACTORY_DEFAULT_COMPLETE`をcommitする。

RESET_PENDING後に電源断した場合も、この順序で再開できる状態を保持する。旧Wi-Fi認証情報、旧所有者認証情報、初期化前の未送信ログを、通常利用できる状態へ戻さない。

### 19.3 削除・invalidate対象の代表例

少なくとも次を、各データ管理機能の指示に従って対象とする。

- 所有者・登録端末の情報
- 端末認証情報、所有者復旧用の検証情報等、利用者のセキュリティに関する状態
- Wi-Fi protected settingおよび旧Wi-Fi storage key state
- ACTIVE/PREVIOUS/STAGED等の利用者関連VPS管理設定
- 初期化前利用者に関連する未送信log

### 19.4 保持対象

少なくとも次はfactory resetだけを理由として削除・巻戻ししない。

- RA8M2 Unique ID由来Device IDの生成元（Device ID文字列の永続copyは持たない）
- 製品情報管理のProduct Descriptor、Unit Product Data、製造情報、hardware profile、calibration、`highestCommittedProductDataRevision`
- device固有VPS認証情報、VPS trust anchor等の製品固有trust情報
- 初回所有者登録用の製品固有登録秘密情報
- FACTORY設定
- running signed firmwareそのもの、およびOTA更新/セキュリティ管理が保持対象とするfirmware/Security state
- SecurityGen
- highestCommittedGeneration
- bootInstanceId
- 時刻管理のTrusted Time Record／timeTrustRevision／timeSyncGeneration等の時刻trust state
- fixed boot/recovery trust情報

製品固有のデバイス鍵と所有者・端末認証情報を、同一の論理データ集合として一括消去しない。

### 19.5 中断復旧

RESET_PENDING commit後に電源断・resetした場合、次回起動で通常operationへ戻さずfactory reset継続を要求する。

物理消去済み／未消去を推測で完了扱いせず、各datasetのlifecycle state・revision・key stateを再確認して冪等に継続する。

## 20. 記憶容量管理

### 20.1 容量確認

PERSISTは各partition／critical poolについて少なくとも次を提供する。

- logical capacity
- used amount
- free amount
- writable allocation unit有無
- reclaimable amount
- media availability
- 次のatomic updateに必要なcopy／journal余裕の有無

### 20.2 固定percentしきい値を設けない

初期製品では「残20%警告」「残10%異常」等の全partition共通固定しきい値を設けない。

用途ごとに「次の必要更新を安全に実行できるか」で容量不足を判断する。

### 20.3 用途別容量不足

| 領域 | 容量不足時の基本処理 |
| --- | --- |
| PERSIST_CRITICAL | 新しい保存確定ができないことをデータ管理機能・異常管理へ通知する。巻戻しによって意味が変わるデータを古い版へ戻さない |
| Product Data | 新校正／製造data更新を拒否。現在の最新値が正常なら維持 |
| Time Record | 新time updateを拒否／中断結果を時刻管理へ返す。古いrecordからtrustを捏造しない |
| CONFIG | 新しいSTAGED/ACTIVEへの更新を拒否する。現在使用中の設定と、巻戻し防止のための世代の下限値を維持する |
| WIFI | 新設定保存を拒否。現在の有効設定は維持。latest invalid時に古い認証情報へfallbackしない |
| NORMAL log | ログ・診断のpolicyに従い送信済み等をreclaim、不可ならnew NORMAL drop |
| IMPORTANT log | ログ・診断の優先reclaim、最終的な未送信喪失は明示count |
| OTA_CANDIDATE | OTA開始不可。PRIMARY維持 |
| OTA_PREVIOUS | OTA開始不可。PRIMARY書換え禁止 |

### 20.4 partition越境禁止

一partitionがfullでも隣接partitionへ越境して書き込まない。

BULK_RESERVEをruntimeに無断で他partitionへ動的転用しない。

## 21. 書換え寿命と書込み頻度制御

### 21.1 基本方針

採用MRAMおよびSerial NORのdatasheet enduranceを基準に、想定製品利用回数・log頻度・OTA回数・設定変更回数・時刻同期回数から寿命を見積もる。

固定70%/90%等の寿命しきい値による自動切替機能は初期製品へ追加しない。

### 21.2 MRAM

高頻度counterはappend journal等でwrite位置を分散する。

所有者登録、SecurityGen、Product Data、時刻信頼情報、工場出荷状態への初期化等、更新頻度の低いデータ集合には、二重複製、または管理元の一連の処理に適した固定保存枠の更新方式を使用する。

### 21.3 log ring

logはerase blockを循環利用し、同一blockだけへ書込み続けない。

IMPORTANT/NORMALは別partition内で各々循環する。

### 21.4 metadata

cursor metadataをeventごとに全面書換えせず、32 record checkpointやbatch単位lifecycle journalを用いて書込み回数を抑制する。

### 21.5 OTA

CANDIDATE/PREVIOUSはOTA取引単位でerase/programし、失敗による無制限自動再試行を行わない。

OTA更新のotaOfferId／download retry policyに従う。

## 22. 記憶媒体異常・再試行・縮退

### 22.1 識別する異常

少なくとも次を識別する。

- MEDIA_INIT_FAILED
- MEDIA_UNAVAILABLE
- READ_FAILED
- PROGRAM_FAILED
- ERASE_FAILED
- READBACK_MISMATCH
- TORN_WRITE_FOUND
- CRC_INTEGRITY_FAILED
- SECURITY_INTEGRITY_FAILED_RESULT
- FORMAT_UNSUPPORTED
- REVISION_CONFLICT
- ROLLBACK_REJECTED
- NO_SPACE
- PARTITION_HEADER_CORRUPT
- FACTORY_RESET_INCOMPLETE
- CRITICAL_CAPACITY_EXCEEDED

### 22.2 再試行

初期製品の単一media operationは、**初回＋追加1回**を基本上限とする。

追加試行前にdriver/interface状態を再確認し、必要なら再初期化する。初期製品ではmedia retryのための秒単位固定backoffを設けず、再初期化完了後の次の安全な実行点で追加1回を行う。

上位transaction／起動／minimum saveのdeadlineがある場合は当該deadlineを優先し、追加retryによってdeadlineを延長しない。P0 minimum saveでは200 ms内に完了可能な場合だけ追加試行する。

二回目も失敗した場合、同一operationを無期限に繰り返さず異常として確定する。

### 22.3 CRITICAL異常

内蔵領域の重要データ集合を正常に使用できない場合は、異常管理とそのデータを管理する機能へ、対象のデータ集合、最新の版・下限値、使用可能な保存用複製、および失敗種別を通知する。

CRC正常な古いcopyが存在しても、rollback-sensitive datasetをPERSIST判断で古いrevisionへ戻さない。

### 22.4 BULK異常

外付けSerial NOR使用不可時は次を基本とする。

- OTA利用不可
- log永続保存縮退
- Wi-Fi設定／VPS関連補助dataが使用不可なら該当通信機能利用不可
- CONFIG_STORE不可時は設定管理がFACTORY等へfallback可否判断
- 所有者・セキュリティの重要情報が正常なら、BLE認証基盤を一律に失効させない
- Product Data／Time trust等のMRAM criticalは外付けmedia異常だけで無効化しない

異常管理/システム状態管理が全体操作可否を判断する。

### 22.5 自動全消去禁止

media異常を理由として外付けNVM全体を自動format/eraseしない。

全領域scanから任意世代を探索して自動再構築する高度復旧も行わない。

## 23. セキュリティ・プライバシーとの連携

### 23.1 秘密情報

PERSIST diagnosticへ秘密payloadを出力しない。

共通診断ではdatasetId、長さ、revision、保存結果、破損状態等だけを提供する。

### 23.2 confidentiality/integrity

セキュリティ管理が機密性と完全性を必要と判断したdatasetはAEAD、HMAC、Wrapped Keyその他セキュリティ管理の方式を使用する。

PERSISTはprotected blobのstorageを担当し、暗号鍵を汎用PERSIST keyとして共用しない。

### 23.3 rollback-sensitive data

少なくとも次をrollback-sensitiveとしてdataset catalogへ明示する。

- SecurityGen
- highestCommittedGeneration
- highestCommittedProductDataRevision
- ownerDataRevision／revocation state
- wifiCredentialRevision／Wi-Fi key state
- bootInstanceId
- 時刻管理のtime trust revision／update transaction state
- OTA更新のtrial/settlement/recovery state

古い複製のCRCが正常であることだけを理由に、現在有効なデータへ戻さない。データ管理機能／セキュリティ管理が要求する状態保護用MAC、版の下限値、および一連の更新処理の状態を確認する。

### 23.4 factory reset secure invalidation

credential等についてセキュリティ管理からsecure invalidation/erase要求を受けた場合、PERSISTは指定datasetをinvalidate/eraseする。

crypto erase/key rotationを採用する場合はセキュリティ管理が意味と順序を所有し、PERSISTはRESET_PENDING後のatomic key state保存と旧blob lifecycle更新を実行する。

## 24. 状態表示・ログ・診断情報

### 24.1 診断情報

少なくとも次を提供する。

- MRAM critical使用可否
- external Serial NOR使用可否
- persistent layout version
- 各partition capacity/used/free
- critical 32 KiB capacity proof／runtime allocation状態
- 各critical logical dataset 現在のrevision／rollback floor確認結果
- torn write有無
- corrupt dataset有無
- unsupported format有無
- RESET_PENDING有無
- CONFIG/Product Data/Time/OTA recovery transaction有無
- 直近read/write/erase結果
- retry count
- capacity shortage対象

秘密値そのものは提供しない。

### 24.2 event

少なくとも次をログ・診断へ提供する。

- media初期化失敗
- dataset read/write/erase失敗
- torn write検出
- physical redundant copy使用
- rollback reject／latest revision使用不能
- unsupported format
- capacity shortage
- critical dataset異常
- factory reset開始/継続/完了/失敗
- config/product/time/OTA transaction persistence失敗
- minimum save結果

古いデータ内容の版へのfallbackを許可していないdatasetで「old copy fallback」を正常eventとして記録しない。

### 24.3 logger自身が利用不能な場合

ログ・診断の保存自体が利用不能な場合、PERSIST異常をlogへ残せないことを異常処理の完了条件にしない。

可能なcurrent diagnostic状態と異常管理への通知を優先する。

### 24.4 状態表示

PERSIST異常によって通常操作が制限される場合、異常管理/システム状態管理で確定した主理由を状態表示・利用者通知へ提供する。

PERSISTが独自の利用者向け表示文言を決めない。

## 25. 実行時間・固定資源・並行処理方針

### 25.1 基本値

| 項目 | 基本値 |
| --- | ---: |
| `PERSIST_CRITICAL`総量 | 32 KiB |
| fixed boot/recovery executable＋trust | 最大224 KiB |
| PRIMARY | 最大768 KiB |
| external Serial NOR | 8 MiB以上 |
| log logical NVM | 1 MiB |
| CONFIG_STORE | 256 KiB |
| WIFI_STORE | 64 KiB |
| OTA_CANDIDATE | 1 MiB |
| OTA_PREVIOUS | 1 MiB |
| Unit Product Data logical payload | 最大4 KiB（製品情報管理） |
| Trusted Time＋Update logical data | 合計1 KiB以下（時刻管理） |
| minimum save logical payload | 最大1 KiB |
| minimum save physical reservation | 4 KiB |
| minimum save完了 | 200 ms以内 |
| MRAM request queue | 8 slot |
| Serial NOR request queue | 16 slot |
| log metadata checkpoint | 最大32 record間隔 |
| media同一operation retry | 初回＋追加1回、固定backoffなし |

上表の容量・時間・queue・checkpoint・retryは評価確定待ちを含む基本設計で管理する値である。32 KiB critical内の個別physical slot sizingはcapacity proofで確定し、成立しない場合は本書へ戻す。

### 25.2 RAM

PERSIST共通work RAMは32 KiB以下を基本目標とする。

OTA HTTP 16 KiB buffer、ログ・診断のevent queue等の他機能所有bufferをPERSIST共通workへ二重確保しない。

### 25.3 非同期処理

通常write/eraseはPERSIST workerで処理する。

安全taskはrequest受付後にPERSIST完了を待ってdeadlineを失わない。

P0処理も安全処理より上位には置かない。

### 25.4 watchdog

長いSerial NOR erase、OTA copy等でもsystem watchdog監視を無効化しない。

固定ブート・復旧/電源・省電力管理の監視契約へ従い、長時間処理をbounded chunk化し、正常進捗を確認できる点でのみwatchdog更新を許可する。

## 26. 検証方針と異常注入

### 26.1 正常系

- critical dataset二面更新
- 所有者情報のスナップショットの更新と、失効後の旧スナップショットの拒否
- AES-GCM Wi-Fi設定更新・wifiCredentialRevision更新
- CONFIG_COMMIT_PENDINGを含む設定commit
- Unit Product Data＋highestCommittedProductDataRevision更新
- Trusted Time／Time Update transaction
- log ring循環
- OTA candidate/previous保存、trial/settlement、otaResultReportState更新
- normal shutdown marker
- minimum save
- factory reset＋Wi-Fi key rotation

### 26.2 power cut injection

少なくとも次で電源断/resetを発生させる。

- inactive copy header書込み後
- payload途中
- CRC/tag書込み後
- readback途中
- commit marker直前／直後
- 旧データの保存用複製再利用中
- CONFIG_COMMIT_PENDING各段階
- Product Data candidate／highest revision commit各段階
- Time Update PREPARED、RTC set前後、COMMITTED確定各段階
- log record途中
- log metadata checkpoint途中
- SENT lifecycle更新途中
- RESET_PENDING直後
- Wi-Fi key rotation前後
- factory reset delete途中
- INSTALL_REQUESTED commit直前／直後
- PRIMARY_OVERWRITE_STARTED commit直前／直後
- TRIAL_ARMED commit直前／直後
- trialAttempted commit直前／直後
- TRIAL_BOOT_VALIDATED commit直前／直後
- otaResultReportState PENDING/SENT更新途中
- minimum save途中

各処理の契約に従い、更新前の有効データの維持、新しいデータへの更新完了、データ管理機能への復旧要求、未実施の試行起動、PREVIOUSによる復旧等のいずれを行うかが一意に決まることを確認する。処理途中の値を、現在有効な値として使用しないことも確認する。

特に`TRIAL_ARMED=true`かつ`trialAttempted=false`でresetした場合はcandidate trialを一回開始でき、trialAttempted=trueかつ未VALIDATEDならPREVIOUS recoveryとなることを確認する。

### 26.3 media／data fault

- MRAMの片方の保存用複製破損
- MRAM両copy破損
- latest Wi-Fi credential破損＋旧revision正常
- latest Product Data破損＋旧revision正常
- 所有者情報の失効後に最新の所有者スナップショットが破損し、旧ACTIVEのスナップショットが正常な場合
- SecurityGen／highestCommittedGeneration／highestCommittedProductDataRevision state MAC不正
- external NOR未接続
- OSPI timeout
- read/program/erase failure
- partition header破損
- log ring部分破損
- CONFIG_STORE全体使用不可
- CANDIDATE/PREVIOUS片側破損

rollback-sensitive dataで古いデータ内容の版へ自動fallbackしないことを確認する。

### 26.4 capacity

- PERSIST_CRITICAL 32 KiB full physical capacity proof
- Unit Product Data 4 KiB＋A/B／HMAC
- Time Record 1 KiB＋atomic update
- 所有者・セキュリティ・OTA・カウンタ・最小保存データが同じ領域に存在する場合
- NORMAL/IMPORTANT log満杯
- CONFIG slot不足
- Wi-Fi store不足
- OTA candidate容量不足
- previous領域使用不可

用途別policyが隣接領域を侵食しないことを確認する。

### 26.5 endurance

想定利用年数、起動回数、ログ頻度、設定更新、所有者情報の更新、OTA回数、時刻同期回数を用い、MRAM/Serial NORの書込み・消去回数を最悪条件で見積もる。

最低100回以上のOTA成功/失敗/power cut組合せ、および長時間log循環を評価する。

### 26.6 performance

- minimum save 200 ms
- 起動時critical確認時間
- Product Data／Time HMACを含むstartup負荷
- bounded 32 record log recovery時間
- max log/OTA load時CPU/RAM
- Serial NOR erase中の安全task deadline
- queue full時の非block性
- retry追加1回時のdeadline成立性

## 29. 他文書へのフィードバック

### F-01 OTA更新／固定ブート・復旧

fixed boot/recovery＋trust最大224 KiB、`PERSIST_CRITICAL` 32 KiB、PRIMARY最大768 KiBを相互非重複化する。

OTA更新基本設計で更新されたtrial契約を使用し、TRIAL_ARMED=true＋trialAttempted=falseは未実施trial、trialAttempted=true＋未VALIDATEDはPREVIOUS recoveryとする。固定ブート・復旧基本設計第8章および第21.2節はこの契約と整合済みであり、旧記述に関するフィードバックは反映済みとする。

`otaResultReportState`をcritical保存し、local resultとVPS報告状態を分離する。

### F-02 システム構成・ハードウェア

製品記憶部は、内蔵MRAM critical 32 KiBと、RA8M2 OSPI_Bから使用可能なSerial NOR 8 MiB以上の二層構成として具体化する。

外付け型式選定ではFSP/MCUboot対応、erase単位、write endurance、継続調達性、実装性を確認する。

### F-03 設定管理

設定管理基本設計で更新された`CONFIG_COMMIT_PENDING`→CONFIG_STORE確定→`highestCommittedGeneration`→pending finalize→GLOBAL_COMMIT順序をPERSIST側で支援する。

CONFIG_STOREとMRAM counterを一物理transactionと仮定しない。

### F-04 ログ・診断

1 MiB log ring、128 byte immutable record、CRC32C、LOG_META_JOURNAL、32 record checkpoint、bootInstanceId critical counterを維持する。

### F-05 所有者・操作端末管理／セキュリティ／Wi-Fi

所有者登録情報と利用者認証情報を重要データ領域へ配置し、工場出荷状態への初期化で使用するRESET_PENDINGを、P0で保存・確定する。

Wi-Fi設定全体をAES-256-GCM protected blobとしてWIFI_STOREへ保存し、K_WIFI_STORE／wifiNoncePrefix／wifiCredentialRevisionをcriticalへ保持する。factory resetではRESET_PENDING後にkey stateをrotateし、古い認証情報を再利用可能状態へ戻さない。

### F-06 製品情報管理

製品情報管理のUnit Product Data logical payload最大4 KiBおよび`highestCommittedProductDataRevision`をcriticalへ保持する。

製品情報管理基本設計第13.2節の「新snapshotとhighest revisionを一つのcommit」とは一つの**機能上の整合を保つ一連の処理**として実現し、複数physical recordを一書込みと仮定しない。製品情報管理レビュー時にpending/recovery順序を本書と整合する。

Device ID文字列はNVMへ基準となる値として保存しない。

### F-07 時刻管理

Trusted Time Record／Time Update Record logical合計1 KiB以下をcriticalへ保持し、同一updateTransactionIdでPREPARED/COMMITTED/ABORTEDを整合させる。

工場出荷状態への初期化、所有者再登録、OTAだけを理由に、時刻信頼情報を削除しない。

### F-08 起動・終了・再起動／電気安全

minimum save 保存対象データ本体の容量上限1 KiB、physical 4 KiB reservation、200 ms以内write/readback/commit、終了識別子と電源条件世代の相関を維持する。

### F-09 異常管理・状態表示

CRITICAL/BULK media failure、dataset corruption、rollback reject、NO_SPACE、critical capacity不足、factory reset incomplete等を異常管理へ提供し、通常操作への影響を異常管理/システム状態管理で判断する。

- running firmware identityは製品情報管理のsigned imageから取得するものとし、PERSISTはOTA更新のOTA role/settlement metadataだけを保持する責任分界へ修正した。

- minimum save 1 KiB／200 ms契約を維持した。
- factory reset RESET_PENDING先行commit、send-ban、Wi-Fi key rotation、削除、保持、完了commitの順序を具体化した。
- SecurityGen、highestCommittedGeneration、highestCommittedProductDataRevision、bootInstanceId、Time trustをfactory resetで巻き戻さない。
- external NVM異常だけで安全関連critical dataを推測破棄しない。
- media operation retryを初回＋追加1回、固定backoffなし、上位deadline優先として基本設計化した。
- 安全処理をNVM書込み完了待ちで阻害しない。
- 固定queue・固定バッファ・malloc禁止を維持した。

### 30.2 初版完了判断

D-01～D-26は本基本設計で採用する方式として確定する。

E-01～E-22は採用方式・基本設計値の成立性・性能・容量・部品選定を確認する実装・実機評価事項であり、初版基本設計を停止するユーザー判断待ち事項ではない。

F-01～F-09は関連基本設計・hardware設計・詳細設計へのフィードバック事項である。設定管理/ログ・診断/OTA更新/セキュリティ管理/製品情報管理/時刻管理の後続契約は本書へ反映済みである。

MRAM physical address、critical logical datasetごとの最終physical slot size、FSP MRAM書込み方式、外付けSerial NOR具体型式、erase/program単位、OSPI timing、physical partition address等は、基本方式を変更しない範囲で後続設計・評価に委ねる。ただし32 KiB critical capacity proofが成立しない場合は詳細設計で吸収せず本書へ戻す。

現時点で、永続データ管理基本設計の初版完了を妨げるユーザー判断待ち事項は残していない。

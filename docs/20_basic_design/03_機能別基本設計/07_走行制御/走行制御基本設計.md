## 1. 本書の目的

### 1.1 目的

本書の目的は、公開用システム要求仕様「07. 走行制御」を実現するため、左右2基のDCモータを用いる走行制御の基本方式、責任分界、走行指令処理、モータ出力生成、停止、異常監視および関連機能との契約を、詳細設計へ展開可能な粒度まで具体化することである。

### 1.2 対象範囲

本書は、Tank_Robotの左右2基のDCモータを使用する走行制御について、走行指令の受付、左右モータ目標出力の生成、加速・減速、方向反転、DPC-XGL1-JP付属モータドライバとのI2C連携、通常停止・安全停止・緊急停止、過負荷・拘束監視、設定、異常処理および関連機能とのインターフェースを具体化する。

#### 基本設計値と実機評価の扱い

**本書では、詳細設計を未定義値のまま開始しないため、最大走行出力、通常加速・減速および方向反転時の零保持時間について初期基本設計値を定める。ただし、これらは現行機体・路面・電源条件で安全性および操作性を実証済みであることを意味しない。** 初期基本設計値は第14章の走行安全プロファイルとして使用し、第19章の実機評価で転倒、滑り、キャタピラ脱落、電流、機構衝撃および操作性を確認する。評価の結果、変更が必要な場合は詳細設計だけで値を変更せず、本基本設計へフィードバックして改訂する。モータドライバ通信仕様、過負荷・拘束しきい値および実際の停止距離等、現物・機構・路面・電源条件に強く依存する事項は推測で確定せず、第19章の実機評価事項として明示する。

また、本構成ではエンコーダ等による実速度・実走行距離のフィードバックを使用しない。このため、本書でいう「出力停止確認」または「方向反転の停止相当条件」は、指令出力、モータドライバ通信結果、保留要求の破棄および評価済み停止時間等による**制御側・設計評価上の確認**であり、実機の速度零を常時測定した結果ではない。

| 用語 | 本書での意味 |
| --- | --- |
| 進行方向成分 | 前進・後退の方向および操作量を表す符号付き走行指令 |
| 旋回成分 | 機体を左・右へ旋回させる方向および操作量を表す符号付き走行指令 |

| `driveEpoch` | 停止、電源変更、設定変更等によって以前の走行実行資格を失効させる本機能内の実行世代 |

## 2. 設計方針と適用範囲

### 2.1 維持する上位方針

本書では次を変更しない。

1. 左右2基のDCモータを個別に制御する。
2. エンコーダ等を使用した本体側の閉ループ速度制御を行わない。
3. 左右モータを互いに反対方向へ駆動する超信地旋回を行わない。
4. 旋回は進行中の左右出力差および片側停止によって行う。
5. 進行方向成分が中立の場合、旋回成分だけで走行を開始しない。
6. 左右モータ・機構差を自動補正する直進補正を初期製品へ追加しない。
7. バッテリー電圧・温度等に応じた多段階走行デレーティングを初期製品へ追加しない。
8. Wi-FiまたはVPSを走行操作経路へ使用しない。
9. 走行の通常停止は砲塔・砲身を停止させる通常操作とはしない。
10. 安全停止・緊急停止・電気安全保護は通常走行処理より優先する。

### 2.2 本書で採用する基本方式

走行指令を正規化された進行方向成分と旋回成分として受け取り、左右モータの論理目標出力へ変換する。

通常走行では、左右モータの出力符号を同一方向または零に限定する。最大旋回入力では内側モータを零、外側モータを進行方向へ駆動する。進行成分が零の場合は左右とも零とする。

左右目標出力をそのままモータドライバへ急変させず、通常走行では評価済みの加速・減速率で適用出力へ追従させる。前進と後退の符号が反転する場合は、一度出力零へ移行し、停止相当条件を成立させてから反対方向へ駆動する。

通常停止では通常走行用の減速方式を用いて出力零へ移行する。安全停止・緊急停止では通常の加減速ランプを待たず、旧指令の実行資格を直ちに失効させ、左右出力を零／出力禁止側へ移行する。独立した本体側緊急停止経路は、このソフトウェア処理とは別に走行駆動出力を禁止できる構成を維持する。

### 2.3 実速度・位置の推定値を制御の基準にしない

本構成では実速度、左右車輪回転数および走行距離を通常走行制御の基準となる値として取得しない。

`appliedLeftOutput=0`および`appliedRightOutput=0`が成立しても、「車体が物理的に完全静止した」とは表現しない。惰性走行、路面状態、機体質量、傾斜等を含む停止距離・停止時間は実機評価で確認する。

エンコーダを搭載した機構が存在する場合でも、本要求範囲では閉ループ速度制御・常時不一致監視へ使用しない。将来使用する場合は要求および基本設計を改訂する。

### 2.4 設計成立に必要な前提

| 前提 | 未成立時の扱い |
| --- | --- |
| 現行モータドライバのI2C制御仕様を確認できる | 未確認なら通常走行を評価済み扱いにしない |
| 左右モータの正しい極性・出力零状態を確認できる | 走行出力を有効化しない |
| 最大出力・加減速・方向反転条件を実機評価できる | 初期基本設計値で評価し、安全性・操作性を確認できなければ通常利用へ移行しない |
| 走行駆動系電流スナップショットを正常に取得できる | 出力中に監視を維持できなければ安全停止を要求 |
| 過負荷・拘束を合計電流から必要範囲で識別できる | 識別不能なら要求達成済みとせず、監視方式・ハードウェアへフィードバック |
| 本体緊急停止の独立走行出力禁止経路が実機で成立する | 通常ソフトウェア停止だけで緊急停止要求を達成済みとしない |

## 3. 責任分界と共通条件

### 3.1 情報の管理元と決定主体

| 対象 | 管理元・最終判断主体 | 走行制御の担当 |
| --- | --- | --- |
| システム状態・全体操作可否 | システム状態管理 | 現行条件を参照し、走行固有の利用可否を提供 |
| BLE接続・認証・受信順序 | BLE接続・認証 | 指令データの内容・値域、現在の状態での受付可否、および実行結果を判断 |
| 操作端末役割・権限 | 所有者・操作端末管理 | BLE接続・認証/所有者・操作端末管理から提供された現行権限に従う |
| 操作指令タイムアウト | 停止・緊急停止管理 | 走行継続操作中か、および機能固有受付結果を提供 |
| 停止種別・目的・停止取引全体 | 停止・緊急停止管理 | 左右モータの局所停止を実行し結果を返す |
| `PWR_DRIVE`実状態・電源ON/OFF | 電源・省電力管理 | 出力無効化・再初期化・電力変更準備を実行 |
| 電圧・電流・温度・電気保護 | バッテリー・電気安全監視 | 電流スナップショットを使い走行固有の過負荷・拘束を判断 |
| 異常影響度・処置・復旧可否 | 異常管理 | 走行異常を検出し、一次安全化・局所診断結果を提供 |
| 設定パッケージ全体適用 | 設定管理 | 走行設定候補の局所検証・反映・切戻しを行う |
| 走行指令→左右出力・加減速・反転 | 本機能 | 本書で一意に管理 |
| システム全体表示 | 状態表示・利用者通知 | 走行固有の状態・制限・異常情報を提供 |

### 3.2 通常走行実行条件 `C_DRIVE_RUN`

次をすべて満たす場合だけ新しい非零走行出力を生成する。

- システム状態管理が現在のシステム状態・全体操作可否として通常走行を許容している。
- BLE接続・認証の現行操作セッション・認証・権限が有効である。
- 停止・緊急停止管理の通常停止、安全停止、緊急停止または走行禁止条件が未成立である。
- 異常管理から適用された未復旧の走行機能制限がない。
- 電源・省電力管理で`PWR_DRIVE`が使用可能な実状態である。
- バッテリー・電気安全監視が走行開始・継続に必要な電気安全条件を正常としている。
- 現行の走行安全プロファイルが有効である。
- モータドライバ制御経路が使用可能である。
- 走行制御周期・システム監視が使用可能である。

条件不明は成立とみなさない。

### 3.3 走行開始条件と継続条件を分ける

走行開始時には`C_DRIVE_RUN`の全条件を確認する。走行中も制御周期ごとに、少なくとも停止禁止、電気安全、電源、設定世代、`driveEpoch`およびモータドライバ利用可否を再確認する。

開始時に正常だった条件が後で失われても、前回確認結果だけで出力を継続しない。

### 3.4 出力実行資格の失効 `DRIVE_INVALIDATE`

安全停止、緊急停止、通常停止取引開始、電源変更、設定切替、操作セッション変更、認証・権限失効、走行異常または復旧開始時には、次を一つの局所処理として行う。

1. 新しい通常走行指令の受付を禁止する。
2. `driveEpoch`を更新する。
3. 未実行の通常指令と未送信の非零モータ出力更新を破棄する。
4. 既に送信中のモータドライバ取引を識別し、結果不明の非零取引を新しい正常状態へ流用しない。
5. 要求種別に対応する停止・無出力処理へ移る。

更新後の`driveEpoch`はBLE接続・認証へ提供し、BLE接続・認証が現在の走行操作の有効性を確認するための情報としてスマートフォンアプリへ通知できるようにする。出力再許可より前に操作世代を更新し、古い操作世代の指令を受け付け可能な時間窓を作らない。

禁止解除時に旧指令を復元しない。

### 3.5 優先順位

ソフトウェアで処理する範囲では、次を基本とする。

1. 電気安全上の即時保護・独立緊急停止・強制電源遮断
2. 緊急停止
3. 安全停止
4. 通常終了・低消費電力移行等の電力変更準備
5. 通常停止
6. 通常走行指令

全体の優先判断は停止・緊急停止管理、電源・省電力管理、バッテリー・電気安全監視、システム状態管理の各担当機能の判断に従い、本機能がシステム状態・電源状態を独自変更しない。

## 4. 走行指令の受付

### 4.1 論理指令

走行指令は次の2成分とする。

| 項目 | 型・値域 | 意味 |
| --- | --- | --- |
| `longitudinal` | 符号付き整数 `-1000..+1000` | `+`=前進、`-`=後退、0=中立 |
| `turn` | 符号付き整数 `-1000..+1000` | `+`=機体の向きを右へ旋回、`-`=左へ旋回、0=直進 |

この値域は本基本設計で採用する論理値であり、物理速度、PWMデューティ比、電流または百分率の実測値ではない。

### 4.2 本体側中立範囲

本体はスマートフォン側の入力処理とは独立して中立範囲を適用する。

初期基本値として、進行方向・旋回成分とも`D_NEUTRAL=50`を使用する。

```text
abs(x) <= D_NEUTRAL:
    deadband(x) = 0

abs(x) > D_NEUTRAL:
    deadband(x)
      = sign(x) * round((abs(x)-D_NEUTRAL) * 1000 / (1000-D_NEUTRAL))
```

中立外の操作量を0～1000へ再正規化することで、中立範囲の境界で大きな出力段差を作らない。

`D_NEUTRAL`は操作性評価対象であるが、初期製品ではVPSから遠隔変更する設定にしない。変更が必要な場合は走行安全評価と本基本設計を見直す。

### 4.3 BLE接続・認証機能から受け取る指令の付随情報

走行指令のデータは、BLE接続・認証機能が提供する、少なくとも次の論理情報と対応付けて受け取る。

- `protocolVersion`
- `commandType`
- `sessionId`
- `authorizationRevision`
- `actuationEpoch`（走行制御機能が管理する`driveEpoch`の値を、通信データに含めるための項目）
- `commandSeq`
- `requestId`
- BLE受信時刻
- 通信層の重複・旧指令判定結果

#### 通信情報の管理

`commandSeq`の値の循環処理、BLE受信時刻、および操作セッション内の重複・逆順の排除は、BLE接続・認証機能が管理する。
走行制御機能は、受け取った通信情報を別の管理元として複製しない。

#### 実行世代の管理と確認

走行用の`actuationEpoch`に入れる値と、その更新は、走行制御機能が管理する。
BLE接続・認証機能は、走行制御機能から取得した現在の`driveEpoch`を、通信データの`actuationEpoch`へ符号化して配送する。

停止前に送られた古い世代の指令でないことは、走行制御機能が最終確認する。
指令の受付時と実行直前の確認方法は、5.5「実行世代と要求・結果の対応付け」に従う。

### 4.4 指令検証順序

| 順序 | 確認 | 不成立時 |
| ---: | --- | --- |
| 1 | BLE接続・認証で共通メッセージ・認証・権限・新旧判定済み | 通常走行指令として受け取らない |
| 2 | `longitudinal`、`turn`が定義値域内 | `INVALID_PAYLOAD` |
| 3 | 現行セッション・`authorizationRevision`と一致し、受信`actuationEpoch`が現行`driveEpoch`と一致 | `STALE_CONTEXT` |
| 4 | `C_DRIVE_RUN`または中立停止を安全に受け付け可能 | `INHIBITED` |
| 5 | 検証済みの現行`driveEpoch`を保持して最新指令スロットを更新 | 旧未実行指令を`SUPERSEDED` |
| 6 | 機能固有受付結果をBLE接続・認証へ返す | BLE接続・認証が最終有効受信情報を確定 |
| 7 | 制御周期直前に`driveEpoch`と禁止条件を再確認 | 失効なら非零出力を実行しない |

外部からの範囲外値をクランプして有効指令にしない。

### 4.5 最新指令優先

未実行の通常走行指令は1件だけ保持し、新しい有効指令で置換する。

古い走行指令をFIFOで順番に再生しない。送信遅延によって複数指令が存在しても、現在の操作意図を優先する。

停止要求は通常走行指令スロットとは別経路で保持する。通常指令キューの空きやI2C通常更新待ちを理由として停止受付を遅延しない。

### 4.6 中立指令

`longitudinal`が中立となった走行指令は、旋回成分に関係なく左右目標出力を0とする。

中立指令は通常走行の「出力零目標」として扱い、第7章の通常減速方式で停止側へ移行する。これはスマートフォンの「通常停止ボタン」による停止・緊急停止管理の通常停止取引とは別である。

停止・緊急停止管理から明示的な通常停止要求を受けた場合は、通常指令による中立より優先し、第10章の停止取引として扱う。

### 4.7 最終有効受信情報との連携

走行制御機能は、走行指令のデータの意味、値域、および現在の走行受付可否を判断する。
その結果を`DriveCommandValidationResult`として、同じBLE指令へ対応付けて返す。

BLE接続・認証機能は、通信層の条件と走行制御機能の受付結果がともに正常な指令だけを、走行の最終有効受信情報として確定する。

操作指令タイムアウトは、停止・緊急停止管理機能が判断する。
判断には、BLE接続・認証機能の最終有効受信情報と、走行制御機能が提供する走行継続状態を使用する。
走行制御機能は、独自の「最後に受けたBLE時刻」をタイムアウト判定の基準として管理しない。

継続走行指令は、停止・緊急停止管理基本設計で確定した基本送信周期50 msおよび操作指令タイムアウト300 msの共通性能配分に従う。
走行制御機能は、これらと異なる独自のタイムアウト値を設けない。

## 5. 内部状態と管理データ

### 5.1 機能全体状態

| 状態 | 意味 | 非零出力 |
| --- | --- | --- |
| `UNINITIALIZED` | 初期化未完了 | 禁止 |
| `INITIALIZING` | 出力禁止でドライバ・設定・監視を確認中 | 禁止 |
| `AVAILABLE` | 走行制御機能自体を使用可能 | 個別条件による |
| `QUIESCING` | 終了・低消費電力・設定適用等の準備中 | 禁止。停止専用処理のみ |
| `LIMITED` | 未復旧異常等で走行機能を制限 | 禁止 |
| `RECOVERING` | 許可された局所診断・復旧中 | 禁止 |
| `UNAVAILABLE` | 安全な走行制御を成立させられない | 禁止 |

これはシステム状態ではない。`AVAILABLE`であっても、システム状態管理がBLE接続待機等の場合は走行しない。

### 5.2 走行動作状態

| 状態 | 意味 |
| --- | --- |
| `OUTPUT_DISABLED` | 非零出力を生成できない。起動・電源変更・停止後等 |
| `STOPPED_READY` | 走行可能条件成立、左右適用出力0 |
| `RAMPING` | 最新目標へ加速・減速中 |
| `DRIVING` | 非零適用出力を継続中 |
| `REVERSAL_BRAKING` | 方向反転のため零へ減速中 |
| `REVERSAL_ZERO_WAIT` | 反対方向を開始せず停止相当条件を確認中 |
| `NORMAL_STOPPING` | 中立または通常停止要求により通常減速中 |
| `SAFETY_STOPPING` | 安全停止・緊急停止で安全優先停止中 |
| `DRIVER_RECOVERY` | 出力禁止のままモータドライバを再初期化・確認中 |

### 5.3 左右出力管理データ

各側について次を区別する。

- `targetOutput`：走行指令を左右モータへ配分した後の目標出力
- `appliedOutput`：加減速・反転・停止処理を反映した適用出力
- `driverRequestedOutput`：最新のモータドライバ送信要求値
- `driverConfirmedOutput`：通信上、正常完了を確認した最新要求値
- `outputDirection`：FORWARD / REVERSE / ZERO
- `lastDriverTxnSeq`：ドライバI2C取引相関用内部順序

`driverConfirmedOutput`は実モータ速度の測定値ではない。

### 5.4 実速度・走行距離

本初版では次を常に未測定情報として扱う。

- `actualLeftSpeed = UNKNOWN`
- `actualRightSpeed = UNKNOWN`
- `actualVehicleSpeed = UNKNOWN`
- `travelDistance = UNKNOWN`

指令出力からこれらを推定し、状態表示や停止完了の実測値として扱わない。

### 5.5 実行世代と要求・結果の対応付け

#### 有効範囲と初期値

`driveEpoch`は、本体アプリケーションの同一起動内で使用する32ビット符号なし整数（uint32）とする。
0は未確立・無効を示す予約値とし、初回の有効値は1とする。

値は単調に増加させ、同じBLE操作セッション内では、上限到達後に小さい値へ戻したり、以前の値を再使用したりしない。

#### 更新する場合

`driveEpoch`は、少なくとも次の場合に更新する。

- 安全停止・緊急停止
- 通常停止取引開始
- 操作セッションまたは権限世代変更
- `PWR_DRIVE`電源変更・再初期化
- 設定切替・切戻し
- 異常による機能制限
- 復旧開始・完了

#### 指令の受付・実行時の確認

`DRIVE_COMMAND`では、次のように世代値を受け渡し、受付時と実行直前に確認する。

1. BLE接続・認証機能は、走行制御機能が提供した現在の`driveEpoch`をスマートフォンアプリへ通知する。
2. スマートフォンアプリは、通知された値を、送信する指令の`actuationEpoch`に含める。
3. 走行制御機能は、指令の受付時に、受信した`actuationEpoch`と現在の`driveEpoch`が一致することを確認する。
4. 一致した指令だけを、確認した世代値とともに保持する。
5. 実行直前にも現在の`driveEpoch`との一致を再確認し、停止前の古い世代を持つ遅延指令、保留指令または再送指令を破棄する。

受信時点の現在の世代値を、指令へ無条件に後付けしない。

#### 上限到達時・再起動時の扱い

次回の更新で`0xFFFFFFFF`を超える場合は、BLE接続・認証機能へ現在の操作セッションの失効を要求する。
再認証後の新しい操作セッションで、世代値を再初期化する。

異なる起動の間でもBLE操作セッションを再確立する。
起動単位をまたいで、世代値だけを比較したり、以前の値を継続使用したりしない。

#### 他機能が発行する識別子との区別

次の識別子は、それぞれ発行元の値を保持し、`driveEpoch`で置き換えない。

- 停止・緊急停止管理機能の停止要求識別子
- 起動・終了・再起動管理機能の終了識別子
- 電源・省電力管理機能の低消費電力移行識別子
- 異常管理機能の異常処置要求識別子

## 6. 走行指令から左右モータ目標出力への変換

### 6.1 座標系

中立処理後の進行方向成分を`d`、旋回成分を`t`とし、ともに`-1000..+1000`とする。

- `d > 0`：前進
- `d < 0`：後退
- `t > 0`：機体の向きを右へ旋回
- `t < 0`：機体の向きを左へ旋回

旋回方向は前進・後退によらず、機体上面から見た向きの変化として定義する。

### 6.2 左右モータへの基本配分

`d=0`の場合は、`t`に関係なく左右とも0とする。

`d>0`の場合を次とする。

```text
右旋回 (t >= 0):
    mixL = d
    mixR = d * (1000 - t) / 1000

左旋回 (t < 0):
    mixL = d * (1000 + t) / 1000
    mixR = d
```

`d<0`の場合を次とする。

```text
右旋回 (t >= 0):
    mixL = d * (1000 - t) / 1000
    mixR = d

左旋回 (t < 0):
    mixL = d
    mixR = d * (1000 + t) / 1000
```

整数演算では中間値のオーバーフローを防ぎ、除算時の丸め方式を左右で対称にする。

### 6.3 左右モータへの配分方式の性質

上記方式では次が成立する。

- 左右出力は常に同符号または零であり、超信地旋回を生成しない。
- `t=0`なら左右出力は等しい。
- `abs(t)=1000`なら旋回内側の出力が0となる。
- `d=0`なら旋回入力だけで走行しない。
- 左右モータの個体差を補正する係数を追加しない。

通常直進で左右の実速度差が生じても、本初版では自動補正しない。

### 6.4 最大走行出力の適用

初期基本設計値として最大走行出力`U_MAX=300`を使用し、単位を0～1000のpermille相当とする。したがって、入力側が最大走行指令を要求しても、左右モータの論理目標出力はモータドライバ論理最大出力の30%相当を上限とする。

```text
targetL = round(mixL * U_MAX / 1000)
targetR = round(mixR * U_MAX / 1000)
```

`U_MAX=300`は現行ハードウェアで安全性を実証済みの最終値ではなく、E-01の実機評価を開始するための初期基本設計値である。E-01では、低出力から段階的に走行可能性を確認した上で、300における転倒、滑り、キャタピラ脱落、電流、発熱、停止特性および操作性を確認する。300で安全な通常走行を成立させられない場合、または通常使用に必要な走行を成立させられない場合は、詳細設計だけで値を変更せず本基本設計へフィードバックする。

`U_MAX`は必ず`1..1000`の範囲かつ現行の評価済み上限以下とし、実機評価前に1000へ拡大しない。

出力下限を持ち上げる最低駆動補正は本初版へ追加しない。低い出力でモータが回転しない場合でも、実速度フィードバックがないため「回らない分だけ自動的に出力を増やす」処理を行わない。

### 6.5 モータ取付極性

論理出力の正負とモータドライバの実方向コマンドの対応は、左右それぞれ`motorPolarity`を製品プロファイルとして固定する。

極性は製造・機構情報と一致することを無出力・低出力の評価手順で確認する。利用者設定またはVPS管理設定で反転できる項目にしない。

### 6.6 数値異常

次を制御異常とする。

- 計算中間値のオーバーフロー
- `U_MAX`その他の設定未確定・不正
- 左右モータへの配分結果が定義範囲を超える
- 左右出力が通常走行で互いに逆符号となる
- 無効な方向列挙・モータ極性情報

異常値をクランプして通常走行を継続せず、新規出力を禁止して停止・緊急停止管理/異常管理へ安全処理を要求する。

## 7. 出力変化・方向反転・通常走行停止

### 7.1 出力変化率

左右モータごとに、最大加速出力変化率`R_ACCEL`と最大減速出力変化率`R_DECEL`を持つ。単位はpermille/s相当とする。

初期基本設計値を次とする。

- `R_ACCEL=600 permille/s`
- `R_DECEL=1200 permille/s`

`U_MAX=300`の場合、停止状態から最大走行出力までの加速時間は約500 ms、最大走行出力から通常減速で出力零へ移行する時間は約250 msとなる。これは実速度が当該時間で零または最大速度になることを意味せず、論理モータ出力の変化時間である。

制御周期`dt`での最大変化量を次とする。式には、`dt`を秒で表した値を代入する。

```text
deltaAccel = R_ACCEL * dt
deltaDecel = R_DECEL * dt
```

現在の絶対出力を増やす方向は`R_ACCEL`、零へ近付ける方向は`R_DECEL`を使用する。

左右それぞれ独立に適用するため、旋回量変更時に片側だけ加速、他側だけ減速となることを許す。

`R_ACCEL=600`および`R_DECEL=1200`は、急激な出力変化を避けつつ評価可能な走行挙動を一意にする初期基本設計値である。E-01/E-02では、転倒、滑り、キャタピラ脱落、異常電流、機構衝撃、停止距離および操作性を確認し、変更が必要な場合は本基本設計へフィードバックする。

### 7.2 通常走行開始・速度変更

`STOPPED_READY`から非零目標を受けた場合、最初の制御周期から`R_ACCEL`に従って出力を増加させる。

新目標が同符号で現在出力より小さい場合は`R_DECEL`で減少させる。

走行指令を一回で最大値へ変更しても、適用出力を一周期で最大へ飛ばさない。

### 7.3 旋回量変更

旋回目標の変更によって内外輪が入れ替わる場合も、各側の出力変化率制限を維持する。

最大旋回で内側モータを0へ移行する際も`R_DECEL`を適用する。反対側をそれ以上に増加させて総出力を補償しない。

### 7.4 前進・後退反転

左右いずれかについて、現在の非零適用出力と最新目標出力の符号が反対となる場合、当該側を直ちに反対方向へ駆動しない。

基本シーケンスを次とする。

1. 反転対象側の最新目標符号を記録する。
2. `R_DECEL`で適用出力を0へ減少させる。
3. モータドライバへ0出力を反映し、正常完了を確認する。
4. 当該側について未完了・旧非零ドライバ要求が存在しないことを確認する。
5. `T_REVERSE_ZERO_HOLD=200 ms`の間、反対方向の出力を開始しない。
6. `driveEpoch`および最新目標を再確認する。
7. 新しい方向へ`R_ACCEL`で出力を開始する。

`T_REVERSE_ZERO_HOLD=200 ms`は初期基本設計値であり、反転指令を受けた直後に逆方向へ駆動することを防ぐための最低零保持時間とする。最大走行出力から方向反転する場合、論理出力は`R_DECEL=1200`により約250 msで零へ移行した後、零出力反映・旧要求不存在を確認し、さらに200 ms保持するため、反対方向の非零出力開始は少なくとも約450 ms後となる。I2C処理時間等は別途加わる。

### 7.5 停止相当条件

方向反転時の停止相当条件は、少なくとも次をすべて満たすこととする。

- 反転対象側の`appliedOutput=0`。
- モータドライバへの0出力要求が正常完了。
- 旧非零要求が未処理キュー・再送対象に残っていない。
- `driveEpoch`が反転処理開始時から有効。
- `T_REVERSE_ZERO_HOLD=200 ms`が満了。

この条件は実速度零を測定したものではない。`T_REVERSE_ZERO_HOLD=200 ms`は最大機体質量、路面、傾斜、バッテリー、モータ、キャタピラの条件で、反転時の過大電流・滑り・脱落・機構衝撃を防げることをE-02で確認する。200 msで成立しない場合は実測最悪値に安全余裕を加えた値へ本基本設計を改訂する。

### 7.6 中立による通常停止

有効な中立指令では左右目標を0とし、両側を`R_DECEL`で零へ移行する。

左右の適用出力が0となり、モータドライバへの零出力反映を確認した時点で、走行制御上の中立停止を`STOPPED_READY`とする。

車体の実速度零は測定しないため、利用者向け表示で「速度0 km/hを測定済み」とは表現しない。

### 7.7 急な周期遅延

大きなスケジューリング遅延が生じた場合、経過時間分を一回で加算して出力を大きく飛ばさない。

通常制御周期の許容遅延を超えた場合は、出力追従を続けて帳尻を合わせず、第12章の制御周期異常として安全停止へ連携する。

## 8. モータドライバおよびI2C制御

### 8.1 採用構成

「Tank_Robotシステム構成」に従い、DPC-XGL1-JP付属モータドライバを使用し、RA8M2からI2Cで制御する。

#### 現物確認が必要な項目

本書ではI2Cを使用する構成を確定事項とする。
ただし、次の物理仕様・通信仕様の値は、採用現物・資料との照合が必要であり、本書では未確定として扱う。

- I2Cアドレス
- I2C通信速度
- 左右モータの具体的なコマンド／レジスタ
- 出力値の符号・分解能・停止コマンドの表現
- 応答データの形式
- モータドライバの異常通知と異常状態の取得方法
- 通信処理のタイムアウト値
- モータドライバ内部の零出力時の電気的動作（惰性走行（coast）／制動（brake）など）

これらは、第19.2節のE-03で採用現物・資料と照合する。
I2Cアドレス、通信速度、コマンド・応答、通信処理のタイムアウトなどの実装値は、第8.8節・第16章の時間条件を変更しない範囲で、詳細設計で確定する。

#### 基本設計を見直す場合

零出力時の実際の電気的動作、またはモータドライバの異常通知機能では、本書で定めた停止方法、停止性能、異常検出または安全処理を成立させられない場合がある。
その場合は、詳細設計だけで代替動作を追加せず、本基本設計または関連ハードウェア設計へフィードバックする。

零出力時の動作や異常通知機能は、現物確認前に対応済みとは扱わない。

### 8.2 論理`MotorDriverAdapter`

走行制御はモータドライバ固有プロトコルを直接各処理へ分散させず、論理的な`MotorDriverAdapter`を介して次を要求できる構成とする。

- `InitializeDisabled`
- `SetMotorPair(leftOutput, rightOutput)`
- `SetZeroBoth`
- `DisableDriveOutput`（ドライバが対応する場合）
- `ReadDriverStatus`
- `ClearPendingTransaction`
- `ReinitializeDisabled`

これは基本設計上の責任境界であり、具体的なC関数名・クラス名を固定するものではない。

### 8.3 左右出力の一つの論理更新

一つの制御周期で計算した左右出力は、同一の論理更新としてモータドライバへ反映する。

ドライバプロトコル上、左右が別I2C取引となる場合も、更新世代を対応付け、片側だけ新値、片側だけ旧値が長時間継続しないようにする。

途中で片側更新だけ成功して他側が失敗した場合、通常走行を継続せず0出力・安全停止へ移行する。

### 8.4 I2C取引管理

モータドライバI2C要求を無制限FIFOへ積まない。

通常走行では、現在制御周期の最新1件を次の送信候補とする。未送信の旧通常出力は新しい出力で置換できる。

一度I2C送信を開始した要求は、`driverTxnSeq`と対応付けて正常完了、失敗または結果不明を区別する。

結果不明の非零要求を、同じ値でも「送れていなかった」と推測して無条件再送しない。まず新規非零出力を禁止し、停止側処理へ移る。

### 8.5 正常完了の確認に使用する情報

少なくとも次を区別する。

- I2C通信処理の開始
- ACK／プロトコル上の正常応答
- 左右出力要求の正常完了
- モータドライバの状態読出し結果
- モータドライバの異常通知の有無

単にAPI呼出しが戻ったことだけを、モータドライバへの正常反映確認としない。

モータドライバが、どこまでの応答や異常状態を提供できるかは、第19.2節のE-03で確認する。
公開用システム要求仕様「07. 走行制御」で要求される通信正常完了および異常通知を現物から取得できない場合は、ソフトウェアで存在しない状態情報を仮定しない。
その場合は、モータドライバ／ハードウェア設計へフィードバックする。

### 8.6 通信異常時

NACK、バスエラー、タイムアウト、応答不正、モータドライバの異常、左右更新の部分失敗または通信処理の結果不明を検出した場合は、次を行う。

1. 新しい通常走行指令を禁止する。
2. `driveEpoch`を更新する。
3. 未送信の非零出力要求を破棄する。
4. 可能な停止側I2C要求を優先して実行する。
5. 停止・緊急停止管理機能へ安全停止を要求する。
6. 異常管理機能へ通信異常と現在の出力確認範囲を通知する。
7. 必要な独立走行出力禁止・電源保護を妨げない。

### 8.7 再試行と再初期化

走行中に結果不明となった非零出力を同じ取引として繰り返し再送しない。

再初期化は、左右の新規走行出力が禁止され、可能な停止処理を実行し、停止・緊急停止管理/異常管理の処置として再初期化が許可された場合だけ行う。

再初期化後は、以前の`targetOutput`、`appliedOutput`およびBLE走行指令を自動復元しない。左右出力零・出力禁止を確認し、通常操作が再許可された後に到着する新しい走行指令を必要とする。

### 8.8 I2Cと制御周期の関係

走行制御の論理周期は第16章の10 msとする。

走行中のモータドライバ更新は、この周期内で扱える構成とする。
I2Cの待ち時間によって、安全停止の受付やシステム監視を長時間妨げない。

同期I2C方式を採用する場合は、通信処理のタイムアウトを、一走行制御周期より短い上限として詳細設計で定め、実機で通信余裕を確認する。
必要なら非同期I2C方式を用いる。

具体的なI2C通信のタイムアウト値は、ドライバ仕様・通信速度を確認する前に本書で固定しない。
ただし、詳細設計で選定する値は、10 msの制御周期、20 msの局所応答目標および第10.6節の停止開始時間を満たす内部実装値とする。
これらの基本設計上の振る舞いを変更せず、成立させられない場合は本基本設計へフィードバックする。

## 9. 起動・再初期化・電源復帰

### 9.1 起動時の安全状態

起動時は、左右モータへ非零出力を要求しない状態を最初に確立する。

基本順序を次とする。

1. 走行通常指令スロット、出力要求、`driveEpoch`を初期化する。
2. ソフトウェア上の走行出力許可を禁止状態とする。
3. モータドライバを出力禁止／零出力前提で初期化する。
4. I2C基本通信と必要な状態情報を確認する。
5. 走行安全プロファイルとモータ極性を確認する。
6. 電源・省電力管理の`PWR_DRIVE`実状態とバッテリー・電気安全監視の監視利用可否を確認する。
7. 独立緊急停止経路が通常走行を禁止していないことを、利用可能な状態情報の範囲で確認する。
8. 初期化結果を起動・終了・再起動管理へ返す。

起動診断のためにモータを自動回転させない。

### 9.2 起動結果の3区分

起動・終了・再起動管理/異常管理との共通契約に合わせ、次を区別する。

| 結果 | 意味 |
| --- | --- |
| 安全状態成立・利用可能 | 左右非零出力禁止を確認し、ドライバ・設定・監視も通常走行に使用可能 |
| 安全状態成立・利用不可 | 左右非零出力禁止は確認できるが、ドライバ・設定・監視等の理由で通常走行不可 |
| 安全状態未成立 | 左右出力を安全側へ確立・確認できず、走行安全を保証できない |

本機能はシステム起動全体を完了または失敗へ遷移させない。異常管理が異常影響・復旧を判断し、起動・終了・再起動管理が起動シーケンスを管理し、システム状態管理が最終システム状態・操作可否を決定する。

### 9.3 `PWR_DRIVE`再投入

電源・省電力管理による`PWR_DRIVE`再投入後も、以前の走行出力を再開しない。

出力禁止のまま次を確認する。

- 電源実状態
- I2C通信
- モータドライバ初期状態
- モータドライバの状態
- 走行安全プロファイル
- バッテリー・電気安全監視の通常監視利用可否
- 未復旧の走行異常・停止ラッチ

正常確認後も、システム状態管理/停止・緊急停止管理の通常走行条件と新しいBLE走行指令が届くまで左右出力零を維持する。

### 9.4 低消費電力からの復帰

低消費電力からの復帰では、過去の`targetOutput`および`appliedOutput`を再開用に使用しない。

復帰後は`OUTPUT_DISABLED`から無出力初期化を行い、走行利用可否を再確立する。走行可能状態へ戻っても、新しい走行指令がない限り`STOPPED_READY`の零出力を維持する。

### 9.5 ドライバ再初期化

モータドライバ再初期化は、走行中に状態を保ったまま通信だけ再開する方式としない。

再初期化前に非零出力を禁止し、旧I2C要求を失効させる。再初期化後は必ず零出力から開始し、新しい走行指令を必要とする。

## 10. 通常停止・安全停止・緊急停止・電力変更準備

### 10.1 停止結果で区別する情報

本機能は「停止完了」という一つの真偽値だけを返さず、少なくとも次を区別する。

- 新規通常走行指令禁止済み
- 未実行通常指令破棄済み
- 左右`targetOutput=0`
- 左右`appliedOutput=0`
- モータドライバへ零出力／停止要求反映済み
- 未完了の旧非零ドライバ要求なし
- ソフトウェア走行出力許可禁止済み
- 独立出力禁止状態の確認結果（確認手段がある場合）
- `powerChangeReady`
- 証拠範囲

証拠範囲は`CONTROL_AND_DRIVER_RESPONSE`等の制御側証拠として扱い、実速度零の測定結果にはしない。

### 10.2 明示的通常停止

停止・緊急停止管理から通常停止目的・停止要求識別子を伴う要求を受けた場合、次を行う。

1. 当該停止取引について新しい通常走行指令を禁止する。
2. 未実行通常指令を破棄する。
3. 左右目標出力を0とする。
4. `R_DECEL`に従って左右適用出力を0へ減少させる。
5. モータドライバへ左右0出力を反映し、正常完了を確認する。
6. 旧非零ドライバ要求が存在しないことを確認する。
7. 同じ停止要求識別子で`DriveStopResult`を停止・緊急停止管理へ返す。

通常停止において、急な逆方向駆動による制動を行わない。

### 10.3 通常停止と物理的停止

通常停止の局所完了は、走行制御が確認可能な出力零・ドライバ反映・旧要求不存在を根拠とする。

製品本体では車体の実速度零を測定しない。路面、傾斜、荷重、キャタピラ状態を含む停止距離・停止時間は、性能・品質・検証基本設計が所有する`T_PHYS_*`の開始点・終了点・初期合否値に従ってE-02で外部測定する。通常停止方法が転倒、過大滑り、キャタピラ脱落、異常電流または機構破損を発生させないことも確認する。

必要な利用者向け停止説明では「走行出力停止確認」と「実速度測定」を混同しない。

### 10.4 安全停止

安全停止では通常の`R_DECEL`完了を待たない。

1. `DRIVE_INVALIDATE`を適用する。
2. 左右目標出力を0とする。
3. 通常ランプをバイパスして、モータドライバへ最短の評価済み停止／零出力要求を開始する。
4. 可能な出力禁止機構を有効側へ維持する。
5. モータドライバ取引結果と出力禁止状態を確認する。
6. 停止・緊急停止管理へ同じ停止要求識別子で局所結果を返す。

安全停止のために一時的な反対方向駆動を生成しない。

DPC-XGL1-JP付属モータドライバにおける零出力時の惰性走行（coast）／制動（brake）等の実際の電気的動作はE-03/E-02で確認する。確認前に特定の制動方式を仮定しない。

### 10.5 緊急停止

ソフトウェアで受ける緊急停止要求については、安全停止と同じ安全優先走行停止を行う。

本体側緊急停止操作では、システム構成/停止・緊急停止管理で定める独立した走行駆動出力禁止経路が、通常ソフトウェア処理および通常I2C通信に依存せず並行して動作する。

本機能は独立経路の作動を妨げず、ソフトウェアが実行可能な場合は通常指令の破棄、モータドライバへの零出力要求、状態・ログ更新を行う。

独立停止経路に動作状態を確認する信号がない場合、ソフトウェアだけで「独立経路が物理的に作動済み」と推測して返さない。確認可能範囲を`DriveStopResult`へ明示する。

### 10.6 時間性能

公開用システム要求仕様「22. 性能・品質・耐久性」に従い、次の上位時間要求を侵食しない。

- 有効な通常停止・安全停止条件検出から走行停止出力更新開始：100 ms以内
- 本体側緊急停止入力変化検出から走行停止出力または出力無効化開始：50 ms以内
- 本体が有効な緊急停止要求を受けてから走行駆動出力無効化開始：50 ms以内

本機能内では、停止・緊急停止管理等から有効停止要求を受けてから次の走行制御周期を待つだけで停止開始が遅れない構成とし、**20 ms以内を局所的な停止出力更新開始目標**とする。

この20 msは全体停止完了時間ではなく、本機能が安全側の出力更新を開始するまでの内部配分である。

停止・緊急停止管理の`T_CTRL_NORMAL_STOP_TX_MAX`、`T_CTRL_SAFE_STOP_TX_MAX`、`T_CTRL_ESTOP_TX_MAX`および`T_CTRL_COMMAND_TIMEOUT_TO_TX_MAX`は、`DriveStopResult`を含む制御側停止取引の完了上限である。本機能は局所結果をこの期限内に返せるよう設計するが、停止・緊急停止管理の評価指標を車体実速度零の測定時間へ読み替えない。

車体の物理停止時間・停止距離は性能・品質・検証基本設計の`T_PHYS_*` 評価指標で外部測定する。走行制御は減速率、通常停止方式、安全優先の零出力／禁止方式およびドライバへの反映方法を定め、物理停止の合否値を別に定めない。

### 10.7 通常終了・低消費電力移行

通常終了・低消費電力移行では、停止・緊急停止管理が管理する停止取引を唯一の通常物理停止要求経路とする。

- 通常終了：起動・終了・再起動管理の終了識別子を停止・緊急停止管理の停止要求識別子へ相関
- 低消費電力：電源・省電力管理の移行識別子を停止・緊急停止管理の停止要求識別子へ相関

本機能は、停止・緊急停止管理から受けた停止目的に従い、通常停止方式で左右出力を0とし、旧指令を破棄し、モータドライバを停止側へ移し、`powerChangeReady`を返す。

実際の`PWR_DRIVE`電源OFFは電源・省電力管理が行う。

電源・省電力管理から同じ物理停止を直接重複して実行する要求経路を設けない。

### 10.8 既に停止済みの場合

要求受信時点で左右出力0、非零未処理要求なし、出力禁止が維持され、未復旧の停止異常がない場合、物理停止を再実行せず`PREEXISTING_OFF`または同等の局所結果を返せる。

過去の停止失敗が未復旧である場合、この分岐で正常化しない。

### 10.9 停止失敗

次を停止失敗として扱う。

- 左右0出力要求を正常完了できない。
- I2C取引結果が不明。
- 片側だけ停止要求が反映された。
- 旧非零要求の残存を排除できない。
- 出力禁止後に非零要求が再び反映された。
- 停止結果の確認情報が不整合。

停止失敗を停止・緊急停止管理/異常管理へ通知し、停止・緊急停止管理が追加安全処理、異常管理が影響・復旧を判断する。

`PWR_DRIVE`遮断または独立停止経路によって最終的に駆動が止まった場合でも、当初のソフトウェア停止失敗を正常へ書き換えない。

## 11. 過負荷・拘束監視

### 11.1 検出方針

本機能はバッテリー・電気安全監視が提供する**走行駆動系合計電流**と走行指令・適用出力の組合せから、走行固有の過負荷または拘束疑いを検出する。

左右個別電流または実回転速度を取得しないため、左右のどちらが拘束したかを常に特定できるとは扱わない。異常情報では`affectedSide=UNKNOWN_OR_DRIVE_SYSTEM`を許容する。

### 11.2 バッテリー・電気安全監視から受け取る監視値スナップショット

少なくとも次を同じスナップショットとして使用する。

- 現在の走行駆動系電流状態
- `I_RMS20`
- 必要な場合の`I_RMS500`、`I_RMS2000`
- 最大値
- 計測更新世代
- 取得・確定時刻
- 品質・有効性
- 各時間窓の有効サンプル数・必要サンプル数・全窓成立可否
- `PWR_DRIVE`の監視対象状態
- 電気安全側の保護状態・新規出力禁止

同じ計測更新世代を再読して、過負荷継続時間を新たに加算しない。

欠測区間を0 A、直前値または平均値で補間しない。

### 11.3 電気安全保護との分離

バッテリー・電気安全監視が持つ危険過電流、低電圧、温度およびハードウェア保護を本機能で再定義しない。

バッテリー・電気安全監視の暫定走行駆動系電気安全値を、そのまま本機能の拘束しきい値として使用しない。

走行固有の拘束判定が「正常」となっても、バッテリー・電気安全監視の電気保護を解除、緩和または遅延させない。

### 11.4 走行負荷区分

合計電流を評価するため、指令・出力上の負荷区分を少なくとも次に分ける。

| 区分 | 条件 |
| --- | --- |
| `OUTPUT_OFF` | 左右適用出力0 |
| `START_TRANSIENT` | 停止から非零出力を開始した評価済み短時間 |
| `TWO_SIDE_DRIVE` | 左右とも非零出力 |
| `ONE_SIDE_DRIVE` | 片側停止旋回等で片側のみ非零 |
| `TURNING` | 左右とも同符号だが出力差がある走行 |
| `REVERSAL_TRANSIENT` | 方向反転の減速・零待ち・再始動区間 |
| `NORMAL_STOPPING` | 通常減速で零へ移行中 |

`TURNING`を`TWO_SIDE_DRIVE`へ統合できるかはE-04で正常負荷分布と拘束検出の分離を評価する。統合しても第11.8節の分離条件とSYS-DRIVE-050～052を満たせることを確認した場合に限って採用し、負荷区分構成を変更する場合は詳細設計だけで変更せず本基本設計へ反映する。

### 11.5 基本判定方式

負荷区分ごとに、評価済みの機能過負荷しきい値`I_DRIVE_TRIP[c]`、ヒステリシス`H_DRIVE[c]`を持つ。

有効な`I_RMS20`について、次を基本とする。

```text
I_RMS20 >= I_DRIVE_TRIP[c] が T_DRIVE_OVER 以上継続
    -> 走行過負荷・拘束疑い

I_RMS20 <= I_DRIVE_TRIP[c] - H_DRIVE[c] が T_DRIVE_CLEAR 以上継続
    -> 過負荷候補を解除可能
```

`T_DRIVE_OVER=100 ms`、`T_DRIVE_CLEAR=100 ms`を評価開始用の暫定基本値とする。`I_DRIVE_TRIP[c]`、`H_DRIVE[c]`とともにE-04で実機評価し、評価結果を本基本設計へ反映して正式値として確定する。これらは詳細設計専用値ではなく、過負荷・拘束の成立時点と安全停止開始を決める値として、基本設計で管理する。

`I_DRIVE_TRIP[c]`および`H_DRIVE[c]`は現時点で実測根拠がなく評価確定待ちである。E-04による分離成立確認と本基本設計への正式値反映が完了するまでは、評価済み走行安全プロファイルとして一般利用の通常走行を許可しない。E-04の開発・評価では、バッテリー・電気安全監視の電気安全保護、現行`U_MAX`、出力禁止および評価手順上の安全条件を維持し、未確定の走行固有しきい値を正常保護として仮定しない。

始動・方向反転による一時電流増加を無期限に許可しない。バッテリー・電気安全監視の一時増加区間200 ms以内という電気安全上の扱いと整合し、本機能の一時区間も200 msを超えて延長しない。

### 11.6 全窓未成立時

`I_RMS20`の20 ms全窓がまだ成立していない場合、取得済み有効区間の値を「完全な20 ms窓で過負荷が継続した」として使用しない。

開始直後は、取得済み値の品質、バッテリー・電気安全監視の高速電気保護および始動一時区間を維持し、全窓成立後に通常の走行固有判定へ移る。

### 11.7 監視値利用不能

非零走行出力中に、走行固有の過負荷監視に必要な電流スナップショットが無効・更新停止・確認不能となった場合、監視不能のまま走行を継続しない。

本機能は新しい非零出力を禁止し、停止・緊急停止管理へ安全停止を要求する。監視値異常自体の通知は、正式な管理元であるバッテリー・電気安全監視が行い、本機能は走行への影響を異常管理へ提供する。

### 11.8 拘束検出の成立条件

E-04では、前進、後退、直進、旋回、片側停止旋回、始動、通常停止、方向反転、傾斜および実際の片側／両側拘束について合計電流を測定する。

評価済みの全通常条件と検出対象拘束について、少なくとも次の分離が成立することを確認する。

```text
正常負荷最大 + 測定・個体差・環境余裕
    < I_DRIVE_TRIP[c]
    <= 検出対象拘束の最小電流 - 検出余裕
```

この分離が成立しない場合、「しきい値を設定した」だけでSYS-DRIVE-050～052を満たしたことにしない。左右個別電流、回転情報その他の監視方式の追加、または要求・ハードウェア設計の見直しをフィードバックする。

### 11.9 過負荷・拘束成立時

1. `DRIVE_INVALIDATE`を適用する。
2. 停止・緊急停止管理へ過負荷・拘束を理由とする安全停止を要求する。
3. 左右出力を安全停止方式で0／禁止側へ移行する。
4. 異常管理へ負荷区分、指令、適用出力、電流、継続時間、計測世代を通知する。
5. バッテリー・電気安全監視の電気安全処理を妨げない。
6. 明示的な復旧完了まで新規走行を禁止する。

停止・異常通知・ログ保存の順序待ちで走行停止を遅延させない。

## 12. 異常処理と復旧

### 12.1 走行制御異常分類

少なくとも次を識別する。

| 異常 | 主な検出例 | 一次処理 |
| --- | --- | --- |
| 走行指令異常 | 指令データの値域外、内容の矛盾、操作セッションや操作世代の不整合 | 指令拒否。安全継続不能なら安全停止 |
| モータドライバ通信異常 | NACK、タイムアウト、応答不正、結果不明 | 新規出力禁止、安全停止 |
| 走行出力更新異常 | 左右部分更新、要求値／応答不整合 | 安全停止 |
| 走行出力無効化異常 | 零出力不能、旧非零要求残存、停止後再出力 | 停止失敗として追加安全処理要求 |
| 走行過負荷・拘束 | 第11章の持続条件 | 安全停止、機能制限 |
| 走行設定異常 | 未設定、範囲外、プロファイルの不一致 | 出力禁止、機能利用不可 |
| 走行制御周期異常 | 正常周期完了が進行しない、期限超過 | 安全停止・出力禁止連携 |

### 12.2 異常管理への通知

異常管理へ少なくとも次を提供する。

- 走行異常区分
- 異常通知取引識別子
- 発生時の走行動作状態
- 左右の目標出力・適用出力・ドライバで確認済みの出力
- モータドライバとの通信処理・結果
- 走行安全プロファイル世代
- 電流スナップショットの計測更新世代・品質・値
- 関連する停止要求識別子・電気安全事象
- 現在の局所利用可否
- 原因解消判定に必要な情報

異常管理の受付結果を待って一次停止を遅延しない。

### 12.3 同一異常と停止取引

走行異常を検出して停止・緊急停止管理へ安全停止を要求した後、異常管理から同じ異常に対する停止処置が要求された場合、同じ物理停止を重複して開始しない。

異常処置要求識別子と停止・緊急停止管理の停止要求識別子を対応付け、進行中または確定済みの局所停止結果を返す。

### 12.4 原因解消

| 異常 | 原因解消に必要な局所条件 |
| --- | --- |
| 指令異常 | 不正指令を破棄し、内部状態正常。新しい正常指令は新規検証 |
| ドライバ通信異常 | 出力禁止、バスまたはドライバの異常原因解消、無出力再初期化・状態確認 |
| 出力更新・停止異常 | 原因是正、無出力確認、必要な停止試験再実施 |
| 過負荷・拘束 | 障害物・機構拘束解消、損傷なし確認、バッテリー・電気安全監視が正常、停止維持正常 |
| 設定異常 | 評価済み安全プロファイルまたは正常設定の復元・再検証 |
| 周期異常 | 実行基盤原因解消、監視再確立、無出力診断正常 |

電流が零になっただけで機械的拘束原因解消とは判定しない。

### 12.5 復旧シーケンス

1. 原因解消結果を異常管理へ提供する。
2. 異常管理から対象・権限を確認済みの復旧開始要求を受ける。
3. 非零出力禁止のまま、設定、I2C、ドライバの状態、監視、出力零を診断する。
4. 同じ復旧要求識別子で局所結果を返す。
5. 異常管理の最終復旧結果を確認する。
6. 当該異常に対応する局所制限だけを解除する。
7. `STOPPED_READY`へ戻せる条件が成立しても、以前の走行指令を再開しない。

### 12.6 再起動による自動復旧禁止

明示的復旧を必要とする異常を、再起動・`PWR_DRIVE`再投入・I2C初期化だけで解消済みとしない。

未復旧異常の正式な管理元は異常管理とし、本機能は起動時に適用される制限へ従う。

## 13. 関連機能とのインターフェース

### 13.1 基本原則

本章の名称は論理インターフェースを示し、具体的な関数名・メッセージID・構造体の配置を固定するものではない。

要求、受付、進行中、局所完了、失敗、取消し、上位処理による中断を区別する。

### 13.2 受信する情報・要求

| IF | 送信元 | 内容 | 主な返答 |
| --- | --- | --- | --- |
| IF-01 | システム状態管理 | 現在状態、状態遷移に関する情報、operationAvailability、主制限理由、状態の世代 | DriveAvailability、局所制限 |
| IF-02 | BLE接続・認証 | BLE共通の通信情報と走行指令データ | DriveCommandValidationResult、実行結果 |
| IF-03 | 停止・緊急停止管理 | 停止目的、停止要求識別子、上位相関ID | DriveStopResult |
| IF-04 | 起動・終了・再起動管理 | 起動段階識別子、初期化要求 | 3区分初期化結果 |
| IF-05 | 電源・省電力管理 | `PWR_DRIVE`要求／実状態、復帰・再初期化条件 | 無出力初期化、電力変更に対する本機能の処理結果 |
| IF-06 | バッテリー・電気安全監視 | 走行電流スナップショット、電気安全使用可否、出力禁止 | DriveActivity、局所停止結果 |
| IF-07 | 異常管理 | 機能制限、復旧開始、最終復旧結果 | 原因解消・局所診断結果 |
| IF-08 | 設定管理 | 設定PREPARE/APPLY/GLOBAL_COMMIT/ROLLBACK | 本機能での設定検証結果・適用結果 |
| IF-09 | ログ・診断 | 診断・評価トレース取得要求 | 走行診断・トレース情報 |
| IF-10 | 状態表示・利用者通知 | 状態参照 | 走行利用可否・出力状態・異常の概要 |

### 13.3 BLE接続・認証へ返す走行指令結果

`DriveCommandValidationResult`は少なくとも次を区別する。

- VALID / INVALID
- ACCEPTED / INHIBITED / STALE_CONTEXT / SUPERSEDED
- 対象`sessionId`、`commandSeq`、`requestId`との相関
- 受信した通信データ内の`actuationEpoch`
- 指令データの検証結果とその理由
- 受付時の現行`driveEpoch`
- 継続走行対象か

BLE接続・認証はこの結果を使用して最終有効受信情報を確定する。

### 13.4 走行継続状態

本機能は停止・緊急停止管理へ、少なくとも次を提供する。

- 継続走行入力が必要な動作中か
- 対象操作セッション
- 現在`driveEpoch`
- 走行中／零目標への通常減速中／停止済み

停止・緊急停止管理がBLE接続・認証の最終有効受信情報と組み合わせて操作指令タイムアウトを判断する。

### 13.5 `DriveStopResult`

少なくとも次を含む。

- 停止・緊急停止管理の停止要求識別子
- 停止目的
- 上位相関識別子
- `ACCEPTED / IN_PROGRESS / COMPLETED / FAILED / CANCELLED / PREEMPTED / UNKNOWN`
- 新規走行禁止結果
- 通常指令破棄結果
- 左右`appliedOutput`零確認
- ドライバ零出力取引結果
- 旧非零I2C要求不存在確認
- 出力禁止維持可否
- 独立停止経路の確認範囲
- `powerChangeReady`
- 証拠範囲

停止・緊急停止管理はこの局所結果を他アクチュエータ結果と集約し、停止取引全体を完了させる。

### 13.6 `DriveActivity`

バッテリー・電気安全監視等へ次を提供可能とする。

- 左右の目標出力・適用出力
- 出力符号
- 走行負荷区分
- 始動／反転／停止一時区間の開始・終了
- 左右出力零確認時刻
- `PWR_DRIVE`利用要求の有無

これは実速度・実負荷の測定値ではない。

### 13.7 `DriveAvailability`

システム状態管理/状態表示・利用者通知へ次を提供する。

- 走行機能利用可能／利用不可
- 出力禁止中か
- 走行安全プロファイル有効性
- ドライバ通信利用可否
- 過負荷監視利用可否
- 未復旧の走行固有制限理由

システム全体の`operationAvailability`はシステム状態管理が最終判断する。本機能は全体可否を再決定しない。

### 13.8 `ControlProgressCheckpoint`

重要周期処理の正常完了ごとに、少なくとも次をシステム監視経路へ提供する。

- `controlProgressSeq`
- 最終正常完了時刻
- 現行`driveEpoch`
- 制御周期を監視すべき状態か
- 意図的休止中か

本機能がこのチェックポイントだけを理由としてIWDTを更新しない。

### 13.9 重複・遅延・再送

同じ停止要求識別子の再送では、同一停止取引の進行中または確定結果を返し、物理停止を二重実行しない。

古い完了結果を新しい停止・設定・復旧要求へ流用しない。

結果不明は正常完了へ変換しない。

停止前に送信済みで、同じBLEセッション内の未受信`commandSeq`として停止後に到着した走行指令も、受信`actuationEpoch`が現行`driveEpoch`と一致しなければ`STALE_CONTEXT`として拒否する。`commandSeq`が大きいことだけで停止境界後の新指令へ昇格させない。

## 14. 設定・走行安全プロファイル

### 14.1 初期製品の設定方針

公開用システム要求仕様「07. 走行制御」は最大走行出力、加速、減速、方向反転、中立判定および過負荷・拘束判定に関する設定を要求している。

本初版では、これらを**評価済み走行安全プロファイルとして本体側に保持する安全関連設定**とし、VPSのREMOTE_MANAGED設定にはしない。

理由は次のとおりである。

- 最大出力・加減速・方向反転は機体質量、路面、キャタピラ、電源・モータ特性に依存する。
- 過負荷・拘束しきい値は実測分離を確認するまで遠隔変更可能にすべきでない。
- 公開要求は「設定を適用すること」を要求するが、遠隔変更を要求していない。
- 設定管理のschemaVersion 1は、走行基本設計未完成を理由に`settings.drive`を含めていない。

将来、正式な評価済み範囲と運用上の必要性が確定した場合だけ、設定管理の新しいschemaVersionで一部項目をREMOTE_MANAGED化する。

### 14.2 設定項目

| 項目 | 型・単位 | 初版の扱い | 未設定・不正時 |
| --- | --- | --- | --- |
| `commandRange` | 符号付き整数 | -1000..+1000固定 | 未対応のコマンド拒否 |
| `D_NEUTRAL_LONG` | 0..999 | 初期基本値50 | 通常走行不可 |
| `D_NEUTRAL_TURN` | 0..999 | 初期基本値50 | 通常走行不可 |
| `U_MAX` | 1..1000 permille | 初期基本値300。E-01で妥当性確認 | 通常走行不可 |
| `R_ACCEL` | 正数、permille/s | 初期基本値600。E-01で妥当性確認 | 通常走行不可 |
| `R_DECEL` | 正数、permille/s | 初期基本値1200。E-01/E-02で妥当性確認 | 通常走行不可 |
| `T_REVERSE_ZERO_HOLD` | 正整数、ms | 初期基本値200。E-02で妥当性確認 | 方向反転を許可しない |
| `I_DRIVE_TRIP[c]` | mA | 基本設計で管理し、評価結果を基に確定する値。E-04評価後に本基本設計へ区分別正式値を反映 | 通常走行不可 |
| `H_DRIVE[c]` | mA | 基本設計で管理し、評価結果を基に確定する値。E-04評価後に本基本設計へ正式値を反映 | 通常走行不可 |
| `T_DRIVE_OVER` | ms | 暫定基本値100。E-04評価後に本基本設計へ正式値を反映 | 通常走行不可 |
| `T_DRIVE_CLEAR` | ms | 暫定基本値100。E-04評価後に本基本設計へ正式値を反映 | 通常走行不可 |
| `driverProfileId` | 識別子 | 採用ドライバ仕様と一致必須 | 利用不可 |
| `motorPolarity[2]` | ±1相当 | 製品・機構固定 | 利用不可 |
| `driveEvaluationRevision` | revision | 現行構成の評価済み版 | 不一致なら通常走行不可 |

### 14.3 設定妥当性

少なくとも次を確認する。

- 中立範囲が0以上1000未満。
- `U_MAX`が1..1000の範囲内であり、現在の評価済みの版で許容された上限以下。
- `R_ACCEL`、`R_DECEL`が正で現在の評価済みの版の許容範囲内。
- `T_REVERSE_ZERO_HOLD`が正で、E-02によって確認された最悪条件を満たす。
- 過負荷しきい値・ヒステリシス・継続時間がE-04の分離条件を満たす。
- `motorPolarity`と実機の前進・後退対応が一致する。
- `driverProfileId`が現物モータドライバと一致する。
- 評価済みの版が現行モータ、キャタピラ、機体質量、電源構成へ適用可能。

候補不正値をクランプして正常設定として採用しない。

### 14.4 設定適用

設定管理の原子的設定適用契約へ従う。

将来走行設定をREMOTE_MANAGED化する場合でも、PREPAREで走行出力零・設定受入れ可否を確認し、APPLY中は非零走行を禁止し、GLOBAL_COMMIT後に新設定を使用開始する。

一部機能だけ新設定、他機能は旧設定という混在を許可しない。

### 14.5 初期基本設計値と正式採用

`U_MAX=300`、`R_ACCEL=600`、`R_DECEL=1200`、`T_REVERSE_ZERO_HOLD=200 ms`は、本基本設計で採用する初期値であり、詳細設計はこれらを前提として開始する。ただし、実機未評価の段階で一般利用に対する安全性・操作性を保証する正式工場出荷値とは扱わない。

E-01/E-02では、初期基本設計値のままで公開要求に定める安全性、操作性、停止特性および電気的条件を満たすことを確認する。成立した場合は現行`driveEvaluationRevision`の評価済み値として正式採用する。成立しない場合は、評価結果と変更理由を本基本設計へフィードバックし、値を改訂した上で再評価する。

初期基本設計値を未評価であることだけを理由に詳細設計側で別の値へ置き換えない。また、実機評価を行わず安全側と推測して1000等へ拡大しない。

走行固有過負荷・拘束の`I_DRIVE_TRIP[c]`、`H_DRIVE[c]`、`T_DRIVE_OVER`および`T_DRIVE_CLEAR`も、E-04で評価後に本基本設計へ反映して正式採用する。これらの正式値は走行安全プロファイルの一部であり、詳細設計内だけで変更しない。

## 15. 状態通知・ログ・永続情報

### 15.1 状態表示・利用者通知へ提供する情報

少なくとも次を提供する。

- 走行機能利用可否
- 走行出力禁止中か
- `STOPPED_READY / RAMPING / DRIVING / REVERSAL / STOPPING`等の公開可能な走行状態の概要
- 左右指令出力の概要
- 通常停止・安全停止の局所処理中／結果
- ドライバ通信異常
- 過負荷・拘束異常
- 設定未確定／走行機能制限

状態表示・利用者通知は表示・通知用に変換する。本機能がRGB LEDや7セグを直接制御しない。

### 15.2 一般利用者へ実速度と誤認させない

左右出力値をアプリへ提供する場合は、「走行指令出力」「制御出力」等の意味として提供する。

km/h、rpm、走行距離へ換算して実測値として表示しない。

### 15.3 イベントログ

通常運用で少なくとも次の意味イベントを提供する。

- 初期化・再初期化結果
- 通常走行開始／中立停止
- 前後方向反転開始・結果
- 停止・緊急停止管理の通常停止／安全停止／緊急停止の局所結果
- モータドライバ通信異常
- 出力更新・停止異常
- 過負荷・拘束候補成立・確定・解消候補
- 走行機能制限・復旧
- 設定検証・適用結果
- 制御周期／進行監視異常

継続走行指令を毎周期通常ログへ保存して容量を消費しない。

### 15.4 評価用トレース

評価用に、10 ms走行制御周期へ対応して少なくとも次を取得元としてログ・診断へ提供可能とする。

- `longitudinal`、`turn`
- 不感帯処理後の`d`、`t`
- 左右`targetOutput`
- 左右`appliedOutput`
- 左右のドライバ要求値・結果
- 走行動作状態
- `driveEpoch`
- バッテリー・電気安全監視の電流スナップショットの`I_RMS20`、品質、計測更新世代
- 停止要求識別子・停止結果
- `controlProgressSeq`

トレースのリングバッファ、前後保持時間、永続保存量はログ・診断が管理し、本機能が同じ大容量データを常時重複保持しない。

### 15.5 永続情報

本機能固有の最後の走行指令、左右出力、走行方向を再開目的で永続保存しない。

再起動・電源復帰後は常に走行出力零から開始し、新しい走行指令を必要とする。

保存する走行安全プロファイルの正式な管理元は設定／製品情報側との契約に従い、本機能は現在の版と妥当性を確認する。

未復旧異常の正式な管理元は異常管理とする。

## 16. 実行周期・処理時間の配分・システム監視

### 16.1 走行制御周期

走行制御の論理周期を**10 ms**とする。

周期ごとに少なくとも次を行う。

1. 停止・電気安全・電源・`driveEpoch`の再確認
2. 最新走行指令の取得
3. 不感帯処理・左右モータへの配分・最大出力の適用
4. 加減速・方向反転状態更新
5. モータドライバ出力更新要求
6. 過負荷・拘束監視更新
7. 状態・結果更新
8. 制御周期の正常完了を示すチェックポイントの更新

### 16.2 通常操作応答の内部配分

公開用システム要求仕様「22. 性能・品質・耐久性」の総合150 ms要求に対し、本機能ではBLE接続・認証から有効な走行指令を受け取ってから、モータドライバへの対応出力更新を開始するまで**20 ms以内を内部目標**とする。

これはスマートフォン入力からの総合時間ではない。BLE送信・認証・指令の振分け等は各担当機能の配分を含む。

### 16.3 通常操作終了

有効な中立走行指令を受けてから、左右目標を零へ変更して減速処理を開始するまで20 ms以内を内部目標とする。

初期基本設計値`R_DECEL=1200 permille/s`、`U_MAX=300`では、最大論理出力から適用出力零まで約250 msを要する。公開用システム要求仕様「22. 性能・品質・耐久性」の総合操作終了応答150 msは「操作終了をアクチュエータ出力へ反映するまで」の要求であり、250 msの全減速完了時間とは区別する。中立受信後20 ms以内に減速側の出力更新を開始し、実際の停止距離・停止時間はE-01/E-02で確認する。

### 16.4 停止処理の内部配分

停止・緊急停止管理から有効な通常停止・安全停止・緊急停止要求を受けてから、安全側の走行出力更新を開始するまで20 ms以内を内部目標とする。この内部目標、停止・緊急停止管理の制御側停止処理の評価指標および性能・品質・検証基本設計の車体の物理停止の評価指標を、それぞれ別の終了点を持つ時間条件として管理する。

安全停止・緊急停止はログ保存、状態表示、異常管理応答、I2C通常出力キューを待たない。

### 16.5 I2C処理時間

#### 維持する時間条件

I2Cの正常処理時間に加え、タイムアウトや再試行に要する時間を含めても、次の条件を維持できる構成とする。

- 10 msの走行制御周期
- 20 ms以内の停止出力更新開始目標
- 停止・緊急停止管理基本設計で定める、制御側停止取引の完了上限

性能・品質・検証基本設計で定める物理停止時間は、I2C通信が完了したことだけで合格としない。
停止方式を含む実機評価で確認する。

#### 詳細設計で決める通信仕様

次の項目は、第19.2節のE-03による現物確認後に詳細設計する。

- I2Cアドレスおよび通信速度
- コマンド・応答の形式
- 通信処理のタイムアウト値
- ドライバAPI

ただし、タイムアウト値、再試行、または同期／非同期方式の選択によって、次の条件を変更しない。

- 10 msの走行制御周期
- 20 msの局所応答目標
- 通信異常時の即時の新規出力禁止
- 第10.6節の停止開始時間

#### 条件を満たせない場合

これらの条件を成立させられない場合は、詳細設計だけで時間条件を緩和しない。
本基本設計または関連ハードウェア設計へフィードバックする。

### 16.6 制御の進行を示すチェックポイント

正常な走行制御周期を最後まで完了したときだけ`controlProgressSeq`を増加させる。

処理入口で増加させない。I2C待ち、ロック待ち、計算異常等で周期途中に停止した場合を正常進行として見せない。

### 16.7 独立したシステム監視

`controlProgressSeq`、最終正常完了時刻、現在の走行制御有効／意図的休止状態を、走行制御自身とは独立したシステム監視経路へ提供する。

システム監視経路は、現在のシステム状態で走行制御が監視対象の場合に進行を確認し、停止・デッドロック・期限違反を異常管理およびIWDT更新許可条件へ連携する。

本機能自身がIWDTを直接更新しない。

### 16.8 IWDTより早い安全化

走行制御進行停止時にIWDTリセットを待つと停止性能を満たせない場合、システム監視経路から停止・緊急停止管理または独立走行出力禁止経路へ、安全停止・出力禁止を先行要求できる構成とする。

具体的なシステム監視周期・処理の進行停止を判定する時間は本書で固定せず、本体ソフトウェアアーキテクチャで全重要周期処理をまとめて確定する。

### 16.9 低消費電力・意図的休止

`PWR_DRIVE`停止、低消費電力または明示的な制御休止中は、10 ms周期が進まないことを異常としない。

休止開始・復帰時はシステム監視へ監視モードを明示し、復帰後は出力禁止でチェックポイントを再確立してから通常走行を許可する。

## 17. 検証方針と確認ケース

### 17.1 指令・左右モータへの配分

- -1000～+1000の境界値と範囲外拒否
- 中立範囲±50付近のチャタリング防止
- `d=0`で`turn`最大でも左右出力0
- 前進・後退直進で左右同符号同出力
- 前進右／左、後退右／左の旋回方向
- 最大旋回で内側モータ0、外側モータだけ進行方向
- 全組合せで左右が反対符号にならない
- 旧走行指令をFIFO再生しない
- 停止前に送信済みの指令が同じセッションの未受信`commandSeq`で停止後に遅延到着しても、旧`actuationEpoch`として`STALE_CONTEXT`拒否され、指令スロットおよび最終有効受信情報を更新しない

### 17.2 加減速・方向反転

- `U_MAX=300`で最大論理出力が300を超えないこと
- `R_ACCEL=600 permille/s`で停止→最大出力が約500 msとなること
- `R_DECEL=1200 permille/s`で最大出力→零が約250 msとなること
- 走行中の速度操作変更
- 旋回量急変時の左右別変化率
- 前進→後退、後退→前進
- 反転中に再度指令方向が変化した場合の最新指令優先
- 出力零・I2C零反映・旧要求不存在・`T_REVERSE_ZERO_HOLD=200 ms`成立前に逆方向を開始しない
- 最大出力から反転した場合に反対方向開始まで少なくとも約450 ms＋I2C処理時間を確保すること
- 周期遅延後に一回で大出力へ追い付かない
- 初期基本設計値について転倒、滑り、キャタピラ脱落、異常電流、機構衝撃および操作性を実機で確認する

### 17.3 通常停止

- 中立入力による通常減速
- 停止・緊急停止管理の通常停止要求による停止取引
- 高出力・最大質量・各路面・傾斜での停止距離と停止時間
- 停止時の転倒、過大滑り、キャタピラ脱落、異常電流、機構衝撃
- 通常停止失敗から停止・緊急停止管理の安全停止への移行

### 17.4 安全停止・緊急停止

- 安全停止で通常ランプ完了を待たず零出力更新開始
- BLE緊急停止によるソフトウェア停止
- 本体側緊急停止の独立経路とソフトウェア停止の同時動作
- I2Cハング／NACK中にも独立経路で出力禁止開始
- 片側I2C更新だけ成功した場合の安全化
- 停止後に旧非零要求が再実行されない
- 同一停止要求再送で物理停止を二重実行しない

### 17.5 モータドライバ通信

- I2Cアドレス／コマンド／応答の現物照合
- 左右方向・出力・零出力の全境界
- NACK、バスエラー、タイムアウト、応答破損
- ドライバの異常通知／状態の取得
- 結果不明の非零取引を無条件再送しない
- 再初期化後に旧走行出力を復元しない
- 10 ms周期・20 ms内部応答目標を通信負荷下で満たす

### 17.6 過負荷・拘束

- 左右直進、後退、旋回、片側停止旋回
- 始動、方向反転、通常停止の一時電流
- 最大機体質量、傾斜、代表路面
- 左右片側拘束・両側拘束
- 正常負荷と拘束を合計電流で分離可能か
- `I_RMS20`全窓未成立時の扱い
- 同じ計測更新世代再読で継続時間を増やさない
- 欠測・更新期限超過時に走行継続しない
- バッテリー・電気安全監視の危険過電流保護を走行判定が緩和しない
- E-04で確定した`I_DRIVE_TRIP[c]`、`H_DRIVE[c]`、`T_DRIVE_OVER`、`T_DRIVE_CLEAR`が本基本設計の現行値と一致すること

### 17.7 起動・電源・復帰

- 起動中に非零モータ出力を発生させない
- 3区分の起動結果
- `PWR_DRIVE` OFF→ON後に旧出力を再開しない
- 低消費電力復帰後に新指令まで停止維持
- ドライバ再初期化中に非零出力なし

### 17.8 設定

- `U_MAX=300`、`R_ACCEL=600`、`R_DECEL=1200`、`T_REVERSE_ZERO_HOLD=200 ms`が現行基本設計値として適用されること
- プロファイルの不一致、極性不一致
- 不正設定のクランプ採用禁止
- 将来のPREPARE/APPLY/COMMIT/ROLLBACK中に走行しない
- 設定管理のschemaVersion 1が`settings.drive`を受け付けない現行方針との整合

### 17.9 実行監視・同時処理

- `controlProgressSeq`を正常周期完了時だけ更新
- 走行制御タスクの停止・I2C待ち固着
- システム監視からの安全停止先行
- 走行＋砲塔・砲身同時操作
- Wi-Fi/VPS、ログ、状態表示同時実行
- CPU／RAM／スタック／キューに安全余裕があること

### 17.10 長時間・繰返し

- 起動→走行→停止→BLE切断→復帰の繰返し
- 方向反転の繰返し
- 長時間連続走行
- キャタピラ、車輪、軸、取付部、配線、コネクタの摩耗・緩み
- 長時間後も停止性能・通信・電流監視が要求範囲内

## 20. 他文書へのフィードバック

### 20.1 F-01 BLE接続・認証／スマートフォンアプリ

次を共通契約として反映する。

- 走行指令は`longitudinal`、`turn`の符号付き-1000～+1000
- `turn>0`は機体の向きを右、`turn<0`は左
- スマートフォン側も古い未送信走行指令を最新値で置換する
- 切断、認証変更、通常操作終了、停止時に旧走行指令を再送しない
- BLE接続・認証は共通メッセージの管理情報と最終有効受信情報の正式な管理元となり、走行指令データの正常受付結果後に有効受信を確定する
- 継続走行指令は停止・緊急停止管理で確定した基本送信周期50 ms、操作指令タイムアウト300 msに従う

### 20.2 F-02 停止・緊急停止管理

停止・緊急停止管理で定めた停止取引へ、本書の`DriveStopResult`を接続する。

- 通常停止：初期基本設計値`R_DECEL=1200`を用いる通常減速→零出力。ただし実機評価で不成立なら基本設計を改訂する
- 安全停止・緊急停止：通常ランプ完了を待たない安全優先零出力／禁止
- 停止証拠は制御側・driver responseであり実速度測定ではない
- 停止・緊急停止管理の`T_CTRL_*`は制御側停止取引、性能・品質・検証基本設計の`T_PHYS_*`は外部測定する車体物理停止として、一方の合格を他方へ読み替えない
- 同一停止要求の再送で二重物理停止しない
- 通常終了／低消費電力は`powerChangeReady`を局所結果として返す

### 20.3 F-03 バッテリー・電気安全監視

バッテリー・電気安全監視の監視値スナップショット契約は本書で受けた。

走行固有過負荷しきい値をバッテリー・電気安全監視の危険過電流値へ流用せず、E-04で機能保護値を評価し、本基本設計へ反映して正式確定する。

### 20.4 F-04 電源・省電力管理／電源・ハードウェア

- `PWR_DRIVE`実電力状態の正式な管理元は電源・省電力管理とする
- 走行側は局所停止・出力禁止・電力変更準備だけを返す
- DPC-XGL1-JPモータドライバの電源投入／遮断時に不意なモータ駆動が出ないことを確認する
- 本体側緊急停止の独立走行出力禁止経路、信号極性、read-back、リセット時safe stateをハードウェア設計で具体化する

### 20.5 F-05 設定管理

初期製品では走行設定をREMOTE_MANAGEDにしないため、設定管理のschemaVersion 1へ`settings.drive`を追加しない。

`U_MAX=300`、`R_ACCEL=600`、`R_DECEL=1200`、`T_REVERSE_ZERO_HOLD=200 ms`を本基本設計の初期値として使用し、E-01/E-02で正式採用可否を確認する。走行固有過負荷・拘束の評価確定待ち値はE-04後に本基本設計へ反映して走行安全プロファイルの正式値とする。将来、評価済みfactory value・許容範囲と遠隔変更の必要性が確定した場合、新しいschemaVersionで追加する。

### 20.6 F-06 ログ・診断

第15.4節の10 ms走行トレース項目を、ログ・診断の固定容量評価用トレースへ接続する。

本機能が無制限bufferを持たない。

### 20.7 F-07 本体ソフトウェアアーキテクチャ

- 走行制御10 ms周期
- `controlProgressSeq`
- 独立システム監視
- 走行制御からIWDTを直接更新しない
- 必要時はIWDTリセットより先に安全停止／独立出力禁止を要求できる

という共通実行監視方式を本体ソフトウェアアーキテクチャへ反映する。

### 20.8 F-08 インターフェース・通信／ハードウェア

E-03でモータドライバの具体的なI2Cプロトコルを確認し、インターフェース基本設計へ次を一意に集約する。

- I2Cアドレス・通信速度
- 左右出力・方向・停止コマンド
- 応答／異常状態
- タイムアウト／再試行／再初期化
- 信号レベル／電気条件
- 独立緊急停止との関係

公開用システム要求仕様「07. 走行制御」の通信正常完了・異常通知を現物ドライバが提供できない場合は、必要なハードウェア監視方式を追加検討する。

### 20.9 F-09 状態表示・利用者通知

状態表示・利用者通知へ走行機能の局所利用可否、出力禁止状態、走行異常の概要を提供する。

システム全体の`operationAvailability`と`primaryRestrictionReason`はシステム状態管理が管理する現在値を使用し、状態表示・利用者通知や本機能で再合成しない。

## 21. 初版の自己確認結果と引継ぎ条件

### 21.1 自己確認結果

初版作成後に全章を通して次を確認した。

- 公開用システム要求仕様「07. 走行制御」の31要求すべてへ主対応章を設定した。
- 進行方向成分・旋回成分の論理値域と本体側中立範囲を具体化した。
- 進行中の旋回および片側停止旋回を実現し、超信地旋回を生成しないmix方式とした。
- 進行成分中立時に旋回成分だけでモータを駆動しない構成とした。
- 左右モータの実速度・実距離を存在しない測定値として扱っていない。
- 最大出力、加減速および方向反転待ち時間について、`U_MAX=300`、`R_ACCEL=600`、`R_DECEL=1200`、`T_REVERSE_ZERO_HOLD=200 ms`を初期基本設計値として定め、実機評価で正式採用可否を確認する構成とした。
- 前進／後退反転で出力零と200 msの零保持条件を経由する方式を定めた。
- BLE接続・認証をBLE共通メッセージの管理情報と最終有効受信情報の正式な管理元とし、走行制御が管理する`driveEpoch`を通信データ内の`actuationEpoch`で受け渡し、走行側が停止境界をまたぐ古い操作世代の指令を受付前と実行直前に拒否する構成とした。
- 走行側へ独立した操作指令タイムアウト判定を重複実装していない。
- 停止・緊急停止管理の停止目的・停止要求識別子・上位相関IDを保持し、停止取引の局所結果を返す構成とした。
- 通常停止と安全／緊急停止の停止方法を分離した。
- 本体緊急停止の独立走行出力禁止経路を通常I2C停止へ置換していない。
- 停止結果を実速度零の測定結果と誤認しないよう証拠範囲を分離した。
- 電源・省電力管理を`PWR_DRIVE`実状態の正式な管理元とし、本機能が電源ON/OFFを直接決定しない構成とした。
- 低消費電力・通常終了の物理停止要求を停止・緊急停止管理経由に一本化し、電源・省電力管理との二重停止を作っていない。
- バッテリー・電気安全監視の品質・世代・時間窓付き監視値スナップショットを使用し、同一世代再読・欠損補間を過負荷継続時間へ使用しない構成とした。
- 電気安全保護と走行固有過負荷保護を分離した。
- 合計電流による拘束検出の成立性をE-04で明示確認し、成立しない場合の設計フィードバックを隠していない。
- 走行固有過負荷・拘束の正式しきい値・ヒステリシス・継続時間をE-04評価後に本基本設計へ反映する構成とした。
- モータドライバI2C protocolを資料未確認のまま推測していない。
- ドライバ通信結果不明時に古い非零要求を無条件再送しない構成とした。
- 起動、再初期化、電源復帰後に以前の走行出力を自動再開しない構成とした。
- 設定管理の現行schemaVersion 1へ未評価の走行設定を追加していない。
- 走行制御10 ms周期の正常完了を示すチェックポイントを独立システム監視へ提供し、本機能自身がIWDTを更新しない構成とした。
- 150 ms操作応答、100/50 ms停止出力開始要求を満たすための内部20 ms目標を設定した。
- `malloc/free`や無制限走行指令FIFOを必要としない固定資源方式で詳細設計可能な構成とした。

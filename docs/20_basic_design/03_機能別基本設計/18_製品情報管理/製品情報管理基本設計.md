## 1. 本書の目的

### 1.1 目的

本書の目的は、システムアーキテクチャで独立機能として定義した「製品情報管理」について、各機能が同じ製品・個体・ハードウェア・校正情報を一貫して参照できる基本方式を定めることである。

公開用システム要求仕様には「製品情報管理」という単独章は存在しない。本機能は、VPS接続・デバイス認証、ログ・診断、OTA更新、永続データ管理、データ・プライバシー管理、セキュリティ管理、管理Webアプリ、法令・規格・量産移行等に分散している製品固有情報の責任を、システムアーキテクチャの情報の管理原則に従って集約する。

### 1.2 対象範囲

本書は、Tank_Robot本体におけるDevice ID、製品・機種識別、ハードウェア構成識別、製造情報、個体別校正情報、実行中ファームウェア識別その他の製品固有情報について、正式な管理元、生成元、保存場所、整合性確認、更新権限、利用条件、工場初期化時の保持および関連機能との責任分界を具体化する。

製品情報管理は、製品情報を通常設定として自由に変更する機能ではない。製品・機種・ハードウェアプロファイルの識別情報は固定ブートとapplicationが同一sourceから生成するProduct Descriptorを基準となる情報とし、個体別製造・校正情報は製造・開発・保守工程だけで更新できる製品固有データとして扱う。

#### 基本設計と詳細設計の区分

本書で定めるDevice ID形式、Product Descriptor項目、Unit Product Data上限、revision、rollback条件、更新transaction、startup上限、calibration domain数その他、利用可否・互換性・安全動作に影響する方式または値は、評価確定待ちを含む基本設計で定める事項とする。実機評価で変更が必要となった場合は詳細設計だけで変更せず、本書または値・方式を定める関連基本設計へ反映する。byte offset、C構造体、driver API、task、具体storage address等、外部から見た振る舞いを変更しない実装方法は詳細設計で具体化してよい。

## 2. 設計方針と適用範囲

### 2.1 基本方針

製品情報管理は次の原則で設計する。

1. Device ID、製品、機種、ハードウェア構成、製造情報、校正情報、firmware情報を利用者データと分離する。
2. 製品・機種・hardwareProfileIdは通常VPS設定、所有者操作またはfactory resetで変更しない。
3. Device IDはRA8M2 128 bit Unique IDを元に、同じUnique IDには常に同じ値が得られる規則で生成し、通常NVMへ重複保存しない。
4. 製品・機種・hardwareProfileIdは固定ブートとapplicationで同じ生成済みProduct Descriptor sourceを使用する。
5. 個体別製造・校正情報は一つのUnit Product Dataスナップショットを機能上の更新単位として原子的に更新し、部分更新済みの混在状態を通常利用しない。
6. Unit Product Data snapshotと`highestCommittedProductDataRevision`を一つの物理書込みと仮定せず、データ管理機能が一連の更新を管理し、永続データ管理が保存を行う方式で電源断後も一意に復旧できるようにする。
7. 校正値、安全評価済み限界、component variantを通常VPS設定から自由に変更しない。
8. Product Descriptorはfixed boot trust boundaryまたは署名済みapplication imageの一部として保護する。Unit Product Dataは永続データ管理の記憶媒体への保存とセキュリティ管理のHMAC保護を使用する。
9. firmware identityはrunning imageに対応するsigned/build metadataから取得し、OTA管理上の正常確定済みFW状態およびセキュリティ管理の現在の許可済みSecurityGenと区別する。
10. Product Data全体の正常性と、個々のcalibration domainの利用可否を分離する。一つのdomain不正だけで無関係な正常domainを破棄しない。
11. 製品情報が不正な場合、安全値を推測して補完しない。影響する機能を利用不可またはDEGRADEDとして扱う。
12. 標準`malloc/free`を使用せず、固定構造・固定上限で実装する。

### 2.2 対象範囲

本書の対象は次とする。

- Product Descriptor
- Device ID
- BLE用短縮本体識別子
- hardwareProfileId
- mechanismRevision
- component variant識別
- 製造番号・製造lot等の個体情報
- 個体別校正情報
- Product Dataのrevision・domain approval state
- running firmware identityの参照
- 関連機能へのread-only情報提供
- 製造・開発・保守工程での製品情報更新契約
- 工場出荷状態への初期化・所有者再登録時の保持
- 製品情報異常

### 2.3 対象外

次は本書の対象外とする。

- 一般利用者プロフィール・所有者情報
- BLE端末認証鍵
- Wi-Fi credential
- VPS device private key/certificateの秘密情報そのもの
- VPS管理設定
- 設定package generation
- SecurityGenの正式な管理
- OTA install/recovery state
- event log本体
- 製造履歴DB、部品購買DB、VPS管理Webの製造トレーサビリティDB
- firmware署名生成秘密鍵

## 3. 責任分界と情報の管理原則

### 3.1 機能別責任

| 機能 | 管理する情報・主な責任 |
| --- | --- |
| 製品情報管理 | 製品・機種・HW profile・component class・製造情報・校正情報の意味と利用条件、Device ID生成、Product Data transaction、read-only提供 |
| 永続データ管理 | Unit Product Dataの保存用の複製、commit marker、pending/finalize metadata、CRC、電源断復旧支援 |
| セキュリティ管理 | Unit Product DataのK_SEC_STATE_MAC生成・検証、rollback-sensitive metadata認証 |
| VPS接続・デバイス認証 | Device IDを使うHTTPS/TLS通信、VPSとの対応関係 |
| BLE接続・認証 | advertising/GATT/session、Device ID/short IDの通信上の使用 |
| 設定管理 | REMOTE_MANAGED設定、targetDeviceId、hardwareProfile等との局所照合 |
| OTA更新 | firmware候補のproduct/model/hardware compatibility、FW確定状態 |
| 固定ブート・復旧 | 起動対象imageとProduct Descriptor/Boot Interfaceの互換性、署名済みmetadataの起動前検証 |
| ログ・診断 | 製品/HW/FW情報を診断情報のスナップショットへ収録、ログ保存・VPS送信 |
| 砲塔・砲身制御 | 製品情報から受けた校正・profile値の使用可否と制御上の最終受入れ |
| バッテリー・電気安全監視 | センサ校正情報の使用可否、安全監視上の最終受入れ |
| 異常管理 | 製品情報異常の影響度、通常操作可否、復旧方針 |

### 3.2 情報意味と物理保存を分離する

本書は`hardwareProfileId`や校正値の意味、更新権限、使用可能条件、Product Data transactionの機能側で更新を確定する順序を定める。

永続データ管理はこれらをどのMRAM address、copy、journalへ保存するかを管理し、PERSISTが校正値の安全性やcomponentの意味を独自判断しない。

### 3.3 Product DescriptorとUnit Product Dataを分離する

Product Descriptorは製品buildに固定する情報である。Unit Product Dataは個体差を持つ情報である。

hardwareProfileIdそのものを個体ごとに通常書換え可能なNVM値にはしない。異なるhardwareProfileIdを持つ構成へ改造・置換する場合は、対応するfirmware/Product Descriptorとハードウェア構成を一つの保守・製造変更として扱う。

## 4. 製品情報の論理分類

### 4.1 分類

| 分類 | 代表情報 | 生成・更新元 | factory reset |
| --- | --- | --- | --- |
| BUILD_FIXED | productFamilyId、modelId、hardwareProfileId、component class profile | build/release | 保持 |
| MCU_DERIVED | Device ID | RA8M2 Unique ID | 変化しない |
| UNIT_PROVISIONED | manufacturingSerial、lot、製造日 | 製造・開発工程 | 保持 |
| UNIT_CALIBRATED | servo端点、sensor calibration | 製造・保守工程 | 保持 |
| RUNTIME_BUILD | SemVer、BuildID、firmwareId、build fingerprint、image SecurityGen | running signed image | OTAでimageに応じ変化 |
| SECURITY_REFERENCE | 現在の許可済みSecurityGen、certificate状態等 | セキュリティ管理等 | 本機能を正式な管理元としない |

### 4.2 製品データ全体の状態（Product Data状態）

Unit Product Data全体が`READY`でも、すべての校正項目群が使用可能とは限らない。
全体の構造・完全性の状態と、個々の校正項目群を使用できるかの判断を分ける。

Unit Product Data全体の構造・完全性の状態は、次の4種類で管理する。

- `UNPROVISIONED`
- `READY`
- `DEGRADED`
- `INVALID`

`READY`は、取得した一組の情報（スナップショット）全体について、形式、版・世代、CRC、HMACおよびハードウェアプロファイルとの対応が正常であることを示す。
個々の校正項目群の承認状態と使用可否は、第4.3節で扱う。

### 4.3 校正項目群の承認状態

独立して利用可否を判定する校正値のまとまりを、「校正項目群（calibration domain）」と呼ぶ。
各校正項目群は、製品データ全体の状態とは別に、次の承認状態を持つ。

- `UNPROVISIONED`
- `EVALUATION_ONLY`
- `APPROVED`
- `INVALID`

#### 使用する環境ごとの条件

| 使用する環境 | 校正項目群の承認状態に関する条件 |
| --- | --- |
| 通常運用（`NORMAL_OPERATION`）の製品 | 当該校正項目群を使用する場合は、`APPROVED`を基本とする |
| 開発・評価中 | セキュリティプロファイルが`DEVELOPMENT`または`EVALUATION`であることを条件に、`EVALUATION_ONLY`を使用できる |

`EVALUATION_ONLY`を、量産工場出荷時の校正として扱わない。

#### 一部の校正項目群が不正な場合

一つの校正項目群が`INVALID`でも、他の校正項目群の構造・HMAC・ハードウェアプロファイルの一致が正常なら、その正常な校正項目群まで一律に`INVALID`としない。

影響は、各校正項目群を使用する機能と、異常管理機能が判断する。
全体状態が`READY`であることや承認状態だけで、使用する機能側の最終的な受入れを省略しない。

## 5. Product Descriptor

### 5.1 目的

Product Descriptorは、固定ブート・復旧のfixed boot、application、OTA build toolが同じ製品・機種・hardware profileを識別するためのbuild固定情報である。

### 5.2 基本項目

初期製品では少なくとも次を持つ。

| 項目 | 型・上限 | 初期基本値・意味 |
| --- | --- | --- |
| `descriptorVersion` | uint16 | 1 |
| `productFamilyId` | ASCII 16 byte以下 | `TANK_ROBOT` |
| `modelId` | ASCII 8 byte以下 | `TR1` |
| `hardwareProfileId` | uint32 | 0予約、release/profileごとに割当て |
| `hardwareProfileName` | ASCII 32 byte以下 | 診断用名称 |
| `mechanismRevision` | uint16 | 機構互換性revision |
| `controlBoardVariantId` | uint16 | 制御基板互換class |
| `bleModuleVariantId` | uint16 | BLE module互換class |
| `wifiModuleVariantId` | uint16 | Wi-Fi module互換class |
| `motorDriverVariantId` | uint16 | motor driver互換class |
| `servoVariantId[2]` | uint16×2 | turret/barrel servo互換class |
| `externalFlashVariantId` | uint16 | Serial NOR互換class |

具体ID割当表はhardware/release構成管理で管理する。

### 5.3 component variantの意味

component variant IDは、具体的なメーカー品番やsupplierをそのまま表す番号ではなく、firmware interface、校正方式、安全包絡および互換性の観点で同一として扱えるcompatibility classを表す。

同等部品supplier変更でfirmware、校正schema、安全定格および挙動へ影響しない場合は、同じcomponent variant IDを維持できる。

具体的なMPN、supplier、lot、BOM revisionはhardware/製造管理側の履歴とし、本体Product Descriptorへ無制限に持ち込まない。

### 5.4 生成方法と固定ブート・復旧との分担

Product Descriptorは手作業で複数ソースへ重複記載せず、build/release用の一つのdescriptor sourceから、少なくとも次を生成する方式を基本とする。

- fixed boot用定数
- application用定数
- OTA manifest/firmware signed metadata用定数
- build report用人間可読一覧

本体アプリケーション側descriptorは署名済みimageの一部として保護する。

fixed boot側descriptorは固定ブート・復旧のfixed boot/recovery trust boundaryに含める。固定ブート・復旧はapplication ProductInfo APIへ依存せず、このdescriptorとcandidate imageの署名保護metadataを起動前に比較する。

固定ブート・復旧の`bootInterfaceVersion`はProduct Descriptorのhardware identityとは別のfixed boot/application ABI識別子である。candidate imageはOTA更新/セキュリティ管理の署名保護`bootInterfaceMin/Max`を持ち、hardwareProfile一致だけでBoot Interface互換性成立とみなさない。

共通generatorによりfixed bootとapplicationの`hardwareProfileId`不一致をbuild時に検出可能とする。

### 5.5 hardwareProfileId=0

0はINVALID/UNASSIGNEDとして予約する。NORMAL_OPERATION buildで0を使用しない。

## 6. Device IDと短縮本体識別子

### 6.1 Device ID生成元

VPS接続・デバイス認証の設計判断を本書の基準とし、Device IDはRA8M2の128 bit Unique IDから、同じUnique IDには常に同じ値が得られる規則で生成する。

外部形式は`TR1-` + 32桁lowercase hexadecimalとし、ASCII 36 byteである。

### 6.2 canonical byte order

詳細設計ではRA8M2 Unique ID register/FSP APIから得る16 byteを、MCU memory mapで定義される低address側から高address側のbyte順に`uidBytes[0..15]`へ正規化し、各byteを上位nibble→下位nibbleの順にlowercase hex化する。

FSP APIの内部表現変更によってDevice ID文字列が変化しないよう、Device ID canonicalizationの試験vectorを固定する。

### 6.3 NVMへ重複保存しない

Device IDは毎回同じMCU Unique IDから生成可能であるため、Device ID文字列を通常のUnit Product Dataへ基準となる値として重複保存しない。

診断用cacheをRAMへ保持してよいが、再起動後に使用する値の取得元にはしない。

### 6.4 変更禁止

Device IDを所有者操作、一般操作端末、BLE通常管理message、VPS設定package、factory reset、OTA application更新から変更できないようにする。

MCU交換を行った場合はUnique IDが変わるため、同じDevice IDの個体修理としては扱わず、製造・保守上の個体識別変更として管理する。

### 6.5 BLE短縮識別子

BLE接続・認証の`TankRobot-XXXXXX`用に、Device ID payload末尾6 hex digitをuppercaseへ変換した`shortDeviceId`を提供する。

shortDeviceIdは人が近傍機体を区別する補助識別子であり、暗号学的identity、一意性保証または認証には使用しない。

### 6.6 Device ID生成失敗

RA8M2 Unique IDを正常に取得できない場合、仮Device ID、all-zero ID、乱数IDを生成して通常運用へ進まない。

`PRODUCT_DEVICE_ID_UNAVAILABLE`として異常管理へ通知する。VPSデバイス認証およびDevice IDを認証対象に含むBLE application認証は利用不可とする。Device ID非依存安全処理は継続する。

## 7. ハードウェアプロファイル

### 7.1 役割

hardwareProfileIdは、firmware、fixed boot、設定、OTA、校正および制御機能が、このハードウェア構成に対して使用可能かを照合する互換性キーとする。

### 7.2 profileが表す範囲

一つのhardware profileは少なくとも次の組合せを固定する。

- MCU family/variant
- control board revision/class
- BLE module compatibility class
- Wi-Fi module compatibility class
- motor driver compatibility class
- servo compatibility class
- mechanism revision
- external NVM compatibility class
- calibration schema compatibility
- firmwareが前提とするhardware electrical characteristics

### 7.3 profile変更条件

MCU/board、motor driver class、servo仕様class、mechanism可動範囲、sensor conversion方式、external flash interface/class、安全包絡へ影響する回路等の変更で互換性評価が必要な場合、新しいhardwareProfileIdを割り当てる。

単なる同等部品supplier変更でfirmware/校正/安全性へ影響しない場合は同一profile内BOM revisionとできる。判断はhardware/量産設計が行う。

### 7.4 実機構成との照合

初期製品は自動部品識別busを追加しない。実装部品classとhardwareProfileIdの一致は製造・組立・保守工程のBOM、全数確認および校正手順で保証する。

## 10. 個体別校正情報

### 10.1 校正snapshot

個体別校正はUnit Product Dataの一部として扱い、一つの`calibrationRevision`に対して整合したsnapshotを使用する。

### 10.2 共通属性

| 項目 | 型 | 意味 |
| --- | --- | --- |
| `calibrationRevision` | uint32 | 0無効、1以上を正常revision |

| `calibratedAtUtcMs` | int64 | 時刻管理でtrusted absolute timeを取得できた場合の補助trace。取得不能時0 |

`pHardwareMin/Max`、servoVariant、mechanismRevision、評価済みV/A上限はProduct Descriptor/profile側から提供する。`p0/p1000`は`pHardwareMin/Max`内でなければSERVO_GEOMETRYを有効化しない。

バッテリー・電気安全監視が要求するbattery voltage gain/offset、drive/servo current gain/offset、battery temperature conversion/calibration、motor driver temperature conversion/calibration等を対応domainへ保持可能とする。

各domainの固定小数点形式、scale、offset、NTC係数表現はバッテリー・電気安全監視の詳細設計と本書詳細設計で一致させる。

### 10.6 安全性

必要domainが未設定、破損、profile不一致、範囲外またはNORMAL_OPERATIONでAPPROVEDでない場合、nominal値を推測して安全監視・actuator制御を通常許可しない。

影響する機能へdomain単位の`CALIBRATION_INVALID`情報を提供し、異常管理がシステム全体の影響度を判断する。無関係な正常domainまで一律INVALIDにはしない。

## 12. 製品情報レコードとrevision

### 12.1 Unit Product Data snapshot

Unit Product Dataは小容量の一つの論理snapshotとして扱う。初期製品のデータ本体の容量上限を4 KiBとする。

### 12.2 共通header

少なくともmagic、formatVersion、totalLength、`productDataRevision`、`hardwareProfileId`、`calibrationRevision`、Product Data state、calibration domain validity bitmap、domain approval states、CRC32C、security MAC tagを持つ。保存処理の確定 stateは永続データ管理側metadataで管理する。

### 12.3 productDataRevision

`productDataRevision`はuint32、0を無効、1～4294967294を通常値とする。

製造情報または校正情報を正常確定するたびに1増加させる。通常の所有者操作、工場出荷状態への初期化、OTAだけを理由に増減させない。最大値へ到達した場合は自動的に周回させず、保守エラーとする。

### 12.4 highestCommittedProductDataRevision

過去に機能上の条件を満たして更新確定した最大`productDataRevision`を永続データ管理の別critical metadataとして保持する。

Unit Product Dataのrevisionが当該値より小さい場合、古い正常copyを自動採用して校正を巻き戻さない。新校正確定後に最新copyが破損しても古い校正へ暗黙に戻らない。

物理MRAM全体を過去snapshotへ戻す高度rollbackに対する限界はセキュリティ管理/セキュリティ横断設計のsecurity residual riskと同じである。

### 12.5 Product Data update transaction

Unit Product Dataのスナップショットと`highestCommittedProductDataRevision`は別の論理データ集合であり、一回の物理的な原子書込みで保存できるとはみなさない。

本機能が一連の更新処理の整合を管理する。永続データ管理は、候補データ、`PRODUCT_DATA_COMMIT_PENDING`、確定済みの最大版を保持するレコード、および更新の完了を示すレコードを、それぞれ原子的に保存する。

## 13. 永続保存・完全性・原子的更新

### 13.1 保存場所

Unit Product Dataおよび`highestCommittedProductDataRevision`は永続データ管理の内蔵MRAM `PERSIST_CRITICAL`へ保存する。ログ/OTA用外付けSerial NORだけに依存させない。

永続データ管理が行う、重要データを32 KiBへ収容できることの容量確認には、最大4 KiBのUnit Product Data、冗長化した保存用複製、HMAC/CRC、確定待ち状態の管理情報、および確定済みの最大版を含める。

### 13.2 機能側で更新を確定する順序

更新は次の順を基本とする。

1. 現在のACTIVEスナップショットと`highestCommittedProductDataRevision`を維持する。
2. `productDataRevision+1`の候補スナップショットを生成する。
3. 本機能が全体構造と、変更対象のデータ区分ごとの内容の妥当性を検証する。
4. セキュリティ管理へ、データ集合固有のドメインを用いた`K_SEC_STATE_MAC`の生成を要求する。
5. 永続データ管理が、使用していない保存用複製へ候補データのバイト列をそのまま書き込む。読戻し、エンベロープ、長さ、CRCおよび`persistRevision`を確認する。この時点では通常の利用側へ公開せず、commit markerも確定しない。
6. セキュリティ管理が、読み戻したバイト列のHMACを検証する。
7. 本機能が、読み戻したデータ本体のプロファイル、`productDataRevision`、構造、および対象の更新処理との対応関係を再確認し、候補データの保存確定を許可する。
8. 永続データ管理へ`PRODUCT_DATA_COMMIT_PENDING`を原子的に保存する。少なくとも更新前後のデータ内容の版、候補データの保存用複製への参照、候補の`persistRevision`、transaction IDを含める。
9. 永続データ管理が、候補データのcommit markerを確定する。
10. `highestCommittedProductDataRevision`を新しい版へ単調に進め、保存を確定する。
11. 候補スナップショットを現在有効なデータとして扱うための完了管理情報を保存・確定し、`PRODUCT_DATA_COMMIT_PENDING`を完了状態にする。
12. 本機能が、ACTIVEとして参照できるデータを新しいスナップショットへ切り替える。
13. 影響を受ける利用側へ版の変更を通知し、再読出しと各機能での妥当性検証を要求する。

スナップショットと確定済みの最大版を、一回の保存処理で確定できるとは仮定しない。新しい最大版の保存確定後は、電源断を理由に旧スナップショットへ戻し、版の下限値を小さくしてはならない。

### 13.3 電源断・reset時の復旧

起動時に`PRODUCT_DATA_COMMIT_PENDING`が存在する場合、本機能は永続データ管理からold/new snapshotの保存処理の確定状態、CRC結果、readback bytes、`persistRevision`、pending new revisionおよび現在の`highestCommittedProductDataRevision`を取得し、セキュリティ管理からcandidate HMAC検証結果を取得する。本機能がこれらとProduct Dataのデータ内容の版／profileを照合して次を判断する。

- 確定済みの版の最大値が旧値のままで、製品情報管理が新しい候補への更新をまだ確定していないことを確認できる場合：未完了処理を取り消し、旧ACTIVEを維持できる。
- highest revisionがnewへ進んでおり、new candidateが正常である場合：new candidateをfinalizeしてACTIVE化する。
- highest revisionがnewへ進んでいるのにnew candidateを正常確認できない場合：old revisionへrollbackせず`PRODUCT_DATA_FAILED`／service requiredとする。
- pending状態・highest revision・candidateの関係を一意に判断できない場合：古いsnapshotを推測採用せず`PRODUCT_DATA_FAILED`とする。

書込み途中recordを正常校正として扱わない。

### 13.4 完全性とstate MAC domain分離

偶発破損検出にCRC32Cを使用する。

Unit Product Dataはセキュリティ管理の`K_SEC_STATE_MAC`でHMAC-SHA-256認証する。state MAC入力はセキュリティ管理の契約に従い、Product Data固有domain separator、Device ID、dataset/type識別、formatVersion、productDataRevision、hardwareProfileIdおよびcanonical snapshot payloadを含め、別datasetの正常tagを流用できない形式とする。

具体byte layoutは詳細設計で固定してよいが、HMAC coverageの意味を詳細設計だけで削減しない。

秘密情報ではないためUnit Product Data本体を一律暗号化することは必須としない。

### 13.5 HMAC依存関係

セキュリティ管理が必要とするDevice ID等はEARLY_READYで先に提供する。Unit Product DataのHMAC検証はその後に行うため、Product Info DATA_READYとSecurity初期化に循環依存を作らない。

### 13.6 Product Descriptor保護

本体アプリケーション側Product Descriptorは署名済みfirmware imageの一部として保護する。fixed boot側Product Descriptorは固定ブート・復旧のtrust boundaryに含め、通常NVM書込みAPIから変更しない。

## 14. 起動時初期化と二段階READY

### 14.1 二段階状態

製品情報管理は次の二段階availabilityを提供する。

- `PRODUCT_IDENTITY_EARLY_READY`
- `PRODUCT_DATA_READY` / `PRODUCT_DATA_DEGRADED` / `PRODUCT_DATA_FAILED`

### 14.2 EARLY_READY

application Product Descriptor利用可能、productFamilyId/modelId/hardwareProfileId有効、Device ID生成成功、running firmware基本metadata読出し成功の場合にEARLY_READYとする。

EARLY_READYはmutable calibration/NVMの正常性を意味しない。fixed bootはapplication ProductInfo APIを呼ばず、同じgenerator sourceから生成された固定ブート・復旧側Product Descriptorを直接使用する。

### 14.3 Product Data transaction復旧

DATA_READYの判定前に、永続データ管理から`PRODUCT_DATA_COMMIT_PENDING`の有無を取得する。未完了処理が存在する場合は第13.3節を完了し、現在有効なProduct Dataの版を一意に確定してから、通常の利用側機能へスナップショットを公開する。

### 14.4 DATA_READY / DEGRADED

次を確認する。

- 永続データ管理の重要データ用の保存領域が利用可能
- 製品情報管理が管理する更新処理が未完了ではない、または復旧完了済み
- 現在有効な最新のUnit Product Dataのスナップショットを読出し済み
- CRCが正常
- セキュリティ管理によるHMAC検証が正常
- formatVersionに対応
- productDataRevisionとhighestCommittedProductDataRevisionが整合
- calibrationHardwareProfileIdが一致
- スナップショット全体の構造と、各フィールドの値の範囲が正常

校正領域ごとに、未設定／EVALUATION_ONLY／INVALIDの状態を保持する。スナップショットの構造が正常であれば、一部の校正領域が利用できなくても、`PRODUCT_DATA_DEGRADED`として他の正常な校正領域の情報を提供できる。

### 14.5 DATA_FAILED

現在有効な最新のスナップショットを確定できない、CRC/HMAC検証に失敗した、巻戻しを検出した、hardwareProfileId全体が一致しない、形式に対応していない、永続データ管理の重要データ用の保存領域を利用できない、またはProduct Dataの更新処理を一意に復旧できない場合は、DATA_FAILEDとする。

古いsnapshotを正常DATA_READYとして自動採用しない。

### 14.6 startup timeout

Product Info初期化全体の基本上限を100 msとする。NVM/RSIP異常時は規定時間内でDEGRADED/FAILEDを返し異常管理/起動・終了・再起動管理へ渡す。

100 msは基本設計で管理し、評価結果を基に確定する値であり、成立しない場合は起動全体10秒上限と安全性を維持して本書へフィードバックする。

### 14.7 bulk領域非依存

外付けSerial NOR全scan、event log全件確認、OTA image確認をProduct Info READY条件にしない。

## 15. 製品情報参照インターフェース

### 15.1 読取り専用の参照API

通常実行時に使用するAPIとして、少なくとも次を提供する。

- `ProductInfo_GetIdentity()`
- `ProductInfo_GetHardwareProfile()`
- `ProductInfo_GetManufacturingInfo()`
- `ProductInfo_GetCalibration(domain)`
- `ProductInfo_GetFirmwareIdentity()`
- `ProductInfo_GetStatus()`

### 15.2 スナップショットの扱い

APIは、内部NVMを書き換えられるポインタを直接公開しない。呼出し元へは固定構造のスナップショット、または読取り専用の参照を返す。更新処理中の候補を通常の呼出し元へ公開しない。

### 15.3 世代・版の扱い

各応答には必要に応じて、hardwareProfileId、productDataRevision、calibrationRevision、domainApprovalState、validityを付ける。取得後に版が変化した場合、呼出し元は古いスナップショットを新しい版のデータとして使用しない。

### 15.4 秘密情報を提供しない

Product Info APIから、デバイス秘密鍵、BLE端末鍵、Wi-Fiパスフレーズ、設定用MAC鍵、所有者復旧用の秘密情報を取得できない。

## 16. VPS接続・デバイス認証との連携

### 16.1 Device ID提供

VPS接続・デバイス認証へEARLY_READY後のfull Device IDを提供する。VPS接続・デバイス認証は別ロジックでDevice IDを再生成しない。

### 16.2 certificateとの対応

セキュリティ管理/VPS接続・デバイス認証はdevice certificate/provisioning metadataが対象Device IDと対応することを確認する。Product Infoは比較元Device IDを提供し、不一致時はVPS通信を開始しない。

### 16.3 VPS送信情報

管理・保守に必要な場合、Device ID、productFamilyId/modelId、hardwareProfileId、manufacturingSerial、productDataRevision/calibrationRevision、calibration domain summary、firmware identityをVPSへ提供可能とする。

通常管理通信でraw calibration係数一式を常時送信することを必須としない。

### 16.4 targetDeviceId

VPSから取得した設定/OTA情報のtargetDeviceId確認では本書のDevice IDを比較元とする。

## 17. BLE接続・認証との連携

### 17.1 advertising

BLE接続・認証へ`shortDeviceId`を提供し`TankRobot-XXXXXX` local name生成に使用する。shortDeviceIdは認証結果を代替しない。

### 17.2 application authentication / registration proof

BLE接続・認証/セキュリティ管理の通常HMAC認証、初回OWNER追加認証、GENERAL登録時の認証用の証明データ、OWNER再登録時の認証用の証明データで対象本体識別情報が必要な場合、本書のfull Device IDを使用する。

Product Infoはproof/HMAC計算・session認証を担当しない。

### 17.3 Device ID unavailable

Device ID生成失敗時は未認証の代替IDで通常BLE操作・登録を成立させない。限定discoveryを行う場合でも通常操作可能状態へ進めない。

## 18. 設定管理との連携

### 18.1 targetDeviceId

設定管理の設定package検証へfull Device IDを提供する。

### 18.2 hardware/calibration context

設定利用機能が局所PREPAREで必要とするhardwareProfileId、mechanismRevision、component variant class、calibrationRevision、対象domain approval/validityを提供する。

### 18.3 REMOTE_MANAGED禁止

productFamilyId/modelId、hardwareProfileId、manufacturingSerial、component variant class、calibration value、calibrationRevision、Device IDを通常VPS設定packageへ含めない。

### 18.4 calibrationと設定の関係

運用設定が評価済み安全包絡を越えないことを確認するため、設定利用機能はProduct Infoのprofile/calibration contextを使用できる。設定管理自身が校正値の意味を再実装しない。

## 19. OTA更新・固定ブートとの連携

### 19.1 OTA compatibility

OTA更新へproductFamilyId、modelId、hardwareProfileId、running firmware identity、product/calibration summary statusを提供する。

OTA更新はcandidate signed metadataの対象製品・model・hardwareProfileIdと比較する。

### 19.2 固定ブート・復旧のfixed boot共通descriptor

固定ブート・復旧のfixed bootはapplicationとは別の手入力定数を持たず、build生成Product Descriptorを共通sourceから取り込む。application Product Info初期化を待たない。

### 19.3 起動前互換性

固定ブート・復旧は起動候補imageの署名保護metadataに含まれるproduct/model/hardwareProfileと、自身が持つProduct Descriptorを比較する。

さらに固定ブート・復旧の`bootInterfaceVersion`とimageの署名保護`bootInterfaceMin/Max`を比較する。Product Descriptor一致だけでBoot Interface互換性成立としない。

Unit Product Dataの個体校正値をfirmware署名検証の代替に使用しない。

### 19.4 trial boot

trial candidate起動時、Product Infoはcandidateのrunning build metadataと`runningImageSecurityGen`を提供する。

OTA更新は期待candidate identityとの一致を正常起動判定へ使用し、セキュリティ管理の現在の許可済みSecurityGenとは別に扱う。

### 19.5 Product Descriptor変更

異なるhardwareProfileIdをサポートするfirmwareへ更新する場合、hardware変更を伴わない通常OTAだけでprofileを勝手に切り替えない。

hardware profile変更は製造・保守変更として、実機構成、Product Descriptor、firmware、校正の組合せを一括管理する。

## 20. 砲塔・砲身・電気安全との連携

### 20.1 砲塔・砲身

砲塔・砲身制御へhardwareProfileId、mechanismRevision、servoVariantId[2]、pHardwareMin/Max[2]、calibrationRevision、p0/p1000[2]、SERVO_GEOMETRY approval/validity、評価済みprofile側速度/加速度上限情報を提供する。砲塔・砲身制御が最終的な局所受入れを行う。

### 20.2 manual datumとの分離

砲塔・砲身制御のMANUAL_DATUM_ARMは起動後の姿勢基準設定手順であり製造校正revisionとは別物とする。MANUAL_DATUM_ARMでp0/p1000等の永続校正値を書換えない。

### 20.3 電気安全

バッテリー・電気安全監視へ対象sensor calibration domain snapshotを提供する。必要domainを使用できない場合、当該測定値をVALIDとして安全判定に使用しない。

### 20.4 calibration change中の通常操作

校正更新transaction中に旧/新校正が混在した状態でactuatorまたは安全監視を通常再開しない。

新snapshotの機能側で更新を確定した後、影響機能が新revisionを再読出し・受入れした後に再開可否を判断する。

## 21. ログ・診断・管理Webとの連携

### 21.1 診断スナップショット

ログ・診断機能へ、次の情報を提供可能とする。

| 情報の分類 | 提供する項目 |
| --- | --- |
| 本体・製品識別 | Device ID、`productFamilyId`、`modelId` |
| ハードウェア・機構 | ハードウェア構成の識別子・名称（`hardwareProfileId`／`hardwareProfileName`）、`mechanismRevision`、部品の互換性区分の要約 |
| 製造・校正 | `manufacturingSerial`、`productDataRevision`、`calibrationRevision`、校正項目群ごとの承認状態・有効性の要約 |
| 実行中ファームウェア | SemVer、BuildID、ビルド識別値（`firmwareBuildFingerprint`） |
| セキュリティ世代 | `runningImageSecurityGen`、`currentAllowedSecurityGen` |
| 利用可能状態 | 製品情報管理の状態 |

### 21.2 ログ

ログ・診断機能へ、次の事象を提供する。

| 事象の分類 | 提供する内容 |
| --- | --- |
| 初期化・識別情報の確認 | 製品情報管理の初期化結果、Device ID取得失敗、Product Descriptor異常 |
| 保存データ・巻戻し | Unit Product Data破損、巻戻しの検出 |

| 版・世代の変更 | 製造情報・校正情報の版・世代の変更 |

秘密情報そのものや、不要な詳細校正値をイベントログへ常時出力しない。

### 21.3 管理Web

管理Webのdevice一覧で必要なDevice ID、製品/機種、hardware構成、firmwareをVPSへ提供できる製品情報として定義する。本体から管理Webへ直接通信しない。

### 21.4 利用者表示

一般操作者向け表示にDevice ID全文、manufacturingSerial、内部profile IDを常時表示することを必須としない。近傍機体識別にはshortDeviceId等を使用できる。

## 22. 所有者再登録・工場出荷状態への初期化

### 22.1 所有者再登録

所有者再登録だけを理由としてDevice ID、Product Descriptor、manufacturingSerial/lot、productDataRevision、calibrationRevision/values/domain approval、component class、firmware identityを変更・削除しない。

### 22.2 factory reset

所有者・操作端末管理/公開用システム要求仕様「19. データ・プライバシー管理」/永続データ管理/セキュリティ管理に従い、factory resetでも次を保持する。

- Device IDの生成元Unique ID
- Product Descriptor
- Unit Product Data
- manufacturing information
- hardware profile information
- calibration information
- running firmware identityの取得元となるsigned image metadata
- productDataRevision / highestCommittedProductDataRevision
- Product Data HMAC/rollback metadata

factory reset中にUnit Product Dataを利用者datasetと同じerase単位で巻き込まない。

### 22.3 利用者データとの分離

Unit Product Dataへ、所有者ID、terminalRegistrationId、Wi-Fi認証情報等を混在させない。

## 23. 製造・開発・保守による更新

### 23.1 通常利用者更新禁止

Unit Product Data更新APIを通常BLE/VPS管理APIへ公開しない。

### 23.2 更新を許可する環境

初期製品ではDEVELOPMENT buildでの開発者校正、EVALUATION buildでの評価校正、製造provisioning/calibration tool、定義された有線保守手順だけを更新主体とする。

NORMAL_OPERATIONから汎用的に校正変更できる保守sessionを新規追加しない。

### 23.3 update prepare

更新前に少なくとも次を確認する。

- actuator output無効
- 通常操作禁止
- 現在のhardwareProfileId確認
- update sourceが開発/製造/保守権限を持つ
- バッテリー・電気安全監視の重要データ書込み開始可能条件
- 永続データ管理のProduct Data transaction利用可能
- 別のProduct Data update transactionなし
- 候補の全体構造と、変更対象のデータ区分ごとの内容の妥当性検証が正常に完了している

### 23.4 revision

正常更新ごとにproductDataRevisionを増加する。校正内容またはdomain approvalが変化した場合はcalibrationRevisionも増加する。製造lot情報のみ変更ならproductDataRevisionのみ増加できる。

### 23.5 manufacturing identity lock

量産出荷用にmanufacturingSerialを正式provisionした個体ではNORMAL_OPERATIONの保守処理から変更しない。訂正は監査可能な製造再provisioning手順とする。

### 23.6 calibration change後

更新完了後、影響機能へproductDataRevision/calibrationRevision変更を通知し、再読出しとlocal validationを要求する。旧runtime cacheを継続使用しない。

---

## 24. 製品情報異常と縮退

### 24.1 異常種別

少なくとも次を識別する。

- `PRODUCT_DESCRIPTOR_INVALID`
- `PRODUCT_DEVICE_ID_UNAVAILABLE`
- `PRODUCT_DATA_UNAVAILABLE`
- `PRODUCT_DATA_CORRUPT`
- `PRODUCT_DATA_HMAC_FAILED`
- `PRODUCT_DATA_ROLLBACK_DETECTED`
- `PRODUCT_DATA_TRANSACTION_INCOMPLETE`
- `PRODUCT_PROFILE_MISMATCH`
- `PRODUCT_CALIBRATION_DOMAIN_UNPROVISIONED`
- `PRODUCT_CALIBRATION_DOMAIN_INVALID`
- `PRODUCT_CALIBRATION_PROFILE_MISMATCH`
- `PRODUCT_COMPONENT_PROFILE_INVALID`
- `PRODUCT_FIRMWARE_IDENTITY_INVALID`
- `PRODUCT_UPDATE_FAILED`

### 24.2 異常管理へ提供する情報

failure type、affected dataset/domain、hardwareProfileId、productDataRevision、calibrationRevision、affected function mask、recommended operation restriction、service recovery要否を提供する。

### 24.3 影響度

Product Info自身はシステム状態を最終決定しない。manufacturingLotが未設定なだけなら通常操作へ影響しない場合がある。一方、SERVO_GEOMETRYが不正なら砲塔操作ができず、電気安全に必須のデータ区分が不正なら安全監視が成立しなくなる可能性がある。それぞれの利用側機能と異常管理が、影響を判断する。

### 24.4 domain局所縮退

一つのcalibration domainだけが不正な場合、Product Data全体のHMAC・profile・revisionが正常であれば当該domainをINVALIDとし他の正常domainを提供できる。

### 24.5 古い校正への暗黙fallback禁止

`highestCommittedProductDataRevision`より古いsnapshotしか正常読出しできない場合、古い校正へ自動fallbackしない。service recoveryが必要な状態として扱う。

### 24.6 safety優先

Product Info保存・log・diagnostic失敗によって緊急停止、電源保護、安全停止を遅延させない。

---

## 25. セキュリティ・プライバシー

### 25.1 secretとの分離

Product Infoは公開識別・構成・校正情報を扱うが、秘密鍵・passwordを所有しない。

### 25.2 HMAC

Unit Product Data snapshot全体はセキュリティ管理の`K_SEC_STATE_MAC`でHMAC-SHA-256認証し、dataset domain分離、Device ID、format、revision、canonical payloadを認証対象へ含める。

### 25.3 個人情報

Device ID、manufacturingSerialは製品個体識別子であり利用者実名ではない。ただしVPS上でログ等と結び付くため公開用システム要求仕様「19. データ・プライバシー管理」に従い管理・保守目的に必要な範囲で使用する。

### 25.4 BLE advertise

BLE advertisingへfull Device IDやmanufacturingSerialを常時公開せず、shortDeviceIdだけを人間向け補助識別に使用する。

### 25.5 debug/maintenance

通常保守UARTから校正値を参照する場合も、書換え機能をログ・診断の一般read-only診断commandへ混在させない。書換えは管理された別工程とする。

## 26. 実行時間・RAM・固定資源方針

### 26.1 基本値

| 項目 | 基本設計値 |
| --- | ---: |
| Product Descriptor | 512 byte以下 |
| Device ID string | 37 byte buffer（NUL含む） |
| shortDeviceId | 7 byte buffer（NUL含む） |
| Unit Product Data payload | 4 KiB以下 |
| calibration domain | 最大8 domain |
| Product Info startup | 100 ms以内基本上限 |
| read-only API | RAM snapshot取得1 ms以内目標 |
| concurrent Product Data update transaction | 1件 |

これらは評価確定待ちを含む基本設計で管理する値である。実機評価で変更する場合は本書へ反映する。

### 26.2 fixed memory

identity cache、現在のProduct Descriptor view、Unit Product Data 現在のsnapshot、candidate update buffer、HMAC work request descriptor、transaction metadata、event/diagnostic response bufferを静的確保する。

### 26.3 no malloc

標準`malloc/free`を使用しない。

### 26.4 safety taskとの分離

HMAC、MRAM write/readback、校正updateはcontrol ISRや緊急停止処理内で同期完了させない。

## 27. 検証方針

### 27.1 Device ID

- 同一MCUで100回以上rebootして同一Device ID
- factory reset前後で同一Device ID
- OTA前後で同一Device ID
- UID test vectorから期待32 hexへ一致
- shortDeviceId生成一致
- Device ID unavailable時に仮IDでVPS/BLE通常認証・登録しない

### 27.2 Product Descriptor / firmware identity

- 固定ブート・復旧のfixed boot/application/OTA metadataのproduct/model/hardwareProfileId一致
- hardwareProfileId=0をNORMAL_OPERATIONで拒否
- incompatible candidate firmware拒否
- bootInterfaceVersionとsigned bootInterfaceMin/Maxを別条件として照合
- runningImageSecurityGenとcurrentAllowedSecurityGenを別値として取得・照合
- component classとbuild report/BOM照合

### 27.3 Unit Product Data

- 初回provisioning
- calibration更新
- manufacturing情報のみ更新
- domain一つだけのINVALID/EVALUATION_ONLY
- candidate write前後
- `PRODUCT_DATA_COMMIT_PENDING` commit前後
- highestCommittedProductDataRevision commit前後
- finalize前後
- 各段階power cut/reset
- CRC破損
- HMAC破損／別dataset tag流用拒否
- length/version不正
- hardwareProfileId不一致
- productDataRevision巻戻し
- highest new＋candidate破損時にold calibrationへ自動fallbackしない

### 27.4 利用側機能との連携

- 砲塔・砲身制御が、サーボまたはプロファイルに適合しない校正情報を拒否する
- バッテリー・電気安全監視が、無効なセンサ校正値をVALIDとして扱わない
- VPS接続・デバイス認証が、同一のDevice IDを使用する
- 設定管理がtargetDeviceIdを照合する
- OTA更新／固定ブート・復旧が、候補の対象製品・HW・Boot Interfaceを照合する
- ログ・診断が、正しい製品・HW・FWの情報を診断出力へ反映する

### 27.5 lifecycle

- 所有者再登録時に製品情報・校正情報を保持する
- factory resetでproduct/calibration/rollback metadata保持
- 所有者・Wi-Fi情報と同じ消去単位に誤って混在させない
- manufacturingSerialをnormal BLE/VPS settingから変更できない
- EVALUATION_ONLY domainがNORMAL_OPERATIONで無条件使用されない
- 製造時に導出Device IDとcertificate/manufacturing recordが一致する

### 29.1 設計判断

| D-11 | Product Data全体状態とcalibration domain approval/validityを分離する |

| D-15 | Unit Product DataをPERSIST_CRITICALへ保存する |

## 30. 他文書へのフィードバック

### F-01 固定ブート・復旧

固定ブート・復旧は完成済みであり、fixed boot/applicationが同じgenerated Product Descriptor sourceを使用し、candidate signed metadataのproductFamilyId/modelId/hardwareProfileIdと`bootInterfaceMin/Max`を起動前に比較する契約を本書でも使用する。

固定ブート・復旧基本設計第8章および第21.2節のOTA trial未実施時契約はOTA更新/永続データ管理と整合済みである。本書はProduct Descriptorおよびboot compatibility情報の管理元と分担範囲を扱い、trial semantic、trial markerおよび起動可否・起動先の判断を再定義しない。

### F-02 OTA更新

OTA更新のproduct/model/hardwareProfileIdを本書Product Descriptorと一致させる。Device IDは個体target、hardwareProfileIdはhardware compatibility、runningImageSecurityGenは実行image identityとして用途を分離する。

### F-03 永続データ管理

永続データ管理へUnit Product Data最大4 KiB、`PRODUCT_DATA_COMMIT_PENDING`、`highestCommittedProductDataRevision`を渡し、snapshotとhighest revisionを一つの保存処理の確定と仮定しないデータ管理機能が管理する transactionを使用する。永続データ管理側はこの契約を反映済みである。

latest revisionが不正でもhighest revisionより古いcopyを自動ACTIVEにしない。

### F-04 セキュリティ管理

セキュリティ管理の`K_SEC_STATE_MAC`をProduct Data固有domainで使用し、productDataRevision/highestCommittedProductDataRevisionをrollback検査対象に含める。セキュリティ管理側はProduct Data/Time Recordまでstate MAC対象を拡張済みである。

EARLY_READYのDevice IDをSecurity初期化で利用し、DATA_READYとの循環依存を作らない。

### F-05 砲塔・砲身制御

pHardwareMin/Max、servo compatibility class、mechanismRevisionをprofile側、p0/p1000をSERVO_GEOMETRY unit calibration側として受け渡す責任分界を維持する。

### F-06 バッテリー・電気安全監視

sensor calibration domainのpayload形式、必要精度、domain invalid時の安全処置を詳細設計で本書と整合する。

### F-07 BLE接続・認証

`TankRobot-XXXXXX`のXXXXXXをDevice ID末尾6 hex uppercaseへ固定し、security identityおよび登録時の認証用の証明データにはfull Device IDを使用する。

### F-08 ログ・診断／管理Web

製品情報管理から、製品・モデル・HWプロファイル・製造情報・校正データ区分の要約・FWの要約を取得する。権限とプライバシーに応じて、診断・VPS表示へ反映する。

### F-09 量産・保守設計

manufacturingSerial/lot/record IDの正式採番、hardwareProfile/BOM対応、具体MPN・supplier履歴、製造時校正、部品交換時のprofile/calibration更新手順を具体化する。

製造時はDevice IDを書き込むのではなく、UID由来Device IDを読出し、製造記録およびdevice credentialと照合・対応付ける。

## 31. 初版の自己確認結果と引継ぎ条件

### 31.1 初版自己確認

初稿作成後の自己確認および後続基本設計との整合レビューを含め、次を確認・修正した。

- 製品情報管理に独立の公開要求章がないことを明示し、関連公開要求を主対象要求群として追跡した。
- RA8M2 Unique ID由来Device IDを変更せず、Device IDとmanufacturingSerialを分離した。
- 製造時Device ID処理を外部注入ではなくUID由来Device IDの検証・記録・credential対応付けとした。
- Product DescriptorとUnit Product Dataを分離し、product/model/hardwareProfileIdを通常設定として書換え可能にしていない。
- 固定ブート・復旧の完成後の責任を反映し、fixed boot/applicationのProduct Descriptor共通sourceとBoot Interface互換性を別軸として整理した。
- component variantを具体MPNではなくcompatibility classとして扱い、詳細BOM履歴を製造管理へ分離した。
- 砲塔・砲身制御/バッテリー・電気安全監視が要求する校正情報をdomain責任分界付きで取り込んだ。
- Product Data全体状態とdomain approval/validityを分離し、一domain不正で無関係domainを破棄しない方式を維持した。
- Unit Product DataをPERSIST_CRITICALへ配置し、永続データ管理の32 KiB capacity proof対象とした。
- Unit Product DataのスナップショットとhighestCommittedProductDataRevisionを、一つの物理的な原子操作で確定できると仮定した旧記述を修正した。PRODUCT_DATA_COMMIT_PENDINGを用い、データ管理機能が一連の更新処理を管理する方式と整合させた。
- 確定済みの最大版が新しい値へ進んだ後に、旧版のProduct Dataへ巻き戻さない電源断復旧規則を具体化した。
- Unit Product DataをCRC32C＋セキュリティ管理のdataset-domain分離K_SEC_STATE_MACで保護した。
- EARLY_READY→Security HMAC→transaction recovery→DATA_READYの順序を明示し循環依存を避けた。
- running firmware identityのimage SecurityGenとセキュリティ管理の現在の許可済みSecurityGenを別項目として扱うよう修正した。
- 所有者再登録・工場出荷状態への初期化でも、製品・校正情報と巻戻し防止用管理情報を保持する方式とした。
- 時刻管理の時刻品質を校正時刻の補助traceへ反映し、未信頼時刻を正常UTCとして保存しないようにした。
- EVALUATION_ONLY domainを正式factory calibrationと混同しない。
- shortDeviceIdを人間向け補助識別に限定した。
- 通常BLE/VPS設定から製品・校正情報を変更できない構成を維持した。
- `malloc/free`に依存しない固定資源方式とした。
- 容量・時間・domain数・transaction数等を評価確定待ちを含む基本設計で管理する値として明確化した。

### 31.2 初版完了判断

D-01～D-30は本基本設計で採用する方式として確定する。

E-01～E-17は採用方式の成立性、精度、製造・保守運用を確認する評価事項であり、本基本設計を停止するユーザー判断待ち事項ではない。

F-01～F-09は既存基本設計、詳細設計、hardware/量産設計へのフィードバック事項である。永続データ管理/セキュリティ管理/固定ブート・復旧の後続契約は本書へ反映済みである。

hardwareProfileId/component classの具体番号、量産製造番号採番、sensor calibration fixed-point形式、Product Descriptor generator、Product Data record byte layout等は、基本方式を変更しない範囲で詳細設計へ委ねる。

現時点で、製品情報管理基本設計の初版完成を妨げるユーザー判断待ち事項は残していない。

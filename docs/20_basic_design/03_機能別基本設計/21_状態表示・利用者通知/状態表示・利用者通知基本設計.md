## 1. 本書の目的

### 1.1 目的

本書の目的は、公開用システム要求仕様「21. 状態表示・利用者通知」を実現するため、本体側の限られた表示手段へ安全上重要な状態を優先して提示し、詳細表示手段へ現在状態、操作可否、異常、復旧可否および処理結果を一貫して提供する方式を、詳細設計へ展開可能な粒度まで具体化することである。

### 1.2 対象範囲

本書は、Tank_Robot本体におけるシステム状態、通常操作可否、停止・緊急停止、電源・バッテリー状態、異常・復旧、OTA更新、起動・終了、通信状態、時刻状態その他の利用者向け状態について、各機能が確定した状態や処理結果を受け取り、本体の電源LED、状態表示用RGB LEDおよび2桁7セグ表示器へ一貫した優先順位で反映し、スマートフォンアプリ、管理Webアプリおよび保守用診断手段へ必要な通知情報を提供する基本方式を定める。

状態表示・利用者通知機能は、システム状態、操作可否、安全処理、異常の影響度、復旧可否またはOTA成否を独自に決定しない。システム状態管理が確定したシステム全体の状態・通常操作可否・主制限理由と、各担当機能が管理する現在の詳細状態を受け取り、表示・通知用に選択、変換および提示する責任だけを持つ。

#### 基本設計と詳細設計の区分

本書で定めるRGB pattern、表示priority、indicatorCode、低消費電力LED周期、本体表示反映上限、BLE通知上限、視認性条件、固定queue/page上限その他、利用者から見た表示・通知挙動または資源保証を変える方式・値は、評価確定待ちを含む基本設計で定める事項とする。実機評価で変更が必要となった場合は詳細設計だけで変更せず、本書または値・方式を定める関連基本設計へ反映する。GPIO極性、driver IC、task/ISR、mutex、具体C構造体等、基本設計の外部挙動を変更しない実装方法は詳細設計で具体化してよい。BLE外部通信データのmessage type、各項目のオフセットおよびencodingはBLE接続・認証の通信契約に従い、本書側の詳細設計事項として重複所有しない。

## 2. 設計方針と適用範囲

### 2.1 基本方針

状態表示・利用者通知は次の原則で設計する。

1. 各機能が確定した状態や処理結果を使用し、表示機能が状態・操作可否・安全性・復旧可否を再判定しない。
2. システム全体の状態、状態遷移に関する情報、通常操作可否および主制限理由は、システム状態管理が提供する読取り専用のスナップショットから取得する。本機能が他機能の詳細情報からこれらを再構成しない。
3. 本体表示は通信に依存せず、BLE/Wi-Fi/VPS未接続でも安全上重要な状態を確認できるようにする。
4. 本体側は限られた表示手段で最優先の状態を示し、同時成立中の他要因は詳細通知手段へ残す。
5. RGB LEDは色だけで状態を識別せず、点灯/点滅周期も組み合わせ、色覚特性へ配慮する。
6. 操作可能状態はRGB LED消灯を正常表示とし、「緑点灯」を正常の必須表示にしない。
7. 2桁7セグは異常停止・起動失敗の補助識別だけに使用し、通常状態、数値監視値または進捗率を表示しない。application起動前の固定ブート・復旧の起動失敗・wired recovery requiredは「起動失敗」に相当するearly表示として同じコード体系を使用する。
8. 2桁コードは内部異常IDと分離した安定した利用者向けコードとし、詳細異常IDへ対応付ける。
9. 表示完了やBLE通知完了を安全処理・状態遷移・復旧処理の成立条件にしない。
10. 遷移先や処理完了を先読み表示せず、確定結果を受け取った後に表示する。
11. 取得不能・無効・古い監視値を正常な現在値として表示しない。
12. 表示制御自身の異常をソフトウェアで可能な範囲で監視するが、実発光read-back専用ハードウェアは初期製品へ追加しない。
13. `malloc/free`を使用せず、固定サイズsummary、page bufferおよび通知queueで構成する。
14. 一般操作者向けメッセージは安全な行動に必要な意味を本書で定め、画面レイアウト・装飾・最終文言調整はスマートフォンアプリ設計へ委ねる。
15. 状態変化から本体表示・通知開始までの最大時間、視認性条件、固定page/queue上限等は評価だけに委ねず、本書の暫定合否値として所有する。

### 2.2 本書で決めないこと

次は各担当機能が管理・決定し、本書で再定義しない。

- システム状態遷移条件
- システム全体の通常操作の許可・制限・禁止判定および主制限理由
- 安全停止、緊急停止および解除条件
- 電圧・温度・電流の警告/危険判定
- 異常の影響度、処置および復旧可否
- OTA stage/結果
- BLE/Wi-Fi/VPS接続状態
- RTC/時刻信頼状態
- スマートフォンアプリの画面レイアウト・操作UI
- 管理Webアプリの画面構成

## 3. 責任分界と情報の管理原則

### 3.1 主な責任分界

| 機能 | 本書が受け取る情報 | 情報の管理責任 |
| --- | --- | --- |
| システム状態管理 | 現在状態、遷移中かどうか、遷移元・遷移先、状態の世代、`operationAvailability`、`primaryRestrictionReason` | システム状態、遷移に関する情報、システム全体の通常操作可否・主制限理由 |
| 起動・終了・再起動 | 起動・終了の処理段階、結果、起動失敗原因 | 起動・終了処理の結果 |
| 停止・緊急停止 | 安全停止、緊急停止、解除可否、解除を妨げる理由、`stopStatusGeneration` | 停止状態および`StopStatusSnapshot`の世代 |
| 異常管理 | 発生中の異常、処置、操作への影響、復旧可否、`faultGeneration`、`faultListGeneration` | 異常状態、異常ごとの影響・復旧可否、および発生中の異常のスナップショットの世代 |
| 電気安全 | 電源供給の危険、警告、測定の有効性 | 電源・バッテリー判定 |
| 走行／砲塔・砲身 | 局所利用可否、制御異常 | 各アクチュエータ機能の局所状態 |
| OTA更新 | 処理段階、試行起動・更新の確定処理、本体での結果、復旧状態 | OTA状態・結果 |
| BLE/Wi-Fi/VPS | 各通信状態、失敗理由 | 通信状態 |
| 時刻管理 | 信頼状態・品質、VPS利用制限・有線保守が必要な理由 | 時刻信頼状態 |
| 固定ブート・復旧 | 起動失敗、有線復旧の要否 | アプリケーション起動前の結果 |
| 本機能 | 本体表示の調停、RGB表示パターン、indicatorCode、詳細通知への変換、`statusGeneration` | 表示・通知への変換および`UserStatusModel`の要約情報の世代 |

### 3.2 表示は管理元の情報を上書きしない

本機能は、各管理元が提供する情報を表示・通知に利用する機能であり、その情報自体を決定する機能ではない。

例えば異常管理が`recoveryAllowed=false`と判断している異常に対し、本機能が表示の都合で「再試行可能」と表示しない。

同様に、停止・緊急停止管理/異常管理/バッテリー・電気安全監視/BLE接続・認証等が提供する局所状態・影響情報を用いて、本機能がシステム状態管理とは別のシステム全体`operationAvailability`または`primaryRestrictionReason`を生成しない。

### 3.3 表示選択と異常選択を分離する

異常管理はactive異常を個別に本機能へ提供する。

本機能は7セグへ表示する代表コードを選択するが、これは異常管理の主異常、処置、異常ごとのoperation impactまたは復旧可否を変更する行為ではない。また、代表コードの選択結果をシステム状態管理の`primaryRestrictionReason`へ逆流させない。

## 4. 論理構成

### 4.1 機能構成

本機能の論理的な機能構成を次に示す。

| 論理機能 | 責任 |
| --- | --- |
| `IND_INPUT` | 各機能snapshotの受付・generation管理 |
| `IND_MODEL` | 詳細通知用status model構成 |
| `IND_ARB` | 本体表示優先順位の調停 |
| `IND_RGB` | RGB pattern選択・位相管理 |
| `IND_POWER_LED` | 電源LED点灯/低消費電力点滅 |
| `IND_7SEG` | indicatorCode選択、表示/消灯 |
| `IND_NOTIFY` | BLE/App、VPS/Web、診断向け通知更新 |
| `IND_HEALTH` | logical render更新停止・driver error監視 |
| `EARLY_IND` | fixed boot用最小表示経路 |

### 4.2 表示処理の一方向性

処理方向を次とする。

`各情報の管理元機能 → IND_INPUT → IND_MODEL/IND_ARB → display driver / notification transport`

表示結果から管理元の状態へ逆向きに状態変更を行わない。

### 4.3 イベントだけを表示の判断基準にしない

状態変更イベントを即時更新のきっかけにしてよい。ただし、表示の判断基準は各機能が提供する現在のスナップショットとする。

イベントの欠落・再送によって古い状態を保持しないよう、定期的な照合でも現在のスナップショットを再取得する。

---

## 5. 表示・通知入力モデル

### 5.1 共通入力属性

各入力スナップショットには、少なくとも次の情報を含める。

- 情報の提供元機能
- 提供元が管理する世代・版
- 有効性
- 現在の状態／結果
- 適用対象となるシステム起動・セッションの世代
- 最終更新時の単調増加時刻（提供可能な場合）

### 5.2 SystemStatusInput

システム状態管理の読取り専用スナップショットから、少なくとも次を一体として受け取る。

- 現在のシステム状態
- 遷移中かどうか
- 遷移元・遷移先の状態
- `operationAvailability`
- `primaryRestrictionReason`
- 状態の世代

このスナップショットに含まれる`operationAvailability`と`primaryRestrictionReason`を、システム全体の確定済み判定値として使用する。異常管理その他の提供元から受け取った詳細情報を使って、同等の値を再構成しない。

### 5.3 StopStatusInput

停止・緊急停止管理から少なくとも次を受ける。

- safeStopActive
- safeStopCause class
- safeStopCompleted
- emergencyStopActive
- emergencyStopReleaseAllowed
- emergencyStopReleaseBlockReason
- `stopStatusGeneration`

これらは、停止・緊急停止管理が同じ`stopStatusGeneration`で原子的に公開する読取り専用の`StopStatusSnapshot`から取得する。本機能は`stopStatusGeneration`を生成・更新せず、異なる世代の停止状態フィールドを一つの入力へ混在させない。停止処理の対応関係を識別する`stopRequestId`を、スナップショットの世代として扱わない。

### 5.4 ElectricalStatusInput

バッテリー・電気安全監視から少なくとも次を受ける。

- powerSupplyDanger
- lowBatteryWarning
- powerOperationRestricted
- powerShutdownRequired
- battery voltage validity/value
- temperature validity/value summary
- monitor generation

### 5.5 FaultStatusInput

異常管理は、表示対象となる発生中の異常を逐次参照できる読取り専用インターフェースを提供する。

異常1件の要約情報には、少なくとも次を含める。

- faultId
- 情報の提供元機能
- 異常の種別・分類
- 現在の処置
- 操作への影響
- 復旧可否
- 利用者に求める操作の分類
- 発生中か解消済みか
- `faultGeneration`

発生中の異常の集合には`faultListGeneration`を対応付ける。`faultGeneration`および`faultListGeneration`を書き換える機能は異常管理だけとし、両者の意味も異常管理が定める。本機能は受け取った値を変更せずに使用する。逐次参照中に`faultListGeneration`が変化した場合は、異なる世代の要素を一つの集合として使用しない。

本体表示を選択するときは、発生中の異常を一件ずつ走査し、表示候補として最も優先するものだけを固定RAMへ保持する。表示側で「最初の16件だけ」のように打ち切らない。

異常管理自身が管理可能な異常件数の上限を超えた場合の処置は、異常管理が担当する。本機能は`faultOverflow`等の状態情報を受けて、詳細情報を提供する手段へ通知する。

異常管理の`operation impact`は個別異常の影響情報として使用し、システム全体の`operationAvailability`を確定する情報として扱わない。

### 5.6 OTAStatusInput

OTA更新から少なくとも次を受ける。

- OTA active
- stage
- install/trial/recovery state
- `TRIAL_BOOT_VALIDATED`/`CONFIRMED`相当状態
- `otaSettlementPending`
- local final result
- `otaResultReportState`（NOT_READY/PENDING/SENT）
- wired recovery required
- ota generation

local OTA成否とVPS result report状態を分離する。`otaResultReportState=PENDING`だけを理由として、正常確定済みOTAを利用者へ失敗と表示しない。

### 5.7 Communication/Time inputs

BLE接続・認証/Wi-Fi接続/VPS接続・デバイス認証/時刻管理から、詳細通知に必要な接続・認証・時刻信頼状態を受ける。

時刻については少なくとも、信頼状態、`TIME_QUALITY_*`、VPS利用不能理由、有線保守の要否を区別する。時刻管理のTIME_TRUSTED喪失後に、VPS接続・デバイス認証がセッションの終了処理を行っている場合がある。この場合に、詳細状態として「時刻未信頼」と「VPS利用不可/切断中」を矛盾なく提示できるよう、提供元の情報の世代を保持する。

これらを本体RGBの常時表示対象に増やさず、公開用システム要求仕様「21. 状態表示・利用者通知」の優先順位で明示されたBLE待機や時刻起因の通常操作禁止等に必要な場合だけ代表表示へ反映する。システム全体の禁止・制限状態そのものはシステム状態管理の`operationAvailability`と`primaryRestrictionReason`に従う。

## 6. 通常操作可否と主理由モデル

### 6.1 operationAvailability

詳細通知では次を区別する。

- `ALLOWED`
- `LIMITED`
- `PROHIBITED`
- `UNKNOWN`

本機能は、各機能の局所的な操作可否を組み合わせて、この値を独自に生成しない。

システム状態管理が提供するシステム全体の`operationAvailability`を、確定済みの値としてそのまま使用する。停止・緊急停止管理／異常管理／バッテリー・電気安全監視／BLE接続・認証等が提供する局所停止状態、異常ごとの操作への影響、電源制限、通信状態等は、詳細通知の項目として保持する。これらを組み合わせて、システム状態管理とは別に全体の操作可否を判定しない。

### 6.2 primaryRestrictionReason

`primaryRestrictionReason`には、システム状態管理が確定したシステム全体の主制限理由を使用する。本機能が複数の提供元から取得した詳細理由を使って選び直さない。

表示・通知上は利用者向けの安定したreason classとして扱う。初期製品では少なくとも次を区別する。

- `NONE`
- `SYSTEM_STATE`
- `SAFE_STOP`
- `EMERGENCY_STOP`
- `POWER_WARNING_OR_RESTRICTION`
- `FAULT`
- `OTA`
- `STARTUP_INCOMPLETE`
- `SHUTDOWN_IN_PROGRESS`
- `TIME_TRUST_OR_VPS_RESTRICTED`
- `OWNER_OR_REGISTRATION_REQUIRED`
- `CONFIG_OR_PRODUCT_DATA_INVALID`
- `UNKNOWN`

内部faultIdや機密なsecurity detailをそのまま一般利用者向けreasonへ流さない。

各情報の管理元機能から取得した局所的な詳細理由は、詳細情報のページや提供元ごとの要約情報として提供する。システム状態管理の`primaryRestrictionReason`を置き換えない。

### 6.3 LIMITED

例えば一部actuatorだけが利用不可で他機能を安全に利用可能な場合、担当機能/異常管理は局所的なoperation impactを提供する。システム全体として`LIMITED`とするかはシステム状態管理が最終判断し、本機能はシステム状態管理が`LIMITED`を確定した場合だけその値を通知する。

表示機能が推測してLIMITEDへ格下げ・格上げしない。

## 7. 本体表示ハードウェア抽象化

### 7.1 論理出力

本体アプリケーション側の表示managerは次の論理出力だけを扱う。

- `PowerLed_Set(bool)`
- `Rgb_Set(logicalColor, logicalLevel)`
- `SevenSeg_Set2Digits(code)`
- `SevenSeg_Blank()`

GPIO極性、PWM方式、driver IC、multiplex方式はHALへ閉じ込める。

### 7.2 2桁7セグのscan

表示器がdynamic scanを必要とする場合、segment scanは表示managerの50 ms論理render周期とは分離し、専用timer/ISRまたはdriver ICでちらつかない周期を確保する。

具体scan周波数はhardware詳細設計で決め、両桁とも見かけ上100 Hz以上を目標とする。

### 7.3 本体表示電源

電源LED、RGB LEDおよび7セグは、少なくともPWR_CTRLが利用可能で、applicationまたはfixed bootが実行可能な間に表示できる電源系統へ配置する。

アクチュエータ負荷電源やWi-Fi/BLEモジュール電源を表示成立条件にしない。

## 8. 電源LED基本設計

### 8.1 通常電源供給中

主電源ON後、PWR_CTRLが確立して表示を制御できるようになった後は、固定ブートと本体アプリケーションのどちらが表示を担当する場合も、低消費電力状態を除いて電源LEDを連続点灯する。

### 8.2 低消費電力

低消費電力状態では、電源LEDを短パルス点滅する。

初期基本値を次とする。

- period：2.0 s
- ON：50 ms
- OFF：1.95 s

低消費電力監視の周期復帰と整合させ、LED点滅だけのために高頻度wakeを追加しない。

50 ms ONは評価確定待ちの基本設計値である。視認性と消費電力の実機評価で変更が必要な場合は、本書を更新したうえで100 ms以内を次候補として再評価する。詳細設計だけで変更しない。

### 8.3 主電源OFF

主電源OFF後、表示電源が遮断される前にソフトウェアから消灯可能な場合は消灯要求を行う。

最終的には電源遮断によって消灯する。

## 9. RGB LEDパターン体系

### 9.1 原則

RGB LEDは色だけで状態を区別せず、pattern shapeも状態識別へ使用する。

初期製品の論理色は次を使用する。

- RED
- AMBER（R+G）
- BLUE
- CYAN（G+B）
- MAGENTA（R+B）
- OFF

GREEN単独を「安全」「正常」の必須意味として使用しない。

### 9.2 基本pattern

| Pattern ID | 色 | パターン | 主用途 |
| --- | --- | --- | --- |
| `RGB_POWER_DANGER` | RED | 125 ms ON / 125 ms OFF | 電源供給継続危険 |
| `RGB_ESTOP` | RED | 500 ms ON / 500 ms OFF | 緊急停止 |
| `RGB_FAULT` | RED | 200 ms ON / 200 ms OFF / 200 ms ON / 1400 ms OFF | 異常停止・起動失敗 |
| `RGB_OPERATION_BLOCKED` | AMBER | 250 ms ON / 250 ms OFF | 通常操作禁止、安全停止等 |
| `RGB_POWER_WARNING` | AMBER | 500 ms ON / 500 ms OFF | 低バッテリー・電源制限 |
| `RGB_OTA` | MAGENTA | 750 ms ON / 250 ms OFF | OTA更新 |
| `RGB_SHUTDOWN` | CYAN | 250 ms ON / 750 ms OFF | 終了処理 |
| `RGB_STARTUP` | BLUE | 250 ms ON / 250 ms OFF | 起動処理 |
| `RGB_BLE_WAIT` | BLUE | 連続点灯 | BLE接続待機 |
| `RGB_OPERATION_READY` | OFF | 消灯 | 操作可能 |
| `RGB_UNKNOWN` | AMBER | 100 ms ON / 900 ms OFF | 表示入力不明・縮退表示 |

### 9.3 pattern phase

patternを切り替えたときは原則として新patternのON phase先頭から開始する。

高優先度状態へ切り替わったことを視認しやすくするため、低優先度patternの残り時間を引き継がない。

### 9.4 色覚特性

RED系とAMBER系、BLUE/CYAN/MAGENTAを色だけで区別することを禁止する。

異なる安全意味には異なる点滅周期またはdouble flashを組み合わせる。

実機評価では明るさ、拡散材、観察角、周囲照度の識別性も確認する。

## 10. 本体表示優先順位と調停

### 10.1 優先順位

公開用システム要求仕様「21. 状態表示・利用者通知」の優先順位をそのまま使用する。

| 優先 | 表示対象 | RGB pattern |
| ---: | --- | --- |
| 1 | 電源供給継続が危険 | RGB_POWER_DANGER |
| 2 | 緊急停止 | RGB_ESTOP |
| 3 | 異常停止または起動失敗 | RGB_FAULT |
| 4 | 現在stateとは別に成立する通常操作禁止条件 | RGB_OPERATION_BLOCKED |
| 5 | 低バッテリー警告または電源による操作制限 | RGB_POWER_WARNING |
| 6 | OTA更新 | RGB_OTA |
| 7 | 終了処理 | RGB_SHUTDOWN |
| 8 | 起動処理 | RGB_STARTUP |
| 9 | 低消費電力 | RGB OFF。電源LED点滅が主表示 |
| 10 | BLE接続待機 | RGB_BLE_WAIT |
| 11 | 操作可能 | RGB_OPERATION_READY |

### 10.2 一つだけ選択

RGB LEDへ複数patternを時分割して順番表示しない。

同時成立中は最優先patternだけを表示し、その他は詳細statusへ保持する。

### 10.3 同一priority内

同一priorityへ複数candidateがある場合もRGB patternが同じなら表示内容の意味は変えない。

表示候補の根拠となる提供元を一つ選ぶ必要がある場合は、次の順を基本とする。

1. 人身・電気安全へ直接関係するもの
2. 通常操作を全面禁止するもの
3. 復旧に利用者操作を必要とするもの
4. 発生継続中のもの
5. 同条件なら提供元の機能ID／faultIdの固定順

この順序は、本体表示の候補とその提供元を一つ選ぶためだけに用いる。システム状態管理の`primaryRestrictionReason`を選択・変更する規則ではなく、異常管理の処置優先順位も変更しない。

## 11. システム状態別の基本表示

### 11.1 表示mapping

より高優先度candidateが存在しない場合、現在のシステム状態を次へmappingする。

| システム状態 | 電源LED | RGB | 7seg |
| --- | --- | --- | --- |
| 起動処理 | ON | RGB_STARTUP | OFF。ただし起動失敗確定後は第14章 |
| BLE接続待機 | ON | RGB_BLE_WAIT | OFF |
| 操作可能 | ON | OFF | OFF |
| 低消費電力 | blink | OFF | OFF |
| OTA更新 | ON | RGB_OTA | OFF |
| 終了処理 | ON | RGB_SHUTDOWN | OFF |
| 緊急停止 | ON | RGB_ESTOP | OFF |
| 異常停止 | ON | RGB_FAULT | indicatorCode |
| 起動失敗 | ON | RGB_FAULT | indicatorCode |

### 11.2 状態遷移中

システム状態管理が状態遷移中を管理している間、遷移先stateを確定表示しない。

現在有効stateの表示を維持しつつ、遷移に対応する優先candidateが別に成立済みの場合だけそのcandidateを表示する。

### 11.3 操作可能へ入る瞬間

システム状態管理が操作可能状態を確定する前にRGBを消灯して「操作可能」を示さない。

確定後の最初のrenderでRGB_OPERATION_READYへ切り替える。

## 12. 安全停止・緊急停止表示

### 12.1 安全停止

停止・緊急停止管理がsafe stopのactive/completed状態を提供し、システム状態管理の`operationAvailability`が`PROHIBITED`または安全停止に伴う制限を示している間は、priority 4の`RGB_OPERATION_BLOCKED`を表示する。

安全停止そのものが異常停止stateへ遷移した場合はpriority 3の異常表示を優先する。

### 12.2 詳細通知

安全停止について詳細手段へ少なくとも次を提供する。

- safe stop発生中/完了：停止・緊急停止管理
- cause class：停止・緊急停止管理
- system `operationAvailability`：システム状態管理
- restart/operation resume allowedか：該当する管理元機能
- resumeを阻害する詳細理由：該当する管理元機能

停止・緊急停止管理の停止詳細からシステム全体の`operationAvailability`または`primaryRestrictionReason`を再計算しない。

### 12.3 緊急停止

emergency stop active時はsystem stateまたは他の低優先candidateに関係なく`RGB_ESTOP`を表示する。

緊急停止状態だけでは7segを使用しない。

### 12.4 緊急停止解除

詳細通知では次を提供する。

- emergencyStopActive
- releaseAllowed
- releaseBlockReason
- release request result

解除要求を受け付けただけではRGB_ESTOPを解除しない。

停止・緊急停止管理/システム状態管理が緊急停止解除と次stateへの遷移を確定した後に表示を更新する。

---

## 13. バッテリー・電気安全表示

### 13.1 電源危険

バッテリー・電気安全監視が電源供給継続危険または即時電源遮断必要を確定した場合、表示可能な間はpriority 1の`RGB_POWER_DANGER`を選択する。

ただし表示継続のために危険な電源供給を延長しない。

### 13.2 低バッテリー警告

バッテリー・電気安全監視のlowBatteryWarningがactiveで、より高優先度candidateが存在しない場合、`RGB_POWER_WARNING`を表示する。

### 13.3 電源による操作制限

バッテリー・電気安全監視が電源に関する局所制限・警告を提供した場合、公開用システム要求仕様「21. 状態表示・利用者通知」のpriorityに従って表示candidateへ反映する。システム全体の操作可否はシステム状態管理が最終判断する。

システム状態管理の`operationAvailability`が`PROHIBITED`で当該主理由が電源関連であればpriority 4、低バッテリー警告または電源の局所制限として提供される場合はpriority 5とする。

### 13.4 監視値

スマートフォン/診断へ電圧・温度等を提供する場合は値と同時にvalidityとsample generation/timeを提供する。

invalid/staleの場合は値を`N/A`相当として扱わせる。

本体7segへバッテリー電圧数値を表示しない。

---

## 14. 異常停止・起動失敗表示

### 14.1 RGB

異常停止状態または起動失敗状態では`RGB_FAULT`を表示する。ただしpower dangerまたはE-stopが同時成立している場合は公開用システム要求仕様「21. 状態表示・利用者通知」の優先順位に従い上位patternを表示する。

### 14.2 7seg

異常停止/起動失敗中にdisplayable faultが1件以上存在する場合、一つのindicatorCodeを表示する。

application起動前のfixed boot failureではシステム状態管理/異常管理のactive fault一覧を利用できない場合があるため、第26章の固定ブート・復旧のfailure reason→indicatorCode mappingを使用する。これは起動失敗のearly表示であり、通常状態に7segを拡張するものではない。

### 14.3 詳細通知

詳細表示手段へactive異常ごとに少なくとも次を提供する。

- public fault class / stable display identifier
- source function class
- operation impact：異常管理
- recoveryAllowed：異常管理
- required user action class
- 現在のtreatment/recovery state

システム全体の`operationAvailability`と`primaryRestrictionReason`はシステム状態管理のSystemStatusInputから別途提供し、個別異常のoperation impactから再計算しない。

内部register値、鍵、credential、stack address等を一般利用者向け情報へ含めない。

### 14.4 起動失敗原因がapplication前の場合

fixed boot起動失敗ではapplicationのIND_MODELが動作しないため、固定ブート・復旧のearly indicator経路を使用する。

固定ブート・復旧/永続データ管理が保持したboot failure情報を、次回application起動可能時にログ・診断が診断・ログへ取り込めるようにする。applicationが起動不能の間、ログ・診断自身の実行をboot failure保存条件にしない。

---

## 15. 2桁7セグ異常コード体系

### 15.1 基本原則

`indicatorCode`は00～99のdecimal 2桁とする。

`00`は「表示なし/予約」とし、異常コードとして利用しない。

内部faultIdが変わっても利用者向けコードが不用意に変化しないよう、コードrangeは機能領域と利用者行動の意味を基本に割り当てる。

### 15.2 range

| Range | 意味 |
| --- | --- |
| 01～09 | 未分類・システム共通 |
| 10～19 | 起動・固定ブート・復旧 |
| 20～29 | 電源・バッテリー・電気安全 |
| 30～39 | 走行・砲塔砲身・停止制御 |
| 40～49 | BLE・所有者・操作端末 |

## 16. 2桁7セグ表示選択と優先順位

### 16.1 表示対象条件

application動作中に7segを点灯するのは次をすべて満たす場合とする。

- system stateが異常停止または起動失敗
- displayable active faultが存在
- indicatorCodeが01～99で有効

application起動前は第26章のearly起動失敗条件を使用する。

### 16.2 code選択priority

active faultを逐次走査し、次の選択keyでbest一件だけを保持する。

1. 電源/人身安全への重大影響
2. wired/service recoveryが必要
3. 通常操作全面禁止
4. startup/bootを成立させない
5. recovery不可
6. fault treatment severity
7. 同条件ではindicatorCodeの小さい順
8. 同codeではfaultId固定順

このpriorityは7segへ一つを選ぶ表示規則であり、実際の安全処置priorityでもシステム状態管理の`primaryRestrictionReason`選択規則でもない。

### 16.3 表示切替

現在表示中faultがresolvedしても、別のactive faultが残っている場合は次priority candidateへ直ちに切り替える。

異常停止/起動失敗が解除されdisplayable faultがなくなったら消灯する。

### 16.4 コードの点滅

初期製品では7segコード自体を点滅させず連続表示とする。

RGBが状態の動的patternを担当し、7segの読み取りやすさを優先する。

## 17. OTA更新・復旧表示

### 17.1 OTA更新中

OTA更新がOTA activeで、より高い安全priorityが存在しない場合`RGB_OTA`を表示する。

7segへ更新率やstage番号を表示しない。

### 17.2 詳細通知

詳細手段へ少なくとも次を提供する。

- OTA active
- stage
- install/trial/recovery state
- `otaSettlementPending`
- local final result
- `otaResultReportState`
- system `operationAvailability`：システム状態管理
- wired recovery required

percent progressは初期製品の必須表示にしない。

### 17.3 OTA成功

OTA成功確定はOTA更新の`CONFIRMED`相当かつ`otaSettlementPending=false`となったlocal resultを受けた後にだけ通知する。

candidateがBLE_WAITへ到達しただけ、`TRIAL_BOOT_VALIDATED`だけ、またはVPS result reportがPENDINGであるだけでは成功/失敗を誤表示しない。VPS result reportがPENDINGでもlocal OTA SUCCESSが確定済みなら、local成功表示を取り消さない。

### 17.4 OTA失敗/復旧

PREVIOUS復旧中はOTA/recoveryの詳細状態を提供する。

システム状態が異常停止/起動失敗に該当する場合、本体RGB/7segはpriority 3を優先する。

PREVIOUS復旧に成功し通常起動へ戻った後、アプリ/管理Web向け履歴通知として「OTA失敗・復旧成功」を提供可能とする。

## 18. 起動・終了・低消費電力表示

### 18.1 起動

applicationのIndicator Manager初期化後、システム状態管理が起動処理状態である間`RGB_STARTUP`を表示する。

fixed boot実行中の表示は第26章による。

### 18.2 BLE待機

BLE接続待機state確定後、上位candidateがなければBLUE連続点灯とする。

### 18.3 終了処理

終了処理state確定後は`RGB_SHUTDOWN`を表示する。

終了完了を先読みしてLEDを消灯せず、起動・終了・再起動管理/システム状態管理の終了処理中状態を維持する。

### 18.4 低消費電力

低消費電力状態そのものを代表表示する場合はRGBおよび7segをOFFとし、電源LEDの短パルスだけを残す。

ただし低消費電力中にpower danger、E-stop、異常停止相当その他priority 1～8の上位表示対象が成立した場合は、公開用システム要求仕様「21. 状態表示・利用者通知」のpriorityを優先する。電源・省電力管理が必要な表示機能を選択的に復帰可能な範囲で、当該上位RGB/7seg表示へ切り替える。表示のために安全処理・電源遮断を遅延しない。

低消費電力代表表示だけを理由にRGB/7seg用の高頻度wakeを行わない。

## 19. BLE・Wi-Fi・VPS・時刻状態の扱い

### 19.1 BLE

BLE未接続はBLE接続待機stateのBLUE連続点灯で示す。

操作可能state中にBLE linkが一時切断してstate遷移前の場合は、システム状態管理/BLE接続・認証の確定状態に従い先走ってBLE待機表示へ変更しない。

### 19.2 Wi-Fi/VPS

Wi-Fi未接続、VPS未接続をRGB LEDで常時個別表示しない。

詳細notificationへ状態を提供する。

Wi-Fi/VPS異常について異常管理がoperation impactを提供した場合、その詳細を通知へ含める。システム全体の通常操作禁止・制限または異常停止への昇格はシステム状態管理のstate、`operationAvailability`、`primaryRestrictionReason`に従って本体表示へ反映する。

### 19.3 時刻

`TIME_UNTRUSTED`単独では本体RGBの独立patternを追加しない。

時刻管理の設計どおりlocal安全操作は継続可能なため、詳細通知で、

- trust state
- `TIME_QUALITY_*`
- VPS management unavailable due time
- wired maintenance required

を提供する。

TIME_TRUSTED喪失によりVPS接続・デバイス認証が既存VPS sessionを終了した場合、そのsessionを認証済みとして表示し続けない。

時刻問題がシステム全体の通常操作禁止へ昇格した場合だけ、システム状態管理の確定結果に従ってpriority 4表示を行う。

## 20. 詳細状態モデルと一般操作者向けメッセージ

### 20.1 内部UserStatusModel

内部では、現在の状態を表す一つの論理モデルを保持する。

少なくとも次を含める。

- schemaVersion
- statusGeneration
- systemState
- transitionInProgress
- operationAvailability
- primaryRestrictionReason
- safeStopの要約情報
- emergencyStopの要約情報
- stopStatusGeneration
- 電源の警告・制限の要約情報
- activeFaultCount
- faultListGeneration
- 選択したindicatorCode
- OTAの要約情報（処理段階、更新の確定処理、本体での結果、報告状態）
- BLE/Wi-Fi/VPSの要約情報
- 時刻の信頼状態・品質の要約情報
- 設定の適用元の要約情報
- 製品を識別するための短縮情報
- 有効性・不明状態を示すフラグ

`systemState`、`transitionInProgress`、`operationAvailability`および`primaryRestrictionReason`は、システム状態管理の同一の読取り専用スナップショットから取得する。その他の要約情報は、各詳細情報の管理元から取得する。これらを用いてシステム状態管理の全体判定を上書きしない。

この内部モデルをそのまま一つのBLEパケットへ格納して送信しない。

### 20.2 active fault詳細

異常管理が提供する、現在管理中の異常の集合をページ単位で参照する。

`FAULT_DETAIL_PAGE`は1ページ最大8件とし、ページ番号（page index）、異常管理から取得したfaultListGeneration、itemCount、hasMoreを持つ。本機能独自の異常一覧のページ世代は生成しない。

各異常は、1件ずつ固定サイズの概要情報へ変換する。

ページの取得中にfaultListGenerationが変化した場合、取得側はページ0から取得し直す。これにより、固定RAMの範囲で管理中のすべての異常を確認できる。

## 21. スマートフォンアプリへの通知契約

### 21.1 責任

本機能はスマートフォンへ表示すべき状態や処理結果を提供する。

BLE GATT message framing、認証セッション、notification再送/切断処理はBLE接続・認証の責任とする。

### 21.2 BLE接続・認証の64 byte上限

BLE接続・認証機能が定めるapplication messageの最大64 byteと、固定24 byteの共通headerを前提とする。
この範囲で現在の状態概要を通知するため、即時状態通知にはpayload 40 byte以下の`STATUS_SUMMARY`を使用する。

#### `STATUS_SUMMARY`へ含める情報

`STATUS_SUMMARY`には、少なくとも次を圧縮して含める。

- statusGeneration : u32
- faultListGeneration : u32
- systemState : u8
- operationAvailability : u8
- primaryRestrictionReason : u8
- bodyDisplayPattern : u8
- indicatorCode : u8
- flags（safe stop/E-stop/power warning/fault/OTA/time/source incomplete等） : u16
- selected fault class : u8
- activeFaultCount : u8
- OTA stage/result summary : u8/u8
- OTA settlement/report summary : u8
- BLE/Wi-Fi/VPS/time quality summary : 各u8
- battery state summary : u8
- detail availability bitmap : u16

`systemState`、`operationAvailability`および`primaryRestrictionReason`には、システム状態管理機能が確定した値を符号化する。
状態表示・利用者通知機能が独自に再判定した値は送信しない。

上記項目を含めても、payloadは40 byte以下とする。

#### 通知内容とBLE通信形式の担当

| 担当 | 定める内容 |
| --- | --- |
| 状態表示・利用者通知機能（本書） | 各項目の意味、通知へ反映する条件、`statusGeneration`の更新規則 |
| BLE接続・認証機能 | message type、各項目の通信上の位置（field offset）、符号化方式、購読、および再取得の通信規則 |

BLE通信上の形式は、BLE接続・認証基本設計 §10.10の`STATE_SNAPSHOT`／`STATUS_SUMMARY_V1`の定義に従う。
protocol 1.0では、固定28 byteのpayload、共通header込み52 byte、little-endianの項目配置を使用する。

本書は通知内容の意味を定めるが、BLE上のバイト配置を重複定義しない。

### 21.3 詳細取得

`STATUS_SUMMARY`は、現在の状態を64 byte以内のBLE application messageで通知するための概要情報である。
異常の詳細、監視値、復旧理由など、概要へ収める必要のない情報は`STATUS_SUMMARY`へ詰め込まない。

これらの詳細情報は、固定サイズの詳細取得要求・応答（detail request/response）で取得する。

管理中の異常（active fault）の詳細取得には、第20章で定める**1ページ最大8件**の方式を使用する。

`STATUS_SUMMARY`の`detail availability bitmap`などで詳細情報の有無を示し、必要な場合だけ詳細取得へ進めるようにする。

### 21.4 認証前/認証後

一般の詳細状態は認証済みsessionへ提供する。

認証前のアドバタイズに、異常詳細、所有者情報、Device ID全文等を載せない。

### 21.5 初回同期と通知対象となる変化

#### 認証直後の初回同期

操作端末の認証が成立した後、現在の`STATUS_SUMMARY`を一回送れるようにする。
これにより、接続前に発生していた状態も含めて、アプリが現在状態へ同期できるようにする。

#### 通知対象となる変化

初回同期後は、利用者へ通知する意味のある変化が生じたときにNotificationを生成する。
通知対象となる変化には、少なくとも次を含む。

- システム状態管理が提供する状態・遷移情報、operationAvailability、primaryRestrictionReasonの変更
- 停止・緊急停止管理の`stopStatusGeneration`で識別される`StopStatusSnapshot`の変更
- 電源の警告・制限の変更
- 異常管理の`faultListGeneration`で識別される、発生中の異常のスナップショットの変更
- 選択したindicatorCode／bodyDisplayPatternの変更
- OTAの処理段階、更新の確定処理、本体での結果、有線復旧状態の変更
- BLE/Wi-Fi/VPSの状態、時刻の信頼状態・品質について、利用者へ伝える内容の変化
- sourceDataIncompleteまたは詳細情報の参照可否の変更

#### 異常一覧の世代変更

異常管理機能は、管理中の異常一覧またはその公開内容が変化したときに`faultListGeneration`を進める。
状態表示・利用者通知機能は、その値を受け取って`STATUS_SUMMARY`へ反映する。

発生中の異常の件数と選択したコードが偶然同じでも、受け取った`faultListGeneration`が変化した場合は、次のように扱う。

1. 新しい`faultListGeneration`を`STATUS_SUMMARY`へ反映する。
2. 状態表示・利用者通知の`statusGeneration`を進める。
3. アプリが異常詳細を再取得する必要があることを認識できるようにする。

#### 未送信の通常状態を最新の一件へまとめる

BLE接続・認証機能は、まだ送信していない通常の`STATE_SNAPSHOT`が複数生じた場合、最新の`statusGeneration`を持つ一件へまとめることができる。

これは、**未送信の通常状態を最新の一件へまとめる送信上の最適化**であり、状態表示・利用者通知機能が`statusGeneration`を生成する規則は変更しない。

中間の世代をすべてNotificationで受信できることを、履歴保証とはしない。

#### Notificationを取りこぼした場合の再取得

次の場合は、BLE接続・認証の`STATUS_QUERY`を使用して現在の`STATE_SNAPSHOT`を再取得し、最新状態へ収束する。

- Notificationを受信できなかった場合。
- 受信した世代に飛びがある場合。
- BLEを再接続・再認証した場合。

### 21.6 反映時間

認証済みBLE接続が成立しnotification送信可能で、link congestionまたは切断がない通常条件では、情報の提供元機能が表示・通知対象状態を確定してから本体が`STATUS_SUMMARY`送信を開始するまで**500 ms以内を暫定上限**とする。

スマートフォンアプリ側は、正常な`STATUS_SUMMARY`を受信してから現在状態のデータモデルへ反映するまで500 ms以内を上限として設計する。したがって、同条件における提供元の状態確定からスマートフォンアプリの現在状態のデータモデルへの反映までを、**1.0 s以内の暫定システム上限**とする。画面レイアウトやアニメーションの処理完了を、この状態反映の判定の前提にしない。

BLE未接続、認証未完了、通信の混雑または切断中は、この一連の反映時間を保証しない。再接続・再認証後は、現在の状態の要約情報を再取得して最新状態へ収束する。

500 ms/1.0 sを実機評価で変更する場合は、本書およびスマートフォンアプリ基本設計へ反映する。

### 21.7 generation

`statusGeneration`は状態表示・利用者通知が所有する`UserStatusModel`および`STATUS_SUMMARY`の本体アプリケーションの同一起動内でのみ有効なuint32とし、0を未確立へ予約し、Indicator Manager初期化後の初回有効summaryを1として公開する。第21.5節の通知内容の変化を反映した新しいsummaryを原子的に公開するときに一回進め、単なる再通知または同じsummaryの再参照では進めない。wrap時は0を使用しない。

停止・緊急停止管理の`stopStatusGeneration`および異常管理の`faultListGeneration`は、各情報の提供元機能から受け取る世代である。本機能が`statusGeneration`と同じカウンタとして採番しない。提供元の世代変更を反映した結果、表示・通知用の要約情報の内容が変化した場合に、状態表示・利用者通知が自身の`statusGeneration`だけを進める。

異なるapplication bootまたは再認証セッションをまたいで単純大小比較しない。notification欠落時、アプリはcurrent summary再取得で収束可能とする。

### 21.8 復旧操作結果

復旧要求者へ、担当機能から確定した次の結果を提供する。

- SUCCESS
- FAILED
- UNKNOWN/RESULT_NOT_CONFIRMED

要求受付だけでSUCCESSと通知しない。

固定4件のdetail result queueはpush通知待ちの有限bufferであり、復旧結果を確認するときの唯一の基準にはしない。要求元へ返す結果は担当機能が管理するtransaction/request resultを使用し、queue満杯で重要結果を成功扱いにして破棄しない。pushできない場合はcurrent summary/detail pending状態から再照会できるようにし、要求元が結果を確認できない場合はUNKNOWNとして扱う。

### 22.1 管理Web

本体が管理Webへ直接通信しない。

VPSへ送信するログ/診断/status dataを通して、管理Webが必要な状態を確認できるよう、その状態を示す情報を提供する。

### 22.2 保守診断

ログ・診断の保守用UART等から、少なくとも次を参照可能にする。

- 選択した本体表示パターン・コード

- 表示情報の提供元が管理する各世代
- 表示機能の健全性
- 最後の描画結果

システム状態、通常操作可否とその理由は、システム状態管理が提供する情報であることを診断情報上も識別可能とする。

### 22.3 本体表示と詳細情報の不一致確認

診断時は「本体で現在選択している表示内容」と「その選択根拠となった情報の提供元」を確認可能とし、表示誤りの解析に使用できるようにする。

## 23. 状態遷移中および処理中結果の表示

### 23.1 状態遷移中の表示

遷移元の状態に`transitionInProgress`がある場合でも、遷移先の状態が確定するまでは現在状態を有効な状態として扱う。

### 23.2 完了結果

次は、担当機能から完了結果を受け取った後だけ成功表示へ移す。

- 安全停止の完了
- 緊急停止の解除
- 異常からの復旧
- OTA更新
- 終了処理
- 保守による時刻の復旧

### 23.3 UNKNOWN

結果返信timeout、reset、通信断等により結果を確認できない場合、詳細通知はUNKNOWNを保持する。

表示機能が前回成功結果から成功を推測しない。

## 24. 監視値の有効性・更新停止・不明表示

### 24.1 値＋validity

数値を通知する場合、必ずvalidityを付ける。

- VALID
- INVALID
- UNAVAILABLE
- STALE

### 24.2 stale判定

各測定値のstale条件は計測を担当する機能が管理する。

本機能は一律の「1秒経過したらstale」等を独自設定しない。

### 24.3 現在状態のスナップショットを再取得できない場合

提供元のスナップショットを取得できなかった場合は、前回値を無期限に現在値として扱い続けない。

該当フィールドをUNKNOWNにし、表示モデルの`sourceDataIncomplete`を設定する。

システム状態管理がシステム全体のoperation禁止・制限を確定していない限り、本機能自身がoperation禁止・制限を決定しない。

### 24.4 body fallback

現在のシステム状態を正常に取得できない等、表示内容の意味を保証できない場合は、管理元の情報に基づく、より優先順位の高い安全表示が無い限り`RGB_UNKNOWN`を使用できる。

これは「システム異常停止」を意味せず、表示情報不完全の縮退表示である。

## 25. 表示更新・保持・チャタリング防止

### 25.1 logical render周期

本体アプリケーション側Indicator Managerは次で更新する。

- source event受信時：即時render request
- periodic reconciliation：100 ms
- RGB pattern phase tick：50 ms

### 25.2 最大反映時間

applicationが正常実行中では、情報の提供元機能が表示対象状態を確定してから本体RGB/7seg論理出力を対応状態へ更新開始するまで**200 ms以内を暫定上限**とする。

緊急停止・power dangerはevent-driven pathで、情報の提供元機能が表示対象状態を確定してから対応RGB出力更新開始まで**50 ms以内を暫定上限**とする。ただし表示は安全処理より後回しであり、停止・電源保護そのものの安全処理期限の成立条件にはしない。

source state確定から本機能への通知・snapshot可視化までの内部遅延も上限内budgetへ含める。実機評価で成立しない場合は詳細設計だけで上限を緩和せず本書へ戻す。

### 25.3 情報の提供元で行うヒステリシス判定を再実装しない

battery warningや異常判定のhysteresisは各sourceで完了しているため、表示側で独自に別threshold/hysteresisを設けない。

### 25.4 履歴表示

短時間で解除された状態を本体RGBへ長時間latchedしない。

利用者が後から確認すべき処理結果はアプリ/管理Web/ログの履歴で確認可能とし、本体RGBだけに履歴保持責任を持たせない。

## 26. 起動前・固定ブート・起動失敗時の早期表示

### 26.1 必要性

applicationが起動不能でも起動失敗・wired recovery requiredを本体で識別できる必要があるため、固定ブート・復旧のfixed bootから利用可能な`EARLY_IND`を設ける。

EARLY_INDの初期化・表示更新が失敗しても、固定ブート・復旧のboot/recovery decision、IWDT、安全状態またはwired recovery移行を待たせない。表示完了をfixed boot進行条件にしない。

### 26.2 early表示範囲

fixed bootでは次だけを表示する。

- PWR_CTRL確立後の電源LED：ON
- fixed boot進行中：BLUE 250/250 ms相当
- fixed boot起動失敗：RGB_FAULT
- wired recovery required：RGB_FAULT＋第26.3節のcause-specific 7seg code
- boot critical error：第26.3節のcause-specific 7seg code

BLE/Wi-Fi/VPS状態や通常warningをfixed bootへ持ち込まない。

### 26.3 early 7seg code

固定ブート・復旧のboot failure reasonを本書の同一indicatorCode registryへmappingし、fixed bootが独自コード体系を持たない。

初期基本mappingを次とする。

| 固定ブート・復旧のfailure class | early indicatorCode |
| --- | ---: |
| signed PRIMARY/candidateのhash・signature・product/HW・Boot Interface等の起動前検証失敗 | 11 |
| `CRIT_OTA_BOOT`、install/trial/recovery metadata、Boot Handoff等の起動管理情報異常 | 12 |
| OTA外の自動boot/recovery経路がなくwired/service recovery required | 13 |
| OTA recovery失敗またはOTA後wired recovery required | 72 |
| SecurityGen、critical trust/state MAC、PK_FW_VERIFY等のsecurity trust異常 | 81 |
| 上記へ安全に分類できない起動失敗 | 10 |

同時に複数causeが成立する場合、security trust異常、OTA recovery失敗、image verify失敗、boot metadata異常、generic boot failureの順で、実際の固定ブート・復旧のprimary failure reasonに最も直接対応するcodeを一つ選ぶ。これは表示分類であり固定ブート・復旧の復旧decisionを変更しない。

### 26.4 application handoff前表示

fixed bootが正常にapplicationへbranchする直前まで、起動中表示を維持する。

branch直前にfixed boot自身のRGB pattern timer、7seg scan interrupt等のearly表示更新源を停止し、出力を既知状態へ置く。

application Indicator Managerは起動後に表示HALを再初期化し、システム状態管理の現在状態を取得した後、自身の表示へ切り替える。

## 27. 本体表示ドライバと所有権移管

### 27.1 表示の担当機能

表示ハードウェアを制御するソフトウェアの担当を、次のように区別する。

- `IND_OWNER_FIXED_BOOT`
- `IND_OWNER_APPLICATION`
- `IND_OWNER_NONE`

同一CPU上でfixed bootとapplicationは同時実行しないが、fixed bootが残したtimer/interruptがbranch後も表示registerを更新し続けないよう明示的に停止する。

### 27.2 handoff

handoffは次を基本とする。

1. fixed bootがearly表示更新を停止する。
2. fixed boot用display timer/ISRをdisableする。
3. 現在のearly display reasonをBoot Handoffへ記録する。
4. hardware outputを既知状態へ置く。電源LEDは通常電源供給中を示すためONを維持してよい。
5. applicationへbranchする。
6. applicationが表示HALを再初期化する。
7. システム状態管理の現在状態を取得し、APPLICATION側が表示を開始する。

fixed bootへbranch後の双方向service callや複雑なownership commit protocolは設けない。

### 27.3 application初期化失敗

applicationがIndicator Manager初期化まで到達できない場合、起動・終了・再起動管理/異常管理/固定ブート・復旧の起動失敗処理へ進む。

表示所有権だけを理由に安全処理を待たない。

## 28. 表示制御異常・表示更新停止

### 28.1 検出対象

初期製品でソフトウェアから少なくとも次を検出する。

- display driver API error
- invalid RGB pattern ID
- invalid 7seg code
- 描画状態の破損・制御担当の不正
- periodic render counter停止
- 7seg scan task/ISR heartbeat停止を別監視可能な構成の場合その停止

### 28.2 render監視

`displayRenderGeneration`を正常renderごとに増加する。

`IND_HEALTH`はrender処理とは別の監視contextから、application通常実行中に1秒を超えてgenerationが進行しない場合を`IND_RENDER_STALLED`候補とする。

同一scheduler全体が停止した場合はIND_HEALTH自身も動作できないため、system IWDT等の別監視が最終検出を担当する。

低消費電力、shutdown、意図的表示停止中はmonitor modeを切り替え、誤検出しない。

### 28.3 実発光故障

LED断線、RGB素子故障、7seg segment断線を検出する専用current sensor/photodiode/read-backは初期製品へ追加しない。

これは公開用システム要求仕様「21. 状態表示・利用者通知」の将来検討項目として扱う。

### 28.4 異常時処置

表示機能異常を異常管理/ログ・診断へ通知する。

異常管理は表示異常の局所的なoperation impact、処置および復旧可否を評価し、システム状態管理がシステム全体の通常操作可否を最終判断する。

本機能自身が通常操作禁止を決定しない。

### 28.5 他表示手段

RGB driver異常でも7segが利用できる場合など、単純に利用可能な出力へ表示できる範囲は維持してよい。

高度な故障マトリクスによる動的operation可否判定は初期製品へ入れない。

## 29. 電源OFF・強制遮断・表示消灯

### 29.1 通常終了

終了処理中はRGB_SHUTDOWNを表示し、電源LEDを点灯維持する。

起動・終了・再起動管理が終了完了し電源遮断へ進む際は、可能ならRGB/7seg/電源LEDをOFFへ要求する。

### 29.2 強制遮断

強制電源遮断では表示消灯完了を待たない。

電源遮断を最優先する。

### 29.3 power danger

power danger表示を見せるために遮断を遅延しない。

表示可能な期間だけRGB_POWER_DANGERを出し、その後電源OFFとなることを正常とする。

## 30. セキュリティ・プライバシー・権限制御

### 30.1 secret非表示

次を本体表示、アプリ一般状態、管理Web一般状態へ出力しない。

- private key
- BLE terminal key
- 初回所有者登録用登録秘密情報および登録用一時保護鍵
- Wi-Fi passphrase

- raw authentication token

コードだけからcredential状態やsecurity secretを推測できる詳細分類を避ける。

### 30.3 詳細権限

本機能は、情報を利用する各機能へ利用者の役割に関する情報を渡せる。ただし、BLEの認証・役割とVPS／Webの認可は、それぞれのセキュリティ・所有者管理機能が正式に管理する。

### 30.4 shortDeviceId

利用者が近傍個体を識別する場合、製品情報管理のshortDeviceIdを使用可能とする。

full Device IDやmanufacturingSerialを本体LED/7segへ表示しない。

## 31. 実行時間・固定資源・視認性・性能方針

### 31.1 基本値

| 項目 | 基本設計値 |
| --- | ---: |
| logical RGB render tick | 50 ms |
| 全提供元からの情報再取得と照合 | 100 ms |
| 本体表示反映時間 | 200 ms以内 暫定上限 |
| power danger/E-stop表示反映 | 50 ms以内 暫定上限 |
| 認証済みBLE接続中のsummary通知開始 | 500 ms以内 暫定上限 |
| 提供元での情報確定→スマートフォン内の現在状態のデータモデルへの反映 | 1.0 s以内 暫定上限（正常接続条件） |
| fault detail page | 最大8件/page |
| STATUS_SUMMARYのデータ本体 | BLE接続・認証の`STATUS_SUMMARY_V1`固定28 byte（40 byte以下） |
| detail result push queue | 最大4件 |
| dynamic heap | 使用しない |

上表の時間、page/queue数、データ本体の容量上限は評価確定待ちを含む基本設計で管理する値である。BLE通信データ形式の28 byte layoutおよび52 byte messageはBLE接続・認証の定義に従う。

### 31.2 通知キュー

現在状態の通知は、最新の要約情報1件にまとめる。

状態変化のたびに、容量上限のないFIFOへ追加しない。

復旧結果等、要求元へ通知する重要な結果には、固定4件のキューを用いる。ただし、第21.8節のとおり、このキューの内容を担当機能が管理する結果の確定値として扱わない。キューが満杯になっても重要な結果を成功扱いで破棄せず、要求元が担当機能の処理状況や結果を再照会できる状態を維持する。

### 31.3 視認性の暫定合否条件

本体表示部は屋内利用を前提として、少なくとも次を初期製品の暫定合否条件とする。

- 視認距離：1.0 m
- 水平視野角：正面から±45°
- 垂直視野角：正面から±30°
- 周囲照度：100～1000 lx

上記条件で、Power LED点灯/点滅、RGB主要pattern、2桁7segコードを識別可能であることを確認する。

暗所で過度に眩しくならないこと、より明るい屋内条件で視認性が不足しないことも参考評価する。

筐体、拡散材、LED/7seg部品確定後のシステムテストで成立性を確認する。条件変更が必要な場合はシステムテスト仕様だけで変更せず、本書へフィードバックして暫定合否値を更新する。

### 31.4 CPU負荷

RGB pattern、7seg表示調停、status summary生成は軽量処理とし、安全制御task/ISRをblockしない。

7seg multiplexが必要な場合も長いbusy waitを使用しない。

## 32. 検証方針

### 32.1 状態mapping

- 全9 system stateの基本表示
- 操作可能時RGB OFF
- BLE待機BLUE steady
- 低消費電力でPower LED blink、上位candidateなしならRGB/7seg OFF
- 低消費電力中にpower danger/E-stop等が成立した場合の選択的表示復帰とpriority維持
- shutdown表示からpower offで全消灯

### 32.2 priority

公開用システム要求仕様「21. 状態表示・利用者通知」のpriority 1～11の全組合せについて、少なくともpairwiseで上位が選択されることを確認する。

特に次を故障注入する。

- power danger + E-stop
- E-stop + abnormal stop
- abnormal stop + low battery
- operation prohibited + OTA
- OTA + shutdown
- startup + low battery
- low power + E-stop
- low power + power danger

### 32.3 7seg

- 00をfault codeに使用しない
- 各rangeの代表code表示
- 複数faultの全件走査とbest selection
- active fault解消後の切替/消灯
- invalid code入力時に99またはdisplay errorとして扱い、memory範囲外参照しない
- 固定ブート・復旧のearly failure class→11/12/13/72/81/10 mapping

### 32.4 表示正確性

- state transition途中でtarget表示しない
- E-stop release受付時点で解除表示しない
- recovery要求受付時点でsuccess表示しない
- OTA BLE_WAIT/TRIAL_BOOT_VALIDATEDだけでsuccess表示しない
- OTA local SUCCESS確定後のresult report PENDINGをOTA失敗と誤表示しない
- stale/invalid measured valueを正常値表示しない
- 停止・緊急停止管理/異常管理/バッテリー・電気安全監視等の詳細状態からシステム状態管理とは別の`operationAvailability`/`primaryRestrictionReason`を生成しない

### 32.5 app通知

- 状態表示・利用者通知が定めた各項目を、BLE接続・認証基本設計 §10.10の`STATUS_SUMMARY_V1`の固定28 byteのデータ本体／52 byteのメッセージへ正しく対応付けられる
- システム状態管理のstate／operationAvailability／primaryRestrictionReasonを変更せずに符号化する
- 発生中の異常の集合だけが変化し、件数・コードが同じ場合でも、異常管理の`faultListGeneration`の変更を取り込み、状態表示・利用者通知の`statusGeneration`を更新する
- 状態確定から500 ms以内に送信を開始する
- 正常接続条件で、提供元での情報確定からアプリ内の現在状態のデータモデルへの反映までを1.0 s以内とする
- 認証後に初回同期を行い、未送信の通常状態は最新の一件にまとめる。`STATUS_QUERY`では同一の`requestId`で再取得でき、通知の欠落・世代番号の飛び・再接続後には現在の状態の要約情報を再取得する
- 発生中の異常を1ページ8件ずつ取得する
- ページ取得中に世代が変わった場合は再取得する
- detail result push queue満杯時に結果を成功扱いでdropせず再照会可能であること
- 未認証BLEで詳細状態を提供しない

### 32.6 early indicator

- application image invalid→11
- fixed boot/critical boot metadata invalid→12
- non-OTA wired recovery required→13
- OTA recovery失敗/wired recovery required→72
- SecurityGen/trust state異常→81
- 未分類boot failure→10
- fixed boot表示driver失敗でもboot/recovery処理を待たない
- fixed boot timer/ISR停止後application再初期化
- handoff直前/直後reset

について表示競合がないことを確認する。

### 32.7 color/pattern usability

通常色覚だけでなく代表的な色覚特性を想定したsimulation/実機確認を行い、色を識別できなくてもpattern shapeで主要安全状態を区別可能か確認する。

### 32.8 視認性

1.0 m、水平±45°、垂直±30°、100～1000 lxの暫定合否条件でPower LED、RGB pattern、7seg codeを確認する。

### 32.9 display fault

- render context停止
- driver error
- invalid pattern
- 7seg scan停止
- low power/shutdown中の誤stalled検出防止
- scheduler全体停止時のIWDT fallback

を確認する。

## 35. 他文書へのフィードバック

### F-01 システム状態管理【反映済み】

システム状態管理は、現在状態に加え、`operationAvailability`、`primaryRestrictionReason`、遷移中かどうか、遷移元・遷移先および世代を、読取り専用スナップショットとして提供する契約へ更新済みである。

本書はそのスナップショットをシステム全体の状態についての確定済み情報として使用し、他機能の詳細状態から再構成しない。

### F-02 異常管理【XR-008反映済み】

異常管理は、発生中の異常を逐次参照できる読取り専用インターフェースを提供する。そこでは、faultId、情報の提供元、操作への影響、復旧可否、利用者に求める操作の分類、`faultGeneration`および`faultListGeneration`を原子的に取得できる。

7segに表示する代表異常は異常管理側で選択せず、本書で定める対応表と優先順位に従って、発生中の全異常から選択する。

異常管理のoperation impactは個別異常の詳細情報とし、システム全体のoperationAvailabilityはシステム状態管理が最終判断する。

### F-03 停止・緊急停止管理【XR-008反映済み】

safeStopActive/completed、emergencyStopActive、releaseAllowed、releaseBlockReasonおよび`stopStatusGeneration`を、停止・緊急停止管理が所有するread-only `StopStatusSnapshot`として原子的に提供する。

### F-04 バッテリー・電気安全監視／電源・省電力管理

バッテリー・電気安全監視はpowerSupplyDanger、lowBatteryWarning、powerOperationRestrictedおよび監視値validityを表示用に提供する。

電源・省電力管理は低消費電力中にpriority 1～8の表示が必要となった場合、表示機能を選択的に復帰可能な範囲で復帰させる。表示のために安全処理・電源遮断を遅延しない。

### F-05 BLE接続・認証／スマートフォンアプリ【XR-022反映済み】

状態表示・利用者通知は`STATUS_SUMMARY`の内容と確定条件を管理し、要約項目、通知対象となる変化、`statusGeneration`および提供元の値を再判定しない原則を定める。BLE接続・認証はBLE通信形式の定義元として`STATE_SNAPSHOT`／`STATUS_SUMMARY_V1`を定義する。protocol 1.0では、固定28 byteのデータ本体、ヘッダ込み52 byte、リトルエンディアンのフィールド配置を使用する。

認証後の現在状態の初回同期、通知すべき変化が生じたときのNotification、未送信の通常状態を最新の一件にまとめる処理、`STATUS_QUERY`による現在のスナップショットの再取得は、BLE接続・認証の通信契約へ反映済みである。Notificationの欠落、世代番号の飛び、再接続後の再同期も同契約に従う。`faultListGeneration`が変化した場合は、異常詳細をページ0から再取得する。

本体側は提供元での情報確定から要約情報の送信開始までを500 ms以内、スマートフォンアプリ側は受信後の現在状態のデータモデルへの反映までを500 ms以内とする。正常接続条件では、この一連の反映時間を1.0 s以内の暫定上限とする。

アプリ側はメッセージID・理由IDに対応する日本語の詳細説明を表示する。状態表示・利用者通知の`statusGeneration`または異常管理の`faultListGeneration`が変わった場合は、必要な詳細情報を再取得する。

### F-06 OTA更新

stage、trial/settlement、local result、`otaResultReportState`、recovery/wired recovery requiredを状態表示へ提供し、BLE_WAIT/TRIAL_BOOT_VALIDATED到達とOTA successful settlementを区別する。

### F-07 固定ブート・復旧

EARLY_INDへboot failure reasonを渡し、本書26.3節の11/12/13/72/81/10 mappingを同一indicatorCode registryとして使用する。

branch前にearly表示timer/ISRを停止し、本体アプリケーション側でdisplay HALを再初期化できるBoot Handoff情報を残す。EARLY_IND失敗をboot/recovery進行条件にしない。

### F-08 時刻管理

TIME_UNTRUSTED、`TIME_QUALITY_*`、VPS disabled due time、wired maintenance requiredを詳細statusへ提供し、単独ではRGB常時表示を要求しない。

TIME_TRUSTED喪失時はVPS接続・デバイス認証のsession終了後の認証状態をdetail statusへ反映し、staleなVPS authenticated表示を維持しない。

### F-09 ハードウェア設計

電源LED、RGB LED、2桁7segはPWR_CTRL下でfixed boot/application双方から安全に制御可能なinterfaceとし、reset直後の不定点灯を避ける。

低消費電力時のLED消費電流、7seg scan方式、ドライバ回路を評価する。視認性は31.3節の暫定合否条件を満たすことを基本とし、変更時は本書へ戻す。

### F-10 保守・取扱説明

7seg code 01～99の安定した利用者向け対応表と、一般操作者向けmessage IDの意味を製品取扱/保守資料へ反映する。

## 36. 初版の自己確認結果と引継ぎ条件

### 36.1 初版自己確認

初稿作成後の自己確認および後続基本設計との整合レビューを含め、次を確認・修正した。

- 公開用システム要求仕様「21. 状態表示・利用者通知」の全31要求へ主対応章を設定した。
- 公開用システム要求仕様「21. 状態表示・利用者通知」第21.13節の15具体化事項すべてへ基本設計値、暫定上限または暫定合否条件を設定した。
- システム状態管理をシステム全体の現在状態、transition context、operationAvailability、primaryRestrictionReasonの正式な管理元とし、停止・緊急停止管理/異常管理/バッテリー・電気安全監視等の詳細情報から表示側で再判定しない責任分界へ統一した。
- operationAvailabilityのUNKNOWNをシステム状態管理と同じ意味で扱うよう用語を整合した。
- 走行制御/砲塔・砲身制御/所有者・操作端末管理/永続データ管理を参照文書へ追加し、走行/砲塔砲身/所有者/永続データとの実在する責任を反映した。
- 公開用システム要求仕様「21. 状態表示・利用者通知」の本体表示priority 1～11を変更していない。
- operation ready時RGB OFFを維持した。
- low powerをPower LED 2 s/50 ms blinkで識別し、上位表示がない場合RGB/7segを消灯する構成とした。power danger/E-stop等の上位candidate成立時はpriorityを維持して選択的表示復帰できるよう電源・省電力管理と整合した。
- RGBを色だけに依存せず点滅patternでも識別する構成とした。
- 7segを異常停止/起動失敗専用に限定し、fixed boot early failureを起動失敗相当として同一registryへ統合した。
- 固定ブート・復旧のearly failureの11/12/13/72/81/10 mappingを基本設計で固定し、「13または72等」という曖昧さを解消した。
- internal faultId/固定ブート・復旧のfailure reasonとstable indicatorCodeを分離した。
- 発生中の異常は全件を逐次走査し、詳細は1ページ8件ずつ取得する方式とした。異常管理が管理する`faultListGeneration`を要約情報へ含めた。
- 停止・緊急停止管理の`stopStatusGeneration`、異常管理の`faultGeneration`／`faultListGeneration`、状態表示・利用者通知の`statusGeneration`を分離した。提供元の各スナップショットと表示用の要約情報について、それぞれを書き換える機能を一つに定めた。
- `STATUS_SUMMARY`の意味・世代は状態表示・利用者通知が定め、BLE通信データ形式はBLE接続・認証が定めるものとした。各項目は`STATE_SNAPSHOT`／`STATUS_SUMMARY_V1`の固定28 byteのデータ本体・52 byteのメッセージへ一意に対応付けた。詳細情報の集合だけが変化した場合も、異常管理の`faultListGeneration`と状態表示・利用者通知の`statusGeneration`により再取得を促す。BLE接続・認証側で世代を採番し直さない。
- 認証後の初回同期、通知すべき変化が生じたときのNotification、未送信の通常状態を最新の一件にまとめる処理、`STATUS_QUERY`による再取得、再接続後の現在のスナップショットの再同期を、BLE接続・認証の通信契約と対応付けた。
- 本体表示への反映200 ms、電源供給の危険・緊急停止の表示50 ms、要約情報の送信開始500 msを、単なる目標から暫定上限へ変更した。正常接続条件で、提供元での情報確定からスマートフォンアプリの現在状態のデータモデルへの反映までを1.0 sとする暫定システム上限も追加した。
- 視認性1 m、水平±45°、垂直±30°、100～1000 lxを単なる初期目標ではなく暫定合否条件とした。
- OTA更新の`otaSettlementPending`、local result、`otaResultReportState`を取り込み、result report PENDINGをlocal OTA失敗と誤表示しないようにした。
- 時刻管理のTIME_QUALITYとTIME_TRUSTED喪失時VPS session終了へ整合し、stale VPS authenticated表示を残さないようにした。
- fixed boot起動失敗でも本体表示できるEARLY_INDを維持し、EARLY_IND失敗をboot/recovery/IWDT進行条件にしないことを明確化した。
- 固定ブートから本体アプリケーションへの表示担当の引継ぎは、タイマ・ISR停止 → 分岐 → 本体アプリケーションによる再初期化、という単純な手順を維持した。
- body表示は一つの代表状態だけを示し、他のactive要因を詳細statusへ残した。
- transition先を成立前に表示しない構成とした。
- invalid/stale monitor値を現在正常値として表示しない構成とした。
- display完了を安全処理の前提にしていない。
- display software stallを別監視contextのrender generationで検出し、scheduler全体停止はIWDTへ委ねる責任を維持した。
- hardware実発光read-backを初期製品へ追加していない。
- 現在状態の通知は最新の一件にまとめ、詳細情報には固定容量のページ・キューを用い、malloc/freeを使用しない。詳細結果の通知キューの内容を、担当機能が管理する結果の確定値として扱わない。
- 容量、時間、視認性、ページ・キューの上限を、評価確定待ちを含めて基本設計で管理する値として明確化した。

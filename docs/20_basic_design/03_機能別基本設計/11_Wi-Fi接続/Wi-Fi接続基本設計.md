## 1. 本書の目的

### 1.1 目的

本書の目的は、公開用システム要求仕様「11. Wi-Fi接続」を実現するため、Wi-Fi接続機能が管理する状態、DA16200MODとのホスト通信、Wi-Fi接続設定、接続・切断・再接続、DHCP、低消費電力および異常復旧を、詳細設計へ展開可能な粒度まで具体化することである。

### 1.2 対象範囲

本書は、Tank_Robot本体のWi-Fi通信部について、DA16200MODとのホスト通信、Wi-Fi接続設定、アクセスポイントへの接続、DHCPによるIP通信設定、通信状態監視、切断・再接続、低消費電力連携、モジュール異常復旧、状態通知およびログ連携の基本方式を具体化する。

Wi-Fi接続機能の責任範囲は、Wi-Fi通信部の使用可能化からアクセスポイント接続およびIP通信利用可能状態の確立・維持までとする。VPS接続先の正当性確認、相互TLS、デバイス認証、HTTPS要求・応答および管理・保守アプリケーション通信は「VPS接続・デバイス認証」および「セキュリティ管理」の責任とする。

本書では、Wi-FiをVPSとの管理・保守通信のための通信経路として使用し、走行、砲塔・砲身、通常停止、緊急停止その他の通常操作経路として使用しない。

### 1.3 上位文書・関連文書

主対象要求は公開用システム要求仕様「11. Wi-Fi接続」とし、関連する公開用要求および完成済み基本設計について、Wi-Fi接続との責任分界と連携に必要な範囲を参照する。

`20_要求仕様`および`30_コア要求仕様`は本書の上位要求として使用しない。公開用要求で未確定の方式について本書で具体化する場合は、本書の設計判断として明示する。

関連基本設計との整合確認結果を本書へ反映する。後続基本設計で具体化されたTLS主体、Wi-Fi認証情報保護、永続保存および工場初期化方式が本書の外部振る舞いを具体化している場合は、その確定内容を本書でも使用する。

## 2. 設計方針と適用範囲

### 2.1 基本方針

Wi-Fi接続機能は次の原則で設計する。

1. Wi-Fiは管理・保守通信専用とし、通常操作経路にしない。
2. 正式なWi-Fi設定をRA8M2側永続データに限定し、DA16200MOD内部NVRAMの内容を正式な設定として扱わない。
3. 起動したことだけを理由にAP接続しない。上位機能から利用要求が発生したときだけ接続する。
4. DA16200MODとのホスト通信はUART1によるAT Command方式とする。
5. 最終製品ではUART 230400 bps、8N1、RTS/CTSハードウェアフロー制御を使用する。
6. Wi-Fi設定は1件のみとし、初期製品では2.4 GHz IEEE 802.11b/g/n、WPA2-Personal、AES-CCMP、DHCP IPv4を使用する。
7. Hidden SSID、複数AP、ローミング、固定IP、SoftAP、WPS、汎用ローカル待受けサービスを初期製品の通常機能として提供しない。
8. AP接続・DHCPと、VPSのTCP/TLS/HTTPS・デバイス認証を別責任として扱う。VPS接続・デバイス認証で確定したとおり、DA16200MODはWi-Fi/IP/DNS/TCP transport、TLS 1.3およびHTTPSはRA8M2が担当する。
9. 通信状態が不明な場合はIP通信利用可能と扱わない。
10. 自動再接続は一時的障害に限定し、認証情報不正や非対応方式で同じ条件を無期限再試行しない。
11. DA16200MODの異常復旧はAP再接続と区別し、RESET、必要時の`PWR_WIFI`電源再投入を段階的に使用する。
12. 低消費電力状態ではWi-Fi/VPS通信を維持せず、DA16200MODをSleep mode 2または安全な縮退状態へ移行する。
13. Wi-Fi設定全体をセキュリティ管理のAES-256-GCMで認証付き暗号化し、`wifiCredentialRevision`により古い設定への自動fallbackを禁止する。Wi-Fi設定、パスフレーズ、ネットワーク内部情報を通常ログ・一般利用者向け表示へ平文出力しない。
14. Wi-Fi内部資源は固定上限を持つ静的資源とし、`malloc`/`free`および無制限キューを使用しない。

### 2.2 対象範囲

本書は次を対象とする。

- RA8M2とDA16200MODのUART/AT Command基本方式
- RESET、RTC_WAKE_UP、`PWR_WIFI`との連携
- Wi-Fi設定1件の意味・検証・利用条件
- OWNER端末からBLE経由での設定登録・変更
- DA16200MOD初期化・使用可能確認
- AP接続、WPA2認証、DHCP、IP利用可能判定
- 複数管理機能からのWi-Fi利用要求調停
- 接続監視、切断、再接続
- DA16200MOD無応答時の再初期化・電源再投入
- 低消費電力移行・復帰
- 工場初期化時のWi-Fi設定・認証情報消去と古い認証情報の再利用禁止
- 状態通知、ログ、診断、評価方針

### 2.3 対象外

次は各担当機能で定め、本書で重複して最終判断しない。

- VPS接続先URL、HTTPS API、HTTPメソッド、アプリケーションメッセージ形式
- VPSサーバー証明書検証、本体クライアント証明書、相互TLS、デバイス認証、TLS 1.3の暗号詳細
- RA8M2上のTLS/HTTPSセッション管理およびTCP byte stream上のTLS処理実装
- 設定パッケージ、ログ、OTAファームウェア等のアプリケーションデータ内容
- システム状態遷移の最終判断
- `PWR_WIFI`ロードスイッチの回路設計
- Wi-Fi設定用AES-256-GCMの暗号API、Wrapped Key内部表現、nonce生成実装。ただしセキュリティ管理で確定した設定全体の認証付き暗号化、`wifiCredentialRevision`によるrollback防止およびfactory reset時key rotationを弱めない
- DA16200MOD内部ファームウェアソースの具体変更、ATコマンド文字列・番号
- RA8M2のSCIチャネル、端子、DMAC/DTCの具体設定

### 2.4 初期製品で対象外とする拡張

- 5 GHz Wi-Fi
- WPA3-onlyアクセスポイントを必須とする接続
- Enterprise Wi-Fi（802.1X/EAP）
- Hidden SSID対応
- 複数Wi-Fiプロファイル
- AP優先順位・ローミング・高度な自動選択
- 固定IPv4設定
- IPv6を必須とする運用
- SoftAPによる設定
- WPS
- Wi-Fi Direct
- ローカルLANから本体へ接続するWeb、TCP、UDPその他の汎用サーバー

## 3. 責任分界と共通条件

### 3.1 関連機能との責任分界

| 機能 | 主な責任 |
| --- | --- |
| Wi-Fi接続 | DA16200MODに対するRA8M2からの制御、およびTCP通信の基本操作を提供する唯一の機能。Wi-Fi設定の意味、AP接続、DHCP、IP利用可能状態、切断・再接続、Wi-Fi固有異常を管理する |
| VPS接続・デバイス認証 | Wi-Fi接続が提供するDA16200 TCP通信の基本操作を使用するVPS向けTCP接続・sessionの意味、RA8M2上のTLS 1.3/HTTPS、VPS接続先、VPS正当性確認、本体デバイス認証、VPS要求・応答 |
| BLE接続・認証 | OWNER端末からのWi-Fi設定メッセージの送受信、通信データ形式・分割データの妥当性、session・権限情報、`requestId`、再構成・timeout・transport取消し。上限値はBLE接続・認証基本設計で定める |
| 所有者・操作端末管理 | OWNER役割・有効性の正式な管理、工場初期化全体シーケンス |
| セキュリティ | Wi-Fi設定全体のAES-256-GCM保護、`K_WIFI_STORE`、`wifiCredentialRevision`、nonce・rollback防止、factory reset時key rotation、TLS暗号サービス |
| 永続データ管理 | WIFI_STOREへの認証付き暗号blobの原子的保存、完全性、中断復旧、RESET_PENDING連携、消去 |
| 電源・省電力管理 | `PWR_WIFI`、電力状態、Sleep移行許可、Wake、電源遮断・再投入 |
| 異常管理 | Wi-Fi異常の影響度、復旧許可、対象機能復旧回数、復旧失敗後の処置 |
| 状態表示・利用者通知 | Wi-Fi状態の具体表示 |
| ログ・診断 | Wi-Fiイベントの保存方式、容量、保持期間、VPS送信 |

### 3.2 Wi-Fi利用可能とVPS利用可能を分離する

`IP_READY`は、Wi-Fi AP接続とDHCPが正常に成立し、IP通信経路を上位機能へ提供可能であることだけを示す。

`IP_READY`であっても、VPSの正当性確認、TLS、デバイス認証またはHTTPSが失敗している場合、VPS通信利用可能とは扱わない。

逆に、以前のVPSセッションが存在したとしてもWi-Fi切断またはIP設定喪失時には、そのVPS通信を継続利用可能と扱わない。

### 3.3 安全機能からの独立

Wi-Fi接続、再接続、スリープ、復旧または高負荷通信によって、走行・砲塔制御、安全監視、停止・緊急停止、電源保護、異常管理を阻害しない。

Wi-Fi異常だけを理由として走行・砲塔の安全処理を停止したり、Wi-Fi復旧完了を安全停止完了条件にしたりしない。

## 4. DA16200MODとのホストインターフェース

### 4.1 採用方式

RA8M2とDA16200MODの通常ホスト通信はUART1 AT Command方式とする。

基本値は次とする。

| 項目 | 基本設計値 |
| --- | --- |
| Baud rate | 230400 bps |
| Data bits | 8 |
| Parity | None |
| Stop bit | 1 |
| Flow control | RTS/CTSハードウェアフロー制御 |
| 通信主体 | RA8M2がHost、DA16200MODがWi-Fi/IP/DNS/TCP transportを担当。TLS 1.3/HTTPSはVPS接続・デバイス認証に従いRA8M2が担当 |

最終製品ではTX、RX、RTS、CTSを通常配線として実装する。

評価用US159-DA16200MEVZでは、UART1ハードウェアフロー制御を使用するために評価ボードマニュアルに従った抵抗構成変更が必要となる。評価ボード固有の改造を最終製品の必須回路構成とは扱わない。

### 4.2 補助信号

少なくとも次を使用する。

- `RESETn`：DA16200MODを既知状態へ再初期化するためのリセット
- `RTC_WAKE_UP`：Sleep mode 2からの外部Wake
- `PWR_WIFI`：電源・省電力管理が管理するDA16200MOD電源系統

`RTC_WAKE_UP`はDA16200の外部Wake入力仕様に対して十分な幅を持つ信号とし、初期基本設計では1 ms以上のWakeパルスを使用する。具体的な電圧条件・端子回路はハードウェア詳細設計で確定する。

### 4.3 ATコマンド（AT Command）の要求・応答管理

#### 同時に進行させる要求

RA8M2からDA16200MODへ発行する制御ATコマンドは、原則として、応答待ちを含む処理中の要求を同時に1件だけとする。

Wi-Fi接続機能は、ATコマンドを順番に実行させる調停処理を管理する。
TCPソケットの接続開始、送信、受信、状態取得および切断に必要なDA16200MOD操作も、同じ調停処理を経由する。

#### 上位機能からの利用経路

VPS接続・デバイス認証機能などの上位機能は、DA16200MODへATコマンドを直接発行しない。
Wi-Fi接続機能が提供する、処理に上限を設けたTCP通信の基本操作を利用する。提供する操作と通知は、第17.1節に示す。

TCPソケットの操作も、次に示す識別子、コマンド固有のタイムアウトおよび要求と応答の対応付けを含む、同じモジュール制御規則に従って一件ずつ実行する。

#### 要求ごとに管理する情報

一つのATコマンドの要求から結果確定までを、同じ取引として対応付ける。
少なくとも次の情報を管理する。

- `moduleCommandId`
- `wifiModuleGeneration`
- コマンド種別
- 発行時刻
- コマンド固有のタイムアウト
- 応答待ち状態
- 正常応答／否定応答／タイムアウト／通信異常

ATコマンドに要求識別子が含まれない場合でも、本体側で1要求だけを進行させることで、古い応答を新しい要求へ誤対応付けしない。

### 4.4 非同期イベント

AP切断、IP設定変化、モジュール起動通知その他の非同期イベントはAT Command応答と区別して解析する。

UART受信処理は行単位のAT応答だけを前提とせず、受信リングバッファからフレーム・行境界を復元し、部分受信・複数行連結・非同期通知を処理できる構成とする。

受信解析不能、長さ超過または想定外バイナリを理由として、固定バッファ外へ書き込まない。

### 4.5 `wifiModuleGeneration`

次の場合に`wifiModuleGeneration`を更新する。

- DA16200MODの正常初期化完了
- RESETによる再初期化
- `PWR_WIFI`電源再投入後の再初期化
- モジュール状態を安全に引き継げない通信異常からの復旧

旧generationに属するAT応答、接続結果、DHCP結果、非同期イベントを新generationへ引き継がない。

## 5. Wi-Fi内部状態と管理情報

### 5.1 機能状態

Wi-Fi接続機能は少なくとも次を区別する。

| 状態 | 意味 |
| --- | --- |
| `WIFI_POWER_OFF` | `PWR_WIFI`供給なし |
| `WIFI_INITIALIZING` | 電源・Wake・RESET後のモジュール初期化中 |
| `WIFI_IDLE` | モジュール使用可能、AP未接続 |
| `WIFI_CONNECTING_AP` | AP探索・association・WPA2認証中 |
| `WIFI_WAIT_DHCP` | AP接続済み、DHCP待ち |
| `WIFI_IP_READY` | DHCP完了、IP通信利用可能 |
| `WIFI_DISCONNECTING` | AP切断・通信終了中 |
| `WIFI_SLEEPING` | DA16200MODがSleep mode 2または許可された縮退待機 |
| `WIFI_RECOVERING` | RESET／電源再投入等の復旧中 |
| `WIFI_UNAVAILABLE` | Wi-Fi機能を安全に使用できない |

これらはシステム状態ではない。システム状態はシステム状態管理が管理する。

### 5.2 接続状態とIP状態を分離する

AP接続済みとIP利用可能を同一状態として扱わない。

AP接続後にDHCP失敗した場合は`WIFI_IP_READY`へ遷移しない。

IPアドレス、Gateway、DNSその他のDHCP情報を喪失した場合、802.11リンクが残っている可能性があってもIP利用可能を取り消す。

### 5.3 接続取引情報

接続取引では少なくとも次を管理する。

- `wifiConnectTransactionId`
- `wifiModuleGeneration`
- `wifiCredentialRevision`
- 接続要求元集合
- 現在試行番号
- 接続開始時刻
- 現在phase
- 最終失敗理由
- 自動再試行可否
- 次回再試行時刻

旧設定revisionで進行中の接続結果を、設定変更後の新しい接続へ利用しない。

## 6. Wi-Fi接続設定

### 6.1 正式な設定と保存先

通常運用で保持するWi-Fi設定は1件とする。

正式なWi-Fi設定は、セキュリティ管理の`K_WIFI_STORE`によるAES-256-GCM認証付き暗号化と、永続データ管理による原子的コミットを正常完了し、現在の`wifiCredentialRevision`と一致するRA8M2側設定とする。DA16200MOD内部のNVRAM、直前のAP接続状態または自動再接続状態を正式な設定として使用しない。

DA16200MOD内部へ接続情報を設定する必要がある場合、RA8M2側の正式な設定から当該接続に必要な範囲を設定する。

### 6.2 設定項目

初期製品のWi-Fi設定は次を基本とする。

| 項目 | 基本設計 |
| --- | --- |
| `wifiCredentialRevision` | uint64、セキュリティ管理の単調増加revision。設定保存・factory resetで更新し、wrapして旧値へ戻さない |
| SSID | 1～32 octet |
| Security mode | `WPA2_PERSONAL_AES_CCMP`固定 |
| 認証情報 | WPA2-Personal passphrase |
| Passphrase長 | 8～63 octetを基本 |
| Hidden SSID | 非対応 |
| BSSID固定 | 非対応 |
| IP設定 | DHCP IPv4固定 |
| 固定IP | 非対応 |

64桁16進PSK直接入力、Enterprise認証、WPA/WEP/TKIP、open networkは初期製品の設定値として受け付けない。

`wifiCredentialRevision`はWi-Fi接続の接続世代相関とセキュリティ管理の暗号・rollback防止で同じ値を使用し、別の`wifiConfigRevision`を重複管理しない。次revisionを安全に表現できない場合、revisionを0または小さい値へ巻き戻して設定更新を継続せず、新しいWi-Fi設定変更を利用不可として異常管理および利用者通知へ保守必要状態を提供する。

### 6.3 SSIDの扱い

SSIDは32 octet上限で長さを別管理し、C文字列終端だけに依存しない。

アプリ表示用文字列と無線上のSSID octet列を区別できる構成とし、アプリから受けたSSIDをDA16200MODへ渡す際に無断の文字正規化・切詰め・別文字列への置換を行わない。初期製品で受け付ける文字表現・encodingはE-09の結合評価で成立性を確認して本節へ正式値を反映する**基本設計で定め、評価結果を基に確定する条件**とする。詳細設計だけで利用者入力の受理範囲を変更しない。

SSIDを通常ログ、一般操作者向け状態表示またはVPS通常運用データへ無条件に出力しない。

### 6.4 認証情報

Wi-Fiパスフレーズは秘密情報として扱う。

セキュリティ管理に従い、SSID、security mode、passphraseを含むWi-Fi設定全体をAES-256-GCMで認証付き暗号化し、`K_WIFI_STORE`は他用途鍵と共用しない。Wi-Fi接続機能は設定の意味・長さ・利用条件を所有し、暗号演算・Wrapped Key・nonce生成・state MACはセキュリティ管理、物理保存・原子的更新は永続データ管理が担当する。

状態照会でOWNER端末へ現在SSID・セキュリティ方式を提供できる構成とするが、保存済みパスフレーズを平文読戻しする通常機能は設けない。

### 6.5 rollback・完全性異常

セキュリティ管理が現在の`wifiCredentialRevision`と一致する最新Wi-Fi設定を復号・認証できない場合、古いrevisionの設定へ自動fallbackして過去ネットワークを再有効化しない。

この場合はWi-Fi設定利用不可として扱い、新しいAP接続を開始せず、異常管理・システム状態管理およびOWNER向け状態通知へ設定利用不能を提供する。利用者が新設定を正常登録するか、定義された保守処置を完了するまで古い認証情報を推測利用しない。

## 7. Wi-Fi接続設定の登録・変更

### 7.1 開始条件

Wi-Fi設定の登録・変更は次をすべて満たす場合だけ開始する。

- BLE接続・認証によって認証済みOWNER端末からの管理要求であることを確認できる。
- 所有者・操作端末管理のOWNER登録・権限情報が有効である。
- システム状態管理から管理操作開始可が提供されている。
- システム状態がBLE接続待機状態である。
- アクチュエータが安全状態である。
- 工場初期化、OTAその他の排他管理処理と競合していない。
- 永続データ管理とセキュリティ管理を使用できる。

### 7.2 BLEから受け取る論理設定

BLE接続・認証の`WIFI_SETTING`経路から、完全な論理Wi-Fi設定オブジェクトと非0 `requestId`を受け取る。論理設定の意味・値域は本書で定め、BLE通信データ形式、fragment、再構成、10秒timeout、transport取消しおよび接続・session相関はBLE接続・認証を正式な管理元とする。スマートフォンアプリはBLE接続・認証の契約の送信側であり、上限値を共同所有しない。

論理Wi-Fi設定V1は次の情報からなる。

| 項目 | 型・長さ | 意味 |
| --- | --- | --- |
| `formatVersion` | uint8、1固定 | 論理設定形式 |
| `securityMode` | uint8 | `WPA2_PERSONAL_AES_CCMP`固定 |
| `ssidLength` | uint8、1～32 | SSIDのoctet長 |
| `passphraseLength` | uint8、8～63 | passphraseのoctet長 |
| `ssid` | 1～32 byte | C文字列終端を含まないSSID octet列 |
| `passphrase` | 8～63 byte | C文字列終端を含まないpassphrase octet列 |

論理データ全長は`4 + ssidLength + passphraseLength`で13～99 byteとなる。`wifiCredentialRevision`は完全受信・検証後にセキュリティ管理から採番するため、アプリから受信する論理データへ含めない。

BLE接続・認証は8 byte fragment header、1 fragment最大32 byte data、最大4 fragment、固定99 byte再構成上限、同時1件、先頭正常fragmentから10秒の契約で完全オブジェクトだけを本機能へ引き渡す。本書は部分fragment、別のセッション／別`requestId`の結合結果、timeout／取消し済みbufferをWi-Fi設定候補として受け付けない。

BLE接続・認証からの引渡し後は、受信した完全オブジェクトを固定99 byte以下の秘密用一時領域で扱い、検証・セキュリティ管理の暗号化要求・永続データ管理への引渡しの完了、失敗または電源状態変更時に不要な平文copyをゼロで上書きして消去する。

transport取消しはBLE接続・認証が完全オブジェクトを本機能へ引き渡す前だけ成立する。本機能が完全オブジェクトを受け付けた後は原子的保存との競合を避けるため取消しを成立させず、BLE接続・認証へ`TOO_LATE`または現在結果を返す。GATT Writeまたは全fragment受信だけを保存成功とせず、同じ`requestId`へ受付結果と最終処理結果を分離して返す。

### 7.3 設定検証

永続保存前に少なくとも次を確認する。

- `formatVersion=1`である
- 論理データ全長が`4 + ssidLength + passphraseLength`と一致し、13～99 byteである
- SSID必須・長さ1～32 octet
- Security modeがWPA2-Personal/AES-CCMP
- passphraseが初期製品の長さ・文字条件を満たす
- Hidden SSID要求がない
- 固定IP等の非対応項目が指定されていない
- 現在のOWNER権限・管理取引が有効
- 受信データ長および各offsetが許容範囲内

範囲外SSIDまたはpassphraseを切り詰め、文字を置換し、別の有効設定へ暗黙変換して保存しない。

### 7.4 保存と正式化

Wi-Fi設定変更は次の順序を基本とする。

1. 新設定を検証する。
2. セキュリティ管理から現在値より大きい新しい`wifiCredentialRevision`を取得し、同revisionを設定候補へ対応付ける。
3. セキュリティ管理が新設定全体を`K_WIFI_STORE`でAES-256-GCM認証付き暗号化し、同revisionに対応するnonce・認証metadataを生成する。
4. 永続データ管理へ認証付き暗号blobと必要なmetadataの原子的コミットを要求する。
5. 永続データ管理の正常コミットとセキュリティ管理のrevision・認証metadata整合を確認した時点で新設定を現在の正式なWi-Fi設定とする。
6. DA16200MODの旧接続・自動再接続を停止する。
7. 新設定で接続確認を実行する。
8. 接続確認結果を、BLE接続・認証を介して同じ`requestId`の最終結果としてOWNER端末へ通知する。

旧設定を暗黙の予備プロファイルとして保持しない。新設定の永続コミットまたはセキュリティ管理の認証metadata確定に失敗した場合は新設定を正式な設定として採用せず、旧正常設定を維持する。新revisionを小さい値へ戻して再利用しない。

### 7.5 接続確認

設定変更後の明示的な接続確認は、新設定を使用する1回の接続試行とし、最大30秒で成功または失敗を確定する。

結果は少なくとも次を区別する。

- `TEST_SUCCESS`
- `AP_NOT_FOUND`
- `AUTH_FAILED`
- `DHCP_FAILED`
- `MODULE_ERROR`
- `TIMEOUT`

接続確認失敗だけを理由として正常コミット済み設定を破損扱いにせず、旧設定へ自動ロールバックしない。

### 7.6 設定変更中の電源断

永続コミット前の電源断では旧正常設定を正式な設定として使用する。

永続コミット成功後の接続確認中に電源断した場合、新設定を正式な設定として保持し、次回起動後に「設定保存済み・接続確認未完了または失敗」と識別可能とする。

セキュリティ管理の最新revisionと認証付き暗号blobが不整合な場合は6.5節に従い、古い設定へ自動fallbackしない。

## 8. Wi-Fi通信部初期化

### 8.1 起動時方針

起動時はDA16200MODを使用可能な既知状態へ初期化するが、起動したことだけを理由にAP接続を開始しない。

起動後の初回VPS通信等をどの時点で要求するかはVPS接続・各管理機能が決定する。

### 8.2 初期化シーケンス

基本シーケンスは次とする。

1. 電源・省電力管理へ`PWR_WIFI`通常電力を要求する。
2. 電源供給・電気安全上の利用可能を確認する。
3. 必要に応じて`RESETn`を使用してDA16200MODを既知状態へ移行する。
4. UART 230400/8N1/RTS-CTSを有効化する。
5. DA16200MODの起動完了・AT応答を確認する。
6. モジュール識別・FW情報を取得し、期待するAT機能を使用可能か確認する。
7. Station modeを基本動作とし、SoftAP/WPS/不要待受け機能を無効化する。
8. モジュール側の意図しない自動AP接続・自動再接続を禁止する。
9. 永続データ管理/セキュリティ管理から現在の正式なWi-Fi設定の存在、`wifiCredentialRevision`、復号・認証結果および利用可否を確認する。最新設定の認証に失敗した場合は古い設定へfallbackしない。
10. AP未接続`WIFI_IDLE`として初期化完了を通知する。Wi-Fi設定利用不能は別状態情報として保持し、AP接続要求を拒否できるようにする。
11. 使用要求がなければ電源・省電力管理の方針に従ってSleepへ移行可能とする。

### 8.3 初期化timeout

DA16200MODへの電源・RESET後からAT通信正常確認までを5秒以内に正常完了または失敗として終了する。

5秒以内に正常性を確認できない場合、Wi-Fi機能を使用可能とは扱わず異常管理へWi-Fiモジュール初期化異常候補を通知する。

### 8.4 モジュールNVRAM

DA16200MOD内部に過去SSID、パスフレーズ、自動接続設定その他のNVRAM情報が残り得る場合でも、それをRA8M2側の正式な設定より優先しない。

初期化時に、少なくとも意図しない自動接続を禁止できる状態を確認する。

モジュールFWの制約で認証情報がNVRAMへ保存される場合は、設定変更・失効・工場初期化時にRA8M2側の正式な設定と矛盾しないよう明示的な上書きまたは消去を行う。

## 9. アクセスポイント接続

### 9.1 接続開始条件

次をすべて満たした場合だけAP接続を開始する。

- DA16200MODが使用可能
- 電源・省電力管理からWi-Fi通常電力利用可
- 現在`wifiCredentialRevision`に対応する正常コミット・認証済みWi-Fi設定1件が存在
- Wi-Fi設定の形式・認証情報利用可否を確認済み
- システム状態・優先処理からWi-Fi接続禁止されていない
- 有効な`wifiUseRequestId`が少なくとも1件存在
- 低消費電力移行・終了処理・工場初期化の中断要求が成立していない

### 9.2 接続対象

設定されたSSIDだけを接続対象とする。

設定SSIDが見つからない場合、別のopen AP、同名でないAP、過去NVRAM上のAPへ暗黙接続しない。

BSSID固定は行わないため、同一SSIDを提供する複数BSSIDが存在する場合の選択はDA16200MODの通常Station動作へ委譲する。ただし接続後のセキュリティ方式がWPA2-Personal/AES-CCMP条件を満たさない場合は利用しない。

### 9.3 AP接続timeout

AP探索・association・WPA2認証を含むAP接続phaseは15秒以内に成功または失敗として終了する。

AP接続timeoutまたは明確な認証失敗を、接続済み状態として扱わない。

### 9.4 セキュリティ方式

初期製品ではWPA2-PersonalおよびAES-CCMPを使用する。

open network、WEP、WPA-Personal、TKIPへのダウングレードを行わない。

DA16200MODがWPA3等の追加機能を持っていても、初期製品のWi-Fi設定仕様を暗黙に拡張しない。

## 10. DHCP・IP通信利用可能化

### 10.1 DHCP

AP接続成功後、DA16200MODのTCP/IP stackでDHCP clientを実行してIPv4設定を取得する。

初期製品では固定IPv4設定へfallbackしない。

### 10.2 DHCP確認項目

IP利用可能化に必要な範囲で、少なくとも次の取得成功を確認する。

- IPv4 address
- subnet情報
- default gateway
- DNS server情報

上位VPS通信でホスト名解決を必要とする場合、DNS利用可能性を含めてIP通信利用条件とする。

### 10.3 DHCP timeout

DHCP phaseは10秒以内に正常完了または失敗として終了する。

取得失敗時は以前のIPv4設定を再利用しない。

### 10.4 `WIFI_IP_READY`

AP接続およびDHCPの両方が成功し、現在`wifiModuleGeneration`、`wifiCredentialRevision`および接続取引に対応するIP設定であることを確認した場合だけ`WIFI_IP_READY`とする。

IP利用可能結果として上位機能へ少なくとも次を提供する。

- `wifiUseRequestId`
- `wifiConnectTransactionId`
- `wifiModuleGeneration`
- `wifiCredentialRevision`
- `IP_READY`
- 接続成立時刻

具体的なIPアドレス等を一般操作者向け表示へ無条件に公開しない。

## 11. 接続利用要求と切断

### 11.1 利用要求方式

VPS接続、時刻管理その他の管理・保守機能は、Wi-Fi接続機能へ利用要求を出し、`WIFI_IP_READY`を取得してからWi-Fi経路を使用する。

利用要求ごとに`wifiUseRequestId`、要求元、用途、取消状態を管理する。

### 11.2 複数要求元

複数の上位処理が同一Wi-Fi接続を必要とする場合、一つのAP/IP接続を共有できる。

Wi-Fi接続機能はactive requester集合を管理し、一つでも使用要求が残る間は、低消費電力・終了・異常等の優先要求がない限り接続を維持する。

要求元異常による解放漏れを診断可能とする。

### 11.3 切断条件

次の場合は切断または安全な中断を開始する。

- 全`wifiUseRequestId`が解放された
- 電源・省電力管理から低消費電力移行要求を受けた
- 起動・終了・再起動管理から通常終了・再起動準備を受けた
- 異常管理からWi-Fi利用禁止・復旧要求を受けた
- 工場初期化処理を開始した
- Wi-Fi設定変更で旧設定接続を終了する必要がある

### 11.4 切断処理

上位VPS通信等へIP経路終了予告を通知し、安全な通信終了・中断結果を確認してからAP切断する。

ただし安全処理、電源保護または異常処置が優先される場合、上位通信の通常完了を無期限に待たない。

AP切断処理timeoutを5秒とする。

切断完了後は旧IP設定を無効化し、未完了VPS処理を正常完了扱いにしない。

---

## 12. 接続監視・切断検出

### 12.1 監視対象

少なくとも次を監視する。

- DA16200MODからのAP切断通知
- AP接続状態照会結果
- DHCP/IP設定喪失通知
- UART/AT通信正常性
- `wifiModuleGeneration`不整合
- 予期しないDA16200MOD再起動
- 接続中のモジュール状態取得不能

### 12.2 不明状態

現在AP接続状態またはIP設定を正常に確認できない場合、以前の`WIFI_IP_READY`を維持しない。

不明状態を「一時的に情報が取れないだけなので接続済み」と楽観的に扱わない。

### 12.3 切断通知

AP切断またはIP設定喪失を検出した場合、次を行う。

1. `WIFI_IP_READY`を直ちに取消す。
2. 上位VPS通信・管理機能へIP経路喪失を通知する。
3. 切断前の未完了処理を正常完了扱いにしないよう要求する。
4. 切断理由を分類する。
5. 一時障害なら13章の自動再接続可否を判断する。
6. モジュール異常なら14章へ移行する。

### 12.4 切断理由

少なくとも次を区別する。

- 正常要求による切断
- AP_NOT_FOUND
- AP_LINK_LOST
- AUTH_FAILED
- DHCP_FAILED
- IP_CONFIG_LOST
- MODULE_COMM_ERROR
- MODULE_RESET_DETECTED
- POWER_OR_SLEEP_TRANSITION
- CONFIG_CHANGED
- SYSTEM_SHUTDOWN

---

## 13. 自動再接続

### 13.1 自動再接続対象

自動再接続を許可する主な一時障害は次とする。

- 一時的なAP未検出
- 電波断等のAP_LINK_LOST
- 一時的なDHCP失敗
- 接続確立済み後の一時的IP喪失

### 13.2 自動再接続しない条件

次は同じ条件のまま自動再接続を繰り返さない。

- Wi-Fi設定形式不正
- 非対応セキュリティ方式
- 明確なWPA2認証失敗
- 認証情報を安全に取得できない
- 最新`wifiCredentialRevision`の復号・認証に失敗している
- 工場初期化・設定削除済み
- `PWR_WIFI`利用禁止
- 異常管理による利用禁止
- 低消費電力移行・終了・再起動中

認証失敗が電波要因等と区別不能な場合は診断情報を保持し、無期限再試行へ移行しない。

### 13.3 試行回数とバックオフ

一つの接続取引では、初回接続試行に加えて自動再試行を最大3回まで許可する。

再試行待ちは次を基本値とする。

- 第1再試行：1秒
- 第2再試行：2秒
- 第3再試行：4秒

したがって、一つの接続取引の総試行回数上限は初回1回＋自動再試行3回の4回とする。

第3再試行が失敗した場合は同じ接続取引を失敗として終了し、同一要求のまま自動再試行を継続しない。

### 13.4 接続時間上限

1回の接続試行は最大30秒とする。

最大4試行と1秒・2秒・4秒の待ちを含む1接続取引の理論上限は127秒となるため、実装では130秒以内に必ず成功または失敗へ収束させる。

この130秒は、DA16200MODが使用可能であり接続開始条件が成立した後、当該`wifiConnectTransactionId`の**最初のAP接続試行を開始した時点**を起点として連続計時する。接続試行失敗、backoffまたは同一接続取引内の再試行によってtimerを停止・再開始しない。

DA16200MODの電源投入・RESET後初期化またはSleepからのWakeに要する時間は、この130秒へ含めず、第8.3節および第15.4節の5秒上限を使用する。既に現在世代の`WIFI_IP_READY`が成立している場合は、新しいWi-Fi接続取引を開始せず、上位機能は現在の経路を使用できる。

### 13.5 再接続後

再接続後は新しい接続取引結果として扱う。

切断前のVPS通信、設定取得、ログ送信、OTA取得、HTTP応答待ちその他を正常完了として復元しない。

上位機能が再開可能な処理かどうかは各上位機能が自身の取引識別子・データ状態で判断する。

---

## 14. モジュール異常・再初期化・電源再投入

### 14.1 AP障害とモジュール障害を分ける

AP接続失敗とDA16200MOD自体の異常を同一再試行として扱わない。

次はモジュール異常候補とする。

- AT Command無応答
- UART framing/overflow等により通信継続不能
- 起動完了通知不成立
- 予期しないモジュールreset
- 状態取得不能または矛盾
- Sleep移行不能
- Wake後5秒以内にAT通信復帰不能
- RESET後再初期化不能

### 14.2 復旧段階

異常管理が自動復旧を許可した場合、次を基本順序とする。

1. 新しいWi-Fi利用開始を禁止する。
2. `WIFI_IP_READY`を取消し、上位へ経路喪失を通知する。
3. 未完了AT取引・受信解析状態を破棄する。
4. `RESETn`によるモジュールresetを実行する。
5. 8章の初期化を実行する。
6. 正常復旧しない場合、電源・省電力管理へ`PWR_WIFI`電源再投入を要求する。
7. 電源再投入後に8章の初期化を実行する。
8. 復旧結果を異常管理へ返す。

### 14.3 復旧回数

モジュール異常に対する自動復旧回数は異常管理の管理する上限を使用し、Wi-Fi接続機能独自に無期限RESET・電源cycleしない。

AP接続の自動再試行最大3回と、モジュール異常の自動復旧回数を別カウンタとして管理する。

### 14.4 復旧後

復旧成功後も以前のAP接続、IP設定、UART command、VPS通信を復元しない。

現在有効なRA8M2側の正式なWi-Fi設定と新しい`wifiModuleGeneration`から接続を新規確立する。

## 15. 低消費電力・電源管理との連携

### 15.1 `PWR_WIFI`責任

`PWR_WIFI`の論理電力状態、ロードスイッチ、電源遮断・再投入は電源・省電力管理が管理する。

Wi-Fi接続機能は必要な機能状態を電源・省電力管理へ要求し、実電力状態が利用可能と確認できてからDA16200MODを操作する。

### 15.2 通常未使用時

active requesterが存在しない場合、AP接続を維持する必要はない。

AP・VPS通信を終了し、DA16200MODをSleep mode 2へ移行できる。

### 15.3 Sleep mode 2

通常の低消費電力方式はSleep mode 2とし、Wi-Fiネットワーク接続状態の保持を目的とするDPM常時接続方式を初期製品の基本方式としない。

Sleep前に次を確認する。

- 上位通信が正常終了または安全中断済み
- AP接続を終了済み
- 自動再接続禁止
- 未完了AT Commandなし
- モジュール実状態を確認可能

### 15.4 Wake

Wi-Fi利用要求が発生し、電源・省電力管理が`PWR_WIFI`復帰を許可した場合、RA8M2から`RTC_WAKE_UP`へ1 ms以上のWakeパルスを与える。

Wake後5秒以内にAT通信正常性を確認できた場合`WIFI_IDLE`へ戻す。

正常性を確認できない場合はWake失敗として異常管理へ通知し、14章の復旧へ移行できる。

### 15.5 システム低消費電力状態

電源・省電力管理で定めるシステム低消費電力状態中は、Wi-Fi AP接続、VPS通信、ログ送信、設定取得、OTA確認等を行わない。

定期VPS確認の時刻到来だけを理由にWi-FiをWakeしない。

低消費電力状態からBLE接続要求で通常復帰しても、それだけを理由にWi-Fiを復帰させない。復帰後に実際のWi-Fi利用要求が発生した場合だけWakeする。

### 15.6 Sleep失敗時の縮退

電源・省電力管理の条件に従い、Wi-Fi/VPS通信を安全に終了済みで、モジュール実状態が既知、自動接続禁止、電源・安全・復帰能力を維持できる場合に限り、覚醒通電待機の縮退を許可できる。

この状態をWi-Fi利用可能とは扱わない。

## 16. 工場出荷状態への初期化との連携

### 16.1 所有者・操作端末管理からのPREPARE

所有者・操作端末管理の工場初期化第1段階で、Wi-Fi接続機能は少なくとも次を確認してPREPARE結果を返す。

- active Wi-Fi/VPS通信を安全中断可能
- RA8M2側Wi-Fi設定を消去・利用不能化可能
- セキュリティ管理/永続データ管理と連携して旧`wifiCredentialRevision`を再利用不能とし、`K_WIFI_STORE`をrotation可能
- DA16200MOD内部の利用者SSID・認証情報・自動接続状態を消去または無効化可能

PREPARE段階では不可逆な利用者Wi-Fi設定消去、鍵rotationまたは古い認証情報利用禁止確定を開始しない。

### 16.2 `RESET_PENDING`後の消去

所有者・操作端末管理の`RESET_PENDING`正常コミット後、次を行う。

1. active Wi-Fi利用要求を取消し、新規利用を禁止する。
2. AP/VPS通信を終了または安全中断する。
3. セキュリティ管理へ旧Wi-Fi credential revisionの使用禁止、新しい`K_WIFI_STORE`候補・nonce prefix生成および新security metadataの原子的確定を要求する。
4. セキュリティ管理/永続データ管理の新security metadata確定後、旧Wi-Fi設定の認証付き暗号blobを削除対象とし、旧Wrapped Keyを廃棄する。
5. DA16200MOD内部のSSID、credential、自動接続情報を消去または利用不能化する。
6. Wi-Fi設定なしとして接続開始を禁止し、古い`wifiCredentialRevision`または残存NVRAM情報からAP接続しない。
7. 所有者・操作端末管理へ完了・失敗を返す。

RESET_PENDING後に電源断・リセットまたは途中失敗が発生しても、古い認証情報を通常利用へ戻さない。所有者・操作端末管理/永続データ管理/セキュリティ管理の工場初期化継続情報に従い処理を再開する。

### 16.3 保持対象

工場初期化で、DA16200MOD製造情報、製品固有Device ID、VPSデバイス認証情報、`SecurityGen`、`highestCommittedGeneration`その他のWi-Fi利用者設定ではない製品固有・巻戻し防止情報を本機能の判断だけで削除または巻き戻さない。

### 16.4 所有者再登録

同一所有者による所有者再登録だけを理由として、正常なWi-Fi設定を削除しない。

新OWNER端末は、再認証後にWi-Fi設定状態を確認できるが、保存済みパスフレーズを平文取得できない。

## 17. VPS接続・他管理機能とのインターフェース

### 17.1 VPS接続への提供

#### 接続状態と識別情報

Wi-Fi接続機能は、VPS接続・デバイス認証機能へ少なくとも次を提供する。

- `IP_READY`／利用不可
- `wifiUseRequestId`
- `wifiConnectTransactionId`
- `wifiModuleGeneration`
- `wifiCredentialRevision`
- 経路喪失理由
- 再接続成功・失敗

#### TCP通信の基本操作と通知

さらに、VPS接続・デバイス認証機能がVPS向けTCP接続を構成するために、少なくとも次の論理操作と通知を提供する。

| 用途 | 提供する操作・通知 |
| --- | --- |
| 接続開始 | `openTcp(host, port)` |
| 送信 | `send(bytes, length)` |
| 受信 | 受信したバイト列の通知 |
| 送信結果の確認 | 送信完了・失敗の通知 |
| 状態取得 | TCPソケットの状態取得 |
| 切断 | `closeTcp()` |
| 異常・切断の通知 | DNS失敗、TCPリセット、通信相手からの切断、および通信経路の異常通知 |

#### モジュール操作の窓口

利用経路は、VPS接続・デバイス認証機能からWi-Fi接続機能のTCP通信操作へ要求し、同機能のATコマンド調停処理を通じてDA16200MODを操作する経路に統一する。

上記の操作はすべて、第4.3節で定める、応答待ちを含む処理中のATコマンドを原則1件だけとする調停処理を経由する。
VPS接続・デバイス認証機能がDA16200MODを直接制御する第二の経路は設けない。

### 17.2 VPS接続から受け取る情報

- Wi-Fi利用要求
- Wi-Fi利用終了
- 低消費電力・終了に向けた通信安全中断結果
- VPS通信継続中／終了可能
- VPS接続先host/portを伴うTCP通信の基本操作要求

Wi-Fi接続機能はHTTPS要求・応答の成否をAP接続成功と混同しない。VPS接続・デバイス認証が管理するVPS向けTCP接続・セッションやTLS/HTTPS状態をWi-Fi接続が代理管理しない。

### 17.3 TCP/TLS処理主体

VPS接続・デバイス認証およびセキュリティ管理で確定した責任分界を使用し、RA8M2側のDA16200MOD制御経路はWi-Fi接続へ一元化する。

- DA16200MOD：モジュール内でのWi-Fi、IP、DNS、TCPクライアントスタック／ソケットの通信処理の実行。
- Wi-Fi接続：RA8M2側のUART/ATによる制御、同時に進行させるモジュール要求を1件に制限する調停、`moduleCommandId`／`wifiModuleGeneration`の管理。TCP通信の基本操作を提供する唯一の機能。
- VPS接続・デバイス認証：Wi-Fi接続が提供する基本通信処理を使用した、VPS向けTCP接続・セッションの管理。RA8M2上のTLS 1.3、相互TLS、証明書検証およびHTTPS処理。
- デバイス秘密鍵：RA8M2のRSIP Wrapped Keyとして保持し、DA16200MODへ保存しない

本書はこの前提でUART帯域・buffer・Sleep／reset／再接続を設計する。DA16200MODへTLS終端やデバイス秘密鍵を移すことで資源問題を回避せず、VPS接続・デバイス認証からDA16200MODへ直接AT Commandを発行する経路も追加しない。UART帯域やRAMが成立しない場合はWi-Fi接続/VPS接続・デバイス認証/セキュリティ管理へフィードバックして基本設計を見直す。

### 17.4 設定・ログ・OTA・時刻

設定管理、ログ・診断、OTA、時刻管理等は直接DA16200MODを操作せず、原則としてVPS接続・デバイス認証を経由してWi-Fi利用要求を行う。

Wi-Fi接続機能は上位用途を識別できる情報を保持してよいが、設定パッケージやOTA内容を解釈しない。

## 18. セキュリティ・不要サービス制限

### 18.1 Station専用

通常運用ではDA16200MODをStationとして使用する。

SoftAP、WPS、Wi-Fi Direct、ローカル設定Webサーバー等を有効化しない。

### 18.2 外部待受け禁止

同一LANまたはインターネット側から本体へ直接、走行・砲塔・停止・設定適用・OTA開始その他の通常運用要求を受け付ける待受けサービスを提供しない。

Wi-Fi/TCP-IP stackの未使用server機能・debug serviceを通常製品で有効化しない。

### 18.3 Wi-Fi認証情報保護

SSID、passphrase、security modeを含むWi-Fi設定全体はセキュリティ管理の認証付き暗号blobとして永続保存し、パスフレーズを次へ平文出力しない。

- 通常ログ
- 診断ダンプ
- 状態表示
- BLEアドバタイズ
- VPS通常送信データ
- エラー文字列

DA16200MODへ認証情報を渡す必要がある場合、RA8M2側で必要期間を限定し、固定された秘密用一時バッファを使用し、AT送信完了・取消し・timeout・エラー時に不要な平文コピーを明示的に破棄する。DA16200MOD側へ残るcredentialは8.4節、設定変更および16章の工場初期化条件に従って管理する。

### 18.4 入力検証

BLE経由Wi-Fi設定、DA16200MOD AT応答、非同期イベントおよびIP情報は、使用前に長さ・形式・値域・現在状態を確認する。

外部由来文字列をformat stringとして使用しない。

認証済みOWNER端末には、管理に必要な範囲で設定有無、SSID表示名、接続確認結果を提供できる。

少なくとも次を提供する。

- DA16200MOD初期化成功・失敗
- Wake／Sleep／RESET／電源再投入

- DHCP成功・失敗

- 正常切断・異常切断

- UART/AT通信異常
- モジュール復旧開始・結果
- 工場初期化Wi-Fi消去・key rotation結果

### 19.3 エラー情報の粒度

OWNERアプリへは`AP_NOT_FOUND`、`AUTH_FAILED`、`DHCP_FAILED`、`CONFIG_INVALID`等の対処可能な分類を提供できる。

DA16200MOD内部AT応答全文、credential、ネットワーク内部構成、攻撃に利用可能な不要情報を一般利用者向け表示へ直接出さない。

## 20. 処理時間の配分・資源・並行処理方針

### 20.1 基本時間値

| 項目 | 基本設計値 |
| --- | ---: |
| DA16200MOD初期化・AT正常確認 | 5秒以内 |
| SleepからWake後AT正常確認 | 5秒以内 |
| AP接続・WPA2認証 | 15秒以内 |
| DHCP | 10秒以内 |
| 1接続試行全体 | 30秒以内 |
| 自動再試行 | 初回接続後、最大3回 |
| 再試行待ち | 1秒、2秒、4秒 |
| 接続取引全体 | 130秒以内（最初のAP接続試行開始から） |
| AP正常切断 | 5秒以内 |
| Wi-Fi設定接続確認 | 1試行・30秒以内 |
| 一般AT短時間要求 | 原則2秒、長時間Commandは個別上限 |

DA16200MODの初期化・復帰（Wake）と、Wi-Fi接続取引は、別々の処理区間として計時する。管理・保守要求が未使用状態のWi-Fiを必要とする場合、VPS接続・デバイス認証などの上位機能から見たWi-Fi側の待ち時間は、次の二つの区間を合計する。

| 順序 | 処理区間 | 上限 |
| --- | --- | --- |
| 1 | 必要な初期化またはWake | 最大5秒 |
| 2 | その後に開始するWi-Fi接続取引 | 最大130秒 |

VPS接続・デバイス認証のVPS接続確立130秒は、さらに別の取引として扱う。VPS接続側の計時起点と時間の合計方法は、VPS接続・デバイス認証基本設計およびインターフェース・通信基本設計に従う。

これらは利用者・上位機能から見た接続・復旧・中断挙動を決める**基本設計で管理し、評価結果を基に確定する値**である。DA16200MOD、実AP、電波環境で評価し、正式値または評価済み範囲を本書へ反映する。成立しない場合は詳細設計だけで無制限延長せず、本基本設計の時間配分を見直す。

### 20.2 UART資源

UART受信はDMA/DTCまたは割込みを用いた固定リングバッファ方式を基本とする。

初期評価値として次を置く。

- UART RX ring：4 KiB
- UART TX control buffer：1 KiB以上の固定上限
- AT line/parser buffer：512 byte上限
- module event queue：16件上限

VPS接続・デバイス認証でTLS/HTTPS主体がRA8M2へ確定済みであるため、これらの有限資源はDA16200MOD TCP transportとRA8M2 TLS/HTTPS/OTA streamingを同時に使用した条件でE-02、E-11、E-12を評価する。内部bufferの具体値は実装資源として調整可能だが、評価で必要容量を確定した後は処理不能・安全処理阻害・無制限キュー化を避ける上限として詳細設計へ引き渡す。容量変更によって本書の外部時間上限や安全優先を満たせなくなる場合は本書を見直す。

### 20.3 大容量データ

OTAファームウェア等の大容量データをRA8M2 RAMへ全量保持しない。

VPS接続・デバイス認証/OTA更新で定めるchunk/stream方式で有限バッファを再利用する。

### 20.4 排他

DA16200MOD制御AT Commandは原則1 in-flightとする。

複数上位Wi-Fi利用要求は接続要求として統合可能だが、RESET、Sleep、設定変更、工場初期化と通常接続Commandを同時進行させない。

優先順位は概ね次とする。

1. 電気安全・終了・強制復旧等の上位優先要求
2. 工場初期化・設定変更による接続停止
3. モジュール異常復旧
4. AP切断・IP喪失処理
5. 通常接続・再接続
6. 状態照会・診断

## 24. 他文書へのフィードバック

### 24.1 F-01 BLE接続・認証／スマートフォンアプリ【XR-003反映済み】

Wi-Fi設定はSSID最大32 octet＋passphrase最大63 octet等によりBLE接続・認証の単一64 byteメッセージに収まらないため、論理設定V1を最大99 byteとする。

BLE接続・認証をBLE通信データ形式／分割データの再構成の正式な管理元として、8 byte fragment header、最大32 byte data、最大4 fragment、固定99 byte再構成上限、同時1件、先頭正常fragmentから10秒、同一`requestId`、正順・連続offset、exact retry、transport取消し、session／接続世代変更時zeroize、およびcomplete-only handoffを確定済みである。

将来のスマートフォンアプリ基本設計はBLE接続・認証の契約の送信側として、fragment 0からの正順送信、再送時の同一data＋新`commandSeq`、取消しおよび受付／最終結果の分離を反映する。本書は部分設定を候補化・永続化しない。

### 24.2 F-02 VPS接続・デバイス認証／セキュリティ【反映済み】

VPS接続・デバイス認証/セキュリティ管理で、TLS/HTTPSはRA8M2、DA16200MODはWi-Fi/IP/DNS/TCP transportと確定済みである。本書17.3節、20章、23章へ反映した。

XR-018の責任分界として、DA16200MODに対するRA8M2からの制御とTCP通信の基本操作はWi-Fi接続へ一元化し、VPS接続・デバイス認証はWi-Fi接続のlogical 通信APIだけを使用する。VPS接続・デバイス認証からDA16200MODへ直接AT Commandを発行しない。

XR-019の時間契約として、Wi-Fi接続取引130秒は最初のAP接続試行開始から計時し、初期化/Wake最大5秒とは別phaseとする。VPS接続・デバイス認証はこのWi-Fi側時間を自身のVPS接続確立130秒と混同せず、要求元からの合成上限はVPS接続・デバイス認証/インターフェース・通信基本設計の契約に従う。

RA8M2のデバイス秘密鍵はRSIP Wrapped Keyとして保護し、DA16200MODへ保存しない。UART帯域・RAM・OTA streamingが成立しない場合はTLS主体を暗黙変更せずWi-Fi接続/VPS接続・デバイス認証/セキュリティ管理を見直す。

### 24.3 F-03 電源・省電力管理

電源・省電力管理で定めた`PWR_WIFI`と整合し、本書はSleep mode 2、外部Wake 1 ms以上、Wake後5秒正常確認を採用する。

評価でSleep mode 2が成立しない場合は電源・省電力管理の縮退条件と本書を同時に見直す。

### 24.4 F-04 所有者・操作端末管理／永続データ／セキュリティ

所有者・操作端末管理の工場初期化PREPARE/RESET_PENDING後に、セキュリティ管理の`K_WIFI_STORE` rotation・旧revision利用禁止、永続データ管理のWi-Fi設定blob処理、DA16200内部credential・auto-connect情報の消去を実行し、完了結果を所有者・操作端末管理へ返す契約を反映する。

所有者再登録だけではWi-Fi設定を削除しない。

### 24.5 F-05 異常管理

Wi-Fi接続の一時AP障害、認証失敗、DHCP失敗、Wi-Fi設定認証失敗、モジュール無応答、RESET失敗、電源再投入失敗、Sleep/Wake失敗を区別して異常管理へ提供する。

AP自動再試行最大3回はWi-Fi機能内の接続policy、モジュール異常の自動復旧回数は異常管理で定める事項として重複させない。

### 24.6 F-06 ログ・状態表示

本書19章で定める状態・事象に関する情報を受け取り、具体表示とログ形式を定める。SSID、credential、内部IP等を一般表示・通常ログへ不要に出力しない。

- DA16200MOD内部NVRAMの内容を正式な設定として扱わず、RA8M2側のセキュリティ管理の認証付き暗号＋永続データ管理の正常コミット済み設定を正式な設定とした。
- `wifiConfigRevision`を重複所有せず、セキュリティ管理で確定したuint64 `wifiCredentialRevision`へ統一し、旧revisionへの自動fallbackを禁止した。
- 起動時の自動AP接続を禁止し、利用要求時だけ接続する方式とした。
- AP接続、DHCP、VPS認証済み通信の状態を分離した。
- 接続状態不明時に以前のIP_READYを維持しない方式とした。
- 自動再接続を一時障害だけに限定し、credential不正・Wi-Fi設定認証失敗を無期限retryしない方式とした。
- D-03に合わせ、初期化/Wake最大5秒とWi-Fi接続取引を別phaseとし、最初のAP接続試行開始から初回＋最大3回再試行、1秒→2秒→4秒backoffを含む130秒を再開始せずに管理する構成へ統一した。
- AP再接続回数とモジュール異常復旧回数の所有者を分離した。
- 電源・省電力管理の低消費電力方針と整合し、Wi-Fiを通常復帰だけでWakeしない方式とした。
- 工場初期化でRA8M2設定、セキュリティ管理のWi-Fi key/revision、DA16200内部残存credentialを一体で無効化し、RESET_PENDING後に旧設定へ戻さない方式とした。
- Wi-Fi設定変更は認証付き暗号化・永続コミット後に正式化し、接続確認失敗で破損扱い・自動rollbackしない方式とした。
- SoftAP/WPS/汎用待受けserviceを無効化し、LAN側から直接アクチュエータ操作できない責任分界を維持した。
- VPS接続・デバイス認証/セキュリティ管理で確定した「DA16200MODはTCP transport、TLS 1.3/HTTPSはRA8M2」を反映し、TLS主体を未決定事項から除外した。
- XR-018の担当範囲に従い、RA8M2からのDA16200MOD制御とTCPソケットの基本操作を、Wi-Fi接続側のATコマンド調停処理へ集約した。この調停処理は、同時に実行するATコマンドを1件に制限する。VPS接続・デバイス認証はその機能を利用し、VPS向けTCP接続・セッションとTLS/HTTPSを管理する構成へ統一した。
- `WIFI_SETTING`の論理形式を13～99 byteとして確定し、BLE接続・認証を通信データ形式／分割データの再構成の正式な管理元として8 byte header・最大32 byte data・最大4 fragment・10秒・同時1件・complete-only handoffへ整合した。アプリはBLE接続・認証の契約の送信側とし、共同所有表現を解消した。
- UART資源を固定上限とし、大容量OTAを全量RAM保持しない方針とした。
- SSID/passphraseの最終文字表現、時間値、資源値等で評価結果が製品挙動を決めるものは、基本設計で管理し、評価結果を基に確定する値として本書へ戻すことを明確化した。

## 1. 本書の目的

### 1.1 目的

本書の目的は、公開用システム要求仕様「20. セキュリティ管理」を実現するため、Tank_Robot本体のセキュリティ論理機能が管理する暗号学的処理、秘密情報、信頼情報および関連機能との契約を、詳細設計へ展開可能な粒度まで具体化することである。

### 1.2 対象範囲

本書は、Tank_Robot本体の論理機能「セキュリティ」が管理する、暗号サービス、暗号用途乱数、長期秘密情報、初回所有者登録用登録秘密情報、一般端末登録チケット認証、所有者再登録認証、鍵・証明書・信頼情報、設定HMAC、Wi-Fi認証情報保護、ファームウェア検証、SecurityGen、critical metadata認証、秘密情報を含む永続データ保護、セキュリティ事象および関連機能との責任分界を具体化する。

BLEの接続・ペアリング・操作セッション、VPSのTCP/TLS/HTTPS通信シーケンス、OTA更新シーケンス、設定適用、永続データの物理保存、異常処置および状態遷移そのものは、それぞれの担当基本設計に従う。本書はそれらを重複実装せず、各機能が必要とするセキュリティ処理の共通サービス、鍵ライフサイクルおよび最終的な暗号学的検証結果を担当する。

システム全体の信頼境界、attack surface、全外部入力面、システム横断の認証・認可関係および全機能共通のセキュリティ原則の統合は、完成済みの「セキュリティ横断設計」を基準文書として参照する。本書は横断設計で整理された境界・残余リスクを踏まえつつ、Security論理機能内部の暗号方式、鍵、proof、`credentialState`、critical metadata MACおよび関連機能との契約を定め、その基準文書となる。

#### 基本設計と詳細設計の区分

本書で定める登録時の認証用の証明データ、秘密情報の配送保護、鍵状態、証明書運用値、SecurityGen、rollback判定、factory reset時key lifecycle、resource上限その他、認証・認可可否または外部から見たセキュリティに関する振る舞いを変える方式・値は、評価確定待ちを含む基本設計で定める事項とする。実機評価で変更が必要となった場合は詳細設計だけで変更せず、本書または値・方式を定める関連基本設計へ評価結果を反映する。RSIP API、byte offset、task、mutex、具体record layout等、外部から見た振る舞いを変更しない実装方法は詳細設計で具体化してよい。

### 1.3 上位文書・関連文書

`20_要求仕様`および`30_コア要求仕様`は本書の上位要求として使用しない。公開用要求で方式が未確定である項目は、完成済み基本設計および現行RA8M2/FSPの実装可能性を確認したうえで、本書の設計判断として具体化する。

### 1.4 外部技術資料の位置付け

実装成立性の確認には、参照時点のRenesas RA8M2 DatasheetおよびFSP文書を使用する。

- RA8M2 Group Datasheet
- FSP RA8M2 BSP documentation
- FSP `r_rsip_protected`
- FSP `r_rsip_key_injection`
- FSP `rm_psa_crypto`
- FSP MCUboot Port

参照時点のFSPでは、RA8M2のRSIP-E50D Protected ModeがAES-GCM、HMAC-SHA-256、ECDSA secp256r1、SHA-256、KDF、TRNG、Wrapped Key等を提供する。本書はこれらを上位要求として扱わず、採用方式の実装成立性確認に使用する。

### 1.5 用語

| 用語 | 本書での意味 |
| --- | --- |
| Wrapped Key | RSIPが保護された形式で保持・使用し、通常CPU処理から生鍵を取得しない鍵表現 |
| Secure transient buffer | 登録・発行等で避けられない短時間だけ秘密情報平文を保持し、使用後直ちに明示ゼロ化する固定RAM領域 |
| 初回所有者登録用登録秘密情報 | 製品ごとに異なる256 bit秘密情報。製品ラベルの登録用QRコードと本体内`K_OWNER_REG_AUTH`に同じ秘密を対応付け、初回所有者登録の追加認証にだけ使用する |
| 初回所有者登録追加認証 | 物理登録許可およびLE Secure Connections Just Worksとは別に、初回所有者登録用登録秘密情報を用いて現在の登録取引を認証し、登録用一時保護鍵を導出するアプリケーション層処理。Bluetooth OOB pairingそのものではない |
| 一般端末登録チケット | 認証済みOWNERが開始したGENERAL追加取引を新GENERAL候補へ引き継ぐ128 bit一回限りsecret。raw ticketを新GENERALからBLE送信せず、現在の取引に結び付けた認証用の証明データと一時保護鍵の根として使用する |
| `K_OWNER_RECOVERY_AUTH` | 128 bitの所有者復旧用秘密情報から導出する、所有者再登録の認証用鍵。本体ではRSIP HMAC Wrapped Keyとして保存し、再登録時の証明データの検証に使用する。元の所有者復旧用秘密情報そのものは、本体に永続保存しない |
| trust information | VPS trust anchor、firmware署名検証公開鍵、証明書等、正当性判断の根となる情報 |
| SecurityGen | firmware巻戻し防止用の単調増加generation |
| Security service | 関連機能がSecurityへ要求する乱数、HMAC、AEAD、署名、検証、鍵使用等の論理サービス |
| security profile | DEVELOPMENT / EVALUATION / NORMAL_OPERATION等、debug・provisioning機能の許可範囲 |

## 2. 設計方針と適用範囲

### 2.1 基本方針

1. 暗号通信の成立、相手認証、操作認可を別の判定として扱う。
2. 異なる用途の長期秘密鍵を共用しない。
3. RSIPでWrapped Keyとして扱える長期鍵は原則としてWrapped Keyで保持・使用する。
4. 秘密情報を通常ログ、診断、状態表示、BLE広告、VPS通常データへ平文出力しない。
5. 鍵・証明書・信頼情報の生成、保存、使用、交換、失効・削除条件を情報種別ごとに定める。
6. 初回所有者登録ではLE Secure Connections Just Worksだけを登録相手の認証根拠とせず、本体側物理登録許可に加えて製品固有256 bit登録秘密情報による追加認証を必須とする。
7. GENERAL端末追加では一回限り登録チケットをraw照合せず現在の取引に結び付けた認証用の証明データで検証し、OWNER再登録では所有者復旧用の秘密情報をraw送信せず現在の取引に結び付けた認証用の証明データで検証する。
8. 新端末へ長期認証鍵・所有者復旧用の秘密情報を配送するとき、Just Worksリンク暗号化だけへ秘密性を依存せず、登録取引固有の一時保護鍵によるAEADを使用する。
9. セキュリティ異常を解消するために暗号検証、認証、認可、Secure Boot、巻戻し防止を暗黙に無効化しない。
10. セキュリティ処理の高負荷・異常によって、停止、緊急停止、電源保護、安全監視を阻害しない。
11. 外部入力の構文・長さ・個数・offset・対象・状態を担当機能で検証し、Securityは暗号学的検証を代行しても意味検証を奪わない。
12. 認証情報の失効後に古い永続snapshotを復元して再有効化しない。
13. 初期製品でオンライン鍵ローテーション、汎用secure maintenance session、侵入検知等を追加しない。

### 2.2 本書の対象

- RSIP-E50D初期化とSecurity service利用可否
- 暗号用途乱数
- 初回所有者登録用256 bit登録秘密情報の生成・provisioning・本体側保護・QR対応付け
- 初回所有者登録追加認証と登録用一時保護鍵
- GENERAL登録ticket生成、proof検証、一時保護鍵
- 所有者復旧用の秘密情報の生成、`K_OWNER_RECOVERY_AUTH`、所有者再登録時の認証用の証明データ、一時保護鍵
- BLE端末長期認証鍵と`credentialState`（`CANDIDATE`／`ACTIVE`／`REVOKED`）lifecycle
- Wi-Fi credential保護鍵とAEAD
- VPS device key/certificate/trust anchor
- 設定MAC鍵とHMAC
- firmware検証鍵、署名検証、Boot Interface署名保護
- SecurityGen

## 3. 責任分界と共通条件

Securityは次を最終判断する。

- 指定key handleが正しい用途・状態で使用可能か
- HMAC/AEAD/ECDSA/SHA等の暗号学的処理結果
- 初回所有者登録追加認証の暗号学的検証結果と、その登録取引に対応する一時保護鍵の導出可否
- GENERAL登録ticket proofおよび所有者再登録時の認証用の証明データの暗号学的検証結果と、その登録取引に対応する一時保護鍵の導出可否
- terminal `credentialState`（`CANDIDATE`／`ACTIVE`／`REVOKED`）に対応するkey利用可否
- device certificate/private key/trust anchorの使用可否
- firmware signature verify結果
- 現在許可SecurityGenと対象SecurityGenの比較結果
- Product Data／Time trust／設定rollback metadata等、`K_SEC_STATE_MAC`対象の暗号学的検証結果
- protected secret recordの認証付き復号結果
- RSIP/TRNG/security trust information自身の異常

Securityは次を最終判断しない。

- BLE接続を通常操作セッションとして採用するかというBLE接続・認証の全体判断
- 初回OWNER／GENERAL追加／所有者再登録を開始・確定してよいかという所有者・操作端末管理の全体判断
- 所有者・一般端末の権限
- Wi-Fi設定値の意味
- VPS requestの業務意味
- config値域・適用可否
- firmware OTA開始可否
- Product Dataの内容や時刻の信頼状態が機能上の条件を満たすこと
- 異常時のシステム処置

暗号検証成功は、要求実行許可を意味しない。各機能はSecurity結果に加え、自身の状態・権限・意味検証を満たした場合だけ処理する。

## 4. セキュリティ機能の論理構成

Securityを次の論理要素へ分ける。

| 論理要素 | 主責務 |
| --- | --- |
| `SEC_CORE` | Security初期化、状態、RSIP排他、fault |
| `SEC_RNG` | TRNG、random bytes |
| `SEC_KEY` | wrapped key生成・登録・candidate/active/revoked使用許可・削除 |
| `SEC_AEAD` | AES-256-GCM credential、登録用秘密情報の暗号化転送データ、Wi-Fi保護 |
| `SEC_HMAC` | 初回OWNER追加認証、GENERAL登録時の認証用の証明データ、OWNER再登録時の認証用の証明データ、BLE認証、config HMAC、critical metadata MAC |
| `SEC_PKI` | ECDSA、device certificate、trust anchor |
| `SEC_BOOT` | firmware署名検証、SecurityGen、Boot Interface署名metadata連携 |
| `SEC_PERSIST` | secret/trust metadataと永続データ管理の保護契約 |
| `SEC_EVENT` | security event、fault情報 |

実装上これらを別task/moduleへ分割することは必須としない。

Security serviceはkey handleで鍵を指定し、呼出元へWrapped Key内容や生鍵を返さない。呼出元は用途別の論理key IDだけを扱う。

Firmware署名生成private keyは本体に存在せず、通常VPSにも保存しない。

`K_OWNER_REG_AUTH`のraw 256 bit値は製品ラベルの登録用QRコードにも表現するためprovisioning環境で生成する。本体へはsecure injectionによってWrapped HMAC Keyとして登録し、通常runtimeからraw値を取得するAPIを設けない。QR上のraw値と本体内Wrapped Keyが同じDevice IDへ対応することをprovisioning時に検証する。

`K_OWNER_RECOVERY_AUTH`は、所有者復旧用の秘密情報そのものではない。復旧用秘密情報は128 bitのまま所有者へ発行する。本体では、第15章の版を持つKDFを用いて256 bitの認証鍵を導出し、Wrapped Keyとして保護する。復旧用秘密情報の元の値は、永続保存しない。

### 5.2 一時登録secret／key

次は長期key catalogへ入れず、登録transactionに限定した一時情報とする。

- GENERAL登録ticket：128 bit、一回限り、所有者・操作端末管理の60秒受付内だけ有効
- `K_GENERAL_REG_AUTH`：GENERAL ticketから導出する256 bit一時HMAC鍵
- `K_GENERAL_REG_SESSION`：GENERAL proof成功後に導出する一回限りAES-GCM保護鍵
- `K_OWNER_REG_SESSION`：初回OWNER追加認証成功後に導出する一回限りAES-GCM保護鍵
- `K_OWNER_REREG_SESSION`：所有者再登録時の認証用の証明データ成功後に導出する一回限りAES-GCM保護鍵
- 各登録transactionのchallenge、app nonce、auth attempt ID、AEAD nonce

これらを永続credentialとして使用しない。登録認証情報の寿命は次の二種に分ける。

- **管理transaction-bound**：`managementTransactionId`、対象role、元の60秒deadline、およびGENERAL追加の`K_GENERAL_REG_AUTH`。所有者・操作端末管理が許す計画的なOWNER→新GENERAL接続切替えまたはproof前再試行に限り、同一管理transaction内で保持できる。
- **connection-bound**：`connectionGeneration`へ結び付くchallenge、app nonce、auth attempt、認証用の証明データの検証成功状態、`K_*_SESSION`、secret envelope配送状態、fragment/reassembly状態。接続世代変更時に常に破棄／ゼロで上書きして消去する。

GENERAL登録チケットの元の値は、認証済みOWNERアプリへQR生成用として一度提供する。本体側では、`K_GENERAL_REG_AUTH`の導出が完了し、所有者側の受領を確認できた時点で、元の値をゼロで上書きして消去する。

導出した`K_GENERAL_REG_AUTH`も、同じ管理処理で証明データの検証が成功する前の期間だけ保持する。処理の完了・失敗・取消し・期限超過・リセット、または証明データの検証成功後の接続・配送・受領確認の失敗で破棄する。次の管理処理では新しいチケットを発行し、旧鍵・旧成功状態を再利用しない。

### 5.3 秘密性を要求しないが完全性・rollback耐性が重要な情報

- device certificate
- VPS trust anchor
- firmware verification public key
- SecurityGen
- `highestCommittedGeneration`
- `highestCommittedProductDataRevision`
- ownerDataRevisionの最新性とrevocation state
- Wi-Fi credential revision/key epoch
- Product Data revision／approval metadata
- Trusted Time Record／Time Update Recordのrevision、state、timeSyncGeneration
- key metadata、用途、slot、valid/revoked状態
- 初回所有者登録用登録秘密情報のprovisioning状態・format version・Device ID対応情報

これらを「秘密でないから保護不要」と扱わない。

### 5.4 critical security metadata MAC

`K_SEC_STATE_MAC`は、本体内部専用の鍵である。SecurityGen、highestCommittedGeneration、highestCommittedProductDataRevision、所有者・セキュリティ情報の版、Wi-Fi認証情報の版、Product Data、Trusted Time Record／Time Update Record、信頼ストアの管理情報等のうち、暗号学的完全性が必要な重要管理情報を認証する。

異なるデータ集合を同じHMAC鍵で認証するため、状態保護用MACの入力には、データ集合ごとに版を持つドメイン分離子を必須とする。少なくともDevice ID、datasetIdまたは同等の種別識別情報、formatVersion、内容の版・世代、およびデータ管理機能が定める正規化済みのデータ本体を含める。別のデータ集合の正常なタグを流用できるような、曖昧な連結形式は使用しない。具体的なバイトオフセットは詳細設計で定める。

この鍵を他の用途のHMACに共用せず、本体外へ出力しない。

HMACだけでは、正しい過去のスナップショットが物理的に丸ごと復元されたことを検出できない。このため、各データ管理機能が定める巻戻し防止の下限値と旧版への切戻し禁止、永続データ管理によるその方針の機械的な適用、および第21～22章のデバッグ・書込みアクセス制限を組み合わせる。

## 6. RA8M2 RSIP-E50D Protected Mode

### 6.1 採用方式

初期製品ではRA8M2のRSIP-E50D Protected ModeをSecurityの暗号基盤とする。

少なくとも次を使用する。

- 128 bit TRNG output
- AES-256-GCM
- HMAC-SHA-256
- SHA-256
- ECDSA secp256r1
- ECDSA key pair generation / wrapped private key
- symmetric/HMAC wrapped key

### 6.2 key handle

各用途鍵を`securityKeyId`で識別し、実データはRSIP Wrapped Keyとして永続データ管理のcritical datasetへ保存する。

通常application APIに「raw key export」を設けない。

### 6.3 secure transient buffer

共有先へ初回発行する必要がある秘密だけ、固定`SECURE_TRANSIENT` RAMへ一時的に平文保持できる。

登録用秘密情報の暗号化転送データでterminal key 32 byte＋recovery secret 16 byteを同時に扱い、一時session keyも保持可能とするため、初期製品のSecurity用secret transient aggregate上限を**96 byte**とする。実装は例えば64 byte secret payload領域＋32 byte session-key領域など固定領域に分け、動的確保しない。

次を必須とする。

1. static allocation。
2. 使用者をSecurity登録・復旧処理へ限定。
3. log/diagnostic/dump対象外。
4. 使用後にcompiler最適化で除去されない明示zeroizeを実行。
5. error/timeoutでもfinally相当経路でzeroize。
6. reset後のRAM内容を秘密情報の取得元として使用しない。
7. raw secretを複数の登録transaction間で共有しない。

採用FSP/RSIPで導出したsession keyをtransient Wrapped AES key handleへ直ちにimportできる場合は、raw session keyのRAM滞在をさらに短くしてよい。成立しない場合でもraw長期key exportへ設計を後退させず、上記固定transient範囲内で処理する。

通常運用でWrapped Keyを再び平文へexportする手段は設けない。

### 6.4 TrustZoneの扱い

RA8M2はTrustZoneを備えるが、初期製品でSecurity機能全体をSecure worldへ分離することを必須構成としない。

RSIP Protected Mode、debug access制限、固定APIおよびsecret非exportを初期製品の主要保護とする。

将来製品化でapplication compartmentalizationを強化する場合、Security serviceとcritical key handlingをTrustZone Secure側へ移すことをセキュリティ横断設計のhardening候補とする。

### 6.5 RSIP利用不能

RSIP初期化失敗、fatal fault、wrapped key use failure等を`SEC_CRYPTO_UNAVAILABLE`として異常管理へ通知する。

必要なSecurity serviceを利用できない機能を「検証済み」と扱わない。安全関連処理は継続する。

## 7. 暗号用途乱数サービス

### 7.1 乱数源

暗号用途乱数はRSIP-E50D TRNGから取得し、一般purpose PRNGやRTC、Device ID、timerを秘密値生成に使用しない。

`R_RSIP_RandomNumberGenerate()`相当の128 bit出力を必要回数取得して構成する。

### 7.2 使用例

- 初回OWNER追加認証のdevice challenge 128 bit：1 block
- GENERAL登録ticket 128 bit：1 block
- GENERAL登録時の認証用の証明データ用device challenge 128 bit：1 block
- OWNER再登録時の認証用の証明データ用device challenge 128 bit：1 block
- 登録用秘密情報の暗号化転送データのAES-GCM nonce 96 bit：TRNG出力から必要長を使用
- BLE通常認証challenge 128 bit：1 block
- BLE terminal auth key 256 bit：2 block
- 所有者復旧用の秘密情報 128 bit：1 block
- session/auth IDの乱数部分
- Wi-Fi key生成時のnonce prefix

### 7.3 AES-GCM nonce

Wi-Fi credential用AES-GCM nonceは、同一`K_WIFI_STORE`で再利用しないことを構造的に保証する。

`K_WIFI_STORE`生成時にTRNGから32 bit `wifiNoncePrefix`を生成・保存し、各保存時に単調増加するuint64 `wifiCredentialRevision`を組み合わせて96 bit nonceとする。

`nonce = wifiNoncePrefix[32] || wifiCredentialRevision[64]`

byte orderはnetwork orderを基本とする。

同一keyのもとでrevisionを再利用しない。factory resetでkeyをrotateするときはnonce prefixも新規生成する。

登録用秘密情報の暗号化転送データ用nonceは各envelopeごとにTRNGで新規生成し、同じ一時session keyで同じnonceを再利用しない。登録失敗後の再試行では新しい認証attempt・session key・nonceを使用する。

TRNG failure時に過去prefix/challenge/nonceを再利用して新key generationまたは登録を完了扱いにしない。

## 8. BLE操作端末長期認証鍵

### 8.1 基本方式

BLE接続・認証で確定したHMAC-SHA-256 challenge-response用に、登録端末ごとに異なる256 bit HMAC鍵を使用する。

OWNER、GENERAL_1、GENERAL_2の最大3 slotを持ち、所有者・操作端末管理のterminal slotと1対1に対応させる。

長期認証鍵を新端末へ発行する3経路を区別する。

- 初回OWNER：8.3の`K_OWNER_REG_AUTH` proof成功後に`K_OWNER_REG_SESSION`で保護配送
- GENERAL追加：8.4の一回限りticket proof成功後に`K_GENERAL_REG_SESSION`で保護配送
- OWNER再登録：15章のrecovery proof成功後に`K_OWNER_REREG_SESSION`で保護配送

いずれもraw長期認証鍵をJust Worksリンク上へそのまま送信しない。

### 8.2 端末鍵candidate生成・配送・activation

端末鍵は登録transaction中に次の順で扱う。

1. 所有者・操作端末管理/BLE接続・認証が物理登録条件、暗号化BLE link、現在の`managementTransactionId`と候補端末を成立させる。
2. 対象登録経路のproofを本書8.3、8.4または15章で正常検証し、当該取引固有一時session keyを確立する。
3. SecurityがTRNG 128 bitを2回取得し、256 bit raw terminal keyを`SECURE_TRANSIENT`へ構成する。
4. 同じraw terminal keyをRSIP HMAC-SHA-256 Wrapped Key candidateへ変換し、`credentialState=CANDIDATE`として通常認証には使用不可の状態で保存可能にする。
5. 対象登録経路の一時session keyでraw terminal keyを含む登録用秘密情報の暗号化転送データをAES-256-GCM保護し、BLE接続・認証の有界な登録management transactionで候補端末へ一度だけ配送する。初回OWNER／OWNER再登録では新しい所有者復旧用の秘密情報も同じprotected envelopeへ含める。
6. アプリがOS秘密領域への保存を完了し、同じ`managementTransactionId`に結び付いたapplication受領完了を返したことをBLE接続・認証/所有者・操作端末管理から確認する。
7. 受領完了後、raw terminal keyと登録session keyをゼロで上書きして消去する。登録全体の最終commitまでraw値を保持しない。
8. 所有者・操作端末管理/永続データ管理の新`ownerDataRevision`がcommit済みで、candidate metadataの`terminalRegistrationId`・role・managementTransactionId・expected ownerDataRevisionと一致することを確認した後だけ、セキュリティ管理がWrapped Keyを`credentialState=ACTIVE`にする。
9. commit前に登録が失敗した場合はcandidate Wrapped Keyを使用不可のまま削除し、次取引へ再利用しない。
10. ownerDataRevision commit後にactivation結果を失った場合は旧状態へ推測rollbackせず、同じcommit済みmetadataとcandidate stateを照合して冪等にactivationを完了するか、完了を一意化できなければ候補端末を通常認証へ公開せず異常管理へ通知する。

`CANDIDATE` keyを通常BLE認証に使用しない。raw terminal keyの再表示・再取得APIを設けない。

### 8.3 初回所有者登録追加認証

初回所有者登録では、LE Secure Connections Just Worksによるリンク暗号化を使用するが、Just Worksだけを登録相手の正当性確認手段としない。所有者・操作端末管理の物理登録受付が成立し、BLE接続・認証が現在の登録取引と暗号化BLE linkを確立した後、製品ラベルの登録用QRコードからスマートフォンアプリが取得した256 bit登録秘密情報を用いて、次の追加認証を実行する。

#### 8.3.1 登録秘密情報

- 本体側では`K_OWNER_REG_AUTH`としてRSIP HMAC Wrapped Keyで保持する。
- スマートフォン側では製品ラベルQRから当該登録取引時だけ取得し、通常の端末長期認証鍵として保存しない。
- BLE広告、状態通知、ログ、診断、VPS通常データへ登録秘密情報を出力しない。
- 登録秘密情報はBluetooth OOB pairing keyではなく、Secure Connections Just Works成立後のアプリケーション層追加認証に使用する。
- factory resetでは保持し、次回の初回所有者登録でも同じ製品固有秘密情報を使用する。

#### 8.3.2 認証シーケンス

1. BLE接続・認証からSecurityへ、`managementTransactionId`、`connectionGeneration`、登録対象Device IDおよび新しい`registrationAuthAttemptId`を対応付けて認証開始を要求する。
2. Securityは新しい128 bit `deviceChallenge`をTRNGで生成する。
3. アプリはQR内Device IDと現在接続対象の公開Device IDが一致することを確認し、新しい128 bit `appNonce`を生成する。
4. アプリは次のversioned canonical byte列に対して、QRから取得した256 bit登録秘密情報でHMAC-SHA-256を計算し、`ownerRegistrationProof`として送信する。
5. Securityは`K_OWNER_REG_AUTH`を用いて同じHMACを計算し、constant-time比較で検証する。
6. 検証成功時だけ当該`managementTransactionId`・`connectionGeneration`・`registrationAuthAttemptId`に対して追加認証成功を一回限り有効とし、BLE接続・認証/所有者・操作端末管理へ結果を返す。
7. 失敗、期限切れ、接続世代変更、管理取引変更または再送済みattemptの再使用では成功状態を生成せず、terminal長期認証鍵の生成・登録へ進まない。

認証対象`OWNER_REG_AUTH_BYTES_V1`は少なくとも次を固定順序で含める。

1. domain separator `TR1-OWNER-REG-AUTH-V1\0`
2. protocol major/minor
3. Device ID
4. `managementTransactionId`
5. `connectionGeneration`
6. `registrationAuthAttemptId`
7. `deviceChallenge` 128 bit
8. `appNonce` 128 bit

整数型、byte order、Device ID長および各項目のオフセットはBLE接続・認証のwire formatと合わせて詳細設計で一意に固定する。文字列連結やJSON表記差に依存したHMAC対象を使用しない。

#### 8.3.3 登録用一時保護鍵とsecret envelope

追加認証成功後、同じ登録秘密情報から認証proofとは異なるdomain separatorを用いて一回限りの256 bit `K_OWNER_REG_SESSION`を導出する。

`K_OWNER_REG_SESSION = HMAC-SHA-256(K_OWNER_REG_AUTH, OWNER_REG_KEY_BYTES_V1)`

`OWNER_REG_KEY_BYTES_V1`は`TR1-OWNER-REG-KEY-V1\0`、Device ID、`managementTransactionId`、`connectionGeneration`、`registrationAuthAttemptId`、`deviceChallenge`、`appNonce`を含む。

本体側ではWrapped `K_OWNER_REG_AUTH`からHMAC出力として導出し、Secure transientまたはtransient RSIP key handleで保持する。アプリ側はQRから取得した登録秘密情報から同じ値を導出する。`K_OWNER_REG_SESSION`は永続保存せず、当該登録取引・接続世代・認証attemptだけに使用する。

初回OWNERへは、少なくともraw terminal key 256 bitと新しい所有者復旧用の秘密情報 128 bitを一つのversioned `OWNER_REG_SECRET_ENVELOPE_V1`としてAES-256-GCM保護する。96 bit nonceを新規生成し、128 bit tagを使用する。AADへ少なくともDevice ID、`managementTransactionId`、`connectionGeneration`、`registrationAuthAttemptId`、新OWNER候補`terminalRegistrationId`、envelope versionを含める。

BLE接続・認証の1 application messageへ収まらない場合は、BLE接続・認証/所有者・操作端末管理で定める有界な登録management transactionとしてfragmentし、全fragment受領・AEAD検証・アプリ秘密領域保存完了前に登録用秘密情報の配送成功としない。部分fragmentを次の接続・次の管理取引へ持ち越さない。

登録完了、失敗、取消し、timeoutまたは接続世代変更時に`K_OWNER_REG_SESSION`を直ちにzeroize／破棄する。AES-GCM nonceおよびattemptを再利用しない。

### 8.4 一般端末登録チケットproofと秘密配送

#### 8.4.1 ticket生成・引継ぎ

GENERAL追加では所有者・操作端末管理の管理取引ごとにSecurityが128 bit `generalRegistrationTicket`をTRNGで生成する。ticketは一回限りで、所有者・操作端末管理の60秒受付期限を越えて使用しない。

本体は、所有者として認証済みの既存のOWNERセッションへ、チケット、Device ID、`managementTransactionId`、role=GENERAL、および形式の版を、QR生成用として一度提供できる。所有者のアプリが受領したことを確認した後は、本体側でチケットの元の値を永続保存せず、ゼロで上書きして消去する。

raw ticketをゼロで上書きして消去する前に次の一時認証鍵を導出する。

`K_GENERAL_REG_AUTH = SHA-256("TR1-GENERAL-REG-AUTH-KEY-V1\0" || DeviceID || managementTransactionId || generalRegistrationTicket)`

本体側の`K_GENERAL_REG_AUTH`は、その管理処理の固定された保護付き登録コンテキストだけに保持する。所有者との接続が終了した後も、60秒の期限内で新しいGENERAL接続へ引き継ぐ。永続保存せず、リセット時は登録処理を失敗として破棄する。新しいGENERALアプリは、QRチケットから同じ値を導出する。

#### 8.4.2 proof

新GENERAL接続でBLE接続・認証が暗号化linkを確立した後、Securityは新しい128 bit `deviceChallenge`と`generalRegistrationAuthAttemptId`を生成／割当てし、アプリは新しい128 bit `appNonce`を生成する。

`GENERAL_REG_AUTH_BYTES_V1`は少なくとも次を固定順序で含める。

1. domain separator `TR1-GENERAL-REG-AUTH-V1\0`
2. protocol major/minor
3. Device ID
4. `managementTransactionId`
5. role=GENERAL
6. `connectionGeneration`
7. `generalRegistrationAuthAttemptId`
8. `deviceChallenge` 128 bit
9. `appNonce` 128 bit

新GENERALアプリは`K_GENERAL_REG_AUTH`をkeyとしてHMAC-SHA-256を計算し、`generalRegistrationProof`だけをBLEで送る。raw ticketをBLEへ送信しない。Securityは同じHMACをconstant-time比較し、現在取引・接続世代・attemptに対する成功結果だけをBLE接続・認証/所有者・操作端末管理へ返す。

proof失敗前の再試行を所有者・操作端末管理が許可する場合も、新challenge、appNonce、attemptを使用し受付期限を延長しない。proof成功後はticket／認証成功状態を使用済み候補とし、別端末へ流用しない。

#### 8.4.3 一時保護鍵

##### 鍵の導出と登録秘密情報の保護

認証用の証明データ（proof）の検証に成功した後、次の一時保護鍵を導出する。

`K_GENERAL_REG_SESSION = HMAC-SHA-256(K_GENERAL_REG_AUTH, GENERAL_REG_KEY_BYTES_V1)`

`GENERAL_REG_KEY_BYTES_V1`には、`TR1-GENERAL-REG-KEY-V1\0`と、`GENERAL_REG_AUTH_BYTES_V1`に含まれる取引の対応付け用の項目を含める。

新しいGENERAL端末用の端末鍵そのもの（raw terminal key）を、版を識別できる`GENERAL_REG_SECRET_ENVELOPE_V1`としてAES-256-GCMで保護する。
AADには、少なくとも次の情報を含める。

| 情報 | 内容 |
| --- | --- |
| Device ID | 対象の本体識別情報 |
| `managementTransactionId` | 対象の管理取引識別子 |
| `connectionGeneration` | 対象の接続世代 |
| `authAttemptId` | 対象の認証試行識別子 |
| 新しい`terminalRegistrationId` | 登録する端末の識別子 |
| `role` | 端末の役割 |
| エンベロープの版 | 登録秘密情報の形式を識別する版 |

新しい96ビットのノンス（nonce）と、128ビットの認証タグ（tag）を使用する。

##### 保存完了後に進める処理

BLE接続・認証機能が定める、上限のある登録取引でエンベロープ全体を配送する。
新しいGENERAL端末のアプリは、OSの秘密情報保護領域への保存完了を、同じ`managementTransactionId`と対応付けて返す。

この保存完了が返された場合だけ、所有者・操作端末管理機能による`ownerDataRevision`の確定へ進む。

##### 接続世代変更時に必ず破棄する情報

接続世代が変わった場合は、次の接続単位の情報を常に破棄する。

- 一時保護鍵`K_GENERAL_REG_SESSION`
- 認証チャレンジ（challenge）
- ノンス（nonce）
- 認証試行（auth attempt）の情報
- 証明データの検証成功状態
- 分割データ（fragment）の配送状態

##### 条件付きで保持できる情報

次の条件をすべて満たす場合に限り、`K_GENERAL_REG_AUTH`とチケット検証用の管理情報（ticket検証context）を保持できる。

- 同じ`managementTransactionId`の管理取引であること。
- 元の60秒の受付期限内であること。
- 所有者・操作端末管理機能が、計画的な接続切替え、または証明データによる認証前の再試行（proof前再試行）を許可していること。

この場合も、新しい接続では、認証チャレンジ、ノンスおよび認証試行の情報を新しく生成する。
前記の接続単位の情報を保持してよいという意味ではない。

##### 証明データの検証成功後に失敗した場合

証明データの検証に成功した後、接続、配送または受領確認に失敗した場合は、管理取引を取り消す。
`K_GENERAL_REG_AUTH`も破棄し、新しい管理取引と新しいチケットを用いて開始する。

### 8.5 通常認証時

BLE接続・認証は認証対象byte列とterminalRegistrationIdをSecurityへ渡す。

Securityは対応slotの`credentialState=ACTIVE`であるWrapped HMAC keyだけを使用してHMAC-SHA-256を計算・検証し、MATCH / MISMATCH / KEY_UNAVAILABLE / KEY_NOT_ACTIVE / INTERNAL_ERRORを返す。

認証セッション成立と`sessionId`生成はBLE接続・認証、roleと`authorizationRevision`は所有者・操作端末管理が判断する。セキュリティ管理は所有者・操作端末管理の`terminalSlotState`またはBLE接続・認証のsession状態を更新しない。

### 8.6 challenge

challengeは128 bitとし、認証試行ごとに新規生成する。

BLE接続・認証で確定した認証対象である、protocol version、公開本体識別、terminalRegistrationId、authAttemptId、connectionGeneration、challenge等を含むversioned canonical byte列を使用する。

byte layoutはBLE接続・認証の詳細設計と本書のSecurity interface詳細設計で一つに固定する。

### 8.7 `credentialState`と失効・削除

Security側の端末認証情報の状態を`credentialState`とし、セキュリティ管理だけが正式に管理・更新する。これは、所有者・操作端末管理が管理する`terminalSlotState`とは別の状態である。所有者・操作端末管理からの有効化・失効要求と確定済み管理情報を検証した結果に基づく場合だけ、セキュリティ管理が更新する。

`credentialState`は少なくとも`EMPTY / CANDIDATE / ACTIVE / REVOKED`を区別する。

- `CANDIDATE`：登録用秘密情報の配送前後の候補。通常認証に使用不可
- `ACTIVE`：対応する所有者・操作端末管理の`ownerDataRevision`がcommit済みで、app受領とcandidate metadataの整合が成立し、通常認証に使用可能
- `REVOKED`：所有者・操作端末管理で失効状態が確定し通常認証へ使用禁止。物理Wrapped Key削除前でも使用不可

セキュリティ管理は`credentialState=ACTIVE`の確定結果を所有者・操作端末管理へ返す。これは鍵の利用可能性を示すだけであり、所有者・操作端末管理が端末を`terminalSlotState=ACTIVE`としてBLE接続・認証へ公開したこと、またはBLE接続・認証で認証セッションが成立したことを意味しない。通常認証では所有者・操作端末管理の`terminalSlotState=ACTIVE`も独立して必要とする。

所有者・操作端末管理が端末をrevoked/deletedとcommitした場合、対応key handleをまずREVOKEDとして使用不可へ変更し、その後Wrapped Keyを削除する。

削除後は、古い所有者情報のスナップショットから同じ鍵を再有効化しない。最新のownerDataRevisionが正常であることを確認できない場合、古い認証スナップショットへ自動的に戻さず、OWNER DATA_INVALIDとして扱う。

ownerDataRevision commit後のactivation/deletion後処理が中断した場合は、credential metadataと所有者・操作端末管理のcommitted stateを照合して冪等に完了する。完了状態を一意に確認できない認証情報の候補を`credentialState=ACTIVE`へ推測昇格しない。

## 9. Wi-Fi認証情報の認証付き暗号

### 9.1 暗号方式

Wi-Fi接続が管理するSSID、security mode、passphrase等のWi-Fi設定を、**AES-256-GCM**で認証付き暗号化して保存する。

`K_WIFI_STORE`は他用途と共用しない256 bit AES Wrapped Keyとする。

### 9.2 鍵生成

製品初期化/provisioning時にRSIP KeyGenerate相当でWrapped AES-256 keyを生成し、raw keyをCPUへ出力しない。

key metadata、Wrapped Key、wifiNoncePrefix、wifiCredentialRevisionを永続データ管理の`PERSIST_CRITICAL`内のWi-Fi security logical datasetへ原子的に保存可能とする。旧版の特定physical group名へ依存しない。

### 9.3 protected Wi-Fi record

暗号blobは少なくとも次を含む。

- formatVersion
- `wifiCredentialRevision` uint64
- nonce 96 bit
- ciphertext length
- ciphertext
- GCM authentication tag 128 bit

AADへ少なくとも次を含める。

- domain separator `TR1-WIFI-CRED-V1`
- Device ID
- formatVersion
- wifiCredentialRevision
- Wi-Fi security mode

SSIDを含むWi-Fi設定全体をciphertextへ含め、passphraseだけを部分的に暗号化する方式にはしない。

### 9.4 rollback防止

`wifiCredentialRevision`をcritical monotonic metadataとして管理し、新設定commitまたはfactory reset時に増加させる。

保存blobのrevisionがcurrent expected revisionと一致しない場合、古い認証情報を有効設定として使用しない。

latest revisionのmetadataは`K_SEC_STATE_MAC`によるHMAC認証対象とする。

最新revisionのblobを復号・認証できない場合、古いrevisionへ自動fallbackして過去networkを再有効化しない。Wi-Fi設定利用不可としてWi-Fi接続/異常管理へ通知する。

### 9.5 factory reset

factory resetの`RESET_PENDING`確定後、次の順で処理する。

1. old Wi-Fi credential revisionを使用不可として確定する。
2. 新`K_WIFI_STORE` Wrapped Key candidateと新nonce prefixを生成する。
3. 新key metadata/revisionを永続データ管理のcritical Wi-Fi security stateへ原子的commitする。
4. old credential blobを削除対象として処理する。
5. old Wrapped Keyを廃棄する。

power lossで途中終了してもRESET_PENDINGにより通常利用へ戻さず、次回起動でreset処理を続行する。

旧Flash残存bitが物理的に残っても、旧鍵を最終的に廃棄することで古い認証情報を復号不能にする。

## 10. VPSデバイス秘密鍵・証明書・信頼アンカー

### 10.1 device key

VPS client認証鍵はECDSA P-256とし、初期provisioning時にRA8M2上でRSIP KeyPairGenerate相当を使用して生成する。

private keyはWrapped Keyのまま保存し、raw private keyを本体外へexportしない。public keyだけをprovisioning toolへ出力できる。

### 10.2 device certificate

初期基本方式を次とする。

- X.509 v3
- public key：ECDSA P-256
- certificate signature：ECDSA with SHA-256を基本
- keyUsage：digitalSignature
- extendedKeyUsage：clientAuth
- Device IDをcertificate subject/SANの識別情報へ対応付ける
- certificate serialはCA側で一意管理
- クライアント証明書有効期間：**5年を初期基本値**

具体DER/PEM保存形式は詳細設計で固定し、本体runtimeではDERを基本候補とする。

5年値はオンライン自動rotationを初期製品へ持ち込まず、開発・保守で交換可能とするための基本設計で管理する値である。採用CA運用条件により変更する場合は詳細設計だけで変更せず本書を見直す。

時刻管理がTIME_TRUSTEDを提供する場合、certificate expiryまで90日以下となったことを保守警告として識別できるようにする。90日も初期基本設計値とする。expiry warningだけを理由として通常BLE操作を禁止しないが、期限切れ後のVPS client認証は正常成立しないため保守交換を必要とする。

### 10.3 発行

1. 本体がWrapped key pairを生成する。
2. public key、Device ID、製品情報をprovisioning toolへ提供する。
3. provisioning CAがDevice IDとの対応を確認してクライアント証明書を発行する。
4. certificateを本体へ書込み、永続データ管理でreadback/完全性確認する。
5. certificate public keyが本体Wrapped private keyと一致することをchallenge signing等で確認する。
6. 正常確認後だけdevice credentialをACTIVEとする。

初期製品ではオンラインCSR自動更新を通常運用機能にしない。

### 10.4 VPS trust anchor

VPS server証明書検証に使用するtrust anchorは、通常OSの巨大な動的root storeではなく、製品で承認したcurrent trust anchor setを保持する。

初期製品のACTIVE trust anchor setは1組を基本とし、normal OTAや設定packageで変更しない。

server証明書のchain、hostname、signature、有効期間の検証はVPS接続・デバイス認証がTLS処理として実行し、Securityがtrust anchorの正当性・利用可否を提供する。

### 10.5 保存場所

- Wrapped private keyおよびkey/trust revision：永続データ管理のPERSIST_CRITICAL retained security dataset
- device certificate／certificate chain：永続データ管理が定めるretained criticalまたは`PRODUCT_SEC_AUX`。秘密鍵と同一削除単位へ混在させない
- VPS trust anchorとそのcritical利用可否metadata：永続データ管理のretained security dataset

所有者・端末認証情報と同じ削除単位に混在させない。

### 10.6 RTC信頼喪失時の開発・保守復旧

VPS接続・デバイス認証/時刻管理で確定したとおり、TIME_TRUSTEDなしで通常VPS通信を開始しない。また、初期製品でVPS限定接続によるsecure time bootstrapを実装しない。

TIME_TRUSTEDを失った機体は、時刻管理/システム状態管理の条件が成立する範囲でローカルBLE操作を継続可能とする一方、通常VPS管理を利用不可とする。既存TLS sessionが存在する場合もVPS接続・デバイス認証の契約に従い正常VPS通信へ継続利用しない。

時刻復旧は通常利用者向け操作ではなく、物理アクセスを伴う開発・保守手段で行う。初期基本方式は次とする。

1. DEVELOPMENT/EVALUATIONまたは定義されたwired maintenance手順で機体を保守対象とする。
2. 開発・保守toolが信頼できる外部時刻源を確認する。
3. 時刻管理のwired trusted time設定手順を開始し、Time Update RecordをPREPAREDとして確定する。
4. RTCへUTCを設定・readbackし、時刻管理のcalendar range／transaction整合を確認する。
5. 永続データ管理のCRC・保存処理の確定とセキュリティ管理の`K_SEC_STATE_MAC`検証を経てTrusted Time RecordとTime Update RecordをCOMMITTEDまで確定し、時刻管理が機能上の整合を確認してTIME_TRUSTEDを成立させる。
6. その後にだけ通常VPS certificate validity検証を再開し、必要に応じ認証済みVPS sampleで通常同期する。

RTCへ妥当そうな値を書き込んだだけ、またはproduction firmwareを再起動しただけではTIME_TRUSTEDへ昇格しない。

ログ・診断の通常参照専用maintenance UARTへ汎用`TIME SET` commandを追加しない。具体的wired service utility、DLM/debug条件およびTime Update APIは時刻管理・保守・詳細設計で固定する。

## 11. VPS/TLS向け暗号サービス契約

VPS接続・デバイス認証で確定済みの次を変更しない。

- TLS/HTTPS主体：RA8M2
- TLS 1.3 onlyを基本
- cipher suite：`TLS_AES_128_GCM_SHA256`
- key exchange：ECDHE P-256
- client auth：ECDSA P-256 certificate
- サーバ証明書 verification必須
- 時刻管理のTIME_TRUSTEDなしでは通常VPS通信を開始・継続しない
- TLS Session Resumptionなし

SecurityはTLS stackへ、Wrapped client private keyを用いた署名、TRNG、trust anchorおよびcertificate利用可否を提供する。

TLS session、HTTP request、reconnect、timeout、TIME_TRUSTED喪失時のsession終了はVPS接続・デバイス認証が管理する。Securityは証明書有効期間検証を省略してsession継続を許可するfallbackを提供しない。

採用FSP/Mbed TLS/PSAとRA8M2 RSIP-E50D Wrapped Keyの連携方式はE-07で実機確認し、成立しない場合はprivate keyをraw化して回避せず、本基本設計を見直す。

Security/TLS高負荷によってBLE安全監視・停止処理を阻害しないことを第20章で定める。

## 12. 設定データMAC鍵とHMAC検証

### 12.1 鍵

`K_CONFIG_MAC`はDeviceごとに異なる256 bit HMAC-SHA-256 keyとする。

VPSも同一keyを必要とするため、初期製品ではprovisioning tool/secure provisioning environmentで生成し、次の2方向へ登録する。

- VPS側：当該Device ID専用secretとして制限保存
- 本体側：RSIP HMAC Wrapped Keyとしてsecure injection

本体からraw keyをexportしてVPSへ登録する方式は使用しない。

### 12.2 HMAC対象

HMAC入力をversioned canonical byte列`CONFIG_AUTH_BYTES_V1`とする。

`CONFIG_AUTH_BYTES_V1`の正規化したバイト表現、版の管理、符号化方式、およびHMACの対象範囲は、本機能が定める。各項目の意味、値域、schemaVersionごとの設定パッケージの内容、generation、および更新確定の一連の処理は設定管理が定め、本機能はそれらの意味を再定義しない。設定管理から受け取った値を本節の符号化規則に従って正規化し、`K_CONFIG_MAC`によるHMAC-SHA-256の生成・検証を行う。

schemaVersion 1の基本encodingを次とする。

1. ASCII domain separator `TR1-CONFIG-HMAC-V1\0`
2. `packageId`：設定管理の32桁hexをdecodeした16 byte
3. `schemaVersion`：uint16 big-endian
4. `generation`：uint32 big-endian
5. `targetDeviceIdLength`：uint8
6. `targetDeviceId`：ASCII byte列
7. `settingCount`：uint16 big-endian
8. 全設定項目を固定settingId昇順で連結

各設定項目は次とする。

- settingId：uint16 big-endian
- valueType：uint8
- valueLength：uint16 big-endian
- canonical value byte列

整数は符号有無とbyte幅をschemaで固定しbig-endianとする。stringは正規化済みUTF-8 byte列を使用し、浮動小数点はschemaVersion 1では使用しない。

設定管理のschemaVersion 1の5項目はそれぞれ固定settingIdを詳細設計で割り当てる。

JSON objectのkey順、空白、改行、数値文字列表現および`auth` object自体はHMAC入力に使用しない。JSON parse後の意味値からcanonical byte列を再構築する。

これによりpackageId、schemaVersion、generation、target Device IDおよび全設定値をHMAC対象へ含める。

### 12.3 検証

設定管理は構文上限・必須項目を確認後、canonical byte列をSecurityへ渡す。SecurityはWrapped `K_CONFIG_MAC`でHMAC-SHA-256を検証する。

HMAC mismatch、key unavailable、canonicalization errorを区別して返す。

HMAC成功だけで設定をACTIVEにせず、generation、Device ID、schema、値域、適用条件は設定管理が判断する。

### 12.4 鍵交換

初期製品ではonline config MAC key rotationを実装しない。交換が必要な場合は第24章の有線開発・保守手段を用いる。

## 13. ファームウェア署名検証とセキュアブート

### 13.1 署名方式

OTA更新/公開用システム要求仕様「20. セキュリティ管理」に従い、application firmwareはECDSA P-256＋SHA-256で署名する。

通常OTA対象はapplication firmwareのみとし、firmware verification keyおよびfixed boot trust informationを通常OTA対象にしない。

### 13.2 image形式と署名保護metadata

OTA更新/固定ブート・復旧のMCUboot互換image形式を使用する。

署名保護対象には少なくとも次を含める。

- application image hash
- productFamilyId/modelId
- hardwareProfileId
- firmware identity（firmwareId、SemVer、BuildID等）
- image format version
- SecurityGen
- `bootInterfaceMin`
- `bootInterfaceMax`
- config schema compatibility summary
- persistent format compatibility summary

MCUboot standard header/TLVに不足する製品metadataはprotected custom TLVまたは同等の署名保護metadataとして格納する。具体TLV ID/layoutは詳細設計で固定してよいが、上記保護対象の意味を削減しない。

manifestだけに存在する互換性宣言を起動許可の信頼根とせず、OTA更新/固定ブート・復旧がimage内署名保護metadataとmanifestを照合できるようにする。

### 13.3 検証鍵

`PK_FW_VERIFY`は公開鍵であるため機密性を要求しないが、改ざんされると信頼根が失われる。

初期製品では固定ブート・復旧のfixed boot/recovery trust sectionへ配置し、normal application OTA書込みrangeから物理・linker上分離する。

### 13.4 署名生成鍵

firmware signing private keyはofflineまたは通常VPS runtimeから分離された署名環境で管理する。

source repository、CI log、firmware package、本体、通常VPS filesystemへ平文保存しない。

初期製品では複数階層signing PKIやonline signing serviceを必須としない。

### 13.5 二段階検証とfixed boot minimum security

- OTA candidate使用前：OTA更新がSecurityへ署名・hash・SecurityGen・signed metadata検証を要求する。
- boot前：固定ブート・復旧のfixed boot/recoveryが同じ`PK_FW_VERIFY`、SecurityGen policyおよびProduct Descriptor/Boot Interface条件で再確認する。

一方の検証成功だけを理由として他方を省略しない。

固定ブート・復旧はapplication Security task起動前に動作するため、fixed boot trust sectionの`PK_FW_VERIFY`と、永続データ管理のminimum access pathから取得するSecurityGen／`K_SEC_STATE_MAC`関連critical stateを使用するminimum security bootstrapを持つ。full TLS、BLE HMAC、Wi-Fi AEAD等をfixed bootへ持ち込まない。

fixed boot verifierと本体アプリケーション側Securityで、image hash、ECDSA P-256、protected metadata、SecurityGen、Product Descriptor、Boot Interfaceの意味を別仕様にしない。

## 14. SecurityGenと巻戻し防止

### 14.1 型と採番

`SecurityGen`をuint32とし、0を未設定/invalid用に予約し、正式releaseは1以上を使用する。

Security上の互換性を意図的に断ち、旧firmwareを通常起動・通常OTA対象から排除する必要があるreleaseだけSecurityGenを増加させる。

通常のfeature releaseごとに無意味に増加させない。

uint32最大値へ到達した場合はwrapせず、製品security format改訂を必要とする異常条件とする。

### 14.2 現在の許可済みSecurityGen

Securityが現在許可SecurityGenの意味と比較を所有し、永続データ管理が物理保存を担当する。

recordは少なくともSecurityGen、recordRevision、formatVersion、commit状態、CRC等の偶発破損検出および`K_SEC_STATE_MAC`によるHMAC-SHA-256 authentication tagを持つ。

### 14.3 更新順序

OTA更新の契約を維持し、candidate trial正常確認前に現在の許可済みSecurityGenを増加させない。

`TRIAL_BOOT_VALIDATED`確定後、candidate SecurityGenがcurrentより大きい場合だけ新値を原子的commitする。

### 14.4 rollback時

対象firmware SecurityGen < 現在の許可済みSecurityGenなら、通常OTA・通常boot・PREVIOUS recoveryで使用しない。

latest SecurityGen recordが破損またはHMAC不一致の場合、古い小さいSecurityGenへ自動fallbackして起動許可を広げない。`SEC_SECURITY_GEN_INVALID`として通常操作/通常boot許可を安全側に制限し、定義されたwired maintenanceを要求する。

工場出荷状態への初期化、所有者再登録、設定の切戻しによって、SecurityGenを減少させない。

### 14.5 whole-snapshot physical rollbackの扱い

初期製品は専用hardware monotonic counterを追加しない。このため、攻撃者がNORMAL_OPERATIONのdebug/write access制限を迂回してMRAMのcritical security state全体を過去snapshotへ物理的に書き戻す攻撃を、HMACだけで時系列上検出することはできない。

初期製品では次を組み合わせてこの経路を閉じる。

- NORMAL_OPERATIONのdebug/programming access制限
- 通常softwareからcritical NVM raw writeを許可しない
- generic backup/restore機能を設けない
- authorized maintenanceで古いcritical snapshot restoreを行わない
- logical monotonic revisionとlower fallback禁止

セキュリティ横断設計でもこの点をhardware monotonic counter非採用時の残余riskとして扱う。物理侵襲を含むより強いanti-rollbackが必要な場合のhardware monotonic/OTP等は将来hardening候補とする。

## 15. 所有者復旧情報・所有者再登録時の認証用の証明データ

### 15.1 recovery secret生成

所有者・操作端末管理で確定した所有者復旧用の秘密情報を128 bitとし、SecurityがTRNGから生成する。

所有者へ発行する際は、所有者・操作端末管理／アプリ側で、QRと、曖昧な文字を避けたBase32＋チェックサムの表示を使用する。

### 15.2 本体保存する認証情報

raw recovery secretを永続保存しない。

recovery secret生成時に次の256 bit認証鍵を導出する。

`K_OWNER_RECOVERY_AUTH = SHA-256("TR1-OWNER-RECOVERY-AUTH-KEY-V1\0" || DeviceID || recoverySecret)`

本体は導出値をRSIP HMAC-SHA-256 Wrapped Keyとして保存する。復旧用秘密情報の元の値は、所有者アプリへの保護された配送が完了した後に、ゼロで上書きして消去する。保存対象は、少なくとも次のとおりとする。

- Wrapped `K_OWNER_RECOVERY_AUTH`
- `recoveryRevision`
- 対応する`ownerDataRevision`
- CANDIDATE / VALID / USED状態
- formatVersion
- `K_SEC_STATE_MAC`対象metadata

recovery secretは128 bit暗号乱数であり、アプリは所有者再登録時に入力されたsecretとDevice IDから同じ`K_OWNER_RECOVERY_AUTH`を導出できる。本体側でraw secretを復元・比較する必要はない。

### 15.3 所有者再登録時の認証用の証明データ

所有者・操作端末管理の所有者再登録受付と暗号化BLE link成立後、Securityは新しい128 bit `deviceChallenge`と`recoveryAuthAttemptId`を生成／割当てし、新OWNER候補アプリは新しい128 bit `appNonce`を生成する。

`OWNER_REREG_AUTH_BYTES_V1`は少なくとも次を固定順序で含める。

1. domain separator `TR1-OWNER-REREG-AUTH-V1\0`
2. protocol major/minor
3. Device ID
4. `managementTransactionId`
5. `connectionGeneration`
6. 現在の`recoveryRevision`
7. `recoveryAuthAttemptId`
8. `deviceChallenge` 128 bit
9. `appNonce` 128 bit

アプリは入力されたrecovery secretから`K_OWNER_RECOVERY_AUTH`を導出し、上記byte列のHMAC-SHA-256を`ownerReregistrationProof`として送信する。raw recovery secretをBLEへ送信しない。

Securityは保存済みWrapped `K_OWNER_RECOVERY_AUTH`で同じHMACを計算しconstant-time比較する。VALIDなrecoveryRevision、現在のmanagementTransactionId、現在のconnectionGeneration、現在のattemptにすべて一致するproofだけを成功とし、BLE接続・認証/所有者・操作端末管理へ現在取引の成功結果を返す。

proof失敗ではraw secretを要求せず、新challenge/appNonce/attemptを使用する。旧取引・旧接続・USED recovery key・旧proofを新しい再登録へ流用しない。

### 15.4 再登録用一時保護鍵と新しい秘密情報の配送

proof成功後、次を導出する。

`K_OWNER_REREG_SESSION = HMAC-SHA-256(K_OWNER_RECOVERY_AUTH, OWNER_REREG_KEY_BYTES_V1)`

`OWNER_REREG_KEY_BYTES_V1`は`TR1-OWNER-REREG-KEY-V1\0`と`OWNER_REREG_AUTH_BYTES_V1`の取引相関fieldを含める。

Securityは新OWNER用256 bit terminal keyと新128 bit recovery secretを生成し、新recovery secretから新`K_OWNER_RECOVERY_AUTH` candidateを導出・Wrapped Key化する。

新terminal key＋新recovery secretをversioned `OWNER_REREG_SECRET_ENVELOPE_V1`として`K_OWNER_REREG_SESSION`でAES-256-GCM保護する。新規96 bit nonce、128 bit tagを使用し、AADへ少なくともDevice ID、managementTransactionId、connectionGeneration、recoveryAuthAttemptId、新OWNER候補`terminalRegistrationId`、新`recoveryRevision`、envelope versionを含める。

BLE接続・認証/所有者・操作端末管理の有界登録transactionで配送し、新OWNERアプリがterminal keyをOS秘密領域へ保存し新recovery secretを受領したことを同じmanagementTransactionIdへ対応付けて確認するまでownerDataRevision commitへ進まない。

接続世代変更時は`K_OWNER_REREG_SESSION`、challenge、nonce、auth attempt、認証用の証明データの検証成功状態およびfragment状態をゼロで上書きして消去する。proof前で所有者・操作端末管理が同一管理transaction・元のdeadline内の再試行を許す場合は、新接続で新しいauth attemptを開始する。proof成功後の接続・配送・receipt失敗では新しい管理transactionから開始し、旧セッション key、旧envelope配送状態および旧成功状態を再利用しない。

### 15.5 commit・USED/VALID切替え

所有者・操作端末管理のownerDataRevision commit前は、旧`K_OWNER_RECOVERY_AUTH`をVALIDのまま維持し、新key/recovery情報をCANDIDATEとして通常再登録へ使用しない。

新ownerDataRevisionが、旧OWNER＋全GENERAL REVOKED、新OWNER candidate、旧recovery USED候補、新recovery VALID候補としてcommitされた後、Securityは次を行う。

1. 新OWNER terminal credentialを第8.7節に従い`credentialState=ACTIVE`へ確定する。
2. 旧`K_OWNER_RECOVERY_AUTH`をUSEDとして再認証不可にする。
3. 新`K_OWNER_RECOVERY_AUTH`をVALIDへ切り替える。
4. 旧端末credentialをREVOKED／削除へ進める。

commit後の後処理結果が失われても旧ownerDataRevisionへrollbackせず、同じcommitted ownerDataRevisionとkey stateを照合して冪等に完了する。状態を一意に確認できない場合は旧recovery keyや旧OWNERを再有効化せず異常管理へ通知する。

### 15.6 raw secret処理

raw recovery secretは生成時または所有者アプリ内入力時だけ存在する。本体では新secret生成・envelope暗号化に必要な短時間だけSecure transientへ置き、通常log/diagnosticへ出力せず、処理完了・失敗・timeoutでゼロで上書きして消去する。

本体側の所有者再登録時の認証用の証明データ検証ではraw recovery secretを受信・復元しない。

## 16. 永続秘密情報の保護とrollback防止

### 16.1 保護分類

| データ | 機密性 | 完全性 | rollback防止 | 基本方式 |
| --- | --- | --- | --- | --- |
| 初回所有者登録用登録秘密情報 | 高 | 最高 | 固定製品秘密として保護 | `K_OWNER_REG_AUTH` Wrapped HMAC Key＋provisioning metadata。factory resetで保持 |
| BLE terminal Wrapped keys | 高 | 高 | 必要 | RSIP Wrapped Key＋credential state＋ownerDataRevision＋state MAC |
| 所有者復旧用の認証情報 | 高 | 高 | 必要 | Wrapped `K_OWNER_RECOVERY_AUTH`＋recoveryRevision/ownerDataRevision＋状態保護用MAC |
| Wi-Fi credential | 高 | 高 | 必要 | AES-256-GCM＋wifiCredentialRevision |
| device certificate | 低 | 高 | 必要 | retained trust record＋revision＋state MAC |
| VPS trust anchor | 低 | 最高 | 必要 | retained trust record、state MAC、wired update only |
| FW verification key | 低 | 最高 | 必要 | fixed boot trust section |
| SecurityGen | 低 | 最高 | 必要 | monotonic critical record＋state MAC、lower fallback禁止 |
| config package body | 低～中 | 高 | 必要 | HMAC＋generation/highestCommittedGeneration |
| Unit Product Data | 低～中 | 最高 | 必要 | CRC32C＋K_SEC_STATE_MAC＋productDataRevision/highestCommittedProductDataRevision |
| Trusted Time／Time Update | 低 | 最高 | 必要 | CRC32C＋K_SEC_STATE_MAC＋timeTrustRevision/timeSyncGeneration/update state |
| normal event log | 内容による | CRC | 通常不要 | ログ・診断のCRC32C。暗号学的耐改ざんは初期製品必須外 |

### 16.2 所有者・端末認証情報の巻戻し防止

所有者・操作端末管理のownerDataRevisionは、本体に保持するスナップショットの新旧判定に使用する。

失効済み・削除済みの端末を含む古い所有者情報のスナップショットを代替として自動採用し、それらの端末をACTIVEへ戻さない。

最新の確定済みスナップショットが使用不能で、古いものしか残っていない場合は、OWNER DATA_INVALID／通常操作禁止として扱うよう通知し、明示的な復旧を要求する。

ownerDataRevision、端末の認証情報の状態、および復旧用管理情報は、`K_SEC_STATE_MAC`の認証対象とする。

### 16.3 設定の巻戻し防止

設定管理の`highestCommittedGeneration`以下の候補を、通常の手順で再適用しない。

ACTIVEの破損により代替設定としてPREVIOUS/FACTORYを使用しても、highestCommittedGenerationを減少させない。

highestCommittedGenerationの管理情報も、`K_SEC_STATE_MAC`の認証対象とする。

### 16.4 Product Dataの巻戻し防止

製品情報管理のProduct Dataスナップショットは`K_SEC_STATE_MAC`で認証する。`productDataRevision`と、別の重要管理情報である`highestCommittedProductDataRevision`を照合する。

製品情報管理が新しい版への更新を確定した後は、最新のスナップショットの破損を理由に、古い校正・製造データへ自動的に戻さない。`highestCommittedProductDataRevision`を小さくしない。

スナップショットと確定済みの版の最大値を整合させる更新処理は製品情報管理が管理し、永続データ管理は各レコードの物理保存を担当する。一つの物理的な書込みで両者を同時に確定できるとは仮定しない。

### 16.5 時刻信頼レコードの認証

時刻管理のTrusted Time RecordおよびTime Update Recordは、`K_SEC_STATE_MAC`で認証する。

SecurityはMACの検証結果を返す。RTC値とPREPARED/COMMITTED/ABORTEDの機能上の整合、TIME_TRUSTEDの判定、巻戻し・連続性の判定は、時刻管理が行う。

MACが一致しない古いTrusted Time Recordを採用して、TIME_TRUSTEDへ戻さない。工場出荷状態への初期化、所有者再登録、通常OTAだけを理由に、正常な時刻信頼レコードを削除・巻戻ししない。

### 16.6 秘密情報・重要レコードの保存確定

秘密情報または重要なレコードの保存では、次の役割と確定条件を維持する。

1. 永続データ管理が旧データの保存用複製を保持して、新しいデータのバイト列を書き込む。書き込んだデータを読み戻し、保存形式、長さおよびCRCを確認する。
2. 読み戻したデータについて、各機能が次を確認する。
   - セキュリティ管理は、AEAD／HMAC／状態保護用MACの検証結果を返す。
   - データ管理機能は、データ本体の内容、データ内容の版、巻戻し防止の下限値、および更新処理との対応関係を確認する。
3. 両機能からの正常結果と、データ管理機能からの保存確定の許可を受けた後、永続データ管理が確定マーカーを確定する。

セキュリティ管理は暗号検証を担当し、データの意味や代替データを使用できるかを決定しない。永続データ管理の物理保存用ジャーナルを重複実装しない。確定マーカーの保存成功だけで、データ管理機能が管理する更新処理のGLOBAL_COMMITが成立したとは扱わない。

`fallbackPolicy`の共通の選択肢と物理保存の基本操作は永続データ管理が定める。各データ集合へ適用する方針と巻戻し防止の下限値は、データ管理機能が決定する。最新のデータ内容の版が破損しても、セキュリティ管理またはPERSISTの独自判断で古い版を復活させない。

### 16.7 状態保護用MACの更新

重要なメタデータを更新する場合、新しいレコードへ状態保護用MACを付ける。認証対象には、そのデータ集合を区別する情報、Device ID、形式、データ管理機能が付与する版、および規定の形式にそろえたデータ本体を含める。セキュリティ管理が読み戻したデータのMACを正常と判定し、データ管理機能が内容の整合を確認した後だけ、永続データ管理が保存処理の確定を完了する。

MACを検証できない場合に、「CRCが正常だからセキュリティ関連データは正常」と扱わない。

## 17. 認証・認可結果の共通契約

### 17.1 共通原則

認証結果を次の概念へ分ける。

- transport protected
- peer authenticated / registration proof verified
- identity/role known
- requested operation authorized
- message valid／現在有効
- function-specific safety/state condition valid

一つ成立したことを他の成立とみなさない。

### 17.2 BLE

BLE接続・認証/所有者・操作端末管理がterminal identity、role、authorizationRevision、sessionおよび登録transactionの正式な管理元となり、Securityは次を提供する。

- 通常登録端末HMAC検証
- `K_OWNER_REG_AUTH`による初回OWNER追加認証と`K_OWNER_REG_SESSION`
- GENERAL登録ticketによる現在の取引に結び付けた認証用の証明データと`K_GENERAL_REG_SESSION`
- Wrapped `K_OWNER_RECOVERY_AUTH`によるOWNER再登録時の認証用の証明データと`K_OWNER_REREG_SESSION`
- terminal credential key state利用可否

LE Secure Connections Just Works成立だけを登録相手の`peer authenticated`として扱わない。各登録経路で所有者・操作端末管理の物理・管理条件と本書のcurrent transaction proof成功が対応して初めて、認証情報の候補の配送へ進める。

### 17.3 VPS

VPS接続・デバイス認証がTLS peer authenticationとHTTPS sessionを管理し、Securityはclient key、certificate、trust anchor、certificate crypto verify supportを提供する。

TIME_TRUSTEDは時刻管理が管理する状態であり、VPS接続・デバイス認証が証明書有効期間を含むTLS利用可否へ反映する。Securityは時刻未信頼を暗号検証成功だけで上書きしない。

### 17.4 管理Web

system管理者・開発者のWeb authentication/authorizationは管理Web/VPS側の責任とし、本体SecurityはVPSからの設定package/firmware等を本体側信頼根で暗号学的に再検証する。

Web login成功だけで本体の安全条件を省略しない。

## 18. 外部入力検証・Replay防止・資源上限

### 18.1 責任分界

各通信機能は外部入力をSecurityへ渡す前後で、形式、長さ、配列数、offset、必須項目、対象、値域、処理可能状態を検証する。

Securityは「未検証の任意長bufferを無制限に受ける汎用parser」にならない。

### 18.2 既存上限の尊重

- BLE application message：BLE接続・認証の最大64 byte
- BLE接続・認証の登録／管理transaction：論理データ最大96 byte、1 fragmentのデータ最大32 byte、最大3 fragment、同時1配送。初回OWNER／GENERAL／OWNER再登録用秘密情報の暗号化転送データを部分状態のまま別のセッションへ持ち越さない
- Wi-Fi UART RX等：Wi-Fi接続の固定バッファ
- VPS一般JSON body：VPS接続・デバイス認証の最大16 KiB
- OTA manifest：8 KiB、OTA Range：16 KiB
- config package：設定管理の最大16 KiB
- log VPS body：ログ・診断の最大16 KiBかつ64 event
- maintenance command：ログ・診断の最大64 byte

Securityが上限を超えるbufferを内部copyしてから拒否する方式にしない。

### 18.3 Replay

過去の通信データの不正な再利用（Replay）と、古いデータへの巻戻しを防ぐため、対象ごとに次の情報を対応付けて確認する。

#### BLE操作と通常認証

BLE操作のReplay防止、通信順序（sequence）およびセッションの管理は、BLE接続・認証機能が定める。

セキュリティ管理機能は、通常BLE認証のHMAC対象へセッションや認証試行などの情報を含める。
これにより、暗号検証結果が現在のセッションと対応付くようにする。

#### 登録・再登録の認証対象

初回OWNER追加認証では、次の表の情報を認証対象へ含める。
GENERAL登録とOWNER再登録では、認証用の証明データ（proof）を、表に示す情報へ結び付ける。

| 認証の種類 | 認証対象に含める、または証明データと対応付ける情報 |
| --- | --- |
| 初回OWNER追加認証 | `managementTransactionId`、`connectionGeneration`、`registrationAuthAttemptId`、本体のチャレンジ、アプリのノンス |
| GENERAL登録 | `managementTransactionId`、`role`、`connectionGeneration`、`generalRegistrationAuthAttemptId`、本体のチャレンジ、アプリのノンス |
| OWNER再登録 | `managementTransactionId`、`connectionGeneration`、`recoveryRevision`、`recoveryAuthAttemptId`、本体のチャレンジ、アプリのノンス |

GENERAL登録では、チケットそのもの、`K_GENERAL_REG_AUTH`および証明データの検証成功状態を、別の管理取引へ再利用しない。

OWNER再登録では、使用済み（USED）の復旧用鍵、以前の証明データおよび一時セッション鍵を再利用しない。

#### 登録秘密情報の配送

各登録秘密情報エンベロープは、現在の`terminalRegistrationId`／`recoveryRevision`などをAADへ結び付ける。
新しい96ビットのノンスを使用する。

#### データの不正な再利用・巻戻しの防止

| 対象 | 防止に使用する版・世代などの情報 |
| --- | --- |
| 設定の不正な再利用・巻戻し | 設定世代（`generation`）と`highestCommittedGeneration` |
| ファームウェアの巻戻し | `SecurityGen` |
| Wi-Fi認証情報の巻戻し | `wifiCredentialRevision` |
| 製品情報（Product Data）の巻戻し | `highestCommittedProductDataRevision` |
| 所有者の認証情報の巻戻し | `ownerDataRevision` |
| 時刻の信頼状態の巻戻し | 時刻管理機能の版・世代、更新取引、RTCの継続性と、状態保護用MAC（state MAC）の組合せ |

### 18.4 認証失敗制限

BLE接続・認証/所有者・操作端末管理で確定した受付期限・通常BLE連続認証失敗制限を使用し、Securityは認証失敗count/eventを提供するが、接続切断・30秒待機等のsession policyを重複管理しない。

初回OWNER、GENERAL登録、OWNER再登録時の認証用の証明データの失敗についても、Securityは失敗結果とreason categoryをBLE接続・認証/所有者・操作端末管理へ返す。再試行可否、登録受付終了、接続切断等の管理policyはBLE接続・認証/所有者・操作端末管理が決定し、Security独自の無期限再試行を行わない。

## 20. セキュリティ処理の排他・優先度・実時間影響

### 20.1 RSIP排他

RSIPを同時に複数contextから無制御に操作しない。

Security内に一つのcrypto arbitrationを置き、同期/非同期APIの具体実装は詳細設計で定める。

固定ブート・復旧のfixed boot minimum security bootstrapとapplication Security serviceは同時実行phaseではないが、同じkey/record形式を使用し、相互に矛盾するRSIP初期化方式を持たない。

### 20.2 固定資源

初期基本値を次とする。

| 資源 | 基本値 |
| --- | ---: |
| Security request descriptors | 8 slot固定 |
| Security secret transient aggregate | 96 byte固定 |
| active registration security context | 1 transaction |
| small crypto input copy | 最大256 byte。大容量はstream/chunk参照 |
| raw long-term key export API | 0 |
| simultaneous provisioning transaction | 1 |

TLS/config/firmware等の大容量dataをSecurity内部へ全量copyしない。

8 slot、96 byte、256 byte等は評価確定待ちを含む基本設計で管理する値であり、評価で変更する場合は本書へ反映する。詳細設計がresource不足を理由としてsecret保護、認証proofまたは安全関連deadlineを弱めない。

### 20.3 優先順位

緊急停止、安全停止、電気保護、制御周期はSecurity request処理より上位とし、これらがRSIP完了を待たない。

Security requestの概念優先度を次とする。

1. boot/trust verification（起動時のみ）
2. 現在BLE認証／登録境界で必要な短時間処理
3. critical secret／state MAC record処理
4. TLS/VPS crypto
5. config/maintenance等の管理処理

実装上のtask priorityは詳細設計で決定するが、この優先関係を逆転して安全処理を待たせない。

### 20.4 長時間処理

firmware SHA-256等の長処理はOTA更新のchunk処理と連携し、可能な範囲で時間分割する。

TLS/署名検証/firmware hash/critical MAC最大負荷時にBLE操作response・停止deadlineを満たすことを実機評価する。

## 21. 開発・評価・通常運用プロファイル

### 21.1 profile

初期製品のsecurity profileを次の3つに区別する。

| profile | 目的 | debug/programming |
| --- | --- | --- |
| DEVELOPMENT | firmware開発 | SWD/JTAG等を許可可能。実運用秘密情報を使用しない |
| EVALUATION | 結合・安全・security評価 | 必要なdebugを限定許可。評価用credentialを使用 |
| NORMAL_OPERATION | 通常運用相当 | 不要debug/製造機能を無効またはアクセス制限 |

### 21.2 profileの識別

build artifactとdevice provisioning recordからprofileを識別できること。

NORMAL_OPERATION credentialをDEVELOPMENT deviceへ誤投入しない運用を基本とする。

### 21.3 切替え

profileを通常remote commandで任意切替えできる機能を設けない。

NORMAL_OPERATIONへの移行は明示的provisioning/保守手順で実行し、RA8M2 device lifecycle/access level、debug access、boot mode設定等の具体値はハードウェア/製造security詳細設計で確定する。

不可逆lockを使用する場合は、固定ブート・復旧のwired recovery、量産・保守手順との両立を評価してから適用する。

### 21.4 初期製品のTrustZone方針

初期製品ではTrustZone Secure/Non-Secure分割を必須とせず、1人開発で検証可能な構成を優先する。

この判断によってRSIP Wrapped Key保護、debug access制限、入力検証、Secure Boot等を省略しない。

TrustZone分割は製品化時のhardening候補としてセキュリティ横断設計へ反映済みである。

## 22. デバッグ・保守・有線復旧インターフェース

### 22.1 通常保守UART

ログ・診断の3.3 V UART 115200/8N1参照専用interfaceを維持する。

次を取得できない。

- raw/wrapped key blobのdump
- 初回所有者登録用登録秘密情報および`K_OWNER_REG_SESSION`
- GENERAL登録ticket、`K_GENERAL_REG_AUTH`、`K_GENERAL_REG_SESSION`
- 所有者復旧用秘密情報の元の値、`K_OWNER_RECOVERY_AUTH`、`K_OWNER_REREG_SESSION`
- Wi-Fi credential plaintext/ciphertextの不要なdump
- BLE terminal key
- VPS private key
- config MAC key
- security state MAC key
- TLS session secret/token

### 22.2 SWD/JTAG等

NORMAL_OPERATIONでは不要なSWD/JTAG/debug accessを無効またはdevice security機能でアクセス制限する。

具体的DLM/AL設定、ID code、secure debug手順等はRA8M2採用FSP/デバイス手順を確認して詳細設計する。

### 22.3 wired recovery

OTA更新/固定ブート・復旧で確定したRA8M2 Boot Firmware serial programming＋Renesas Flash Programmerを開発・保守復旧の基本経路とする。

通常利用者が通常操作からboot programming modeへ入れるsoftware commandを設けない。

service pad/boot mode操作、物理アクセス、保守手順を必要とし、normal runtime security boundaryとは分離する。

### 22.4 trust replacement

firmware verification key、VPS trust anchor等のtrust root交換が必要な場合は、通常OTAではなくwired maintenanceを使用する。

交換後に新trust情報の完全性・対象・versionを確認し、旧trustを無効化する前に新trustで既知test artifactを検証する。

## 23. プロビジョニング

### 23.1 初期provisioningの目的

製品固有secret/trust informationを本体とDevice IDへ対応付け、通常運用開始前に検証する。

Device IDそのものは製品情報管理に従いRA8M2 Unique IDから、同じUnique IDには常に同じ値が得られる規則で生成し、PERSIST内へ別の基準値として重複保存しない。

### 23.2 初期provisioning順序

概念順序を次とする。

1. 製品情報管理の規則でDevice IDをRA8M2 Unique IDから確定する。
2. RSIPおよび永続データ管理のcritical storageを初期化する。
3. provisioning環境でDevice IDごとに新しい256 bit初回所有者登録用登録秘密情報を暗号用途乱数で生成し、製品ラベルQR用データを作成する。
4. 同じ登録秘密情報を`K_OWNER_REG_AUTH`としてsecure injectionし、RSIP HMAC Wrapped Keyで保存する。
5. QR用Device ID・format versionと本体内`K_OWNER_REG_AUTH`の対応をchallenge/HMAC testで検証する。
6. `K_WIFI_STORE`とwifiNoncePrefixを本体内生成する。
7. `K_SEC_STATE_MAC`を本体内生成する。
8. `K_VPS_DEVICE` key pairを本体内生成する。
9. public keyを取得してdevice certificateを発行する。
10. device certificateとVPS trust anchorを登録する。
11. `K_CONFIG_MAC`をsecure injectionする。
12. firmware verification public keyを固定ブート・復旧のfixed boot trustへ登録する。
13. SecurityGen初期値を登録・state MAC認証する。
14. key/cert対応、初回所有者登録用HMAC、署名、config HMAC、TLS testを実施する。
15. provisioning completeを原子的に確定する。

BLE端末鍵、GENERALチケット、所有者復旧用情報は、利用者登録時に生成するため、製造時の初期設定では事前共有しない。初回所有者登録用の登録秘密情報は、これらとは異なる製品固有の秘密情報である。製品ラベルQRとの対応付けが必要なため、製造時の初期設定で設定する。

### 23.3 provisioning失敗

一部secretだけ登録された中間状態をNORMAL_OPERATIONとして使用しない。

provisioning complete未成立時は通常操作・通常VPS管理開始を許可せず、開発・保守対象として識別する。

`K_OWNER_REG_AUTH`の本体登録とQRラベル対応確認のいずれかが不明な機体を出荷可能状態として扱わない。

### 23.4 key injection

VPSと共有が必要な`K_CONFIG_MAC`および製品ラベルQRと共有する`K_OWNER_REG_AUTH`は、provisioning環境で生成したraw keyを通常applicationへ渡さず、Renesas key injection/Key Wrap serviceまたは同等の安全なwrapped-key投入経路を使用することを基本とする。

公開用システム要求仕様「20. セキュリティ管理」が将来拡張としている「量産秘密鍵注入基盤」を初期製品で構築することを意味しない。初期製品では開発・provisioning toolによる管理された少数device向け手順でよい。

開発初期のplain InitialKeyWrap評価を使用する場合でも、NORMAL_OPERATION製品の正式provisioning方式とは区別して記録する。

### 23.5 登録用QRコード表現

製品ラベルの登録用QRコードは、少なくとも次の論理情報を一つのversioned UTF-8 payloadとして表現する。

- format identifier / format version
- 製品種別またはprotocol識別
- 公開Device ID
- 256 bit初回所有者登録用登録秘密情報

登録秘密情報はBase64url等のQR読取りに適した固定・可逆表現を使用し、表示上の大文字小文字・区切り・padding差によって別値へ解釈されない形式を詳細設計で固定する。QR image自体には端末長期認証鍵、所有者情報、VPS秘密情報を含めない。

スマートフォンアプリはQR読取り後、payloadのformat/Device IDを検証してから登録秘密情報を使用する。QR画像を通常アプリデータ・ログへ保存しないという公開用システム要求仕様「04. スマートフォンアプリ」の責任を維持する。

## 24. 鍵・証明書・信頼情報の交換・失効

### 24.1 online自動rotationを行わないもの

初期製品では次のonline自動rotationを実装しない。

- 初回所有者登録用登録秘密情報
- VPS device certificate/private key
- config MAC key
- firmware verification key
- VPS trust anchor

BLE端末認証情報と所有者復旧用の認証情報は、所有者・操作端末管理の登録・再登録・工場初期化処理で、本体内で生成・失効させる。このため、ここで示すオンライン更新への非対応とは別に扱う。

### 24.2 device certificate交換

expiry前または鍵交換が必要な場合、wired maintenanceで次を行う。

1. 新Wrapped device key pair candidate生成。
2. 新certificate発行・登録。
3. key/cert pair検証。
4. VPS側で新certificate/Device ID mapping有効化。
5. TIME_TRUSTED下でmTLS test成功。
6. 新credential ACTIVE commit。
7. 古い認証情報を無効化。

古い認証情報を先に破棄して通信不能になる順序を避ける。power loss等で中断した場合にcandidate/old activeを一意に判定できるreplacement transaction stateを永続データ管理のcriticalへ保持し、両方を無条件ACTIVEにしない。

### 24.3 trust anchor/FW verification key交換

通常OTAやconfig packageで変更しない。

wired maintenanceで、物理アクセス、対象製品確認、新trust artifact検証、書込みreadback、boot/TLS testを実施してからACTIVE化する。

FW verification key交換は固定ブート・復旧のfixed boot trust boundaryの更新でもあるため、本体アプリケーション側Security recordだけを書き換えて完了扱いにしない。

### 24.4 失効

BLE terminal keyは所有者・操作端末管理のrevocation/deletionと同期して即時使用禁止とする。

`K_OWNER_RECOVERY_AUTH`は、所有者再登録で旧鍵をUSED、新鍵をVALIDへ切り替え、工場出荷状態への初期化で削除する。

Wi-Fi keyはfactory resetでrotateする。

初回所有者登録用の登録秘密情報は、工場出荷状態への初期化や所有者再登録で失効させない。漏えい・ラベル交換等によって変更が必要な場合は、通常の所有者操作ではなく、物理的な有線保守・再設定によって新しい秘密情報と新しいラベルを一体で更新し、旧秘密情報を使用不可とする。

製品固有VPS credentialとFW trust rootはfactory resetで削除しない。

## 25. 工場出荷状態への初期化・所有者再登録

### 25.1 factory resetで削除・rotateするSecurity情報

- OWNER/GENERAL terminal HMAC keysとcredential state
- `K_OWNER_RECOVERY_AUTH`／recovery revision/status
- Wi-Fi credential blob
- Wi-Fi storage keyとnonce prefix（rotate）
- 利用者session／登録ticket／登録一時鍵／authorization transient information

### 25.2 factory resetで保持するSecurity・trust情報

- 製品情報管理から導出されるDevice ID identity
- 初回所有者登録用`K_OWNER_REG_AUTH`および登録秘密情報provisioning metadata
- VPS device private Wrapped Key
- VPS device certificate
- VPS trust anchor
- config MAC Wrapped Key
- security state MAC Wrapped Key
- firmware verification key/trust information
- SecurityGen
- highestCommittedGeneration
- highestCommittedProductDataRevision
- bootInstanceId等の巻戻し禁止counter
- 製品情報管理のUnit Product Data／製造・校正情報
- 時刻管理のTrusted Time Record／Time Update Recordおよび正常なtime trust metadata
- provisioning/product trust metadata

初回所有者登録用登録秘密情報は利用者が登録したOWNER credentialではなく製品固有の登録用secretである。factory reset後に新しい初回所有者登録を成立させるため保持する。

工場出荷状態への初期化、所有者再登録、通常OTAだけを理由に、製品情報管理のProduct Dataや時刻管理の時刻信頼情報を削除・巻戻ししない。

### 25.3 transaction順序

所有者・操作端末管理/永続データ管理の`RESET_PENDING`を先にcommitする。

SecurityはRESET_PENDINGを確認後だけ利用者secretの不可逆削除・Wi-Fi key rotationへ進む。

Wi-Fi鍵の更新では、第9.5節に従って新しい鍵・版の状態を先に確立し、旧データ・旧鍵へ戻らない。所有者・復旧用認証情報の削除後も、旧ownerDataRevisionを再公開しない。

電源喪失後もRESET_PENDINGから再開し、旧所有者・端末認証情報を使用可能な状態へ戻さない。

### 25.4 所有者再登録

所有者再登録では、第15章に従って旧所有者・一般端末の鍵と旧`K_OWNER_RECOVERY_AUTH`を失効させる。新しいOWNER鍵と復旧用認証情報を、同じownerDataRevisionの更新処理へ対応付ける。

初回所有者登録用の`K_OWNER_REG_AUTH`、Wi-Fi設定／`K_WIFI_STORE`、VPSデバイス認証情報、設定用MAC鍵、状態保護用MAC鍵、ファームウェアの信頼情報、SecurityGen、Product Data、Trusted Time Recordは、所有者再登録だけを理由に変更しない。

## 26. セキュリティ事象・ログ・状態通知

### 26.1 security event

公開用システム要求仕様「20. セキュリティ管理」の最低事象に加え、少なくとも次をログ・診断へ提供する。

- 初回OWNER追加認証失敗、旧transaction/replay拒否、登録秘密情報利用不能
- GENERAL登録ticket proof失敗／replay／期限切れ
- OWNER再登録recovery proof失敗／USED recovery使用／replay
- 登録用秘密情報の暗号化転送データ AEAD失敗／app受領未完了
- BLE auth mismatch / revoked terminal / unauthorized request
- Replay/old session/sequence reject
- oversized/invalid external security input
- Wi-Fi credential AEAD authentication failure
- VPS サーバ証明書 chain/name/time verify failure
- VPS client key/certificate failure
- config HMAC mismatch
- critical security state MAC mismatch
- Product Data MAC/rollback failure
- Trusted Time／Time Update MAC failure
- firmware signature/hash/protected metadata failure
- SecurityGen rollback reject
- trust store corruption
- RSIP/TRNG failure
- unauthorized debug/maintenance attemptをsoftwareから検出できる場合
- provisioning/credential replacement result

### 26.2 log内容

security logへraw secret、key、Wrapped Key内容、初回所有者登録用登録秘密情報、GENERAL登録ticket、ownerRegistrationProof、generalRegistrationProof、ownerReregistrationProof、各登録session key、Wi-Fi passphrase、certificate private material、HMAC expected/actual full value、所有者復旧用の秘密情報を含めない。

必要ならkey ID、certificate fingerprint、Device ID、terminalRegistrationId、managementTransactionId、event reason、generation/revision等の非秘密識別子を記録する。

### 26.3 priority

セキュリティ管理がセキュリティイベントの内容に応じた優先度を次のように基本決定し、ログ・診断はそのpriorityを保存・送信policyへ反映する。

**IMPORTANT**を基本とするもの：

- firmware trust／SecurityGen／fixed boot trust異常
- 必須Security service／RSIP／TRNGの利用不能
- trust store／critical state MAC異常
- revoked credentialやrollback-sensitive stateを安全に判定できない異常
- VPS credential/trust replacement failure等、管理通信を継続不能にするtrust異常

**NORMAL/SECURITY**を基本とするもの：

- 単発のBLE auth mismatch
- 初回OWNER／GENERAL／OWNER再登録時の認証用の証明データの単発失敗
- replay/old session/invalid inputの通常拒否

連続失敗による認証制限成立、登録秘密情報／recovery auth key自体の利用不能、または異常管理へ高影響を通知する状態へ変化した場合はIMPORTANTへ格上げする。

具体event IDは詳細設計で割り当てるが、NORMAL/IMPORTANTの意味を詳細設計だけで変更しない。

### 26.4 利用者通知

通常操作を禁止するsecurity異常について、Securityは内部秘密を露出しないreason categoryを異常管理/状態表示・利用者通知へ提供する。

一般利用者表示にcertificate chain、key ID、内部暗号error code等を直接表示しない。

## 28. 検証方針と異常注入

### 28.1 正常系

- BLE auth mismatch連続

- TLS hostname mismatch
- untrusted CA
- expired/not-yet-valid サーバ証明書

### 28.4 firmware/boot

- image hash mismatch
- ECDSA signature mismatch
- product/hardware mismatch
- bootInterfaceMin/Max改変・範囲外
- config/persistent compatibility metadata改変
- SecurityGen lower
- verification key corruption
- trial/recovery SecurityGen境界

### 28.5 power cut

少なくとも次の途中でpower cut/resetを注入する。

- terminal keyの`credentialState=CANDIDATE`保存／`ownerDataRevision` commit／`credentialState=ACTIVE`確定の各境界
- GENERALチケットの発行後・所有者との接続終了後・候補鍵の配送後
- OWNER再登録時の認証用の証明データ成功後・新recovery candidate保存後・ownerDataRevision commit前後
- Wi-Fi encrypted record/key rotation
- SecurityGen/state MAC commit
- Product Data／highestCommittedProductDataRevision transaction
- Time Update PREPARED／COMMITTED transaction
- provisioning complete
- certificate replacement
- factory reset secret deletion

古い認証情報、旧recovery key、旧Wi-Fi keyまたはrollback-sensitive old snapshotが意図せず復活しないことを確認する。

### 28.6 resource/real-time

- TLS handshake中BLE操作
- firmware hash中緊急停止
- HMAC/state MAC request burst
- 初回OWNER／GENERAL／OWNER再登録時の認証用の証明データ・AES-GCM配送中の安全要求
- RSIP resource conflict
- 8 request queue full
- 96 byte secret transient上限

安全deadlineを満たすことを測定する。

### 28.7 debug/maintenance

- NORMAL_OPERATIONでSWD/JTAG等の禁止/制限成立
- maintenance UARTで秘密情報dump不可
- 通常software commandからwired programmingへ遷移不可
- wired maintenanceで意図したtrust/登録秘密情報replacementのみ可能
- 時刻管理のTime Update transactionを用いたRTC trust recovery procedure

## 31. セキュリティ横断設計との整合

セキュリティ横断設計は完成済みであり、本書の内部key/crypto方式を再定義せず、システム全体の境界を統合する基準文書として扱う。本章ではレビュー時点の整合結果を示す。

### 31.1 trust boundary

セキュリティ横断設計で少なくとも次の境界が整理されている。

- 利用者 ↔ smartphone app
- smartphone app ↔ BLE link
- BLE module ↔ RA8M2
- RA8M2 ↔ DA16200MOD
- Tank_Robot ↔ Wi-Fi AP/LAN
- Tank_Robot ↔ Internet/VPS
- VPS ↔ management Web app/admin
- external maintenance/debug tool ↔ Tank_Robot
- firmware build/signing environment ↔ release artifact
- provisioning environment ↔ device/VPS/製品ラベル

### 31.2 横断原則との整合

本書はセキュリティ横断設計の次の原則と整合する。

- encrypted / authenticated / authorizedを分離する。
- 通信moduleをtrust rootにしない。
- identity、role、session、Safety Gateを別判断とする。
- 外部入力size/state validationをSecurityだけへ丸投げしない。
- 過去データの不正な再使用、旧セッションの再利用、巻戻しは、各情報の管理担当機能で防止する。
- secretが平文となる範囲を登録時の固定transientへ限定する。
- log/diagnostic/displayへsecretを出力しない。
- boot trust chain：PK_FW_VERIFY→signed metadata→SecurityGen→OTA trial/settlementを維持する。
- device trust chain：VPS trust anchor→server cert、device key/cert→VPS authを維持する。
- 所有者登録の信頼の連鎖は、物理的な登録操作 → BLEの保護された通信路 → 登録処理固有の証明データ → 登録用一時保護鍵 → 端末HMAC鍵 → セッション・役割、という関係を維持する。
- factory reset時のdelete/retain境界を維持する。
- DEVELOPMENT/EVALUATION/NORMAL_OPERATION境界を維持する。
- security処理よりsafety処理を優先する。

GENERAL追加とOWNER再登録も、Just Works linkだけを認証根拠とせず、ticket/recovery secretに由来する現在の取引に結び付けた認証用の証明データと一時AEAD保護を要求することで同じ横断原則へ揃える。

### 31.3 residual risk

セキュリティ横断設計で明示された次の残余riskを本書でも維持する。

1. 製品ラベルの256 bit登録秘密情報は物理的に取得可能なbearer secretであり、漏えい時はwired re-provisioning＋ラベル交換が必要である。
2. debug/write制限を物理的に迂回してcritical MRAM全体を整合した過去snapshotへ戻す高度攻撃は、専用hardware monotonic counterなしでは時系列上完全検出できない。
3. TrustZone partitionを初期必須としていないため、正常署名済みapplication内部のsoftware fault/侵害に対するmodule間隔離は限定的である。
4. online certificate/key rotationを持たないため、VPS credential/trust交換にはwired maintenanceが必要である。

初回OWNER、GENERAL追加、OWNER再登録のいずれもJust Works単独で長期credentialを平文受渡ししないため、登録時active-MITMに対する設計上の依存を減らす。

### 31.4 文書ごとに定める範囲

次は本書または各機能基本設計を基準文書として参照する。

- key length、algorithm、Wrapped Key、登録時の認証用の証明データ／一時AEAD方式：本書
- BLE GATT/session/sequence/登録transport/fragment：BLE接続・認証
- 所有者登録情報・登録成立条件・管理処理：所有者・操作端末管理
- Wi-Fi AP/credential データの意味：Wi-Fi接続
- TLS/HTTPS sequence：VPS接続・デバイス認証
- config apply：設定管理
- log storage/priority：ログ・診断
- OTA install/recovery：OTA更新
- NVM physical journal／commitとデータ管理機能が指定するfallback policyの機械的適用：永続データ管理
- Device ID/Product Data：製品情報管理

セキュリティ横断設計の役割はこれらを再定義することではなく、境界をまたいだ抜け・矛盾・二重信頼を発見することである。

## 32. 初版の自己確認結果と引継ぎ条件

### 32.1 自己確認結果

初版作成後のレビューおよび後続基本設計・セキュリティ横断設計との整合確認を含め、次を確認・修正した。

- 公開用システム要求仕様「20. セキュリティ管理」の全62要求へ主対応章を設定した。
- 公開用システム要求仕様「20. セキュリティ管理」第20.17節の33具体化事項へ基本方式または責任を設定した。
- Security論理機能とセキュリティ横断設計の責任を分離し、参照する基準文書を完成済みセキュリティ横断設計へ更新した。
- 機能別基本設計09～16に加え、製品情報管理のProduct Data、固定ブート・復旧のfixed boot、時刻管理のtime trustの後続契約を本書へ反映した。
- 初回OWNER登録について、物理登録許可＋Secure Connections Just Works＋製品QRの256 bit登録秘密情報による追加認証を必須化し、terminal keyだけでなく所有者復旧用の秘密情報も取引固有AEADで保護配送する方式へ明確化した。
- 所有者・操作端末管理で後続具体化されたGENERAL追加について、128 bit ticket raw照合を行わず、ticketから導出した`K_GENERAL_REG_AUTH`による現在の取引に結び付けた認証用の証明データと`K_GENERAL_REG_SESSION`によるterminal key保護配送を基本設計として確定した。
- 所有者・操作端末管理で後続具体化されたOWNER再登録について、raw recovery secretをBLE送信せず、Wrapped `K_OWNER_RECOVERY_AUTH`による現在の取引に結び付けた認証用の証明データと`K_OWNER_REREG_SESSION`による新OWNER key＋新recovery secret保護配送を基本設計として確定した。
- terminal credentialをCANDIDATE/ACTIVE/REVOKEDで区別し、app receipt＋ownerDataRevision commit＋credential state整合前にACTIVE化しない契約へ所有者・操作端末管理と整合した。
- `K_OWNER_REG_AUTH`を製品固有secretとしてprovisioning時にsecure injectionし、製品ラベルQRとのDevice ID対応を検証し、factory resetで保持する構成を維持した。
- RSIP-E50Dで実装可能なAES-GCM、HMAC-SHA256、ECDSA P-256、TRNG、Wrapped Keyを使用する構成を維持した。
- Wi-Fi credentialをAES-256-GCMで保護し、nonceをprefix＋monotonic revisionで一意化し、最新破損時も古い認証情報へfallbackしないWi-Fi接続のpolicyと永続データ管理の記憶媒体への保存へ整合した。
- `K_SEC_STATE_MAC`をProduct Data、highestCommittedProductDataRevision、Trusted Time/Time Update Recordまで拡張し、dataset domain分離を追加した。
- 設定管理が定めた設定パッケージの内容を入力とし、HMAC計算用バイト列`CONFIG_AUTH_BYTES_V1`の正規化した表現・版管理・符号化方式・HMAC対象範囲は、セキュリティ管理が定める担当関係へ整合させた。
- device certificateをX.509v3/ECDSA P-256/clientAuth/5年基本値、90日前warningとし、基本設計で管理し、評価結果を基に確定する値として明確化した。
- RTC trust loss時の復旧を時刻管理のwired Time Update PREPARED→RTC set/readback→COMMITTED契約へ整合し、妥当そうなRTC値だけでTIME_TRUSTEDへ昇格しない方式とした。
- firmware署名保護metadataへOTA更新/固定ブート・復旧の`bootInterfaceMin/Max`、Product Descriptorおよび互換性summaryを追加した。
- 固定ブート・復旧のfixed bootがapplication Security taskへ依存しないminimum security bootstrapを使用する責任分界を明確化した。
- revoked credential、SecurityGen、config generation、Wi-Fi credential、Product Data、time trustのrollback防止を分けて管理した。
- 工場出荷状態への初期化で保持する対象へ、highestCommittedProductDataRevision、Product Data、時刻信頼情報等を反映した。所有者再登録だけでは、これらを変更しないことを明確化した。
- security event priorityをログ・診断の詳細設計へ丸投げせず、正常拒否とtrust/rollback重大異常の基本priorityを本書で定めた。
- secret transient aggregateを96 byteへ見直し、登録用秘密情報の暗号化転送データとsession keyを固定資源で扱えるようにした。
- security処理がsafety処理をblockしない原則を維持した。
- online certificate rotation、IDS、generic maintenance session等の将来機能を初期製品へ追加していない。

### 32.2 初版完了判断

D-01～D-30は本基本設計で採用する方式として確定する。

E-01～E-24は採用方式・基本設計値の成立性、性能、FSP/RSIP連携、debug lifecycle、provisioningおよび残余riskを確認する実装・実機評価事項であり、初版基本設計を停止するユーザー判断待ち事項ではない。

第31章は完成済みセキュリティ横断設計との分担範囲・整合結果であり、本書のSecurity論理機能設計を未決定のまま後続へ先送りするものではない。

BLE接続・認証には、所有者・操作端末管理およびセキュリティ管理で確定した初回OWNER登録・GENERAL追加・OWNER再登録の認証用データ、保護された秘密情報の配送、アプリによる受領確認、論理データ最大96 byte・最大3分割、および管理処理と接続に依存する状態の有効期間の分離を、XR-002で反映済みである。

Wi-Fi設定の分割通信は、XR-003で反映済みである。BLE接続・認証の99 byte・最大4分割・10秒の上限を維持し、接続・セッション変更時は秘密情報をゼロで上書きして消去する。完全な設定を受信した後だけWi-Fi接続へ渡す。

状態通知の世代管理とBLE通信形式の担当は、BLE接続・認証基本設計 §10.10および状態表示・利用者通知基本設計の現行の規則に従う。

具体的RSIP API、FSP/Mbed TLS stack設定、DLM/AL値、certificate DER/CSR tool、provisioning script、security event ID、wire-formatの最終offset等は、基本方式を変更しない範囲で詳細設計・評価へ委ねる。

現時点で、セキュリティ管理基本設計の初版完了を妨げるユーザー判断待ち事項は残していない。

## 1. 設計方針

**位置付けと目的**

- **位置付け**：[「セキュリティ横断設計」](Tank_Robotセキュリティ横断設計.md)を補完する補足設計書
- **目的**：スマートフォンの認証情報のバックアップ・同期・端末移行方針と、DA16200MOD内部のWi-Fi認証情報の保持方針を基本設計として確定する

システム全体のセキュリティ境界はセキュリティ横断設計、OWNER／GENERAL登録・失効・OWNER再登録は所有者・操作端末管理基本設計、認証情報のライフサイクル・暗号処理はセキュリティ管理基本設計、Wi-Fi接続状態・DA16200MOD制御はWi-Fi接続基本設計に引き続き従う。本書は、これらにまたがるバックアップ・同期・モジュール内NVRAMの利用方針だけを補完する。

本書による補完前のセキュリティ横断設計 §8.2、§10.4、§26.2項2およびWi-Fi接続基本設計 §8.4、§18.3、§23.2 E-07に、device-only／backup／syncまたはmodule NVRAM利用可否を後続設計・評価で新規選択する記述が残る場合、本書の補完対象については本書を優先する。

**設計方針**

初期製品では次を採用する。

1. スマートフォン側の長期認証情報は**iCloud等による端末間同期を行わない**。
2. スマートフォン側の長期認証情報は**端末のバックアップから別端末へ自動移行しない**。
3. 新しいスマートフォンを使用する場合、旧端末の認証情報を複製してそのまま認証端末として扱わず、既存の登録／再登録／保守手順に従う。
4. Wi-Fi設定の現在の正式値はRA8M2側でセキュリティ管理/永続データ管理の保護・永続化を正常完了した設定だけとする。
5. DA16200MOD内部NVRAMへSSID／認証情報／自動接続情報が保存されることは許容するが、**それをWi-Fi設定の使用可否を決める情報として扱わない**。
6. DA16200MOD内部に残る情報だけを根拠としてAPへ自動接続しない。

## 2. スマートフォンに保存する認証情報の扱い

### 2.1 保護対象

本方針では、少なくとも次の情報を保護対象とする。

- **端末の長期認証鍵**（terminal long-term key）
- **所有者復旧用の秘密情報**（OWNER recovery secret）
- 認証情報を使用するために必要な機体・端末の識別情報のうち、セキュリティ状態を直接成立させる情報

初回OWNER登録用QRの秘密情報そのもの、GENERAL登録チケット、登録用セッション鍵など、登録処理中だけ使用する一時的な秘密情報は、従来どおり取引終了後に保持しない。

### 2.2 複数端末への同期

端末の長期認証鍵および所有者復旧用の秘密情報は、iCloud Keychain等を利用した複数端末間の同期対象にしない。

同じApple ID等を使用する別のスマートフォンへ、これらの秘密情報を自動的に複製しない。

### 2.3 バックアップからの復元

端末の長期認証鍵および所有者復旧用の秘密情報は、端末バックアップを別のスマートフォンへ復元したときに自動移行させない。

画面設定、Device IDの表示情報、その他の秘密ではない情報がバックアップから復元されても、それだけで新しいスマートフォンをOWNER／GENERALとして認証しない。

スマートフォンの後続設計では、これらの秘密情報に、**端末から別端末へ移行させない保存属性（`device-only`相当）**を使用する。
具体的なKeychain API、accessibility属性、access group等は実装レベルで選定する。

### 2.4 新しいスマートフォンを使用する場合

新しいスマートフォンをTank_Robotで使用する場合は、次の原則に従う。

1. 旧端末の長期認証鍵を複製して、新端末へ移さない。
2. 旧端末の所有者復旧用の秘密情報をバックアップから新端末へ複製し、通常認証へ使用しない。
3. 新端末では、既存のOWNER／GENERAL登録またはOWNER再登録の正規手順を実行する。
4. 現在のOWNER端末が利用可能な計画的移行では、既存の登録・再登録手順を利用して、新しい認証情報を発行する。
5. 現在のOWNER端末を紛失し、所有者復旧用の秘密情報も利用できない場合は、秘密情報の複製による救済を行わない。既存の工場初期化または権限を確認した保守手順など、製品保守の経路へ移る。

具体的にどの画面から端末移行を開始するかはスマートフォンアプリ基本設計で定める。
古い認証情報の複製を、新端末への移行方式として採用しない。

### 2.5 バックアップ復元後の権限確認

アプリのバックアップから画面設定、Device IDの表示情報、その他の秘密ではない情報が復元された場合でも、本体側で現在有効な認証情報と登録状態を再確認する。

確認には少なくとも次を使用する。

- 所有者・操作端末管理が管理する端末登録枠と`ownerDataRevision`
- セキュリティ管理が管理する`credentialState`
- BLE接続・認証が管理する現在の認証・セッション状態

復元されたアプリ内部の状態だけで、OWNER／GENERAL権限を成立させない。

### 2.6 失効済み端末の扱い

一度`REVOKED`となった端末の認証情報を、バックアップからの復元、端末移行、OSの再設定等によって`ACTIVE`へ戻さない。

新端末を使用する場合は新しい認証情報を発行し、本体側で現在確定している端末登録情報と認証情報の状態に従う。

## 3. DA16200MOD内部NVRAMに残るWi-Fi接続設定の扱い

### 3.1 RA8M2側を唯一の正式な管理元とする意味

Wi-Fi設定について「RA8M2側を唯一の正式な管理元とする」とは、次を意味する。

- 現在使用してよいSSID／security mode／passphraseは、RA8M2側でセキュリティ管理による保護と永続データ管理による保存確定が正常完了した、現在のWi-Fi設定から決定する。
- DA16200MOD内部にSSIDや認証情報などの接続設定が残っていても、それだけを理由として現在のWi-Fi設定とは判断しない。
- DA16200MOD内部の値とRA8M2側の現在設定が異なる場合は、RA8M2側を正とする。
- DA16200MOD内部の古い接続設定をRA8M2側へ取り込み直し、現在設定へ昇格させない。

### 3.2 モジュール内部への保存を許容する範囲

DA16200MODの標準Host／AT方式で、Wi-Fi接続設定（profile）がモジュール内部NVRAMへ保存される場合、その保存自体は初期製品で許容する。

ただし、モジュール内部NVRAMの設定は、接続処理に必要な**モジュール内の接続設定**として扱う。
製品として正式に使用するWi-Fi認証情報の管理元や、古い設定へ戻すための復旧元としては扱わない。

### 3.3 起動時の自動接続禁止

DA16200MODの起動、RESETまたは電源再投入時に、モジュール内部NVRAMに残る設定だけを根拠として過去のアクセスポイントへ自動接続する状態を許可しない。

Wi-Fi接続の初期化では、少なくとも次を成立させる。

1. モジュールとのホスト通信を確立する。
2. 意図しない自動接続を禁止または無効化したことを確認する。
3. RA8M2側の現在のWi-Fi設定が有効であることを確認する。
4. Wi-Fi利用要求がある場合だけ、現在の設定に基づいて明示的に接続を開始する。

RA8M2側に現在のWi-Fi設定が存在しない場合、モジュール内部NVRAMに過去の接続設定が残っていてもアクセスポイントへの接続を開始しない。

### 3.4 Wi-Fi設定変更時

新しいWi-Fi設定を正式化するときは、RA8M2側でセキュリティ管理による保護と永続データ管理による保存確定が成功したことを、現在の正式値とする判定根拠とする。

その後、DA16200MODへ必要な接続設定を反映する。

モジュール側に古い接続設定が残る場合でも、その設定を自動的な代替接続先として使用しない。

新しい設定による接続確認が失敗しても、モジュール内部NVRAMに残る古いSSID／passphraseへ自動的に戻さない。

### 3.5 認証情報失効・工場初期化

Wi-Fi認証情報の失効、Wi-Fi設定削除、工場初期化では、既存のWi-Fi接続、セキュリティ管理、永続データ管理の契約に従って次を実施する。

- RA8M2側の現在のWi-Fi設定を利用不能化または削除する。
- 旧`wifiCredentialRevision`を現在値へ戻さない。
- 必要な`K_WIFI_STORE`／nonce prefix／key epochを更新する。
- DA16200MOD内部の旧SSID、認証情報、自動接続情報を削除、上書きまたは利用不能化する。
- モジュール内部NVRAMから古いネットワークへ自動接続させない。

### 3.6 モジュール内部の古い設定を無効化できない場合

DA16200MOD内部の古い認証情報または自動接続状態を、消去・上書き・利用不能化できたことを確認できない場合、Wi-Fi機能を正常利用可能とは扱わない。

少なくとも次を行う。

- Wi-Fi接続は新しいアクセスポイントへの接続開始を許可しない。
- 異常管理へ、Wi-Fiモジュール内に残る認証情報・接続設定を無効化できない異常候補として通知する。
- 必要に応じてDA16200MODのRESETまたは電源再投入を実施するが、それだけで無効化成功とはみなさない。
- RA8M2側に現在設定がない状態で、モジュールに残る古い接続設定から接続できた場合でも、正常状態へ昇格させない。

詳細設計でも、モジュール内の古い設定を無効化できたことを確認できないまま、「通信できるため使用する」という方式を追加しない。

### 3.7 モジュール内部NVRAMに認証情報が残ることの残余リスク

初期製品ではDA16200MODをTrust RootまたはWi-Fi認証情報の正式な管理元にしない一方、モジュール内部NVRAMに接続用認証情報の複製が物理的に残る可能性を受容する。

この残余リスクは次の方法で制限する。

- モジュールを、通常の外部インターフェースから認証情報を読み出す装置として提供しない。
- 保守・診断経路から平文のWi-Fi認証情報を出力しない。
- 工場初期化または認証情報失効時に、モジュール側の接続設定を消去または無効化する。
- 自動接続を禁止する。
- RA8M2側の現在設定と不一致の場合に、モジュール側の設定を優先しない。

将来、モジュールのファームウェアまたは構成によって、認証情報を不揮発保存しない運用を低工数で実現できる場合は、セキュリティ強化候補として検討してよい。
初期製品の必須条件にはしない。

## 4. 責任分界

### 4.1 セキュリティ横断設計

セキュリティ横断設計は次を横断policyとして所有する。

- Smartphone credentialの端末間sync禁止
- Smartphone credentialのbackupによる別端末自動移行禁止
- credential複製によらない端末移行・復旧原則
- untrusted Wi-Fi moduleへcredential copyが存在する場合のtrust boundary

### 4.2 所有者・操作端末管理

所有者・操作端末管理は次を所有する。

- OWNER／GENERAL登録・失効
- OWNER再登録
- `ownerDataRevision`
- terminal slot lifecycle
- factory reset transaction

Smartphone backup／restoreだけを理由としてterminal slotをACTIVEへしない。

### 4.3 セキュリティ管理

セキュリティ管理は次を所有する。

- terminal credential／OWNER recovery 認証情報のライフサイクル
- credential state
- Wi-Fi credential保護
- `K_WIFI_STORE`
- `wifiCredentialRevision`
- key／nonce epoch

### 4.4 Wi-Fi接続

Wi-Fi接続は次を所有する。

- DA16200MOD初期化
- auto-connect禁止確認
- 現在のRA8M2 Wi-Fi設定に基づく接続開始
- module NVRAM profileの削除／上書き／利用不能化
- cleanup失敗時のWi-Fi利用禁止

### 4.5 スマートフォンアプリ後続基本設計

スマートフォンアプリ側は本書のpolicyを変更せず、次を具体化する。

- Keychain等の具体storage API
- device-only相当属性
- synchronizable=false相当設定
- UI上の端末登録／再登録導線
- backup restore後のlocal cache cleanup
- secret zeroize

## 5. 詳細設計へ残す範囲

次は基本設計上の意味を変えない実装事項として詳細設計へ残す。

- Keychain API名／accessibility属性の具体値
- access group
- OS API error mapping
- App内credential wrapper class
- DA16200MOD AT command sequence
- module profile index
- NVRAM消去／disable確認command
- temporary UART buffer
- zeroize実装
- retry／timeout実装
- diagnostic event ID

次は詳細設計だけで変更しない。

- terminal long-term keyのiCloud同期禁止
- OWNER recovery secretのiCloud同期禁止
- 両credentialのbackup経由別端末自動移行禁止
- backup restoreだけで権限を復活させない
- RA8M2側の現在のWi-Fi設定だけを使用可否の判定基準とする
- DA16200MOD NVRAMを現在設定／rollback sourceにしない
- module起動時auto-connect禁止
- credential失効／factory reset時のmodule profile消去・無効化
- cleanup確認不能時のWi-Fi利用禁止

## 6. 検証方針

少なくとも次を確認する。

1. 同一Apple ID等の別端末にterminal key／OWNER recovery secretが自動同期されない。
2. 端末backupから新端末へ復元しても、旧terminal credentialで通常認証できない。
3. local app cacheが復元されても本体の現在のrole／credential確認なしでOWNER／GENERAL扱いしない。
4. revoked terminalをbackup restoreで復活できない。
5. DA16200MOD NVRAMに旧AP profileが残る条件でも、RA8M2側に現在設定がなければAPへ自動接続しない。
6. RA8M2側の現在設定A、module残存設定Bの不一致時にBへ接続しない。
7. Wi-Fi設定変更後、新設定失敗を理由として旧module profileへ自動fallbackしない。
8. factory reset後に旧SSID／credential／auto-connectで通常接続しない。
9. module profile cleanup失敗を検出した場合、Wi-Fi利用可能へ昇格しない。
10. module reset／power cycleだけでcleanup成功と誤判定しない。

本書はGR-08対象の補足設計書としてそれら旧記述より優先する。

本書で確定したbackup／sync／module NVRAM policyを詳細設計事項へ戻さない。

本書により、Smartphone credentialのsync／backup／端末移行方針、restore後の権限扱い、DA16200MOD NVRAMの位置付け、auto-connect、factory reset／失効、cleanup失敗時のfail-safeを基本設計として確定した。

詳細設計担当者がcredential複製可否またはmodule NVRAMを正式な管理元／fallbackとして扱うかを新規選択する必要はない。

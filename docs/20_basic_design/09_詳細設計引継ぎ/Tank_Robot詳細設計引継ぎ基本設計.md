## 1. 本書の目的

### 1.1 目的

本書は、基本設計から詳細設計への引継ぎ区分を横断的に整理する基準文書とする。各事項を定める基本設計で確定済みの事項を詳細設計の再判断事項へ戻さず、詳細設計で具体化してよい実装範囲を統一する。

本書は、基本設計一式に残る旧「詳細設計で決定する」「評価後に方式を決める」「後続基本設計で決める」という記述のうち、すでにその事項を定める基本設計または補足設計書で確定済みとなった事項を再分類する。

### 1.2 対象範囲

本書は、「Tank_Robotシステム構成」、「走行制御基本設計」、「固定ブート・復旧基本設計」、「セキュリティ横断設計」、および外部API、RTCの保持継続確認・時刻復旧、永続データ、未報告OTA結果、認証情報のバックアップ、Wi-Fi設定文字列、スマートフォンのBLE復旧・操作の補足設計書で確定済みとなった、旧引継ぎ記述を対象とする。

本書では機能固有の値、状態、通信、Security、Safety、保存方式その他を新しく決定しない。機能の意味と値は、引き続き各事項を担当する基本設計の定義に従う。本書は、**詳細設計へ何を引き継ぐかという分類だけを横断的に定める。**

### 1.4 文書の優先順位

**本書と関連文書の適用範囲**

1. **本書が定める事項**：システム構成、走行制御、固定ブート・復旧、セキュリティ横断設計、および本書3～9章に示す確定済み事項の詳細設計への引継ぎ区分。
2. **関連文書が引き続き定める事項**：本書が明示的に補完する事項、または文書間で共通の規則として確定する事項以外は、本書で挙げる関連する基本設計の担当範囲と変更責任を維持する。
3. **本書を優先する場合**：上記の事項について本書で基本設計として確定した記述と、当該事項への対応前の旧記述が競合する範囲に限る。対応経緯と、比較基準の版がある場合の識別情報は、末尾の「作成経緯」に示す。
4. **本書を優先しない事項**：詳細設計へ残す内部実装、および補完対象外の状態、機能の動作、安全、セキュリティ、外部との通信・連携規則などは、それぞれを担当する基本設計に従う。

詳細設計へ引き継ぐ際は、次の順序で解釈する。

1. 製品目的・公開用システム要求仕様。
2. 現行の定義元の基本設計および補足設計書。
3. 本書の詳細設計引継ぎ分類。
4. GR対応前から残る各文書の「詳細設計事項」「後続確認」「評価後決定」等の一覧。

4に記載された内容が1～3と矛盾する場合、4の旧分類を無効とし、1～3を使用する。

### 1.5 詳細設計で再決定してはならない事項

次は詳細設計へ新規判断として渡さない。

- 利用者から見た操作、受付、拒否、再接続、復旧または表示の基本挙動。
- 安全性・セキュリティの成立条件、信頼境界、巻戻し・過去データの再使用への対処方針。
- 外部インターフェースの意味、必須項目、一連の処理、ACK、冪等性、セッションの扱い。
- 起動、OTA、工場出荷状態への初期化、永続データ復旧の方針。
- その事項を定める基本設計で確定した型、値域、初期値、予約値、世代更新条件、周回時の扱い。
- 評価による確定待ちであっても、方式、担当機能、未確定時の制限、評価不成立時に見直す文書が、基本設計で決定済みの事項。

### 1.6 詳細設計へ引き継いでよい事項

次は、基本設計の意味を変えない範囲で詳細設計に委ねる。

- C/C++構造体、関数、モジュール、Process、コールバック、ドライバAPIへの対応付け。
- 原子的な更新、クリティカルセクション、スナップショットの公開、キュー・保存枠の内部実装。
- バイトバッファ、構文解析、シリアライズ、検証コード、エスケープ・引用符の処理。
- タイマ・カウンタ、FSP/RSIP/CoreBluetooth等のAPIへの対応付け。
- レジスタ、ピン、コネクタ、PCB配線、部品型式、回路定数。
- DBテーブル・インデックス、Webフレームワークのルート・コントローラ、cookie・tokenの具体的な符号化方式。
- イベントIDの具体的な数値、内部enum値、ログの符号化方式。
- 基本設計で許容された範囲内の評価用計測処理、測定・試験の実装。

## 2. 詳細設計へ引き継ぐ事項の分類

### 2.1 システム構成

#### 状態表示部

システム構成の電源LED、RGB LED、2桁7セグ表示器を「基本方式も未確定」とは扱わない。

基本設計確定済み事項は次とする。

- 状態表示部は電源LED、RGB LED、2桁7セグ表示器で構成する。
- Application動作中の表示電源は`PWR_DISPLAY`として電源・省電力管理/電源・ハードウェア基本設計の契約に従う。
- 状態表示・利用者通知が表示内容の意味、優先順位、RGB pattern、indicatorCodeおよびfixed boot early indicationの意味を定める。
- 固定ブートでは状態表示・利用者通知の`EARLY_IND`契約を使用し、Applicationへの引継ぎ前後で、二つの機能が同時に表示を書き換えない。

詳細設計へ引き継ぐ事項は、LED／7セグの具体型式、driver IC、multiplex方式、pin、電流制限、配線、mechanical visibilityおよび状態表示・利用者通知/電源・ハードウェア基本設計の契約を実現するdriver実装とする。

したがって、システム構成 §6～7に残る「電源LED、RGB LED、2桁7セグ表示器の基本方式を含め未確定」という読み方は失効し、**基本方式確定／具体部品・物理接続詳細待ち**と解釈する。

#### 独立走行停止経路

独立した走行停止経路を設けること自体は確定済みであり、詳細設計で採否を再判断しない。

詳細設計へ引き継ぐのは、電源・ハードウェア基本設計の契約を満たすdriver enable、high-side cutoffその他の具体的物理方式、回路、read-back、部品、配線および故障評価である。

システム構成の「hardware enableまたは`PWR_DRIVE` high-side cutoffのどちらで最終実装するか」は物理実装選択としてのみ残し、「独立停止を設けるか」という方式未決定には戻さない。

### 2.2 走行制御

走行制御基本設計 §5.5で定めた`driveEpoch`の意味は基本設計確定事項とする。

確定済み事項：

- 本体アプリケーションの同一起動内でのみ有効 `uint32`。
- 0は未確立／無効として予約。
- 初回有効値は1。
- 単調更新。
- 同一BLE operation session内でwrapまたは値を再利用しない。
- 次回更新で`0xFFFFFFFF`を超える場合は現行sessionを失効し、再認証後の新しいセッションで再初期化する。
- 更新契機とBLE接続・認証への公開意味は走行制御/BLE接続・認証/インターフェース・通信基本設計の現行契約に従う。

したがって走行制御基本設計 §19.3等に残る「具体型、0予約、初期化、wrap処理を詳細設計で決める」という旧分類は失効する。

詳細設計へ引き継ぐのは、`driveEpoch`の原子的な更新方法、スナップショットの公開方法、クリティカルセクション、メモリ操作の順序保証（memory ordering）、BLE接続・認証への内部APIの対応付け、および通信データの項目と照合する実装である。

### 2.3 固定ブート・復旧

固定ブート・復旧基本設計 §28.5等に残る、固定ブートでの最小限の起動エラー表示を、「後続設計で方式を選択する事項」とは扱わない。

基本設計で確定済みの事項は、次のとおりである。

- アプリケーション起動前に固定ブートが行う初期表示には、状態表示・利用者通知の`EARLY_IND`契約を使用する。
- `PWR_DISPLAY`と、固定ブートから本体アプリケーションへ表示の書込み責任を移管する方法は、電源・ハードウェア基本設計に従う。
- アプリケーションへの分岐前に、初期表示のタイマ・ISRを停止する。本体アプリケーション側が表示HALを再初期化できるように引き継ぐ。
- `EARLY_IND`の表示失敗だけを、起動・復旧を進めるための判断条件にしない。

詳細設計へ引き継ぐのは、LED/7segのドライバ、表示パターンの具体的な時間制御、ピン、タイマ・ISR、引継ぎ用のレジスタ・状態の実装、および表示失敗の診断である。

## 4. RTCの保持継続確認・時刻復旧の引継ぎ

`50_基本設計/03_機能別基本設計/20_時刻管理/RTC継続性・時刻復旧契約基本設計.md`を、RTCの保持継続確認と時刻復旧を定める補足設計書として使用する。

時刻管理/電源・ハードウェア基本設計/システム構成/性能・品質・検証基本設計等に次の旧分類が残る場合、GR-05対象について失効する。

- RTCのバックアップ電池を、初期製品で必須としない。
- 主バッテリーの取外しだけで、RTCの継続性を失う。
- RTCの保持継続を確認する方式を、詳細設計で新規に選択する。
- 保持継続の確認結果が不明でも、詳細設計の判断でTRUSTEDにできる。
- `TIME_UNTRUSTED`からの正式な復旧経路を、製造時設定ツール、保守ツール、保守専用ビルド等から、詳細設計が新規に選択する。

基本設計で確定済みの事項は、RTC専用の交換可能な3 Vコイン型一次電池、`RTC_CONTINUITY_EVIDENCE`、継続性を示すマーカー、確認結果が不明な場合はTRUSTEDにしないこと、`AUTHORIZED_WIRED_TIME_RECOVERY`、および時刻管理が定めるTime Updateの更新処理を使用することである。

詳細設計へ残すのは、具体的な電池・ホルダ、ORing回路、RTCレジスタ、マーカーのビット配置、UARTコマンドの符号化方式、FSP API等である。

**レビュー履歴**：GR-05で、RTC継続性と時刻復旧の確定事項を再分類した。

## 6. 未報告OTA結果の引継ぎ

`50_基本設計/03_機能別基本設計/15_OTA更新/OTA結果保留・次回受付契約基本設計.md`を、未報告OTA結果の保持と次回OTA受付条件を定める補足設計書として使用する。

OTA更新や永続データ管理に残る「新しいOTA開始可否はOTA更新が判断する」という記述だけを根拠に、具体的な受付規則が未定とは扱わない。

次は基本設計で確定済みとする。

- `PENDING`中は、新しいOTA更新処理を開始しない。
- 未報告の最終結果は、論理的に1件保持する。
- 期限切れ、自動削除、および新しい結果による上書きを行わない。
- VPSが同じ論理的な結果を正常に受領したことを確認し、`SENT`となった後だけ、次のOTA更新を許可する。

詳細設計へ残すのは、レコードの配置、再送スケジューラ、要求IDの生成、および記憶媒体への保存方法の対応付け等である。

**レビュー履歴**：GR-07で、未報告OTA結果の保持・再送・次回受付条件を再分類した。

## 7. 認証情報のバックアップとWi-Fiモジュールの情報保持の引継ぎ

`50_基本設計/06_セキュリティ横断設計/Tank_Robot資格情報バックアップ・Wi-Fiモジュール保持方針基本設計.md`を、スマートフォン認証情報の移行とWi-Fiモジュール内の情報保持を定める補足設計書として使用する。

セキュリティ横断設計 §8.2、§10.4、§26.2項2、Wi-Fi接続基本設計 §8.4、§18.3、§23.2 E-07等に、backup/sync/module NVRAM policyを後続設計・評価で新規選択するとした記述が残る場合、その分類を失効する。

基本設計確定済み事項はterminal long-term keyとOWNER recovery secretをiCloud同期・別端末自動移行しないこと、Wi-Fi設定の使用可否はRA8M2側の現行設定を基準とし、DA16200MOD NVRAMを独立した正式な管理元にしないことである。

詳細設計へ残すのは、Keychain APIへの対応付け、DA16200 AT command、接続設定の削除／無効化／読戻し、エラー処理等である。

**レビュー履歴**：GR-08で、認証情報のバックアップ・移行とWi-Fiモジュール内情報の扱いを再分類した。

## 8. Wi-Fi設定文字列の引継ぎ

`50_基本設計/03_機能別基本設計/11_Wi-Fi接続/Wi-Fi設定文字列受理契約基本設計.md`を、Wi-Fi設定文字列の受理条件を定める補足設計書として使用する。

Wi-Fi接続基本設計 §23.2 E-09、§23.3等に、SSID／passphraseの文字集合・encoding・最終受理条件を実機評価後に初めて決定するとした旧分類が残る場合、その分類を失効する。

初期製品の受理契約は表示可能ASCII、SSID 1～32 byte、passphrase 8～63 byte、trim/normalization/置換/切詰めなし、制御文字・非ASCII不許可で確定済みである。

詳細設計へ残すのは、validation code、ATのquote／escape処理、一時バッファ、zeroize、およびUI入力component実装である。実機評価は採用済み契約の成立性確認であり、文字集合を詳細設計の判断だけで変更しない。

**レビュー履歴**：GR-09で、Wi-Fi設定文字列の受理条件を再分類した。

## 9. スマートフォンのBLE復旧・操作の引継ぎ

`50_基本設計/04_インターフェース・通信/Tank_RobotスマートフォンBLE復旧・操作契約基本設計.md`を、スマートフォンのBLE再接続・操作再開条件を定める補足設計書として使用する。

BLE接続・認証基本設計 §14.4、§19.5、§23.1、砲塔・砲身制御基本設計 §4.7、§19.1、§20.2、インターフェース・通信基本設計 §23.6／§24.3等に、スマートフォンアプリ基本設計で再接続回数・間隔、送信queue、ARM UXを新規決定するとした旧分類が残る場合、その分類を失効する。

基本設計確定済み事項は、foregroundのみ有限自動再接続、最大3回、0/1/2秒backoff、総期限10秒、旧操作非再開、`BARREL_TARGET` latest-one、両軸まとめた明示ARM、auto ARM/auto re-ARM禁止である。

詳細設計へ残すのは、CoreBluetooth callback、timer／再試行待ち時間の実装、sliderのdebounce／throttle、queue／slot内部実装、UI widget・画面遷移等である。

**レビュー履歴**：GR-10で、BLE再接続・操作再開の確定事項と詳細設計事項を再分類した。

## 10. 評価確定待ちとの区別

GR-12による分類の整理を理由に、評価による確定待ちの値を「確定済み」として公開しない。

評価確定待ちの横断追跡は`03_機能別基本設計/00_懸案事項.md`の`BD-EVAL-*`を使用する。

次の区分を維持する。

- **基本方式確定＋正式値評価待ち**：担当機能が定める暫定値・制限の範囲内で、詳細設計を進められる場合がある。正式値を変更する場合は、その事項を定める基本設計へ戻す。
- **基本設計確定済み**：詳細設計では意味・方針を再判断せず、内部実装だけを具体化する。
- **未解決**：方式・責任・外部挙動の判断が残っている。詳細設計だけで決定しない。

GR-12は2番目の事項が古い一覧で1番目または3番目のように読める問題を解消するものであり、真の評価確定待ちを削除するものではない。

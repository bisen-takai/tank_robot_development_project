## 2. BLE自動再接続

### 2.1 採用範囲

スマートフォンアプリは、通常操作対象として選択中のTank_RobotとのBLE接続が予期せず失われた場合、自動再接続を行う。

自動再接続の目的は利用者が短時間の通信断から復帰しやすくすることであり、通常操作を継続させることではない。

切断検出時点で、既存要求およびBLE接続・認証の契約どおり次を直ちに行う。

- 通常操作指令の送信を停止する。
- 操作UIを利用不可とする。
- 未送信通常操作を破棄する。
- 旧`sessionId`を再利用しない。
- 旧`connectionGeneration`に属する認証・状態をcurrentとして扱わない。

### 2.2 自動再接続を開始する条件

次をすべて満たす場合だけ自動再接続を開始する。

- 切断が利用者の明示的な切断操作によるものではない。
- スマートフォンアプリが前面表示かつactiveである。
- 画面ロック中ではない。
- 操作対象Tank_Robotが変更されていない。
- スマートフォンアプリ終了処理中ではない。
- 利用者が再接続を取消していない。
- 対象端末の長期credentialがスマートフォンアプリ側で利用可能である。

前記条件を満たさない場合は自動再接続を開始しない。

### 2.3 試行回数とbackoff

自動再接続transactionは最大3回の接続試行とする。

| 試行 | 開始時のbackoff |
| --- | ---: |
| 1回目 | 0秒 |
| 2回目 | 1秒 |
| 3回目 | 2秒 |

backoffは直前試行が失敗として完了した後に適用する。複数のBLE接続試行を並列に開始しない。

### 2.4 総期限

自動再接続transactionの総期限は、最初の再接続開始から**10秒**とする。

- 10秒経過後に新しい自動試行を開始しない。
- 3回未満でも総期限到達で終了する。
- 3回すべて失敗した場合は10秒未満でも自動再接続を終了できる。
- OS／CoreBluetooth側の一回の接続処理が残っていても、スマートフォンアプリは10秒超過を通常操作復旧待ちとして無期限継続しない。

この10秒は公開用システム要求仕様「22. 性能・品質・耐久性」/BLE接続・認証の自動再接続性能条件と整合させる。

### 2.5 自動再接続の成功条件

BLE link再確立だけでは自動再接続成功としない。

次をすべて完了した時点を成功とする。

1. 新しいBLE link確立。
2. Bluetooth LE Secure Connections／必要なlink security成立。
3. BLE接続・認証のアプリケーション層認証成功。
4. 現在のterminal role／permission確認。
5. 現在の`connectionGeneration`／session確立。
6. 現在のシステム状態／operation availability／`actuationEpoch`等の必要状態再取得。
7. 取得情報が現在のsnapshotとして整合することを確認。

成功前は通常操作UIを有効化しない。

### 2.6 自動再接続の中止条件

次のいずれかで自動再接続を即時中止する。

- 利用者が「再接続を中止」を選択。
- スマートフォンアプリがbackground、inactive、画面lockへ移行。
- スマートフォンアプリ終了。
- 操作対象Tank_Robot変更。
- 対象credentialが利用不能／失効と判明。
- 認証結果がretry継続不適当な明示拒否となった。
- factory reset、端末失効等により旧terminal identityがcurrentでないと判明。
- BLE接続・認証/所有者・操作端末管理/セキュリティ管理のセキュリティ上の連携規則により、同じcredentialで再試行してはならない条件が成立。

単なるradio timeout／一時的接続失敗は、回数・期限内なら次試行対象にできる。

### 2.7 foreground／background

自動再接続はスマートフォンアプリ前面表示中だけ行う。

background移行、画面lock、非active化、他アプリへの切替えを検出した場合は、進行中の自動再接続transactionを終了し、通常操作復帰を継続しない。

スマートフォンアプリが再び前面表示となった場合、旧自動再接続transactionを再開せず、current接続・認証・状態を再確認する。必要なら利用者の明示的な再接続操作から新しい接続処理を開始する。

### 2.8 自動再接続失敗後

最大3回または総期限10秒で成功しなかった場合、スマートフォンアプリは自動retryを停止する。

- 「本体との接続が切れています」等の状態を表示する。
- 「再接続」等の明示操作を提供する。
- 利用者操作なしに時間経過だけで再び自動retryを開始しない。
- 旧通常操作を送信待ちとして保持しない。

スマートフォンアプリ再起動または操作対象再選択後の通常接続処理は、新しい接続transactionとして扱う。

### 2.9 再接続後の操作再開禁止

自動再接続成功後も、次を自動再開しない。

- 走行入力
- 砲塔左右継続操作
- 砲身目標操作
- 通常停止以外の旧操作要求
- ARM要求
- 管理操作transaction

通常操作は、再接続・再認証・current状態取得後に利用者が新しく入力した操作だけを送信する。

砲塔・砲身制御が砲塔・砲身を未ARMと報告する場合は、第4章のARM操作完了まで砲塔・砲身操作を有効化しない。

## 3. `BARREL_TARGET`送信待ち契約

### 3.1 基本方針

スマートフォンアプリは、砲身スライダ等の連続入力により複数の`BARREL_TARGET`が短時間に生成された場合、未送信目標をFIFOへ蓄積しない。

**未送信の`BARREL_TARGET`は最新1件だけ保持する。**

新しい砲身目標が入力された場合、まだBLE送信へ引き渡していない古い目標を新しい値で置換する。

### 3.2 保持件数に上限のある送信状態

初期製品では、少なくとも次の保持件数上限を満たす。

- BLEへ引渡し中の`BARREL_TARGET`：最大1件。
- その後に発生した最新の未送信目標：最大1件。
- 3件以上のFIFOキューを作らない。

BLEへ引渡し済みの1件を実装上取り消せない場合でも、その後に発生した複数の入力は最新1件にまとめる。

本体の砲塔・砲身制御は`commandSeq`、`actuationEpoch`およびlatest command slotにより新旧を判断するため、スマートフォンアプリは過去値を順番に再送して追いつこうとしない。

### 3.3 失効条件

次のいずれかで未送信`BARREL_TARGET`を破棄する。

- BLE切断。
- `connectionGeneration`変更。
- session終了／再認証開始。
- `authorizationRevision`変更。
- `actuationEpoch`変更。
- 砲塔・砲身制御が砲身操作不可／未ARMを通知。
- 安全停止／緊急停止／終了／省電力移行。
- スマートフォンアプリがbackground／inactive／画面lockへ移行。
- 操作対象Tank_Robot変更。
- 通常操作画面から離脱。

失効後、再許可されたときに破棄済み目標を自動送信しない。

### 3.4 再送

transport retryが必要な場合も、旧セッション／古い操作世代に属する`BARREL_TARGET`を新しいsessionへ持ち越さない。

同一現在のcontext内のtransport retryはBLE接続・認証の重複・連番規則に従う。スマートフォンアプリ詳細設計でretry queueを無制限化しない。

### 3.5 送信周期

砲身スライダの具体debounce／throttle値は詳細設計へ残す。

ただし次を満たす。

- 公開用システム要求仕様「22. 性能・品質・耐久性」/砲塔・砲身制御の通常操作応答150 ms総合条件を満たす。
- latest-one規則を維持する。
- Safety通信を遅延させない。
- 通信混雑時に古い目標をFIFO蓄積しない。

## 4. `MANUAL_DATUM_ARM` スマートフォン操作契約

### 4.1 基本方針

砲塔・砲身制御で採用済みの`MANUAL_DATUM_ARM`をスマートフォンアプリの正式なサーボ動作許可手順とする。

スマートフォンアプリは、未ARMの砲塔・砲身を通常操作可能に見せない。

初期製品では利用者手順を単純化するため、スマートフォンアプリからの通常ARM操作は**砲塔・砲身の両軸をまとめて準備する一つの操作**とする。

砲塔・砲身制御の内部のaxis識別は維持するが、初期製品のスマートフォンアプリは通常UIから一軸だけを独立ARMする操作を提供しない。

### 4.2 ARMが必要な状態

少なくとも砲塔・砲身制御が`OFF_UNREFERENCED`、`OFF_INHIBITED`その他の未ARM状態を報告する場合、スマートフォンアプリは砲塔・砲身操作を無効化し、「準備が必要」であることを表示する。

砲塔・砲身制御の契約どおり、次の後は過去ARM状態を自動復元しない。

- PWM停止。
- サーボ電源喪失。
- reset。
- 低消費電力からの復帰で再ARMが必要な場合。
- 緊急停止解除。
- 異常復旧。
- その他砲塔・砲身制御が未基準状態へ戻した場合。

BLE再接続自体ではスマートフォンアプリがARM状態を推測せず、再取得した砲塔・砲身制御のcurrent状態を使用する。

### 4.3 利用者への基準合わせ案内

砲塔・砲身制御の安全前提に従い、基準合わせは無駆動で安全に行う。

スマートフォンアプリは、基準合わせが必要な場合に少なくとも次を利用者へ伝える。

- 砲塔・砲身を定義された基準位置へ合わせる必要があること。
- 基準合わせは製品で定める安全な無駆動手順で行うこと。
- サーボのギヤを無理に逆駆動しないこと。
- 通電中またはARM中の可動部を手で押さえないこと。
- ストッパへ力を加えて位置決めしないこと。

砲塔・砲身制御の現行設計で主電源OFF状態での基準合わせを前提とする場合、スマートフォンアプリは「電源を切って基準位置へ合わせ、再起動後にARMする」手順として案内する。

スマートフォンアプリ上の確認だけを実位置検出または基準位置成立の証拠として扱わない。

### 4.4 ARM開始前確認

砲塔・砲身が未ARMの場合、通常操作画面に「サーボ動作を有効にする」等の明示操作を提供する。

ARM開始前に利用者へ少なくとも次を確認させる。

1. 砲塔・砲身を指定の基準位置へ合わせ済みである。
2. 可動範囲に人、手、物体等がない。
3. ARM開始時に機構が少し動く可能性があることを理解している。
4. ARM開始後は完了または失敗表示まで可動部へ触れない。

確認後、利用者が改めて明示的にARM開始操作を行った場合だけBLE接続・認証の`TURRET_ARM`要求を送信する。

### 4.5 ARM要求

初期製品のスマートフォンアプリの通常ARM要求は両軸対象とする。

- current認証済みsessionを使用する。
- 現在の`authorizationRevision`／`actuationEpoch`等、BLE接続・認証/砲塔・砲身制御で要求される現在のcontextへ従う。
- ARM開始前確認は砲塔・砲身制御の一回限り／短時間有効確認契約へ対応付ける。
- 旧確認を再接続後や別epochへ流用しない。

具体的なrequestId、通信データの項目、confirmation identifier表現はBLE接続・認証/砲塔・砲身制御/インターフェース・通信基本設計の契約を変更しない範囲で詳細設計する。

### 4.6 ARM中表示

ARM要求受付後から結果確定まで、スマートフォンアプリは少なくとも次を表示する。

- 「サーボ準備中」等、処理中であること。
- 「可動部に触れない」等の注意。

ARM中は通常の砲塔・砲身操作を有効化しない。

利用者はARM処理を取消せる。取消し時は砲塔・砲身制御の中断契約に従い、旧確認を再利用しない。

### 4.7 ARM成功

砲塔・砲身制御がcurrent transactionについて正常完了し、砲塔・砲身が通常操作可能なARM済み状態であることをcurrent状態として確認した後だけ、スマートフォンアプリは砲塔・砲身操作を有効化する。

ARM成功そのものを実位置測定成功とは表示しない。

成功後も、過去に入力されていた砲塔方向や砲身目標を自動実行しない。利用者の新しい通常操作を待つ。

### 4.8 ARM失敗・中断

ARM失敗または中断時は次とする。

- 砲塔・砲身操作を利用不可のまま維持する。
- 砲塔・砲身制御/異常管理/状態表示・利用者通知等から得た主な失敗理由を表示する。
- 同じARM要求／同じ確認情報で自動再試行しない。
- 利用者の明示操作なしにARMを再開しない。

再試行可能な状態へ戻った場合、利用者は基準合わせ・周囲安全を再確認した上で新しいARM transactionを開始する。

過負荷、監視不能、安全条件不成立、未復旧異常等では、原因が解消される前に再試行可能として表示しない。

### 4.9 BLE再接続との関係

BLE自動再接続に成功しても、スマートフォンアプリは自動ARMを行わない。

再取得したcurrent状態で砲塔・砲身制御が未ARMなら、「接続済み／砲塔・砲身は準備が必要」のように通信復旧とサーボ準備状態を分離して表示する。

## 5. スマートフォンアプリ状態表示

本書の補完対象について、スマートフォンアプリは少なくとも次を区別する。

| 状態 | 利用者への意味 | 通常操作 |
| --- | --- | --- |
| `CONNECTED_READY` | 接続・認証・状態同期済み | 本体側許可に従う |
| `RECONNECTING` | 自動再接続中 | 禁止 |
| `DISCONNECTED` | 切断、自動再接続停止 | 禁止 |
| `CONNECTED_NOT_ARMED` | BLEは使用可能だが砲塔・砲身未準備 | 走行等は本体許可に従う。砲塔・砲身は禁止 |
| `ARMING` | サーボ準備中 | 砲塔・砲身禁止 |
| `ARM_FAILED` | ARM失敗／中断 | 砲塔・砲身禁止 |

具体enum名、画面構造、色、文言はスマートフォンアプリ基本設計／詳細設計で決めてよい。

## 6. 責任分界

### 6.1 スマートフォンアプリ

- 自動再接続transactionの開始・回数・backoff・総期限・取消し。
- foreground/background条件。
- 再接続中／失敗表示。
- 未送信`BARREL_TARGET` latest-one管理。
- スマートフォンアプリのlifecycle変更時の未送信通常操作破棄。
- ARM利用者案内、明示確認、開始操作、処理中／成功／失敗表示。
- ARM成功前の砲塔・砲身UI無効化。

### 6.2 BLE接続・認証

- BLE link／`connectionGeneration`。
- Secure Connections／アプリケーション層認証。
- session／通信メッセージ形式／`commandSeq`。
- 切断時session失効。
- `BARREL_TARGET`／`TURRET_ARM`搬送。
- current状態再同期用BLE通信データ形式。

BLE接続・認証はスマートフォンアプリの自動再接続retry schedulerを保持しない。

### 6.3 砲塔・砲身制御

- `MANUAL_DATUM_ARM`方式。
- 現在のarm state。
- `actuationEpoch`。
- ARM開始可否、完了、失敗、中断。
- 砲塔・砲身通常操作可否。
- `BARREL_TARGET`の本体側latest command slot。

スマートフォンアプリは砲塔・砲身制御の代わりにARM成立や実位置を推測しない。

### 6.4 インターフェース・通信基本設計

インターフェース・通信基本設計は横断的なsession／generation／request／result／失効連携規則を定める。

将来のスマートフォンアプリ基本設計は本書とインターフェース・通信基本設計/砲塔・砲身制御/BLE接続・認証を上位のsystem間契約として使用し、新たな再接続・coalesce・ARM意味を選択し直さない。

---

## 7. 検証契約

少なくとも次を結合確認する。

### 7.1 自動再接続

- 予期しない切断で前面表示中だけ自動再接続を開始する。
- 1回目即時、2回目1秒、3回目2秒backoffを超えて無制限retryしない。
- 3回または10秒で停止する。
- background／lock／利用者取消し／対象変更で即時中止する。
- 再接続成功後に再認証・状態再取得を完了する。
- 旧セッション／旧操作を復元しない。
- 未ARM状態なら接続成功後も砲塔・砲身操作を有効化しない。

### 7.2 `BARREL_TARGET`

- スライダ高頻度変更でも未送信FIFOが増えない。
- 未送信値はlatest oneへ置換される。
- BLE投入中1件＋latest pending 1件を超える無制限queueを作らない。
- 切断、session変更、epoch変更、background、安全停止等でpendingを破棄する。
- 再許可後に旧targetを自動送信しない。

### 7.3 ARM

- 未ARM時に砲塔・砲身UIが利用不可。
- 利用者確認なしに`TURRET_ARM`を送信しない。
- 初期製品UIのARM対象が両軸である。
- ARM中は操作禁止と注意表示。
- 成功後だけ新しい砲塔・砲身操作を許可。
- 成功後も旧操作を再生しない。
- 失敗／中断で自動再試行しない。
- BLE再接続成功だけで自動ARMしない。
